> **研究范围**：`dsh-skill-cockpit@1.5.1`，gitHead `77f52763…`，tarball sha256 `ed3ca5d6…`（352,792 B，65 文件）；DSH 对照 `0.2.1-rc.3`
> **证据成熟度**：源码级（doctor 与文档同步测试实读；未运行 doctor）
> **DSH 立场**：**符合**——独立 CLI 只读为主；`--fix` 只 `mkdir` 缺失的状态目录与 user-dsh 技能根，不覆盖已有内容，不接管宿主启动。
> **一句话**：它的"首启"是一条命令——而且这条命令的输出里直接告诉你装完该看哪儿。
> **借鉴价值**：**① 用退出码当首启结论（0/1/2）；② 检查项六值状态而不是布尔；③ 用测试把 doctor 的检查 id 与排障文档钉在一起。**

## 它想干什么 · 为什么值得借鉴

**意图。** 给 DSH 装一整套技能管理面板（驾驶舱），同时提供一条独立于宿主的自检命令 `dsh-skill-cockpit-doctor` `[PKG]`（`bin/cockpit-doctor.mjs`）。

**意义。** 生命周期里最难的一步是"装完之后到底成没成"。有浏览器卡片的插件可以让用户点一下看，**没有卡片或面板没出现的插件就没有验收面**。它把验收面做成 CLI：退出码 + 可读清单 + `--json`。

**用户价值。** 装之前，用户只能反复重启并盯着侧栏；装之后，一条命令给出三档结论，成功输出里还写着"面板没出现的话：重启 DSH，再确认左侧导航「插件」与「自动化任务」之间" `[SRC-TARGET]`（`bin/cockpit-doctor.mjs:281`）。**它连"去哪儿看"都替你写好了。**

**表达。** 检查项是一条条 `add(id, label, status, detail)` 记进去的 `[SRC-TARGET]`（`:45`），每个 id 都是稳定短名（`local-config`、`roots-safe`、`state`、`user-skills`）。

## 1. 阶段与载体

- **阶段**：首启。它回答"第一次装完，怎么确认能用"。
- **载体**：`own-cli`（一个 `bin`）+ `client-slot`（面板）。**注意：首启的验收面在 CLI，不在面板**——面板本身就是待验证对象。
- **兼看**：装。doctor 也检查安装路径与状态目录。

## 2. 机制

### 退出码就是结论

`[SRC-TARGET]`（`bin/cockpit-doctor.mjs:12`）：

```text
0 = 一切就绪 / 1 = 需要修（--fix 能补的） / 2 = 环境问题（读不了 home 等）
```

三档不是"成功/失败"，而是**"能用 / 我能修 / 你修"**。这比布尔多了一档可执行信息。

### 六值状态（`--fix` 后多一个 `fixed`）

每条检查结果带 `status ∈ {ok, bad, skip, wanted, warn}` `[SRC-TARGET]`（`:45` 的 `add`、`:242` 的汇总）：

| 值 | 含义 | 谁该处理 |
|---|---|---|
| `ok` | 通过 | — |
| `skip` | 不适用（例如"没有 `local.json`，用默认配置"）`[SRC-TARGET]`（`:81`） | — |
| `wanted` | 缺，但可以补（`--dry-run` 时把将要做的动作标成这个）`[SRC-TARGET]`（`:114-115`） | `--fix` |
| `bad` | 坏 | 用户 |
| `warn` | 可疑 | 用户 |
| `fixed` | 已由 `--fix` 补上（退出码不因此变成 1） `[SRC-TARGET]`（`:136`） | — |

`skip` 与 `wanted` 是关键：**"没有配置"不是错误**，而"状态目录不存在"是可以补的。

**退出码比状态少一档**：`bad` 集合只算 `bad` / `warn` / `wanted`（`:242`），所以 `--fix` 成功后的 `fixed` 行仍让退出码为 0——"修完了"与"本来就没事"在退出码上不可区分，这是有意的：脚本只关心"还要不要人管"。

### 把文档变成可机检产物

`test/run-docs.mjs:42-49` 从 doctor 源码里**扫出所有 `add('id')`**，再读 `docs/troubleshooting.md` 的首列，断言两边集合一致 `[SRC-TARGET]`：

```js
const ids = [...new Set([...doctor.matchAll(/add\(\s*'([a-z][a-z0-9-]*)'/g)].map((m) => m[1]))].sort()
const table = read('docs/troubleshooting.md')
const documented = new Set([...table.matchAll(/^\|\s*`([a-z][a-z0-9-]*)`\s*\|/gm)].map((m) => m[1]))
const missing = ids.filter((id) => !documented.has(id))
check('每个 doctor 检查项都在 troubleshooting 表里', missing.length === 0, missing.join(', '))
```

**同一份测试文件还查另外两件事**：平台套件数要与真实套件数一致（`:31-39`）、公开文档不许泄露本机绝对路径（`:52-60`）。这是一个把"文档"当成**构建产物**来验的做法。

**它的边界也同样硬**：`ids` 的正则只认**单引号包裹、小写字母开头**的 `add('id', …)`（`:44`），文档表只认**首列是反引号 id** 的行（`:46`）。新增检查若写成双引号、模板字符串或大写开头，**对账测试会静默漏掉它**——锁住的是"格式"，不是"语义"。

### 三条失败态

| 态 | 表现 | 用户看到什么 |
|---|---|---|
| **环境读不了** | 退出码 `2` `[SRC-TARGET]`（`:59`） | "不是你的错，是环境"——不该让用户去改配置 |
| **可以补但没补** | 退出码 `1`，清单里 `wanted` | 一条 `--fix` 的明确指令 |
| **面板没出现** | doctor 全绿但界面没有 | 成功输出里已经写了"重启 DSH，再确认左侧导航位置" `[SRC-TARGET]`（`:281`） |

## 3. 设计取舍

| 取舍 | 选择 | 代价 |
|---|---|---|
| 首启验收面放哪 | CLI，而不是面板 | 用户得会跑一条命令；换来"面板没出现时仍然能自检" |
| 状态模型 | 六值而非布尔（含 `--fix` 的 `fixed`） | 展示与汇总都要处理六个分支；`fixed` 不参与退出码 |
| 修复的默认行为 | 默认只报告；`--dry-run` 标 `wanted`；`--fix` 才写，成功标 `fixed` | 多一个开关维度 `[SRC-TARGET]`（`:38-40`、`:136`） |
| 文档怎么保证不漂 | 用**测试**对账源码里的检查 id 与文档表 | 检查项改名就要同时改文档，且测试要读源码文本 |

## 4. 与宿主既有行的边界

doctor **不依赖宿主运行**——它是一个独立进程，读 home 目录与配置文件。这意味着：

- 宿主起不来时它仍然能跑（这正是首启最需要它的时刻）；
- 但它也就无法判断"面板是否真的渲染了"，只能检查前置条件 `[OPEN]`。
