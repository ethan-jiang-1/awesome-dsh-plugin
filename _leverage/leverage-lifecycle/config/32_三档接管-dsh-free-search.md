# 三档接管 · free-search

> **阶段**：配 · **载体**：host-row + client-slot + web-route · **兼看**：起
> **影响力**：npm 近 30 天 **71,211**（2026-11-01，42 个过影响力门的 bundle 里最高）
> **研究范围**：`dsh-free-search@0.9.26`，gitHead `7c30dd05…`，tarball sha256 `51d7e742…`（231,171 B，18 文件）；DSH 对照 `0.2.1-rc.3`
> **证据成熟度**：源码级（接管判定、运行时 reclaim、日志去重实读；未实机切换）
> **DSH 立场**：**有条件偏离**——默认应在安装期用 patch 覆盖 `web` 行；运行时 reclaim 只在“必须与宿主设置开关共存”时使用，且要限次、可观测。
> **一句话**：它抢的是"没人设过"的位置，**从来不抢"别人设过的"位置**——包括用户自己。
> **借鉴价值**：**① 按“谁设的”判接管，不按“有没有值”；② 默认用安装期 patch 覆盖，不用运行时 reclaim；③ 只有必须与宿主开关共存时才 reclaim，并限次；④ `apply()` 会重入，日志按进程去重。**

> **不要抄**：把运行时 reclaim 宿主行当默认。默认应在安装期用 patch 覆盖 `web` 行；reclaim 只在“必须与宿主设置开关共存”时使用，并且限次、可观测、可退出。

## 它想干什么 · 为什么值得借鉴

**意图。** 让 DSH 的搜索/抓取默认走它的一整套免费引擎链，而不改宿主的代码 `[SRC-TARGET]`（`lib/index.js:3713-3714` 的 `fetchProviderTakeover`）。

**意义。** 生命周期里"配"这一层最微妙的一件事是**默认值的所有权**：插件想改默认值，但用户可能已经显式选过了。多数实现只看"当前值等不等于空"，于是**把用户的选择也当成"没设"给抢了**。这个样本把判定改成"**是不是出厂默认**"。

**用户价值。** 装之前，用户要么忍受慢的默认搜索，要么手动配一堆 key；装之后默认就快，而且**他一旦显式选了别的，插件就不再插手** `[SRC-TARGET]`（`:4543-4548`）。代价是插件必须盯住自己的"出厂默认"清单，宿主一改默认值它就得跟着改。

**表达。** 客户端只给一个开关配一句人话解释 `[SRC-TARGET]`（`lib/client.js:391-392`）：

> 开启时：`web.fetchProvider` 未设置或仍是出厂默认 http 会接管为 `fs-quality-fetch`。如果你刻意 pin 了 http（例如只想用内置抓取），关掉此项。

**把"什么时候会抢你"写在开关旁边**，这是接管类功能最该抄的一点。

## 1. 阶段与载体

- **阶段**：配。它改的是"没配置时是什么"。
- **载体**：`host-row`（改 `web` 行的 provider）+ `client-slot`（设置页开关）+ `web-route`（设置桥 `/api/dsh-free-search-settings`）。
- **兼看**：起。`apply()` 的重入与 reclaim 都发生在启动期。

## 2. 机制

### 三档判定

| 档 | 当前值 | 行为 |
|---|---|---|
| **未设置 / 出厂默认** | `fetchProvider` 为空或 `http`；`searchProvider` 为 `deepseek-official` | **接管** `[SRC-TARGET]`（`:3714`、`:4540-4552`） |
| **用户显式选择** | 例如 pin 了 `deepseek-search-api`，或显式 `http` 且关掉开关 | **让路，不碰** `[SRC-TARGET]`（`:4537-4539` 注释、`:4545-4546` 判定） |
| **被宿主重置回出厂默认**（只在共存场景） | 用户在 DSH 设置里关掉某个开关，宿主把整行 `- id: web` 删掉，provider 回落 | 运行时补一次 reclaim `[SRC-TARGET]`（`:4536-4552`），`reclaimAttempted` 保证一个进程只补一次；**默认方案仍是安装期 patch** |

第三档是这份样本最容易被忽略、也最实用的一条：**接管不是一次性动作，它会在运行时被冲掉**。

### 防重入与日志

`apply()` 会重入——注释写明 rc.2 的启动重入会把同样的 warn **刷到 65ms 一条**，于是按进程做日志去重 `[SRC-TARGET]`（`:241-248`：`loggedOnce` + `logOnce`）。

### 三条失败态

| 态 | 表现 | 用户看到什么 |
|---|---|---|
| **把用户选择当"没设"** | 显式 pin 的 provider 被覆盖 | 用户以为自己配好了，实际用的是插件的 |
| **只靠安装期 patch、但宿主会重置**（默认方案的边界） | 宿主删行后 provider 回落；这不是 bug，是默认方案的成立边界 | 用户重装/改 patch 即可；不要为此默认加 reclaim |
| **reclaim 无上限** | 与宿主反复互相覆盖 | 配置抖动、日志洪水 |

## 3. 设计取舍

| 取舍 | 选择 | 代价 |
|---|---|---|
| 默认方案 | 安装期 patch 覆盖 `web` 行 | 用户层仍可覆盖；但只能表达“装的时候是什么” |
| 接管判定 | 比对"出厂默认"清单，而不是 `undefined` | 宿主改默认值时要跟版 |
| 用户能不能拒绝 | 一个布尔 `fetchProviderTakeover`，默认开 | 多一个用户要理解的开关 |
| reclaim 次数 | 每个进程一次（`reclaimAttempted`） | 极端情况下仍可能错过一次重置 |
| 日志 | 按进程去重 | 真的要重复诊断时看不到第二次 |

## 4. 与宿主既有行的边界

它**改写 `web` 行的 config**，而不是插一条新行——因为 DSH 的搜索/抓取能力就挂在那一行上，插新行不会生效。**默认应在安装期用 patch 完成这次改写**；运行时 reclaim 只用于“必须与宿主设置开关共存”的场景。这带来一个边界：**它必须认得出“这一行的值是不是出厂默认”**，而这个清单是它对宿主的硬依赖 `[OPEN]`。

## 6. 失效与开放问题

- `[OPEN]` "出厂默认值"清单写在哪、宿主升级后如何更新（本卡只看到 `http` / `deepseek-official` 两处判定）。
- `[OPEN]` reclaim 与用户手动修改之间的竞态（同一进程内多次变化）。
- `[OPEN]` 三档在 `desktop` profile 下是否一致（未实机）。
- `[OPEN]` 未实机验证接管后的实际搜索质量与回退链。
