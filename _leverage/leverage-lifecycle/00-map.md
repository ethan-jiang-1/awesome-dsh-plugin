# 分发与首启宪章

> **单一规则源。** [`README`](./README.md) 只做入口，[`REFERENCE`](./reference/REFERENCE.md) 只给那条路；**口径冲突时以本文件为准**。
> 与前三册平级：本册不计入产品线的篇数与统计，产品线也不计本册。

---

## 0. 定调：尊重 DSH 的约定，灵活度放在插件与流程里

**这一册的最高原则，下面所有条款都从它推出来。**

> **分发、安装、启动，一律走 DSH 已经给出的那条路；需要特别的东西，用 bundle 里的插件、流程和配置去实现，不靠改宿主、也不靠另造一套分发。**

四条推论：

1. **分发不另起**。发一个声明 `dsh.bundle.patch` 的包，让用户在**应用内**装（`dsh web` 与 Desktop 同一句话）。CLI 只作 web 面的自动化。**不做自带安装器、不做 launcher**，除非产品根本不是插件（那时它是 shell，代价是生命周期全归自己）。
2. **灵活度分三层落地**：
   - **插件**——bundle 里的 host 插件消费 DSH 服务（首屏注入、预置会话、工作区初始化）。它不换入口，所以不算偏离；
   - **流程**——命令、向导、自检、可推迟的首启。用户从一条命令或一块面板进入，而不是从"另一个应用"进入；
   - **配置**——分层写在 `cordis.patch.yml` / settings 里，可被更高层覆盖，不写死在代码。
3. **"必须改宿主才能做到"先当成异常**。要么不做，要么认领 shell 那条路的全部代价（安装、启动、更新、降级）。**不要用"反正大家都这么干"来豁免这一条。**
4. **口径随之**：本册写判据、不写教程；教产品怎么不绕，不教用户怎么绕。

**三问判定**（拿不准时按序问）：

```text
① 这件事能不能靠"应用内装"完成？        → bundle 能做的，别碰 CLI 之外的东西
② 不能的话，能不能靠 bundle 里的插件？   → 首屏注入 / 预置会话 / 工作区 / 命令
③ 还不能的话，是不是配置放错了层？      → patch 层 / settings / 自己的文件
④ 三者都不行，才考虑换表层或自带宿主     → 认领 shell 的全部代价
```

## 1. 定位与范围

**一句话**：*这个册子回答"一个 DSH 插件从被用户拿到、到第一次成功，中间那几个动作该由谁做、做在哪一层"——只给判据与载体，不写教程、不评功能。*

| | 收 | 不收 |
|---|---|---|
| 阶段 | 装 / 起 / 配 / 首启 | 功能好坏、界面美丑 |
| 对象 | **载体**（命令、槽位、首屏注入、boot hook、自带 CLI……） | 单个产品的完整画像 |
| 证据 | DSH 机制 + 包清单事实 + 隔离实测 | README 营销词 |
| 产出 | 判据、载体矩阵、反例 | 安装教程、截图步骤 |

### 1.1 边界规则（与产品册互不抢地）

> **DSH 升级会让它变 → 本册；第三方产品发版会让它变 → 产品册。**

推论，两边都要照办：

- 产品册的 `装法` 行只写"**这个样本怎么装**"，不回答"**应该怎么装**"；
- 本册的样本卡只写"**它在这一步用了什么载体**"，不重述产品形态与功能；
- 七层的 **2 / 5 / 6 / 7** 的**定义**归本册，产品册 `horizon` 只留指针与样本清单。

### 1.2 唯一豁免

DSH 自己的第一次安装。产品线的 25 张卡全部假设"DSH 已装好、profile 已存在"，这一段没人写，所以本册必须自己写（`[RUN]` 为主）。

## 2. 目录结构（固定）

```text
leverage-lifecycle/
├── README.md          ← 入口（固定名）
├── 00-map.md          ← 本文件：规则源
├── catalog.md         ← 全量清单
├── reference/         ← 那条路与它的边界
│   ├── REFERENCE.md   被认可的那一条路
│   ├── SURFACES.md    web 与 Desktop 的同一性
│   └── CARRIERS.md    九类载体的判定与矩阵
├── install/           ← ① 装：README（阶段篇）+ 样本
├── boot/              ← ② 起：README（阶段篇）+ 样本
├── config/            ← ③ 配：README（阶段篇）+ 样本
├── first-run/         ← ④ 首启：README（阶段篇）+ 样本
├── negative/          ← 反例：只放样本
├── practice/          ← 拿得走的两篇
│   ├── TRAPS.md       十三条照抄就中招
│   └── CHECKLIST.md   发布前自检
├── research/          ← 怎么做研究
│   ├── RESEARCH.md    漏斗、分类、流水线、质量门
│   └── BACKLOG.md     分诊结果与缺口
└── _证据/             ← 原始定位与实测记录
```

**分类即目录，阶段篇与样本同住。** 一个阶段一个目录：`README.md` 是阶段篇，`NN_*.md` 是样本——**读者读到哪一步，样本就在手边**。五个阶段目录固定，**不新增第六个**；装不下的东西进 `practice/TRAPS.md`。目录内不再往下分层。

## 3. 命名

| 对象 | 规则 | 例 |
|---|---|---|
| 骨架 | 固定名、不编号 | `REFERENCE.md`、`FIRST-RUN.md` |
| 样本 | `<阶段>/NN_关键短语-插件名.md`；**阶段由目录决定**；`NN` **全书唯一**，十位只作区段习惯（1x 装 · 2x 起 · 3x 配 · 4x 首启 · 9x 反例） | `install/11_装后自证-cfbridge.md` |
| 证据 | `_证据/NN_主题.md`；**一卡一 memo**，编号与该卡一一对应 | `_证据/11_装后自证-cfbridge-源码复核.md` |

**五个阶段目录固定**：`install`（装）· `boot`（起）· `config`（配）· `first-run`（首启）· `negative`（反例）。

**编号规矩**：`NN` **全书唯一、不复用、不重排**——因为 memo 文件名是扁平的 `_证据/NN_…`，重号会撞。目录负责分类，编号只负责稳定。退役把十位改成 `9`（如 `91_`），`status` 改 `open`，不删不改名。**一个插件在本册只出一张卡**，跨阶段写进卡内"兼看"。

新增文件**先问能不能并进现有文件**；不能才新增，且必须同时进 `catalog.md` 与本文件 §2。

## 4. frontmatter 与入选门

**七个必填**：`title` / `domain` / `kind` / `positioning` / `read_when` / `status` / `updated`。

- `domain` **固定 `lifecycle`**；
- `kind` ∈ `index` / `charter` / `guide` / `playbook` / `sample` / `evidence`；
- **`playbook` 与 `sample` 必须有 `takeaway`**；`sample` 还必须有**载体一节**（标题含 载体）；
- `positioning` ≤120 字、`read_when` ≤80 字、`title` ≤80 字。

### 4.1 两道门：先影响力，再机制

**第一道 · 影响力门（硬，2026-11-01 定）**——与产品册 `plugin` 同口径：**★ ≥ 200 或 npm 近 30 天 ≥ 2,000**。

理由很实际：生命周期这块最容易"看起来重要"——零配置、开箱即用、一键引导，任何 README 都写得出来。先按真实使用量筛一遍，问的是"**有人真的用过吗**"。

**第二道 · 机制门**——过第一道的人里，只收能写出一条"抄哪一行"的：

1. 有一条**可复现的装法**（命令或安装包 URL）；
2. 至少一个**载体事实来自包清单或源码**，**不能只有 README**；
3. 能写出一条"**抄哪一行**"。

**为什么两道都要**：只用影响力，会收一堆"月下载高但不讲生命周期"的工具；只用机制，会收一堆 ★1 的自娱自乐。**第一道问有没有人用，第二道问有没有东西可学。**

**配额**：每阶段 ≤ 4 张，总数 12–16 张起步。超了先问"是不是该加一个载体类"，而不是加卡。

**已知代价**：这会筛掉 `dsh-bootstrap`（★1 / 月 763）——它恰好是唯一的"首启推荐 + 环境码"样本。处置：留在产品册的观察样本里，本册引用时标 `[CARD]`，**不为它破门**。门槛的价值就在于它也会误伤。

## 5. 证据标签

| 标签 | 含义 | 最低要求 |
|---|---|---|
| `[DSH]` | 上游发行物可核 | **包名 + 文件:行号** |
| `[RUN]` | 本轮隔离实测 | 命令、环境、观察输出 |
| `[PKG]` | npm 包清单事实 | 包名 + 版本 + 字段（如 `dsh.client`） |
| `[CARD]` | 引自产品线样本卡 | 写卡名；**不升级它的证据级别** |
| `[OBS]` | 观察者判断 | 必须给反例或失效条件 |
| `[OPEN]` | 未复核 | 写清下一次怎么复核 |

**为什么多 `[PKG]`**：本册的分类要靠包清单（`dsh.bundle` / `dsh.client` / `bin`）而不是 README，`[DSH]` 管不到第三方包，`[CARD]` 又不对口。

**Desktop 面一律不得标 `[RUN]`**：本机无 Electron 应用。

## 6. 文件骨架

**阶段篇**（`INSTALL` / `BOOT` / `CONFIG` / `FIRST-RUN`）固定五节：原生怎么做 → 实测读到什么 → 样本怎么偏离 → 三条判据 → 失效与开放问题。**不许省掉"样本怎么偏离"**。

**样本卡**固定七节（`verify.mjs` 硬校验前两节与第 5 节）：

```text
## 它想干什么 · 为什么值得借鉴     ← 意图 / 意义 / 用户价值 / 表达
## 1. 阶段与载体
## 2. 机制                        ← 含三条失败态：读不到 / 装不进 / 起了不生效
## 3. 设计取舍
## 4. 与宿主既有行的边界           ← 没有可写就并进 §2
## 5. 可迁移洞察                   ← 七列表，表头逐字照抄产品册
## 6. 失效与开放问题
## 7. 兼看                         ← 跨阶段写这里，不进目录
```

## 7. 五条不变量

1. **骨架不随样本长**：阶段四篇固定，新增只能进 `TRAPS` / `CHECKLIST` / `samples/`。
2. **一条结论一个标签**：同一句里混两个强度就算两条。
3. **能用 `[RUN]` 就不用 `[DSH]`，能用 `[PKG]` 就不用 `[CARD]`**。
4. **不碰用户环境**：实测必须在隔离 `DSH_HOME`，产物落 `.work/`（gitignore）。
5. **不复制产品册结论**：引用给链接，不重述机制。

## 8. 生长协议

| 变化 | 写哪里 | 不要动 |
|---|---|---|
| 发现新坑 | `TRAPS` 一行 + 对应阶段篇一句 | 骨架 |
| 新的实操要求 | `CHECKLIST` 一条 | 不要把 checklist 写成散文 |
| 新样本过机制门 | `samples/NN_*.md` + `catalog` + `BACKLOG` 删行 | 阶段的正文结构 |
| 某载体类出现首个样本 | `CARRIERS` 矩阵补一格 | 不要改已有分类 |
| 上游基线升级 | 受影响断言改版本，`updated` 改日期 | 结论方向 |
| 结论被推翻 | 正文改 + `TRAPS` 记"曾经这么以为" | 不删历史 |

## 9. 反模式

1. **把本册写成安装教程**：教程随版本漂，判据不会。
2. **只写 web 面**：那正是本册要修的病。
3. **拿 README 当载体证据**：营销词会骗人，包清单与源码不会。
4. **用影响力筛生命周期样本**：会把这块地筛空。
5. **实测进了真实 profile**：一次就够污染用户环境。
