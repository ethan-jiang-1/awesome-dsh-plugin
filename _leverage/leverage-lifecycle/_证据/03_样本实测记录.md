
**对照基线**（本册 [`02_隔离实测记录`](./02_隔离实测记录.md) E11）：干净 web profile 首屏 **37,907 字节**；装上 rhine-splash 后 **839,776 字节**。

**结论**：`index-inject` 不是"理论可行"，它确实在页面生成期落地，且体积增量来自注入的样式与资产。

## 3. fail-closed 到底是不是全拒（E23–E26）

先把路径覆盖到隔离目录（否则它会去读真实 home，见 §4）：

```yaml
# $H/tmp/overlay.yml
- id: isolation-gate
  config:
    statePath: $H/tmp/state.json
    rosterPath: $H/tmp/roster.txt
```

写入一份坏 JSON，再读状态端点：

```json
{"files": {
  "stateExists": true,
  "stateError": "状态文件不是合法 JSON（按全禁处理，且不覆盖它）：Expected property name or '}' in JSON at position 2 (line 1 column 3)",
  "rosterExists": false,
  "rosterError": "名单文件不存在：…/roster.txt（按\"一律拒…"
},
 "defaultLevel": "deny",
 "roster": [],
 "policy": []}
```

```sh
$ head -c 20 $H/tmp/state.json
{ this is not json          # ← 没有被覆盖
```

**结论**：坏状态 → `defaultLevel` 仍是 `deny`、`policy` 为空（等于什么都不放行）、**原文件保持原样**；名单缺失 → 一律拒绝。**源码里写的那三句，运行时逐条对上了。**

## 4. 一个必须记下来的隔离陷阱（E23 附带观察）

在一次"完全隔离"的安装里，状态端点回显的默认路径是：

```json
"paths": {
  "state":  "/Users/bowhead/.agents/门禁-授权.json",
  "roster": "/Users/bowhead/.agents/门禁-名单.txt",
  "root":   "/",
  "backupDir": "D:\\回收站\\门禁-名单改前",
  "audit":  "/Users/bowhead/.dsh/dsh-isolation-gate/access-log.jsonl"
}
```

**四条路径里有三条落在真实 home（`~/.agents`、`~/.dsh`），一条是硬编码的 Windows `D:` 盘**——它们**都不跟随 `DSH_HOME`**。

所以"隔离安装"只隔离了 profile，**没隔离插件自己的绝对路径**。要在隔离环境里测这类插件，必须像 §3 那样用 `--patch` 覆盖路径。

## 5. 有没有写坏用户环境

```sh
$ ls /Users/bowhead/.agents/门禁-授权.json /Users/bowhead/.agents/门禁-名单.txt
（均不存在）
$ ls /Users/bowhead/.dsh/dsh-isolation-gate/
```

两次启动、若干次 GET 之后，这三处**都没有被创建**：状态端点是只读的，审计写入没有触发。**真实环境未被改动。**

## 6. 市场判定器实测（E28）

> 目的：验证 `install/12` 的修正——carrier bundle 能否靠自己的 patch 行证明“活着”。
> 环境：隔离 `DSH_HOME=.work/deep/home`（与 E20–E26 的 `.work/mine/home` 分开）。**实验产物（隔离 home、市场包解包）已清理**；市场包按 memo 12 §5 的 URL/sha 重建。

```sh
# 隔离 profile 真装（绝对路径；相对路径会被解析到 profile 目录，见 §7）
$E dsh plugin --profile exp add /…/.work/mine/dsh-origin-plugin/pkg.tgz    # exit 0

# 直接调用市场的判定函数（dshmarket@1.73.6）
$ node --input-type=module - <<'JS'
import { verifyActivation } from '/…/.work/mine/_dshmarket/package/lib/verify.js'
const dir = process.env.H + '/profiles/exp'
for (const live of [new Set(), new Set(['#mcp-origin']),
                    new Set(['dsh-origin-plugin']),
                    new Set(['@deepseek-ai/dsh-mcp-client'])])
  console.log([...live], (await verifyActivation('exp', 'dsh-origin-plugin', live, dir)).state)
JS
```

| 传入的 live 集合 | 判定 | 说明 |
|---|---|---|
| `∅` | `restart` | 入口存在（没判 `broken`），等重启 |
| `#mcp-origin` | `live` | `carriedRowLive`：作者 patch 插入的 id 就够 |
| `dsh-origin-plugin` | `live` | `liveIncludes`：包名匹配 |
| `@deepseek-ai/dsh-mcp-client` | `restart` | 只看到“别人的条目名”，不算活 |

另一个手造的 fake carrier（有 `dsh.bundle`、patch 为空、无入口）：

```text
entryArtifactExists=false · hasLoadableEntry=false · verifyActivation → broken
```

**边界**：这是“真装 + 直接调用市场的判定函数”，不是跑市场 UI 或宿主启动；它证明**判定谓词与证据优先级**，不证明 UI 文案与“卸载动作”本身。

## 7. 这套实测覆盖不到什么

| 未覆盖 | 原因 | 怎么补 |
|---|---|---|
| `desktop` profile | 本机无 Electron 应用 | 一台装过官方 Desktop 的机器 |
| `update-checker` 的重启取证 | 需要真实重启宿主 | 隔离环境里跑一次自更新 |
| 市场 UI 与“判 broken 后卸载”的完整动作 | E28 只调用了判定函数 | 在浏览器里装一个坏包，观察 `node_modules` 是否消失 |
| `noema` / `doctor` 的运行行为 | 一个要拉外部进程、一个要改 profile | 各自单独设计隔离实验 |
| 各插件在宿主升级后的表现 | 只有单一基线 `0.2.1-rc.3` | 换一个版本重跑 §1–§3 |
