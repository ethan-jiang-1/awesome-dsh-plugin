# 机制对但没人用 · dsh-bootstrap

> **阶段**：反例（`negative/`） · **载体**：自有路由 + 首屏注入 + own-cli（`bin`） · **兼看**：首启
> **影响力**：**★ 1 / forks 0**（GitHub API，2026-11-01）· **npm 近 30 天 763**（2026-09-30 ~ 10-29）——**两项都不过本册的影响力门**（★≥200 或 npm≥2,000）
> **研究范围**：`dsh-bootstrap@0.1.0`（**registry 无 `gitHead`**），sha256 `33a18408…`（87,589 B，24 文件）；DSH 对照 `0.2.1-rc.3`
> **仓库时间线**：created `2026-10-17` · pushed `2026-10-17`（**同一天，之后再无提交**）
> **证据成熟度**：源码级（机制实读；未实机装）
> **一句话**：它把"装完还该装什么"这个问题做成了一个产品——**而这个问题，用户不会问**。
> **借鉴价值**：**机制值得抄（计划先于执行、锁不到版本就跳过、幂等、摘要校验、缺能力降级）；但它作为产品是反例——一次性发布 + 不在用户的检索路径上。**

## 它想干什么 · 为什么值得借鉴

**意图。** 新用户装完 DSH 后的第二个问题："我还该装什么？"它给一个悬浮球 → 抽屉（推荐 / 一键安装 / 我的环境 / 导入环境）`[SRC-TARGET]`（`lib/index.js:99-103` 注册路由 + 首屏注入）。

**意义。** 这是本册唯一一个"把首启做成推荐与批量安装"的样本，机制密度很高：计划、精确版本、幂等、环境码、从摘要到完整性、离线种子、能力缺失降级。

**用户价值**：**它证明了机制可以被做出来，但没有证明用户要它。** 发布当天一次推送，之后再无更新；一个月 763 次下载、1 个 star。对需要长期跟随宿主升级的工具来说，**"一次发布"本身就是最强的失败信号**。

**表达。** 它的安装摘要是一行账 `[SRC-TARGET]`（`lib/install.js:213`）：

> 已安装 N 个，已启用 N 个，跳过 N 个，失败 N 个

四个数字各自可核查——这正是本册推崇的"三个成功分开算"。

## 1. 为什么它是反例

不是因为机制差，而是因为三件事同时成立：

1. **它回答的问题不在用户的检索路径上。** 用户会搜"DSH 怎么装""某个插件怎么用"，不会搜"装完还该装什么"。
2. **它需要长期维护才成立**（宿主每月都在变），而它只有一次提交。
3. **它把推荐做成了产品的主界面**，于是"没人用"直接等于"产品不存在"——没有第二条进入路径。

## 2. 机制（真的做了，值得单抄）

| 机制 | 原文 | 位置 |
|---|---|---|
| **计划先于执行** | `一键安装：先出计划（plan），确认后执行` | `[SRC-TARGET]` `lib/install.js:2` |
| **锁不到精确版本就跳过** | `锁定不到精确版本` → 进 `skipped` | `[SRC-TARGET]` `:135` |
| **幂等** | 已安装的包直接 `已安装，跳过` | `[SRC-TARGET]` `:161` |
| **环境码两档编码** | `DSHB1.<base64url>` 明文 / `DSHB1z.<base64url(deflateRaw)>` 压缩，取更短者 | `[SRC-TARGET]` `lib/envcode.js:5-6`、`:18-19` |
| **完整性摘要** | `sha256(稳定序列化)` 取前 16 位，不符即 `mismatch` | `[SRC-TARGET]` `lib/envcode.js:52-59`、`:262-263` |
| **缺能力降级** | 拿不到 `webServer` → `warn` 后跳过路由，不崩 | `[SRC-TARGET]` `lib/index.js:99-103` |

### 三条失败态

| 态 | 表现 | 用户看到什么 |
|---|---|---|
| **没有 webServer** | 打一条 warn、不注册路由 | 无界面，但 DSH 正常 |
| **版本锁不到** | 该项进 `skipped`，不装近似版本 | 计划里明确写"跳过"，不静默 |
| **环境码被改坏** | `digest` 不符 → `mismatch` | 拒绝应用，而不是部分应用 |

## 3. 布局与代价

它是 `bundle` + `bin`，**没有 `dsh.client`** `[PKG]`——界面完全靠首屏注入与自有路由。这让它对宿主版本非常敏感，也是"必须长期维护"的直接原因。

## 4. 与宿主既有行的边界

它**不改宿主的任何行**，只读插件目录数据、写自己的环境码。边界很干净——**干净也意味着它没有嵌进用户已有的动作里**（用户每天用 DSH 时不会碰到它）。

## 5. 可迁移洞察

| 触发问题 | 可迁移洞察 | 机制依据 | 为什么有效 / 代价 | 移植时改什么 | 成立边界 | 抄错后果 |
|---|---|---|---|---|---|---|
| 批量安装要不要先给计划 | **计划先于执行**：逐条列出"装 / 跳过 / 为什么跳过"，确认后再动手 | `[SRC-TARGET]` `lib/install.js:2`、`:135`、`:213` | 用户可预判，失败可解释；代价是要多一轮交互 | 定义计划的字段与"跳过"理由枚举 | 只对"一次改多项"的动作成立 | 直接执行 → 用户不知道被装了什么，也不知道为什么漏了 |
| 精确版本拿不到怎么办 | **跳过，绝不装近似版本** | `[SRC-TARGET]` `:135` | 不引入未验证版本；代价是清单会变短 | 给"锁不到"一个可见状态而不是静默 | 只对"版本敏感"的生态成立 | 退到 `latest` → 装进不兼容版本，坏了还查不到原因 |
| 重复执行 | 幂等：已安装的直接跳过并计入摘要 | `[SRC-TARGET]` `:161`、`:213` | 可反复跑；代价是要能判定"已安装" | 定义幂等键与判定方式 | 只对"可枚举目标"成立 | 不幂等 → 跑两次装两遍 |
| 分享一份"环境" | 自描述格式 + 摘要：两档编码取短，摘要取稳定序列化前 16 位 | `[SRC-TARGET]` `lib/envcode.js:5-6`、`:52-59` | 人可读、机可校验；代价是要维护稳定序列化 | 定义载荷 schema、摘要算法与"未包含=不变"语义 | 只对"双方都能解析"的场景成立 | 无摘要 → 传输截断后静默应用半份配置 |
| **机制完备却没人用** | **先问"用户会不会问这个问题"，再问"我能不能做好"** | `[SRC-TARGET]` 全包的机制密度 vs `[PKG]` ★1 / 763 次下载、`created == pushed == 2026-10-17` | 这是本册唯一"机制门过、影响力门不过"的样本；代价是它的机制只能作为参考，不能作为需求证据 | 发布前先找一个已有的用户动作挂进去 | 任何形态 | 做成一个"很好但没人进入"的产品 |

## 6. 影响力门的代价（明写）

本册 [`00-map` §4.1](../00-map.md) 的第一道门是 ★≥200 或 npm≥2,000。**这个样本两项都不过**，所以它只能待在 `negative/` 与产品册的观察样本里，不能进 `samples/`。

这是**设计选择**，不是遗漏：

- 若为它破门，门槛就会一路降到 ★1，整册的"有人在用"前提消失；
- 但它的机制确实值得抄——所以本册用**一张反例卡**承载，而不是假装没看见。

**这条也回答了一个更普适的问题**：机制做得对，不等于产品成立；**门槛的意义就是承受这种误伤。**

## 7. 失效与开放问题

- `[OPEN]` 未实机安装，运行行为未验证。
- `[OPEN]` 它引用的插件目录数据是否已过期（若数据源失效，推荐会变成误导）。
- `[OPEN]` 一次性发布是否是作者弃坑、还是本就只打算发一版（原始意图未知）。
- `[OPEN]` 若把它挂到"插件市场"这类已有用户动作上，是否会改变结果——本册无法验证。
