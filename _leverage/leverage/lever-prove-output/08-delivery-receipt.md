# 08 · 交付回执：把「谁验收的」与「文件是什么」分开记

> **状态**:`observed`(包级 README 已读) · **基线**:DSH `0.2.1-rc.3` · 名单 @ `efe602e7b`
> **样本**:1 个主标杆 + 1 组官方原生对照(`oxmumu3/dsh-workproof` vs `dsh-tool-present` / `dsh-workspace-changes`)

本卡补 ⑤ 产物环。它比前几张卡「小」,但解决了一个所有门禁都绕不过的问题:**判定发生在「产物已经被写出来之后」,那么判定到底该绑在哪个版本上?** 答案在原生里是缺席的(见 [`01`](./01-quality-chain.md) §3.4),在生态里只有一条样本给出了完整解。

---

## 1. 命题

> 「验收」不是一个布尔值,是**三元组**:`(文件版本, 谁看见的, 谁说的)`。任何把这三样混在一起的验收都是假的——**特别是把「agent 说它检查过」当成文件证据**。所以正确的交付回执应该是三层分明:代理声称 / 文件观测 / 用户决定,而且**模型没有权限写第三层**。

可证伪:

- **P1**:若「文件哈希 + 一个通过标记」就够,则三层分离是过度设计。
- **P2**:若 agent 能代替用户点「接受」,则权限边界可以省。

P1 不成立:哈希正确不代表内容对(`2 + 3 = 9` 的文件哈希完全正确)。P2 不成立:工具的 `decide` 动作**根本不存在**——这是本卡最硬的一条设计。

## 3. 机制

### 3.1 三层记什么、不证明什么(原文表格)

| 层 | 记录什么 | 它**不**证明什么 |
|---|---|---|
| **代理声称** | 标题、明确的文件路径、声明的检查 | 「测试跑过了」或「声称已被独立验证」 |
| **文件观测** | 显式本地文件的**可读性、字节大小、SHA-256** | 正确性、事实准确性、视觉质量、测试覆盖率 |
| **用户决定** | 对**某一个回执版本**的「接受」或「请求修改」 | 密码学意义上的人身份,或已送达他人 |

**这张表的第三列才是重点。** 一个质量工具写「我能做什么」很容易,写「我做的这件事**不**能推出什么」才是克制。这一列一旦被读者当真,90% 的交付纠纷都不会发生。

### 3.2 版本绑定的状态机

```
record ──► inspect ──► review_required ──► accepted / changes_requested
              │                 ▲
              └── recheck ──────┘
                    │
              文件变了 ──► stale（旧决定仍可见，但绑在旧版本上）
                    │
              refresh（显式建新版本，递增版本号，清空接受）
```

状态词的用途是分得很细的:

- `missing` —— 文件不在了;
- `unverifiable` —— 不可读、超大、非普通文件、非法或**正在变化中**;
- `stale` —— 基线哈希/大小不匹配;
- 只有**当前证据完整**才能进入 `review_required` / `accepted` / `changes_requested`。

三条关键规则:

1. **「接受」只在每个当前文件都可读且与基线哈希、大小一致时可用。**
2. **重检永不替换基线。**`recheck` 只重新观测;要新基线必须显式 `refresh`。
3. **刷新清空旧接受。**`refresh` 递增版本号并清掉旧的接受,**旧决定留在有界的历史里**——而新版本必须**单独评审**。

**「重检不改基线」这一条是整个设计的支点。** 若重检顺手更新基线,那么「文件变了」这件事就**永远不会被发现**——旧接受会静默地覆盖新字节。这是 ⑤ 环最容易写错、也最容易被忽略的一处。

### 3.3 权限边界:模型没有 `decide`

工具动作:`record`(1–20 个路径 + 可选声明检查)/ `list` / `inspect` / `refresh`(要 `expectedVersion`)/ `preview` / `export`。

**没有 `decide`。** 原文:

> 「The tool has **no `decide` action**. It cannot record acceptance on the user's behalf, supply trusted hashes, change the workspace root or impersonate another session.」

用户侧入口是斜杠命令与原生 `conversation.view` 槽位,**决定需要回执 id 与当前版本,UI 会拒绝版本已变动的决定**。

作者还补了一句极少见的诚实:

> 「This separation is a product interaction boundary, not protection against code already able to execute in the host process.」

也就是:**这是产品边界,不是安全边界。** 已经能在宿主进程里跑代码的东西当然能写存储——但这不妨碍「模型侧的调用面里没有替签这个动作」是一个有价值的设计。

### 3.4 三个合成演练(作者给的,都能复现)

1. **文章**:接受 v1 → 改一行 → 重检应显示 `stale`,旧决定仍绑 v1 → 建 v2,无决定。**验的是「版本绑定」,不是「文件有没有变」。**
2. **报表**:`report.csv` 里 `2 + 3` 的总数故意写成 `9`。检查项必须**一直显示为「代理声称」**;**一个有效的 SHA-256 不能变成 `2 + 3 = 9` 的证明。** 请求修改 → 改成 `5` → `stale` → 显式建新版本 → 重审。
3. **发布说明**:本地回执**不是**发布,也不是测试报告。导出 Markdown 时要读到它的边界:代理的检查不是独立观测到的测试结果,本地导出不是外部送达。

**演练 2 是本卡最锋利的一段**:它用一个**故意算错的 CSV** 来演示「哈希正确 ≠ 内容正确」。这比任何一段文字说明都更有教育价值。

### 3.5 边界写到了工程细节

- **规模上限**:每回执 ≤20 个唯一相对路径、每会话 ≤100 个回执、每回执 ≤100 条审计事件;声明检查 ≤20 条各 500 字符;标题 200;决定备注 2000。
- **哈希上限 64 MiB / 文件**;文本预览上限 64 KiB,带**显式截断标记**。
- **路径规则**:只支持**真实工作区根之下**的本地普通文件;宿主根先**规范化**(例:macOS `/tmp` → `/private/tmp`);绝对路径、穿越、Windows 盘符/UNC、根下符号链接、目录、FIFO、设备一律拒绝;**检查期间文件发生变化 → 不给 `ok` 观测**。
- **工作区与会话由宿主派生**;工具/浏览器请求**不能指定任意根**。
- **存储用官方 `storageDomain`**(`workproof_delivery_receipts`),**不新建核心会话事件、不替换会话历史**。
- **不做的事**:不跑测试命令、不判内容、**不调模型**、不发布、不发送;无网络请求、无遥测、无后台扫描。
- **零安装脚本**:分发走预构建的 GitHub Release `.tgz`,**没有 `install`/`postinstall`**。
- **已验证范围的诚实**:端到端验收范围限于 **macOS 本地文件**;Windows、Linux、远程工作区与其他 Harness 版本**尚未验证**;peer 依赖写成显式并集(`0.2.0-rc.2 || 0.2.1-rc.3`)。

## 4. 原生对照:指针、摘要,与三个「不」`[DSH]`

| 机制 | 留下什么 | 明确不保证 |
|---|---|---|
| `dsh-tool-present` | 校验路径、**记录绝对路径**;后续目录变更不会重定向已交付文件;`maxFiles` 8 | 「元数据与路径检查**无法原子性地**阻止桌面应用打开文件前的替换」;「编辑会改变打开的内容;源文件删除/移动后无法通过原声明打开」;「Session ZIP 导出**包含声明,不包含文件内容**」——**交付版本持久化与写时复制存储延期实现** |
| `dsh-workspace-changes` | 每轮两个 git tree(`turn/start` 基线、`agent/turn-stopping` 快照)、`diff-tree --numstat`、`check-ignore`、未覆盖路径的二次逐行比对 | 记录的是**本轮改动**,不是「交付版本」;只在 git 仓库外退化为「仅文件工具编辑」 |
| `dsh-client-ui-deliverables` | 轮末变更卡片 + 交付卡片 + 散文内联码引用链接;**来源是记录的摘要与成功的写操作,不是散文** | 无摘要(未改文件 / 插件被组合出去 / 宿主在轮次之后重启)→ **卡片不出现** |

**三条合起来是一句话**:原生把「交付」做成**指针 + 本轮摘要**,而**指针会失效**(被改、被删、被移),**摘要只管一轮**。这正是 workproof 存在的那一格。

一个值得注意的细节:`dsh-workspace-changes` 必须在 `tools/pre-execute` 上**等基线快照排完才允许工具运行**,这样任何变更都不会早于自己的基线;而它在 `agent/turn-stopping` 里做**第二次快照**。也就是说,**DSH 原生已经在用「双向快照 + 摘要」的思路做变更记录**——workproof 把同一思路搬到了「交付」上,并补上了原生不做的两件事:**版本化的用户决定**,和**重检不覆盖基线**。

### 5.1 它与 `present` 的关系:不是替代,是补上原生明确延期的那一段

原生 `present` 的三条限制里,最后一条是「**交付版本持久化与写时复制存储延期实现**」。workproof 没有实现 CoW 存储,但实现了**版本化的交付基线**——这是一个更便宜的近似:不复制内容,而是记录**版本哈希 + 决定**,并在文件变化时把状态判为 `stale`。

**代价**:内容仍然可能丢失(文件被删就只有 `missing`)。**收益**:不需要动文件系统语义,也不产生存储膨胀。

## 6. 对照与反例

### 对照 · 官方 `atomic-write`(借用一句,主读在本域 [`01`](./01-quality-chain.md) §3.4)

`dsh-atomic-write` 保证替换文件时**不暴露部分内容**、跨进程串行化读-改-写,但**不调用 `fsync`,因此不保证崩溃持久性**。把它和「交付回执」放一起看,能得到 ⑤ 环的完整风险谱:

| 风险 | 谁管 |
|---|---|
| 读者看到半个文件 | `atomic-write`(硬) |
| 崩溃后文件内容没落盘 | **没人**(无 `fsync`) |
| 文件被改后交付声明仍有效 | `present` **不管**;workproof 判 `stale` |
| 文件被删 | `present` 只能说打不开;workproof 显示 `missing` |
| 「谁接受了这个版本」 | **只有 workproof** |

### 反例格 · 「接受」被写成密码学证明

原文一句:「An acceptance record is a UI-recorded decision, **not cryptographic proof of who clicked it** or of an external recipient's receipt.」

任何把「用户在 UI 里点了接受」当成**不可否认签名**的用法都是错的。要真的归因,必须回到 [`05`](./05-custody-chain.md) 那条路(签名链 + 链外锚点),而且那也只归因到**密钥**。**两条路都不解决「是谁」。**

## 7. 可借鉴:八条可以直接搬走的做法

### B1 · 三层分离:代理声称 / 文件观测 / 用户决定

**做法**:

| 层 | 记录什么 | 它**不**证明什么 |
|---|---|---|
| 代理声称 | 标题、路径、声明的检查 | 「测试跑过了」或「已被独立验证」 |
| 文件观测 | 可读性、字节大小、SHA-256 | 正确性、事实准确性、视觉质量、覆盖率 |
| 用户决定 | 对**某版本**的接受或请求修改 | 密码学意义上的人身份,或已送达他人 |

**为什么有效**:把这三样混成一句「已验收」,是交付纠纷的根源。分开之后,每一层各自可被质疑、可被替换:代理声称可以错而不影响观测;观测正确而不构成接受。

**怎么搬**:任何「签收 / 验收 / 通过」功能,先画一张三列表(记什么 / 不证明什么 / 谁能写)。**第二列写不出来的,说明你还没分清这三层。**

**反面**:三层分得越细,用户要看的越多。要给一个默认视图(通常只显示最后两层)加一个展开入口。

---

### B2 · 重检永不替换基线

**做法**:`inspect` / `recheck` 只**重新观测**,不更新基线;要新基线必须显式 `refresh`(还要 `expectedVersion`)。

**为什么有效**:**这是整个设计的支点。** 若重检顺手更新基线,「文件变了」这件事就**永远不会被发现**——旧接受会静默地覆盖新字节。这一条看似只是「别偷懒」,实际上是**唯一让「过期」这个概念能够存在的前提**。

**怎么搬**:任何有「基线 / 快照 / 期望值」的系统,都必须把**观测**与**设定基线**分成两个动作。检查方法:搜索代码里同时做「读当前值」和「写基线」的函数——**每一个都是潜在的静默失效点。**

**反面**:分两步会让用户觉得繁琐(要先 recheck 再 refresh)。缓解方式是让 `refresh` 明确显示「你将覆盖 v1 的基线」,而不是省掉那一步。

---

### B3 · 刷新必须清空旧决定,旧决定留在历史里

**做法**:`refresh` 递增版本号、**清掉旧的接受**;**旧决定仍留在有界的历史里**;新版本必须**单独评审**。

**为什么有效**:这里有一个精妙的平衡——**清空**是必须的(旧批准不能覆盖新字节),**保留历史**也是必须的(否则无法回答「上一版是谁批的、为什么改」)。两者同时做到,才既安全又可审计。

**怎么搬**:版本升级时:① 当前决定置空;② 旧决定移入 append-only 的历史;③ 历史有上限(本例 100 条审计事件/回执)。**「清空」和「删除」是两回事。**

**反面**:有界历史会在长期项目里丢早期记录。若合规要求长期留存,要把历史导出到外部存储——**但那已经超出插件的职责,要明说。**

---

### B4 · 模型侧没有 `decide`

**做法**:工具动作只有 `record / list / inspect / refresh / preview / export`。原文:「**no `decide` action**. It cannot record acceptance on the user's behalf, supply trusted hashes, change the workspace root or impersonate another session.」

**为什么有效**:这是本域最干净的一条权限设计——**模型可以产生待验收对象,不能签署验收结论**。任何让 agent 自己点「通过」的实现,在所有权上就不是验收。

**怎么搬**:列出你的工具面,划一条线:**产生数据的能力 vs 认定数据的能力**。前者可以给模型,后者必须给人。检查方法:如果模型可以调用一个函数让某件事变成「已完成」,**那这件事就没有验收**。

**反面**:作者自己补了一句关键的诚实——「This separation is a product interaction boundary, **not protection against code already able to execute in the host process**」。**这是产品边界,不是安全边界。** 不要把它宣传成后者。

---

### B5 · 用「故意算错的样本」演示边界

**做法**:演练 2 里的 `report.csv` 故意让 `2 + 3` 的总数等于 `9`。检查项必须**一直显示为「代理声称」**——**一个有效的 SHA-256 不能变成 `2 + 3 = 9` 的证明**。

**为什么有效**:这比任何一段文字说明都有教育价值。它把「哈希正确 ≠ 内容正确」这句话变成了一个**可复现的演示**——用户可以亲手跑一遍,看到哈希打勾而算术是错的。

**怎么搬**:给每个「能力边界」配一个**可复现的反例样本**,放进 `examples/`,并在 README 里给出三步操作。**能被复现的边界,才是被理解的边界。**

**反面**:反例样本可能被误当成「这个工具会算错」的证据。要在 README 里明说这是**故意的**,以及它演示的是**哪一条边界**。

---

### B6 · 路径规范化到真实根,并拒绝所有逃逸形态

**做法**:只支持**真实工作区根之下**的本地普通文件;宿主根先**规范化**(如 macOS `/tmp` → `/private/tmp`);绝对路径、`..` 穿越、Windows 盘符/UNC、根下**符号链接**、目录、FIFO、设备一律拒绝;**工作区与会话由宿主派生,工具/浏览器请求不能指定任意根**。

**为什么有效**:这是「路径校验」写对了的样子。三个容易漏的点:① **符号链接**(指向根外);② **`/tmp` → `/private/tmp`** 这类规范化(不规范化会让同一路径有两种形态);③ **让调用方指定根**(一旦允许,所有校验都可以被绕过)。

**怎么搬**:按这个顺序校验:`抽取相对路径 → 解析真实根(canonicalize)→ 拼接 → 再 canonicalize → 确认前缀仍是真实根 → 检查类型(普通文件)→ 检查符号链接`。**顺序错了等于没做。**

**反面**:严格拒绝符号链接会挡住合法的 monorepo/pnpm 布局。要提供一条**显式的、受审计的**例外通道,而不是悄悄放宽。

---

### B7 · 上限必须有,且截断必须显式

**做法**:每回执 ≤20 路径、每会话 ≤100 回执、每回执 ≤100 审计事件;声明检查 ≤20 条各 500 字符;标题 200;备注 2000;**哈希上限 64 MiB / 文件**;**文本预览上限 64 KiB,带显式截断标记**。

**为什么有效**:没有上限的机制会在真实使用中被大文件拖死;而有上限但不标记截断的机制,会让用户**以为自己看全了**。两者都是沉默的失败。

**怎么搬**:每个「读取/展示」路径都要有上限,并在**触顶时给出可见标记**。特别是预览类:banner 里写「已显示前 64 KiB / 共 3.2 MiB」。

**反面**:硬上限会让合理的用例失败。要给**明确的错误信息**(「文件超过 64 MiB,本工具不处理」),而不是静默只算一半——**后者会产生一个错误但对得上的哈希**。

---

### B8 · 声明的支持范围必须与实测范围一致

**做法**:peer 依赖写成**显式并集**(`@deepseek-ai/dsh-tools@(0.2.0-rc.2 || 0.2.1-rc.3)`);并明写:「Initial end-to-end acceptance is scoped to **local files on macOS**. Windows, Linux, remote workspaces and other Harness versions are **not yet verified**。」

**为什么有效**:大多数插件用 `>=` 声明兼容范围,实际只在一个版本、一个平台上测过。**这给用户的是一个虚假的保证。** 显式并集 + 实测范围声明,把「能装」和「能信」分开。

**怎么搬**:在 README 里写三行——

1. **测试过的宿主版本**(精确到 rc);
2. **测试过的平台**(精确到 OS,以及本地/远程);
3. **尚未验证的范围**(明确列出)。

**并且**用 `engines` / peer 依赖把这个范围**机械地表达出来**,让 `npm install` 就能挡住不匹配的组合。

**反面**:显式并集意味着每次宿主升级都要发新版本,维护成本高。但代价是显性的;**虚假的兼容声明,代价是隐性的、且由用户承担。**
## 8. 体验

**人看到的**:一个对话 tab(`conversation.view` 槽位),三个状态词(`missing` / `unverifiable` / `stale`),两个按钮(接受 / 请求修改),一个可导出的 Markdown。

**模型看到的**:`record` / `inspect` / `refresh` / `preview` / `export` 的结果——**但它看不到「接受」这个动作存在**。这是体验设计的核心:**让模型知道有回执,但不让它知道回执可以自己签。**

**一个原生 UI 的行为细节被写进了插件文档**:在 rc.2 上,未动过的新会话停在欢迎页、不显示会话标签;要先开始一个正常会话才能看到 tab。**跨版本 UI 差异是插件作者必须替用户承担的阅读成本**——这件小事说明「harness 升级」对质量工具的伤害常常是**入口消失**,而不是逻辑出错。

## 9. 失败模式

| 失败 | 表现 | 根因 |
|---|---|---|
| 交付物蒸发 | 点开交付文件,内容已变/已删 | `present` 是指针,不复制内容 |
| 哈希当正确性证明 | 文件哈希正确,内容算错 | 观测 ≠ 判断 |
| 旧接受覆盖新字节 | 改了文件,旧「已接受」仍然有效 | 重检顺手更新了基线 |
| 模型替用户签收 | agent 自己点「接受」 | 工具面暴露了 `decide` |
| 路径逃逸 | 绝对路径/穿越/符号链接把根外文件拉进回执 | 未规范化根、未拒绝链接 |
| 检查中文件在变 | 哈希取到半写状态 | 未检测「检查期间变化」 |
| 过大产物静默截断 | 只看到前 64 KiB,以为看全了 | 预览上限 + 未标截断 |
| 残留无清理 | 卸载后回执仍在存储里,无 purge | 存储归 `storageDomain`,移除不删除 |
| 误认平台支持 | 在 Linux/Windows/远程工作区上以为可用 | 实测范围只到 macOS 本地 |

## 10. 评估清单

1. 它把「代理声称 / 文件观测 / 用户决定」分开记了吗?还是混成一个「已验收」?
2. 决定**绑定版本**吗?文件变了之后旧决定怎么处理?
3. **重检会不会替换基线**?(会 → 变更将永远不被发现)
4. 模型有没有权限代替用户做决定?
5. 哈希/摘要之外,它明说**不证明**什么了吗?
6. 路径怎么规范化?符号链接、绝对路径、`..`、UNC 怎么处理?
7. 「检查期间文件在变化」有没有单独状态?
8. 大产物与长文本的截断有没有**显式标记**?
9. 卸载后数据怎么办?有没有清理路径?
10. 它宣称支持的平台,和**实测覆盖**的平台一致吗?
