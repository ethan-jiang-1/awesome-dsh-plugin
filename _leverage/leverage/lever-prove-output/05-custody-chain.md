# 05 · 保管链：哈希链能证什么、不能证什么

> **状态**:`observed`(检测边界表双方都公开,已核) · **基线**:DSH `0.2.1-rc.3` · 名单 @ `efe602e7b`
> **样本**:2 组(`030611/qiushi-dsh-evidence-audit` 主标杆 · `zhengqiuyang/dsh-attest-chain` 对照)

④ 证据环里最容易被高估的一格。两个插件都诚实地列出了**自己检测不到什么**,而那张表比任何宣传语都值钱。本卡的核心结论是:**哈希链证明的是「这份文件没被改过」,不是「记录的事是真的」;而它连「这份文件被整个删掉了」都证不了。**

---

## 1. 命题

> 哈希链的价值不在「不可篡改」(它做不到),而在**「篡改会被定位」**:一个不匹配的 `{seq, reason}` 比一句「我不信」有用得多。要让「不可篡改」成立,必须有一个**链外锚点**——而锚点在哪,决定了整条链的可信半径。

可证伪:

- **P1**:若无锚点的哈希链已经足够,则「删整个文件检测不到」不构成缺陷。
- **P2**:若签名能解决锚点问题,则 attest-chain 不需要「发布 head」这一步。

P1 不成立(两边都在 §3.2 / §3.4 明写「No」)。P2 不成立:**签名证明「这是持有私钥的人签的」,不证明「这条链还是原来那条」**——删除尾部后剩下的前缀依然自洽、依然签名有效,只有和**外部公布的 head** 比对才能发现。所以 attest-chain 也必须「publish the head digest」。

## 3. 机制

### 3.1 两者的记录形态

**qiushi(不签名)**:

- 记录**只存哈希**,不存提示词、工具参数、结果正文、原始会话 ID;
- 默认落在 `$DSH_HOME/evidence-audit/evidence-receipts.jsonl`(**不是 cwd**),目录 `0700`、文件 `0600`(尊重 POSIX 的操作系统上);
- 不保存明文 —— **最小化留存本身就是安全设计**:回执可用于追责,却不新增泄密面。

**attest-chain(签名)**:

```
record ──> digest = sha256(canonicalJSON({seq, prevDigest, record}))
        ──> ed25519 签 digest（密钥对在 .dsh-attest-chain/keys/）
        ──> 追加到 .dsh-attest-chain/session.jsonl（一行一条，严格顺序）
```

- 记录**绑定模型可见内容的 sha256**、工具名、`callId`、错误标记;
- **从 shell 输出里提取 commit SHA** 并入链——把工作绑定到仓库历史;
- `sign: false` 可退化为纯摘要链(「只要对已发布 head 的防篡改」时够用);
- 密钥目录必须进 `.gitignore`(README 明写)。

### 3.2 检测边界表(这是本卡最重要的数据)

| 场景 | qiushi | attest-chain | 边界条件 |
|---|---|---|---|
| 改保留行 / 断链 | **Yes** | Yes(签名不匹配) | 除非攻击者重算该行及其后所有哈希 |
| 删掉未动过的**前缀** | **Yes** | Yes | 首个剩余 seq/link 不再从 `0`/`null` 开始;**重写并重链可绕过** |
| 末尾留下**半行** | **Yes** | — | 非空文件必须以完整 JSON 记录 + 换行结尾 |
| **删掉整个文件** | **No** | No | 没有链外锚点时,「重建」与「首次使用」无法区分 |
| **删掉一段完整的尾部** | **No** | No(除非比对已发布 head) | 更短的前缀仍是合法链 |
| 攻击者**重写并重链** | **No** | 签名挡住(无私钥) | SHA-256 无密钥、文件不带可信签名/检查点 |
| 两进程同时追加同一文件 | 未阻止 | — | 无跨进程锁;事后校验会拒绝重复/陈旧 seq |

**读法**:左边三行「Yes」让人以为它很硬;右边两行「No」把它打回原形。**「删整个文件」这一行是所有无锚点哈希链的死穴**——只要攻击者能删文件,链就归零。所以这两条插件的真正约束是**存储位置**:qiushi 把回执放到 `DSH_HOME`、用 `0700/0600`,不是因为洁癖,是因为**文件的删除权限就是链的信任边界**。

### 3.3 校验的产物形状,决定了它有没有用

- qiushi:文件级判定(启动/校验时线性扫描)。
- attest-chain:`verifyChain()` 返回**第一个坏点的 `{seq, reason}`**,并区分「断链 / 摘要不符 / 签名不符」三因。

**这是两者最大的机制差**:「文件坏了」只能让你不信整份记录;「第 417 条起签名不符」能告诉你**从哪一步开始不可信**,从而让前面的记录仍然可用。归因能力是可以被下游消费的(attest-chain 的 `verifyChain` 作为导出 API,被同作者的面板实时调用)——**证据只有能被程序消费,才会被真正使用。**

### 3.4 「证不了什么」——两句原话

- qiushi:「**不能**证明命令执行正确、结果属实、文件由谁产生、或合法尾部未被删除。」
- attest-chain:「两条都是 observe-only 且对限制诚实——**都无法证明一条命令跑对了**,也无法检测在账本首次发布之前被删掉的尾部。」

**这两句话应该被刻在 ④ 环的门口**:证据链证的是**记录完整性**,不是**事实正确性**。一个「有完整哈希链」的项目,完全可能整条链记录的都是错的结果。

### 3.5 两者都写了「什么时候该退役」

attest-chain 有一节叫 **Kill criteria**:若 DSH 出了一等公民的签名会话记录,或某个主流插件原生支持 attestation,这条就冻结在最后一个可用版本并写复盘。**这是本域唯一一个自带退役条件的样本**——它承认自己是一层**补丁**,补丁在原生补上之后应当消失。

### 5.1 它的工程诚实度值得单列

多数「安全插件」的 README 只有功能段。这一条有三样东西:

1. **一张「No」表**——把不能检测的三种情形写成表格;

**判断一个证据插件能不能用,先看它有没有第 1 样东西。** 没有「No」表的完整性工具,通常是把「哈希」当成了「不可篡改」的同义词。

## 7. 可借鉴:八条可以直接搬走的做法

### B1 · 先写「检测不到什么」,再写「检测什么」

**做法**:qiushi 的 README 有一整节 *Integrity detection boundaries*,用表格逐条列出**检测不到**的情形——删整个文件(No)、删完整尾部(No)、重写重链(No)、两进程写同一文件(未阻止)。

**为什么有效**:完整性工具最大的风险不是能力不足,是**被误解为能力更强**。一张「No」表把预期压回真实水平,读者才不会把「有哈希」当「不可篡改」。更重要的是,**这张表本身就是设计文档**:它告诉你攻击面在哪,以及你必须在哪补一层。

**怎么搬**:在写任何安全/证据机制之前,先写这张表。格式:

| 场景 | 能检测吗 | 精确边界 |
|---|---|---|
| 改了保留的一行 | 是 | 除非攻击者重算该行及之后所有哈希 |
| 删掉整个文件 | **否** | 没有链外锚点时,重建与首次使用不可区分 |

**写不出「否」的机制,通常还没想清楚它的信任边界在哪。**

---

### B2 · 锚点必须在链外,而且**发布锚点**是用户动作

**做法**:两家的诚实结论一致:签名证明「这是持有私钥的人签的」,不证明「这条链还是原来那条」——删掉尾部后剩下的前缀依然自洽、依然签名有效。只有和**外部公布的 head** 比对才能发现。而**发布 head 在两家的 README 里都是用户动作,不是插件能力**。

**为什么有效**:这不是实现缺陷,是**逻辑必然**。锚点若在链里,它就是链的一部分,可以一起被重写。**锚点必须在被保护对象之外。**

**怎么搬**:任何「防篡改」设计都要回答「我拿什么和什么比」。三选一:

1. **链外发布**(每次会话结束把 head 发到远端 / 提 PR / 写另一台机器)——最有效,但需要基础设施;
2. **文件系统权限**(`0700/0600`,放到 `DSH_HOME` 而不是 cwd)——便宜,边界是「谁有删除权限」;
3. **没有锚点**——那就只能叫「防内部误改」,不能叫「防篡改」。

**反面**:把「请自行发布 head」写进 README 而没有任何工具支持,等于把最难的一步留给了最不可能做的人。**若要真正落地,发布必须做成一次点击。**

---

### B3 · 只存哈希,不存内容

**做法**:qiushi 的 receipt **只保存哈希**,不存提示词、工具参数、结果正文、原始会话 ID;默认落 `$DSH_HOME/evidence-audit/evidence-receipts.jsonl`(**不是 cwd**),目录 `0700`、文件 `0600`。

**为什么有效**:证据系统本身就是一个新的泄密面——为了将来能追责,把当时的提示词和工具输出全存下来,等于在你的磁盘上复制了一份会话内容。**最小化留存是一项安全设计,不是洁癖。**

**怎么搬**:问三个问题——① 我只为「证明发生过」需要存多少?② 存的位置在不在可能被 `git add` 到的地方?③ 权限位说了什么?**答案通常是:哈希、时间戳、序号、工具名——其余都不必存。**

**反面**:只存哈希意味着**事后无法回看内容**。若你的场景需要「当时那个文件是什么」,就必须存内容,那就要面对留存合规与最小化之间的取舍——**明确写下来,不要假装两者兼得**。

---

### B4 · 校验输出必须是「第一个坏点 + 原因」,不能只是「文件坏了」

**做法**:`verifyChain()` 返回第一个坏点的 `{seq, reason}`,区分「断链 / 摘要不符 / 签名不符」三因。

**为什么有效**:「文件坏了」只能让你**不信整份记录**;「第 417 条起签名不符」能告诉你**从哪一步开始不可信**,从而让前面的记录仍然可用。这是**归因能力**,而归因能力可以被下游消费——attest-chain 的 `verifyChain` 作为导出 API,被同作者的信任面板实时调用。

**怎么搬**:任何校验器都返回**结构化定位**:`{index, expected, actual, kind}`。**错误对象要能被程序读,不只是给人看。** 一条好的校验错误至少包含:位置、期望、实际、类别。

**反面**:定位要求记录有稳定的序号与链式链接。若记录是并发写入的,序号的稳定性会被破坏——这就是为什么 qiushi 建议**一个进程一个文件**。

---

### B5 · 把工作绑定到仓库历史

**做法**:attest-chain 从 shell 输出里**提取 commit SHA** 并入链摘要。

**为什么有效**:只有哈希与序号,记录只证明「发生过某次工具调用」;绑上 commit SHA 之后,记录变成「**在这些代码上**发生过这次调用」。这让事后审计能问出真问题:这条证据对应的是哪个版本?

**怎么搬**:在记录里加入**当时环境的最小标识**——commit、容器镜像 digest、依赖 lock 的哈希、构建号。**证据与环境的绑定关系,决定了证据在多久之后仍然有意义。**

**反面**:从 shell 输出里**猜** SHA 是启发式的,可能抓错(比如输出里同时有多个 SHA)。稳妥做法是让工具显式上报,但那要求工具配合——这就是「启发式 vs 契约」的取舍,需要写清楚。

---

### B6 · 密钥必须在仓库之外,或者至少被明确 gitignore

**做法**:ed25519 密钥对在 `.dsh-attest-chain/keys/`,README 明确要求加入 `.gitignore`;`sign: false` 可退化为纯摘要链。

**为什么有效**:签名方案的安全边界是**私钥**;而「记得配 gitignore」是一个靠人的约束。给出 `sign: false` 的降级路径,让「只要防内部误改」的用户不必承担密钥风险——**把安全性做成可选档,而不是唯一档。**

**怎么搬**:任何需要密钥的插件,都必须回答:① 密钥默认落在哪?② 会不会被提交?③ 不用密钥时功能还剩什么?**第三点最常被忽略,而它决定这个插件会不会被真正用起来。**

**反面**:签名归因到**密钥**,不归因到**人**。一个人把私钥共享给同事,签名就失去区分力。**合规场景需要人-密钥绑定,那是另一层,插件层做不到。**

### B7 · 写下退役条件

**做法**:attest-chain 有一节 *Kill criteria*:若 DSH 出了一等公民的签名会话记录,或某个主流插件原生支持 attestation,这条就**冻结在最后一个可用版本并写复盘**。

**为什么有效**:这是本域唯一一个**自带退役条件**的样本。它承认自己是一层**补丁**,而补丁在原生补上之后应当消失。**一个不写退役条件的机制,会在需求消失后继续存在,并消耗维护注意力与被它误导的用户。**

**怎么搬**:在 README 里写一段:「如果 `X` 出现,本项目应停止,理由如下」。`X` 必须是**可观测的事实**(某个 API 存在、某个能力原生支持),不能是「如果不再需要」。

**反面**:退役条件写得太宽(「如果官方做了更好的」)等于没写。判据必须具体到能被 `grep` 出来。

### B8 · 工程诚实度是一份可检查的清单

**做法**:qiushi 的测试覆盖清单精确到:canonical JSON 接受/拒绝、Unicode 行为、固定 SHA-256 向量、确定性链创建、**精确的篡改/截断边界**、**真实双进程追加竞态**、明文排除、重复 feed 观测、失败收容、安全默认解析、真实 Cordis 挂载/事件/销毁、构建产物加载、publint、精确 pack 列表、从 tarball 安装/导入/挂载、字节一致的官方 `applyEntryPatches` 复现。

**为什么有效**:这份清单可以**直接当成评估表**。它列出了完整性工具应该测的每一件事,而且特别包括两条最容易被跳过的:**「精确的截断边界」**(而不是「测了截断」)和**「真实双进程竞态」**(而不是「考虑过并发」)。

**怎么搬**:评估任何安全/证据插件时,按这四类问:① **边界测试**精不精确(±1 字节、±1 条记录)?② **并发**是真进程还是模拟?③ **明文/敏感数据泄漏**有没有测?④ **安装形态**(tarball、pack 列表)有没有测,还是只在源码目录里跑得通?

**反面**:测试清单长 ≠ 质量高。要同时看它**没测什么**——qiushi 的清单里没有「跨文件系统行为」「Windows ACL」「断电持久性」,而它的限制章节承认了这三点。
## 8. 体验

**人看到的**:几乎没有 —— 两条都是 observe-only,正常使用时**零可见**。它们的体验全部在「出问题那天」:启动时报告断链、`verifyChain` 指出第几条坏了。

**模型看到的**:也没有 —— 它们默认不给模型任何输出。这是刻意的:**证据不该能影响被判者**。若把链状态回灌到 prompt,agent 就会学会「让链看起来正常」,而链的全部价值在于它不受 agent 影响。

**一个反直觉判断**:④ 环最好的用户体验是**平日不可见、事发可定位**。凡是平时就跳出来提示「正在记录」的证据工具,通常在把成本转嫁给每一次对话。

## 9. 失败模式

| 失败 | 表现 | 根因 |
|---|---|---|
| 把哈希当不可篡改 | 声称 tamper-proof,却挡不住删文件/删尾部 | 无链外锚点 |
| 链完整但内容错 | 每条记录都验得过,记录的事却是假的 | 证完整性 ≠ 证真实性 |
| 断电丢尾 | 最后一条回执消失,链仍自洽 | `writeSync` 不是 `fsync` |
| 多进程写同一文件 | 出现重复/陈旧 seq,只能事后发现 | 无跨进程锁 |
| 密钥随仓库泄漏 | 私钥进了 git | 「加进 .gitignore」靠人记 |
| 启动变慢 | 长会话校验线性增长 | 全文件扫描 |
| 证据无人消费 | 有链但没人验 | 判定结果不可被程序读 |
