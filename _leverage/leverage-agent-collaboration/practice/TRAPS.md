# 照抄就中招（协作版）

> 每条都给**反例**。没有反例的提醒没人记得住。

## 1. 把 `writeScopes` 当互斥

**症状**：两个成员同时改同一文件，任务板显示一切正常，产物互相覆盖。
**机制**：官方 Team 的 `writeScopes` 只在投影里 `warnings.add`，**不拦任何写入** `[SRC-DSH]` `dsh-experimental-agent-team/lib/index.js:371`。
**反例**：样本 05 的质量门也只校验 `changedPaths`，不执行任何写锁。
**做法**：互斥只能靠 `pre-execute` deny 或 worktree；`writeScopes` 当提示词用。

## 2. 用进程内锁保护跨进程状态

**症状**：单进程测试全绿，两个成员一开就少一个。
**机制**：`withTeamLock` 是进程内 promise 链，不是文件锁。
**反例**：R4a/R4b——两进程各持锁、各加一个成员，最终只剩 `beta`，**退出码都是 0**。
**做法**：跨进程要么文件锁 + 归属，要么 CAS + 重试；原子写只保证文件不半写。

## 3. 相信 README 写的机制在发布物里

**症状**：文档说有跨进程锁，装完却完全没有。
**机制**：README 描述的是源码，发布物可能是半年前的构建。
**反例**：样本 05 的跨进程锁只在未发布的 v0.3+ 源码；npm 0.2.0 零锁符号（R5）。
**做法**：引用机制前先看发布物；`npm view` + 解包检索，比 README 可靠。

## 4. 把「投递成功」当「被消费」

**症状**：消息显示已送达，模型下一轮却不知道。
**机制**：准入 ≠ 消费；ack 应该发生在接收方**真正进入 step** 的位置。
**反例**：样本 01 的 ack 只在 `agent/pre-step` 准入或状态读取时发生，代码注释写明「Acceptance by Harness is not evidence that a model step consumed input」。
**做法**：邮箱做三态（claim/deliver/read），别用「投递返回」当完成。

## 5. 没有幂等键就重试

**症状**：一重试就重复执行，产物多一份。
**机制**：`reqId` 只做请求关联，不做去重。
**反例**：样本 08 的 `reqId` 超时即删 pending，重试可能重复投递；样本 13 才用幂等键去重。
**做法**：先有消息 id + 去重表，再谈重试；没有就写「不保证」。

## 6. 把「记录存在」当「可恢复」

**症状**：重启后界面还列着 run，点进去什么都没有。
**机制**：持久化记录 ≠ 可续跑的控制面。
**反例**：样本 02 重启后活动 run → interrupted，且 interrupted 被排除在可续跑之外；样本 14 的房间投影在新宿主上退化为空 fold。
**做法**：恢复要过 checkpoint、authority、template hash 三关（样本 18 的做法），不是「读到记录就继续」。

## 7. 在共享 checkout 上并行写

**症状**：两个成员各改各的，合并时互相覆盖。
**机制**：多成员共享同一工作区，谁最后写谁赢。
**反例**：样本 01/05 都共享 checkout；样本 11 用「每 lane 一个 worktree」才隔离，而 R7 证明 worktree **只带已提交文件**，未跟踪/被忽略的不在。
**做法**：写入并行前先隔离；worktree 不是完整沙箱，未提交状态仍共享。

## 8. 用提示词约定当拦截

**症状**：提示词写了「改之前先检查」，还是撞车。
**机制**：提示词是建议，不是拦截。
**反例**：样本 07 的 deny 落在 `tools/pre-execute`（R3 用假 `ctx` 复现：write/edit/bash 重定向全被拒，read 放行）；提示词只是补充。
**做法**：拦截写在写路径上，并在文档里写清覆盖哪些工具。

## 9. 把 approval 当并发控制

**症状**：以为「要审批」就不会有两个写者。
**机制**：approval 是**单次决策**，不是锁；它不阻止第二个调用。
**反例**：`approval/asked` 与 `approval/decided` 成对落日志，但没有「持有」概念 `[SRC-DSH]` `dsh-user-approval/lib/index.js:139`。
**做法**：互斥与审批分开设计；审批管「能不能做」，锁管「现在谁做」。

## 10. 让子代理自己找父邮箱

**症状**：子代理跑完把结果发给父，父不在，消息消失。
**机制**：宿主没有持久 parent mailbox。
**反例**：child→parent 投递要求直接 parent 在线，父缺失时**拒绝而不排队** `[SRC-DSH]` `dsh-subagent/README.md:207,212`。
**做法**：结果落文件/任务板/邮箱，父回来再读；别把「父在线」当前提。

## 11. 拿 `provider.start` 当委派入口

**症状**：包装了 provider，路由却完全没生效。
**机制**：rc.3 在 provider 有 `prepareContinuable` 时走 `startLocal`，`provider.start` 只在 external 分支被调。
**反例**：`dsh-subagent/lib/index.js:3047`；样本 16 真正生效的是 `startActivation` 钩子。
**做法**：路由钉在 `startActivation`；先确认 provider 声明了哪个方法。

## 12. 把「有 DAG」当「能暂停」

**症状**：图画好了，以为进程重启能接着跑。
**机制**：图只表达依赖，不表达 checkpoint。
**反例**：样本 18 的 `resume` 要 run 存在、authority 一致、`semanticHash` 一致；`recorded` 重放还要求源 run 完成且 Artifact 齐全。
**做法**：把「恢复」「重放」「重跑」三件事分开写；没有 journal 就不要承诺暂停。

## 13. 用多 agent 省 token

**症状**：想用拆分降低单会话上下文，结果账单翻十倍。
**机制**：多 agent 是**买 token**（并行上下文），不是省 token。
**反例**：Anthropic 复盘：多 agent 约 15× 聊天 token；token 用量单独解释 80% 的性能方差 `[LIT]`。
**做法**：先算任务价值能否撑起 10 倍 token；不能就用单 agent + 只读子代理。

## 14. 用「同族三个样本」当规律

**症状**：三个团队运行时都这么做，于是写成「行业惯例」。
**机制**：同骨架的三个样本只算一个机制。
**反例**：01/05/12 高度同源；本册已把 05/12 降为变体，只留 01 作典型。
**做法**：先判机制族；同一族只算 n=1，跨族才谈归纳。

## 15. 把锁过期当安全接管

**症状**：原主卡了一下，锁被抢，原主醒来继续写。
**机制**：没有 epoch/fencing 的租约，接管后原主不知道自己已经失去资格。
**反例**：样本 07 的租约无 epoch，被接管时原主静默失锁（但下一次写会被 deny）；样本 05 的锁 30s stale 可被抢。
**做法**：租约带单调 epoch，写前校验；被拒方要能读到原因。

## 16. 在真实 profile 里做实验

**症状**：测完发现自己的 `~/.dsh` 被改了。
**机制**：隔离 `DSH_HOME` 不够——插件自己可能写死绝对路径。
**反例**：lifecycle 的 TRAP 15（隔离 profile 下仍回显真实 home 路径）；本册 R0–R7 全部在 `.work`，不碰真实 profile。
**做法**：临时 `DSH_HOME` + 临时 workspace + 限网；测完核对真实 home 是否被创建/修改。
