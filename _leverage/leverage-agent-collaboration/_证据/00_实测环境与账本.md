## 1. 账本

### R1 · 认领路径的作用域（07）

- **做法**：直接调用 `claim.mjs` 的 `claimsOverlap` / `pathConflict` / `normPath`。
- **观察**：大小写不敏感命中；目录认领覆盖子路径（双向都判 true）；`src/a.ts` 与 `src/a.ts.bak` **不**重叠；`.` 覆盖一切；`../outside` 与绝对路径归一化返回 `null`。
- **解释**：前缀歧义被正确区分（`a.ts` 不是 `a.ts.bak` 的目录）；越界路径被拒。**边界**：只测纯函数，不测扫描时文件系统竞态。

### R2 · stale / 损坏 / 孤儿边车（07）

- **做法**：造四个边车——新鲜、10 分钟前、损坏 JSON、`pid` 已死；`guardHits` 一次检查四个目标。
- **观察**：只有新鲜边车命中（`a.txt（s-other）`）；10 分钟前的按 5 分钟阈值判 stale 不拦；损坏边车**放行**（fail-open）；死 pid 边车不拦；`readClaim` 对损坏文件**抛错**（`认领边车损坏：…`），对缺失返回 `null`。
- **解释**：拦截判定与读取判定是两条不同的失败策略——**guard 静默放行，read 大声抛错**。**边界**：默认 stale 是 `7,200,000 ms`（2 小时），只有带 `pid` 且进程已死的边车会立即失效；**没有 pid 的崩溃残留会挡 2 小时**。

### R3 · deny 是否真的接在 `tools/pre-execute` 上（07）

- **做法**：用假 `ctx` 调插件 `apply()`，捕获 handler；再以六种 `exec` 调用。
- **观察**：`write`/`edit` 命中他人认领 → `deny`（reason 含「dsh-file-claim 拦截」）；自己的 tag → 放行；`read` → 放行；未认领路径 → 放行；`bash` 的 `echo hi > a.txt` → **deny**。
- **解释**：拦截确实在写路径上，且覆盖 shell 重定向。**边界**：假 ctx 只模拟 `workspaceRegistry` 缺失回退；真实宿主里 `resolveByPath` 可能返回不同根。

### R4 · 两个进程各持「锁」仍丢更新（01 / 05）

- **做法**：两个子进程各自 `withTeamLock` → `readTeamSync` → 等 250ms → `writeTeam`，各加入一个成员。
- **观察**：01 与 05 都是最终只剩 `beta`，`alpha` 丢失；两个子进程退出码都是 `0`。
- **解释**：**`withTeamLock` 是进程内 promise 链**（`state.js:38-60`），原子写只保证「文件不半写」，不保证「读改写不丢」。**边界**：模块级复现，不涉及宿主事件顺序。

### R5 · 发布物里到底有没有跨进程锁（05）

- **做法**：在 0.2.0 工件里检索锁符号；查 npm 版本表。
- **观察**：`DSH_TEAMSX_FILE_LOCK` / `flock` / `.lock` / `locks/` **全部未命中**；`'wx'` 只用于原子临时文件；npm 只有 `0.1.0` 与 `0.2.0`。
- **解释**：**装得到的 0.2.0 没有跨进程锁**；memo 记录的跨进程文件锁属于**未发布的 v0.3+ 源码**（`state.ts:153-156`）。**边界**：不能据此说源码没有锁，只能说发布物没有。

### R6 · 任务分波（11）

- **做法**：用 `dsh-taskswarm2@0.2.38` 的 `buildWaves` 跑三条依赖图。
- **观察**：正常图 → `[[a],[b,c],[d]]`；环 `x↔y` → 合成一波 `[[x,y]]`（不报错）；缺失依赖 → `[[e]]` 且 `unresolvedDeps.e=['zzz']`。
- **解释**：分波按依赖正确；**环不拒绝，退化成同一波**，缺失依赖只记录不阻塞。**边界**：只测分波函数，不测执行与合并。

### R7 · worktree 到底隔离了什么（11 的机制底座）

- **做法**：临时 git 仓库（1 个已提交文件 + 未跟踪 + 被忽略）→ `git worktree add -b lane`。
- **观察**：已提交文件在；未跟踪与被忽略文件**不在**；`.git` 是 `gitdir:` 指针；在 worktree 里改文件不影响主检出；移除 worktree 后分支 `lane` **仍在**。
- **解释**：worktree 隔离的是**检出目录**，共享的是**仓库对象与分支命名空间**；清理与合并确实要消费方自己做。**边界**：这是 git 行为，不是 11 插件行为。

## 2. 一条推翻

**卡 05 与 encyclopedia 写的「跨进程文件锁」在发布物上不成立。**

- 证据：R4b（两进程各持 `withTeamLock` 仍丢更新）+ R5（0.2.0 工件无锁符号，npm 只有 0.1.0/0.2.0）。
- 准确表述：**发布物 0.2.0 只有进程内队列 + 原子写；跨进程文件锁只存在于未发布的 v0.3+ 源码。**
- 影响：卡 05 的机制段、`teams/01` 的「05 用跨进程文件锁」、`encyclopedia` 的一句话都要加「未发布」限定；这同时是 `COMPAT` 里「发布物 ≠ 源码」的又一个实例。

## 4. 这些证据不能证明什么

- 不是端到端：没有起 DSH，没有真实事件顺序、审批、profile、模型。
- 05 的 v0.3+ 源码未运行；11 用的是 `dsh-taskswarm2` 临时包，patch 名不匹配。
- R7 是 git 语义，不是 11 的编排语义。
- 所有结论只对 R0 记录的版本与平台成立。
