## 它想干什么 · 为什么值得借鉴

**意图。** 把“全家桶”还原成**最小技术形态**：一个只做挂载的聚合包（全部内容就是一条 bundle patch）+ 一个共享库 + 11 个插件，并顺手把 profile 管理做成一张卡片。它想做的是“证明聚合可以只是数据”。

**意义。** 它回答了“聚合包最少需要什么”——**纯数据即可，不带业务逻辑**。共享库把回环围栏、托管区块、`!!js` 表达式这类宿主半体工具收在一处，避免每个插件各写一遍；这个“共享库不进 bundles”的边界，是很多聚合包会踩的坑。

**用户价值。** 一条命令得到 11 件工具，而且**装之前就知道每件动的是哪一层**（给模型注册工具 / 只改 systemPrompt / 只是界面卡片）；想只装几个也行。Profile 卡片让“我到底在跑哪套配置”第一次变得可操作——创建、复制、改名、删除、逐 profile 端口，都能点。

**表达（界面与交互）。** 装之前先给一张**分面表**：谁会往模型里加工具、谁只改 systemPrompt、谁只是界面卡片——把“装完会变什么”提前说完。Profile 卡片里能直接复制带 `--port` 的启动命令，把“配置”变成可以点的东西。**它的体验不在界面好看，而在“你知道自己在装什么”。**

## 1. 它在产品里的位置

**七层坐标**:**3**(11 个插件各占槽位)+ **5**(默认值:kit-settings 统一设置)+ **7**(分发:聚合包 + 按需装)。它不换表层、不做主题——**界面仍是 DSH 原生**,产品力全在"装什么、怎么配、怎么管 profile"。

**三种聚合形态对照**:

| 形态 | 代表 | 聚合包的内容 | 用户感知 |
|---|---|---|---|
| 功能全家桶 | `dsh-web` | 20+ 自研包 + 商店/皮肤 | "换了一个产品" |
| 界面套件 | `codex-ui` | 单包六微内核 | "换了一套皮和设置" |
| **纯聚合补丁** | **本卡** | **一条 patch + 有序 bundles** | **"一次装齐,界面没变"** |

**它最特别的地方**:`packages/profile` 那张卡片——**一个 profile 级产品,顺手把"管理 profile"也做成了功能**。用户可以在浏览器里创建 `base`/`web`/`headless` 三种模板的 profile、复制改名、配端口、复制启动命令。

## 2. 机制(可照抄)

### 2.1 聚合包 = 纯数据

- 聚合包不带业务逻辑,只提供一个 `dsh.bundle.patch`,把仓库内 11 个包的挂载行写进 `dsh.profile.bundles`;
- 每个插件仍可单独安装;聚合包只是"一次装齐"的快捷方式。

> **照抄点**:**聚合包不要有代码。** 它一旦开始写逻辑,就会变成"第 12 个插件",而且是最难卸载的那个。

### 2.2 共享库:宿主半体的公共设施

`@hyzyn/dsh-kit`(非插件)收四类工具:

- **HTTP 回环围栏**(只允许环回访问);
- **托管区块**(往文档/配置里写一段可被安全替换的区块);
- **`!!js` 表达式**(配置里的受限求值);
- **服务读取**(从宿主拿服务)。

> **照抄点**:11 个插件共用的宿主侧能力,收进**一个库**,而不是复制 11 份。库不是插件,不进 bundles。

### 2.3 分面表:装之前先知道它动了哪一层

README 用一张表回答"装了它意味着什么":

- 给模型**注册工具**(真正改 agent 能力):`tty`(`tty_*`/`sftp_*`)、`docker`(`docker_*`)、`loglens`(只读)、`codegraph`(托管 MCP 行);
- 只往 **systemPrompt** 添一段:`rss`、`search`;
- 只做**界面卡片**:`env`、`mcp`、`prompt`、`profile`…

> **照抄点**:聚合产品的文档必须回答"**装了它会改变什么**",而不是列功能名。用户最怕的是"装完模型行为变了却不知道是谁"。

### 2.4 兼容:11 档显式枚举

- 声明适配 11 个基线(`0.1.7-rc.2`、`0.2.0-rc.1/2`、`0.2.1-alpha.1/2/5`、`0.2.1-rc.1`…`rc.5`);
- "最新五档都是**纯显式声明:对宿主零差异**";
- `0.1.6-alpha.2` 及更早**不再支持**。

> **照抄点**:兼容列表要么写"零差异的显式声明",要么写清每档差异。**不要写"支持 0.2.x"**。

### 2.5 Profile 管理卡片:把"profile 本身"做成 UI

- 查看 `~/.dsh/profiles` 下的 profile;
- 创建:`base` / `web` / `headless` 三种模板;
- 复制 / 改名 / 删除;
- 逐 profile 配端口,并**复制带 `--port` 的启动命令**。

> **照抄点**:profile 产品的用户迟早要管多个 profile。**把"复制启动命令"做进产品**,比写十行文档有用。

## 3. 体验

- **第一次**:装聚合包 → 重启 → 11 个插件各就各位,界面仍是原生 DSH。
- **日常**:kit-settings 统一配置;终端/Docker/日志/搜索各是一张卡;Profile 卡片里能开新 profile 并复制启动命令。
- **按需**:不想全装就单独装某几个,聚合包不强制。

## 5. 借鉴食谱

| 要解决的问题 | 照它的做法 | 要改的地方 | 抄错的后果 |
|---|---|---|---|
| 一次装齐 N 个插件 | 聚合包只放**一条 patch**,不带逻辑 | patch 要可读、可 diff | 聚合包写业务 → 变成最难卸的第 12 个插件 |
| N 个插件重复造轮子 | 共享库收宿主半体工具 | 库**不进** bundles | 把库当插件挂 → 多一层生命周期 bug |
| 用户不知道装完会变什么 | 分面表:模型工具 / systemPrompt / 界面 | 每项写清"装/不装"的差异 | 只列功能名 → 用户装了不敢用 |
| 兼容说法含糊 | 11 档显式枚举 + "零差异"标注 | 每档要么验证要么标 `[OPEN]` | 一句"支持 0.2.x" → 上游一改就靠用户报错 |
| 用户要管多个 profile | 内置 Profile 卡片 + 复制启动命令 | 删除/改名要防误操作 | 只给文档 → 用户手改目录,改坏 profile |
| 按需安装 | 单包与聚合包共存 | id 命名空间要隔离 | 聚合+单装重复注册 → 冲突 |

## 6. 失效条件与降级

- **版本**:只到 `0.2.1-rc.5`;`0.1.6` 及更早明确不支持。
- **分面耦合**:`tty`/`docker`/`loglens` 会**改变模型可见的工具面**;只想"装个界面"的用户会意外获得新工具权限。
- **共享库**:13 个包之间的依赖方向一旦混乱,卸载会留下孤儿。
- **聚合包失效**:patch 行写坏 → 11 个插件一起不加载,且错误信息可能只指向其中一行。
