## Install, enablement, update and recovery

- **[DOC]/[SRC-DSH] Scope.** README instructs adding Suite to `desktop` or `web` profile. The target updater injects public `profileContext` and registers its coordinator keyed by that profile context, storing preferences/cache in that profile directory. It does not establish one machine-global preference or cross-profile coordinator. The Suite patch inserts component rows; the updater’s `targets()` includes installed profile-available rows and marks components `bundledBy: Suite` when an enabled Suite is present. It does not itself disable/enable components through a separate feature toggle. Patch `insert` is not a promise that a package can load successfully.
- **[SRC-TARGET] Update admission.** `packages/updates/lib/index.js` registers an owner-only POST route; manual installation requires explicit confirmation. Registry allowlist is fixed; package identity, semver, `dsh.bundle` metadata, integrity, DSH/Node ranges and stable version are validated before proposing update. Re-fetch immediately before installation and require version/integrity to match prior check. Only registry-sourced packages are managed; local path, git/URL and aliases preserve their existing update route. Suite-managed components are not independent update targets, preventing duplicate member installs; Suite is updated as a whole. Existing enabled state is preserved by installer options.
- **[SRC-TARGET] User consent/state.** `packages/updates/lib/store.js` keeps schema/revision and per-package `checkEnabled`, `autoInstall`, `deferredUntil`, `ignoredVersion` in `<profile>/stardustlc-plugin-updates.json`, and metadata cache separately. Defaults: checks enabled, auto-install disabled. Preferences use revision-checked lock and atomic temp-file rename; unreadable/bad/symlink state fails closed and is retained for repair. File lock is not a distributed transaction with npm/DSH package operations.
- **[SRC-TARGET] Automatic update gate.** `policy.js` allows only enabled, healthy, registry-sourced, not Suite-managed components with stable patch increment; requires explicit per-package consent, no deferral/ignored release, known idle Host agents/jobs, fresh client heartbeat, no dirty/busy page, two minutes quiet, and no pending restart. Checks are at most once/day by default; manual check remains available. Unknown Host activity/page status fails closed. This is policy code, not proof every real UI edit registers a guard.
- **[SRC-TARGET] Transaction/recovery.** `NativeInstaller` prefers Host `updateBundle` if available. rc.3 fallback records exact old name/version/enabled/registry, removes then installs exact new release through official plugin manager, then on failed/cancelled install queries current bundle and reinstalls previous exact version and enabled state. Startup-owned package removal can return `stop-profile`; it installs over it and surfaces restart-required instead of forcing restart. If restoration fails, coordinator enters `restore-failed`; uncertain admitted operation becomes `unknown`; both block retries until user inspects/repairs in official manager and restarts. `cancelInstall` delegates to host; cancellation cannot roll back a package-manager write already completed. Recovery is compensating, not atomic: a crash between remove/install/restore can leave partial state. README updater docs explicitly state no forced restart or DSH self-update.
- **Conflict boundary.** Suite component coexistence is supported by design as same member package graph, but adding same member independently alongside Suite risks duplicate Loader ids/rows. The source updater intentionally suppresses duplicate component update controls; it does not prove arbitrary second bundles with overlapping ids/configs are conflict-free. Another aggregate that inserts same row ids may collide or alter effective config, depending on patch layer/order. No universal conflict checker was found in scope.

## Conclusion and boundary

For an 18-member suite, exact direct package versions and an explicit bundle row/config manifest make the intended release set inspectable; keeping package dependency versions exact is materially stronger than an unbounded range, but it does not freeze transitive resolution without a consumer lockfile. The updater’s per-profile preferences, opt-in stable-patch policy and compensating restoration are concrete mechanisms, with recovery risk still present between package-manager operations. Reuse requires replacing member IDs, profile state owner, Host package-manager contract and recovery procedure; do not generalize the 18-plugin count, config defaults, or rc.3 compatibility declaration into a guarantee for all runtime/profile combinations. The release is source-pinned by npm provenance to commit `b904373…`; no `v0.9.1` tag was available. No broad claims about component internals, real UI behavior, or runtime compatibility are made.
