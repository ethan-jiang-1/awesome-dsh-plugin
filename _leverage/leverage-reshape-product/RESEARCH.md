# RESEARCH · 样本消化与洞察提炼规程

> 本文是 `_leverage/leverage-reshape-product/` 样本研究和洞察写作的操作规程；目录、命名、准入阈值仍以 [`00-map.md`](./00-map.md) 为准。首次校准采用三类代表样本：plugin `12_厚工作台`、profile `11_全家桶`、shell `14_终端即产品`。校准后正式推进顺序优先完成 `profile/`。

## 何时使用

每次将候选提升为正式卡、更新既有卡的机制主张，或从样本提炼一条公共 BORROW 规则时，按本规程研究。它不是写作润色清单：目标是让读者知道一条设计结论来自谁的哪版实现、适用于什么约束、改变条件后会怎样。

## 研究步骤

1. **固定样本坐标**：记录 repo、目标包与版本、不可变 tag/commit、分支观察日、DSH 版本，以及实际交付形态。若卡片分析旧版，优先读该版本；只读到 HEAD 时说明不能回推哪些旧版结论。
2. **先建立文档假设，再找一手实现**：读 README 的 Quick Start / Requirements / Limitations；列出与产品边界、数据、生命周期、失败恢复有关的主张。随后查目标仓库源码、schema/manifest、测试/CI，再查 DSH 实际提供的接缝。仓库里的测试定义不是测试结果，CI workflow 也不是该 commit 已通过的证明。
3. **追一条端到端机制链**：按“入口 → 校验/准入 → 核心变换/调度 → 权威状态写入或外部副作用 → 用户可见结果”画图或列表；分别指出样本代码和 DSH 各负责哪一段。
4. **建数据与状态账本**：按样本适用性记录核心实体/关键字段、schema 与 ID、权威 owner/scope、内存/持久化/缓存边界、状态迁移、版本迁移、并发/幂等与完整性约束。状态是全局、session、profile、设备还是单次 activation，必须写明。找不到依据就记 `[OPEN]`，不从功能文案猜字段或状态机。
5. **查失败与恢复**：针对真实写入面检查坏数据、缺依赖、拒绝/授权、超时/取消、部分完成、重启、升级不兼容、回滚/撤销等路径。标明是文档承诺、目标实现、测试设计，还是本次隔离实测；只写样本实际覆盖到的分支。
6. **解释取舍并提炼洞察**：对有价值的机制回答：当时的约束/失败模式是什么；为何选择此机制；收益和风险转移给谁；什么条件改变后它不再成立。按下方七列写洞察。
7. **完成证据与索引**：原始/实现依据放在 lever 现有 `_证据/`，卡片保留结论与可读引用；同步卡片、`catalog.md`、对应 lever README 卡表。公共规则只有达到 BORROW 门槛才进入 [`BORROW.md`](./BORROW.md)。
8. **反向审查再校验**：从洞察中挑一个反例/失效条件，确认没有把作者自述写成事实、把上游机制写成目标插件机制，或把一个版本的实现推广到全部版本；最后运行 `node _leverage/verify.mjs`。

## 来源标记

原有断言标签回答“这是什么性质的结论”；下列标记回答“证据从哪里来”。两者可以并列，例如 `[OBS][SRC-TARGET]`：源码是事实来源，推论仍是观察者判断。

| 标记 | 来源 | 支撑边界 |
|---|---|---|
| `[DOC]` | 目标项目 README、官方文档、manifest | 证明作者如何描述产品；不单独证明实现或成功运行 |
| `[SRC-TARGET]` | 目标项目固定版本的源码 | 证明该提交内的实现路径，不证明构建/运行结果 |
| `[SRC-DSH]` | 明确版本的 DSH 上游源码或发行包 | 证明该版本提供的契约/实现；不替代目标项目源码 |
| `[TEST]` | 测试源码、CI workflow、兼容矩阵 | 测试源码证明覆盖意图；要称“通过”还需对应 run/命令结果 |
| `[RUN]` | 本轮在一次性隔离环境的实测 | 仅证明记录的 OS、版本、配置、步骤下观察到的行为 |

每条关键结论紧邻给来源和精确路径/行号。目标源码引用 commit permalink；DSH 引用包版本、文件和符号/行号。作者报告的性能数字、发布日期或用户规模与实现证据分开写。★、下载量只作采用信号，不证明机制质量。

## 卡片写法

保留既有开头“它想干什么 · 为什么值得借鉴”和卡片的一页速览。机制正文至少要把核心路径、状态 owner、失败/恢复及约束写清。最终“可迁移洞察”固定使用以下字段；一个字段可简短作答，但不可省略其含义：

| 触发问题 | 可迁移洞察 | 机制依据 | 为什么有效 / 代价 | 移植时改什么 | 成立边界 | 抄错后果 |
|---|---|---|---|---|---|---|
| 何种用户目标或工程约束触发问题？ | 用条件句：“当 X 时，优先 Y，因为 Z”；硬协议约束须注明依据 | 样本怎样实现；引用 `[DOC]` / `[SRC-TARGET]` / `[SRC-DSH]` / `[TEST]` / `[RUN]` 及固定版本 | 如何满足约束，谁获得收益、谁承担维护/安全/复杂度成本 | 替换哪些 API、owner/scope、默认值、预算、权限或恢复行为 | 版本、输入、规模、部署和未验证假设 | 一个具体故障或风险，不写空泛的“会出问题” |

作者的动机标为 `[DOC]`；“我认为它解决了什么/为何可迁移”标为 `[OBS]` 并给反例或失效条件。README 可支持概念参考，不能单独把机制升为已核。安全、权限、密钥、迁移覆盖和回滚等高风险断言，未实测就明确保留为未验证。

## 质量门

每条拟沉淀的洞察都逐项确认：

- **可追溯**：关键机制对应固定版本的一手来源；来源链接可打开，断言与引用范围一致。
- **有机制**：说清数据从哪里来、经过什么判定/变换、写到哪里，以及状态由谁拥有；不止列 UI 或功能。
- **有解释**：约束、选择、收益、代价形成完整因果链，观察性推论没有冒充作者意图或代码事实。
- **可迁移**：读者知道何时可用及需改哪些部分；照搬样本专属 ID、阈值或实现不会被包装成通则。
- **有边界**：至少一个真实失效条件/反例；未知的部分具体列出下一步验证。
- **诚实分级**：代码读过但测试没跑，写“机制已追踪，测试未运行”；workflow 存在不能写“CI 通过”；未测真实安装/宿主就不写“兼容已验证”。

关键项缺失时保留 `[OPEN]`，该结论最多作为概念线索，不能进入“机制参考”或公共 BORROW；影响力门槛不能替代研究深度。

## BORROW 准入

将卡片洞察提升到 [`BORROW.md`](./BORROW.md) 前，要求：

1. 至少有一个目标实现中的可复核机制依据；DOC-only 观察不能包装成已验证工程规则。
2. 能压缩为“条件 + 动作 + 理由”，而不依赖读者先读完整卡。
3. 明确移植前提、必须替换的上下文和至少一个抄错后果。
4. 对上游接缝、版本、数据 owner 和权限的依赖在规则中保留；不可移植的细节留在样本卡。

## 安全与停止条件

第三方源码优先只读。安装、build、执行目标代码或真实数据迁移不是默认步骤；只有在结论确实需要运行验证且能够使用一次性隔离环境时才提出执行计划。不得触碰用户现有 DSH profile、密钥和会话数据。无法安全或公开复现的行为保持 `[OPEN]`，不以推测补齐。
