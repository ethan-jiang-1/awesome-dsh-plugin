### 2. 三层否定：谁在拦、拦得住多久

- `[SRC-TARGET]` 第三层不是权限标记，而是三件具体动作：
  1. **对话层**——`Return to chat`：写 `planReviewState = 'awaiting_feedback'`，`captain.cancel({ kind: 'user' }, { keepInbox: true })` 终止当前规划轮，再 `captain.followup(...)` 注入“问用户要改什么”的文本（[`src/tools.ts:869-L899`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L869-L899)）。
  2. **草稿层**——`Discard`：`archiveTeamDir` 把整个 `<stateRoot>/<teamId>/` **rename** 到 `<stateRoot>/archive/<teamId>/`（旧的同名归档先被搬到隐藏的 `.previous-<uuid>` 再删，失败会回滚），随后活动队的目录已不存在（[`src/tools.ts:901-L917`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L901-L917)、[`src/state.ts:1158-L1196`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L1158-L1196)）。
  3. **上下文层**——在 cancel 之前 `captain.inject(...)` 一条 **user 角色的消息**：“That decision is final for this draft … Do not call agent_teams_create, agent_teams_approve, or recreate a replacement team merely because the old team is no longer active. Wait for a later explicit user request.”（文本 [`:640-L647`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L640-L647)，注入与 cancel [`:918-L925`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L918-L925)）；再加固定系统提示第 4 条 “Discard does not authorize a replacement.”（[`src/index.ts:184`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/index.ts#L184-L184)）。
- `[SRC-DSH]` 第 3 层能活下来靠的是顺序与 `keepInbox`：DSH 的 `inject(m) = send(m, 'next-step', false)`（不唤醒），`cancel()` **在不带 keepInbox 时会清空整个 inbox**，带 `keepInbox: true` 才保留（`dsh-agent-loop/lib/index.js:801-L820`；契约 `dsh-agent/lib/types/runtime-types.d.ts:32-L39`、`:192-L209`）。若 `inject` 抛错，代码只 warn，仍会 cancel——此时第三层只剩系统提示（[`src/tools.ts:918-L925`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L918-L925)）。
- `[SRC-TARGET]` **没有持久化的 deny 标记**：`agent_teams_create` 仅拒绝“当前已有活动队/队 id 被占”（[`src/tools.ts:1039-L1052`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L1039-L1052)），从不扫描 archive 判断“这个草稿被否过”。所以“explicitly prevents automatic recreation”的准确含义是：(a) 草稿已不在活动区，(b) 当前对话里有一条明确禁止的 user 消息，(c) 系统提示里有一条规则。**它挡住的是“同一轮/下一轮擅自重建”，不是“永远不能建队”**——用户后来说“再来一次”时建队是合法的。
- `[OBS]` 因此第 2 层（rename 到 archive）是三者里唯一**durable**的一层；第 3 层会随上下文压缩/新会话失效。这与样本卡“否掉的东西不会自己长回来”的强度判断一致，但机制归属要写成“归档 + 注入指令”，不能写成“权限位”。

### 3. 任务 DAG 语义：依赖、重试、取消

- `[SRC-TARGET]` 依赖的唯一判据是“上游 `status === 'completed'`”：`unsatisfiedDependencies` 只认 completed（[`src/state.ts:139-L146`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L139-L146)）；`claim` 与 `captain takeover` 都先查它（[`src/tools.ts:1836-L1840`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L1836-L1840)、[`:1679-L1683`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L1679-L1683)）。**失败的上游永不满足依赖**——下游不是“跳过”，而是永远 `blocked`，除非显式改图（`edit_plan`）或另建任务。
- `[SRC-TARGET]` 状态机是显式白名单：`pending → claimed | cancelled`；`claimed → in_progress | failed | cancelled`；`in_progress → completed | failed | cancelled`；三个终态无出边（[`src/state.ts:148-L180`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L148-L180)）。`claimed` 不能跳 `completed`（提示词也明说）。
- `[SRC-TARGET]` 互斥粒度是“成员 × 一个开放任务”：`memberOpenTask` 非终态即算占用，claim/转派都会拒绝第二个（[`src/tools.ts:425-L433`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L425-L433)、[`:1844-L1850`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L1844-L1850)）；队长接管同样一次只允许一个（`captainOpenTask`）。
- `[SRC-TARGET]` **重试**有两类，语义不同：
  - 显式 `agent_teams_reassign_task`：`invalidateTaskAttempt` 立刻清 `attemptId`、发新 `handoffId`、把任务打回 `pending` 并置 `reassigning`，旧属主 `stopping = true`；然后在锁外 `drainMemberChildren` 等旧激活退出，再二次加锁校验 `handoffId` 未被并发改掉，才 `beginTaskAttempt`（attempt+1）。旧属主迟到的 `update_task` 因 `attemptId` 不匹配被拒（[`src/tools.ts:1670-L1745`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L1670-L1745)、[`src/state.ts:182-L232`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L182-L232)）。
  - 冷恢复：进程内 `parkedAttempts` 为空时（新进程）看到“成员名下仍有开放 attempt”，自动给**一次**新 attempt；若这次派发也失败，会把上一代状态整体回滚并重新 park，避免无限重试（[`src/scheduler.ts:359-L398`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L359-L398)、[`:455-L484`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L455-L484)）。**同进程内**“成员自己变 idle 但还握着开放 attempt”按设计**不自动重试**，只 park（模块头注释 [`:1-L13`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L1-L13)）。
- `[SRC-TARGET]` **取消**：`cancelUnfinishedTask` 把所有非终态置 `cancelled` 并清 `attemptId/handoffId`（[`src/state.ts:205-L213`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L205-L213)）；它由两个入口触发——面板/HTTP `halt`（`haltTeamWork`：逐任务 cancel、逐成员 `stopping`、落盘后才 `captain.cancel`，并在 drain 结束再 cancel 一次以关掉子代理结算唤醒的尾巴，[`src/tools.ts:557-L627`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L557-L627)）与队长对**从未启动的 pending** 任务的直接 cancel（成员/队长身份与状态都有前置校验，[`src/tools.ts:1962-L1972`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L1962-L1972)）。`agent_teams_resume` 只把 `halted` 清掉、**不复活 cancelled 任务**（[`src/tools.ts:2456-L2505`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L2456-L2505)）。
- `[SRC-TARGET]` 终态不可改：`completed` 任务不能转派（[`src/tools.ts:1667`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L1667-L1667)），`update_task` 对终态任务只接受“追加证据”（`supplementalEvidence`），不改 verdict/status（[`src/tools.ts:1989-L2005`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L1989-L2005)）。
- `[SRC-TARGET]` 自动追加重试的边界：只有**质量类**任务 `failed` 会触发 `applyQualityFollowUp`（repair + 下一轮 review），普通任务失败只等人处理（[`src/tools.ts:2031-L2044`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L2031-L2044)）。

### 4. 活动面板的数据从哪来

- `[SRC-TARGET]` 面板数据是一个 **host 侧快照接口**：`GET /plugins/dsh-agent-teams/state`，`?archived=1` 取归档。它枚举 `workspaceRegistry.list()` 里的**所有 workspace**，对每个算 `<path>/<stateDir>`，再 `collectTeamsActivity` / `collectArchivedTeamsActivity` 汇总（[`src/index.ts:259-L283`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/index.ts#L259-L283)）。**请求里没有 sessionId**——接口返回全局视图，由客户端按 captain/session 过滤。
- `[SRC-TARGET]` 快照 = 磁盘 `team.json` + 活跃度 + 字节审计三合一：成员 `activity` 来自 `memberActivity(ctx, ids)`，实现就是 `ctx.agents.get(id)` 的实时 `status`，不在注册表里的记 `ready`（[`src/snapshot.ts:146`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/snapshot.ts#L146-L146)、[`src/members.ts:1102-L1113`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/members.ts#L1102-L1113)）；任务行还带 `verdictStale`，因为它复用了与 `agent_teams_status` 同一个 `auditTeamWorkspace`（[`src/workspace-audit.ts:1-L54`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/workspace-audit.ts#L1-L54)、[`src/snapshot.ts:218-L230`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/snapshot.ts#L218-L230)）。
- `[SRC-TARGET]` 客户端是轮询，不是推送：`ACTIVITY_POLL_MS = 1000`（热）、`ACTIVITY_PROBE_MS = 5000`（探测/发现），单循环 `fetch(ACTIVITY_STATE_URL)`，归档目标另打 `?archived=1`（[`src/client/activity-monitor.ts:184-L193`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/client/activity-monitor.ts#L184-L193)、[`:253-L277`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/client/activity-monitor.ts#L253-L277)、[`:313-L320`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/client/activity-monitor.ts#L313-L320)）。
- `[SRC-TARGET]` 因此“分段进度条/花名册/DAG 变色”全部是**磁盘状态 + 宿主内存状态**的投影，没有独立事件流：面板不会比 `team.json` 更早知道完成；模型忘了 `update_task` 时面板就停在 `in_progress`（README `:216` 明说 “The activity panel reports persisted state as-is”）。存档面板走 `historic: true`，把 `removed` 成员也渲染出来（[`src/snapshot.ts:290-L300`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/snapshot.ts#L290-L300)）。
- `[OBS]` 代价：1 s 轮询 × 每个 workspace × **每次都对 verdict 相关范围重新读盘做 sha256**（上限 200 文件/范围，见 §5），多个大 workspace 同时开着面板时，这是持续磁盘 I/O；本轮未测。

### 5. 多代理并发与文件冲突

- `[SRC-TARGET]` **没有工作区文件锁、没有 patch/merge、没有按文件预占**。代码里唯一的互斥是任务级（§3）与 team.json 的进程内锁（§6）。`inScope` / `outOfScope` / `changedPaths` 是写进任务与提示词、并在完成时校验的**声明**，不是写入拦截：[`assignmentPrompt` 明确 “Work only this task and only its in-scope paths”](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L266-L266)，而真正的检查发生在 `update_task` 的 `evaluateQualityCompletion`（[`src/quality-gates.ts:546`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/quality-gates.ts#L546-L546)）。README 也把这条边界写清：`toolPolicies` 与 scope 控制都**不是** host 写入拦截（[`:52`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/README.md#L52-L52)、[`:205`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/README.md#L205-L205)）。
- `[SRC-TARGET]` 冲突处理是**事后审计**：`review`/`requirements`/`verification` 收口时读它判定范围内的字节，记 `reviewedArtifacts`（sha256/size/mtime）、`reviewedScope`、`reviewedGaps`、`reviewedDuringDrift`；`verdictStartSnapshot` 在**派发时**就拍一张，收口时比对，若工作区在判定期间被改过就标 `reviewedDuringDrift`（[`src/types.ts:82-L126`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/types.ts#L82-L126)、[`:210-L232`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/types.ts#L210-L232)、[`src/scheduler.ts:386-L392`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L386-L392)、[`src/tools.ts:190-L219`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L190-L219)）。交付前 `canDeclareDelivery` 会把“记录的 pass 与当前字节不一致”判成 blocker/warning（[`src/snapshot.ts:188`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/snapshot.ts#L188-L188)）。
- `[SRC-TARGET]` 审计本身有界且会“自曝不完整”：单范围展开上限 `MAX_EXPANDED_ARTIFACTS = 200`，跳 `.git`/`.dsh`/`.agent-teams`/`node_modules`，不跟随符号链接，越界路径用 `realpath` 拒绝；“读不到”与“不存在”分开记，任何截断/不可读都产出 `ArtifactScopeGap` 而不是短列表（[`src/artifacts.ts:1-L70`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/artifacts.ts#L1-L70)）。

### 6. “磁盘真相”的边界：单进程串行、原子写与 Windows 折返

- `[SRC-TARGET]` 锁是**进程内 Promise 链**：`locks: Map<string, Promise>`，键 `team:<stateRoot>:<teamId>`，`withTeamLock` 只用前一环的 promise 做闸门（[`src/state.ts:58-L85`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L58-L85)、键构造 [`:180-L182`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L180-L182)）。全仓 `grep -Ei "pid|lockfile|\\.lock|flock"` 只命中临时文件名与注释，**没有 pid 文件、没有租约、没有跨进程锁**。
- `[SRC-TARGET]` 写文件是“临时文件 + rename”：`${file}.${process.pid}.${uuid}.tmp`，`writeFile(..., { flag: 'wx' })` 再同目录 `rename`，失败清理临时文件（[`src/state.ts:703-L715`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L703-L715)）。**Windows 上 rename 覆盖会 EPERM**，代码重试几次后降级为**直接覆盖写目标文件**——注释自己承认这条是“content-equivalent degraded path”（[`:648-L701`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L648-L701)）。也就是说原子性在 Windows 上是**尽力而为**。
- `[SRC-TARGET]` 邮箱追加是**整文件重写**：`appendMailbox` 先读全量文本再 `atomicWriteText(file, existing + separator + JSON.stringify(message))`（[`src/state.ts:430-L450`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L430-L450)）。两个进程同时写同一邮箱 = 后写者吞掉前者的消息；一个进程内因为都走 team 锁，没这个问题。
- `[SRC-TARGET]` 归档同样是 rename，且已有同名归档时先搬走再搬入，失败回滚（[`src/state.ts:1158-L1196`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/state.ts#L1158-L1196)）。跨进程时两个 DSH 都认为自己是 owner，会各自 kickTeam、各自认领任务、各自写 `team.json`。
- `[SRC-TARGET]` 队列之外还有一条独立的成员级串行链（`serializeMember`），以及“一队一队长”的 `captain:<stateRoot>:<captainId>` 锁（[`src/scheduler.ts:273-L299`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L273-L299)、[`src/tools.ts:221-L226`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L221-L226)）。它们**都只在一个进程内有效**，这是 README `:215` 那句自陈的实现依据。
- `[OBS]` 结论要写成：“读到的是磁盘真相；写只在**一个** DSH 进程内串行，且 Windows 上原子性会折返”。这比“不跨进程协调”更强——跨进程不是“不协调”，是**会互相覆盖**。

### 7. 队长死了会发生什么

- `[SRC-TARGET]` 调度器的每一步都先解析**活着的** captain：`liveCaptain` 用 `ctx.agents.get(captainSessionId)`，取不到就 `return`——`kickTeam` 与 `kickMember` 都不会派发（[`src/scheduler.ts:182-L185`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L182-L185)、[`:300-L322`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L300-L322)）。**队长不在 ≠ 成员被接管**：没有队长选举，成员工具里根本没有 create/approve/reassign（`MEMBER_TOOL_NAMES` 只有 4 个，[`src/tool-names.ts:10-L13`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tool-names.ts#L10-L13)），成员提示词也明确 “Do not create, approve, edit or resume a team”（[`src/capabilities.ts:13`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/capabilities.ts#L13-L13)）。
- `[SRC-TARGET]` 队长**会话冷但未死**时，从它的 fork 发起的成员操作会尝试把原队长会话“附着”回来：`memberOperationParent` → `resumeLeadAnchor` → `workspaceRegistry.create(cwd)` + `sessionController.create({ sessionId, workspaceId, agentPreset: 'standard' })`，**不带 prompt、不唤醒模型**，也不改写 `captainSessionId`；组合里没有 controller/registry 或附着失败时抛一条有界错误（[`src/tools.ts:441-L476`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L441-L476)、[`:481-L540`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L481-L540)）。批准路径用同一手段拿到 kick 锚点（`liveLeadAnchorAgent`，[`:857`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L857-L857)）。
- `[SRC-DSH]` 这条能成立的前提是宿主的 `sessionController.create` 接受**已存在的 sessionId** 并返回复用/附着的会话（`dsh-api-session-controller/lib/index.js:755-L778`：把 `request.sessionId` 透传给 `agents.createSession`，并要求该 session 属于目标 workspace）。附着要求 workspace 路径对得上；换了 cwd 的 fork 可能附着失败——代码只 warn。
- `[SRC-TARGET]` **真正的“死”有两层**：
  - 进程冷启动（队长会话稍后被用户重新打开）：`parkedAttempts` 是新 Map，成员名下的开放 attempt 会在第一次 kick 时被恢复成新 attempt（§3）。但**这次 kick 仍来自队长**（`status`/`resume`/`edit_plan`/`send_message` 都会调 `kickTeam`），调度器自己**没有定时器/守护扫描**——没有任何东西会在队长缺席时自愈。
  - 队长会话被删/换 workspace：团队目录还在，`findTeamByCaptain` 永远找不到 owner；面板仍能按磁盘渲染，HTTP `halt` 也要求“已附加的 sessionId”（[`src/index.ts:287-L339`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/index.ts#L287-L339)）。此时唯一收尾手段是手工删目录或重建同名队长会话。
- `[SRC-TARGET]` 队长**自己持有的任务**是特例：队长的 idle 边界会把队长名下未完成任务 `invalidateTaskAttempt` 打回共享池并 `kickTeam`，因为“队长没有 scheduler lane 能替它稍后恢复”（[`src/scheduler.ts:497-L521`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/scheduler.ts#L497-L521)）。若进程在队长 turn 中途被杀，这些任务会停在 `claimed` 且带 `attemptId`，直到下一次队长 idle 边界——**恢复依赖队长再次活着**。
- `[SRC-TARGET]` halt 的 drain 也有同样的依赖：队长会话不在时 `stopTeamMemberActivations` 被跳过并 warn，`halted` 已落盘但子代理可能还在跑（[`src/tools.ts:603-L613`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L603-L613)）。
- `[OBS]` 所以“队长死了”不是单一行为：**队长缺席 = 停派发**（安全但停滞）；**队长可附着 = 恢复**；**队长被删 = 孤儿目录**。样本卡只写了“成员失联 → 重试搁浅尝试”，漏了“谁活着才能触发重试”。

- “三层否定的具体实现（会话状态标记？提示词约定？）”：**归档是唯一的持久事实**（整个目录 rename 出活动区），对话层是 `captain.cancel({kind:'user'},{keepInbox:true})`，上下文层是 `captain.inject()` 一条 user 消息 + 固定系统提示；没有“已否决”状态位，也没有在 `create` 里查 archive。
- “磁盘锁不跨进程，要不要加启动期检测”：代码里没有任何 pid/lockfile/端口占用探测；两个进程会各自 kick、各自写 `team.json`、各自整文件重写 inbox。若要补，位置应在 mount 时对 `<workspace>/<stateDir>` 取独占锁（例如 pid+租约文件），而不是在调度器里——这是建议，不是现状。
- “`memberMaxDepth` 默认 0 是安全默认还是能力阉割”：默认 0 只禁成员再生子代理；宿主 `maxActiveSubagents` 默认 8 是**每个父会话**的容量，插件 `maxMembers` 8 与它对齐但不共享配额。是否要层级仍取决于任务，代码没有为深度 > 0 做额外校验。
- “能不能在 DAG 上直接拖拽改依赖”：staged 阶段的 Web 面板支持 `update_task`（改 dependencies）与 `remove_task`/`remove_member`（[`src/tools.ts:120-L150`](https://github.com/NanmiCoder/dsh-agent-teams/blob/3331b903f0e954d59ac69be1a75fd4fd7e1de20e/src/tools.ts#L120-L150)），所以**staged 时已经可以**；运行期改图走 `edit_plan`（只对未开始的 pending 任务）与 `amend_task`（质量契约的受控修订），已开始的任务不能直接改依赖。
