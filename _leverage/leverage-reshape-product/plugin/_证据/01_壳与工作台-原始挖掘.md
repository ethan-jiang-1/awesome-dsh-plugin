## 一、DSH-better-sidebar（omdsh-dev/DSH-better-sidebar）

### 1. 注册/接缝的确切形状

**自建服务面：`ctx.betterSidebar`，两个扩展点 `registerTab` / `registerFileViewer`。** README 只给了 `registerTab` 的调用样例，没有给返回类型声明；但样例的形状本身就是契约：返回反注册函数、用 `ctx.effect` 包住、`inject` 声明依赖名、靠 `import type {}` 触发 TS 声明合并（bs_readme.md §Plugin Ecosystem, L129-137）：

```ts
import type {} from 'dsh-better-sidebar'  // triggers the ctx.betterSidebar type merge
export const inject = ['betterSidebar']
export function apply(ctx: Context) {
  ctx.effect(() => ctx.betterSidebar.registerTab({
    id: 'my-plugin:db', title: 'Database', component: ({ scope }) => <DbView sessionId={scope.sessionId} />,
  }))
}
```

四个可照抄的字段：`id`（带命名空间前缀 `my-plugin:db`，防碰撞）、`title`（字符串，非 thunk）、`component`（React 组件，入参 `{ scope }`，`scope.sessionId` 是会话身份）、以及"内置 6 个 tab + 4 个 viewer 走同一 API"这个自证——内置能力与第三方能力同一条注册路径，也是生态长到 30+ 个插件的结构性原因（原文："the built-in 6 tabs + 4 viewers use the very same API. The GitHub topic … already lists **30+ ecosystem plugins**"，bs_readme.md §Plugin Ecosystem, L127）。

**这条自建服务的上游对应物就是 `ctx.slots`（SlotRegistry）**，形状高度可反推：

- 上游单次真实调用（`dsh-client-ui-sidebar/lib/client.js:611-649`）：
  ```js
  ctx.slots.inject("sidebar", () => ctx.slots.register({
    name: "sidebar", locale: NS,
    children: { "sidebar.brand.mark": { kind: "single", scope: "root" }, ... },
    inject: injectProps
  }, SidebarRoot));
  ```
- 注册方法签名：`readonly register: SlotCore['register']`（`dsh-client-ui-renderer/lib/types/client/registry.d.ts:85`）；声明依赖槽位的钩子是 `inject(key: keyof SlotMap & string, callback: () => SlotInjectionEffect): () => void`（同文件 `:111`）；`registerFactory`（`:95`）；`install(renderer)`（`:118`）。
- `register` 的返回值就是反注册函数，且**必须靠 `ctx.effect` 挂载**：registry 的类型注释明说"disposal through the caller's ctx.effect (fiber unload = cascade)"，并解释了为什么 `register` 必须留成原型方法——Cordis 服务代理在调用时把 `this.ctx` 绑到**调用方**的 context，箭头函数属性会把 effect 冻结到服务自己的 root ctx，"silently break per-plugin disposal"（`dsh-client-ui-renderer/lib/types/client/registry.d.ts:70-84`）。这是你自建 `ctx.xxx` 注册表时最该抄的一条：**注册表方法必须是原型方法，不能是实例箭头属性**，否则每个注册项都挂错 fiber，插件卸载时不回收。
- `ctx.effect` 本身的签名（`@deepseek-ai/cordis/lib/types/fiber.d.ts:157-159`）：`effect(execute: () => SyncEffect, label?: string): Disposable<Promise<void>>`；`Effect` 允许"单个 disposer / Promise / 生成器逐个 yield"，卸载时**逆序**执行（同文件 `:43-52`）。上游到处带第二个参数做诊断标签，如 `"ui-sidebar-files: files tab body"`。
- 槽位声明侧（上游"可挂钩的壳"清单，`dsh-client-ui-layout/lib/types/client/index.d.ts`）：`sidebar`（`:44`，整条左栏，single/root）、`main`（`:53`，keyed，`conversation` 保留键）、`rightbar`（`:70`，single/root）、`shell.bottom`（`:81`，全宽底部，高度会压缩三栏可用高度）、`shell.overlay`（`:95`，list，帧级浮层，"click-through until your entry opts into pointer events"）、`shell.leading`（`:112`，窗口左上角 chrome，仅在左栏完全隐藏时挂载）。根槽 `root` 在 `dsh-client-ui-renderer/lib/types/client/registry.d.ts:32`，注释直接写 **DO NOT register here**：single 槽里再注册不会"并排"，而是**遮蔽**整个 AppFrame，因为动态注册项的优先级低于随包发布的项、反而成为 winner。
- 右栏的扩展是**两段式**，比 better-sidebar 的单函数更细：先 `ctx.sidebarRightTabs.register(definition)`（静态面：`id`/`kind`/`patterns`/`priority`/`canOpen`/`title`/`guide`，返回 disposer，`dsh-client-ui-sidebar-right/lib/types/client/tab-registry.d.ts:164`），再往 keyed 槽 `sidebar.right.pane.tab` 用 `key: <definition.id>` 注册 body（真实例子：`dsh-experimental-session-inspector/lib/client.js:4133-4146`、`dsh-client-ui-sidebar-files/lib/client.js:996-1017`）。地址认领走编辑器解析器语义：`candidates(address)`（`:195`）按 `priority` band（`'extension' | 'builtin' | 'fallback'`，`:44`）→ 命中 pattern 长度 → 注册顺序排序，`claim(address, kind?)`（`:209`）出最终决定；`extension` band 可以**接管**同 kind 的 `builtin`，扩展卸载后 builtin 自动复辟（`tab-registry.d.ts` 模块注释）。导航只用 `ctx.sidebarRight.openResource(address, options?)` / `openTab(kind, options?)`（`dsh-client-ui-sidebar-right/lib/types/client/service.d.ts:161,168`）。
- 布局服务 `ctx.layout`（`dsh-client-ui-layout/lib/types/client/service.d.ts`）：`selectPanel(panelId|null)`（`:32`，未注册的 key 会 **throw** 且保留原选择）、`beginNavigation(): AbortSignal`（`:37`，新导航会 abort 上一次，调用方在提交 UI 状态前检查）、`toggleSidebar()`（`:39`）、`openRightbar(track, fullscreen)` / `closeRightbar()`（`:47,49`）、`dispose()`（`:68`）。
- 服务提供方式：`ctx.reflect.provide(name, value) => () => void`（`@deepseek-ai/cordis/lib/types/reflect.d.ts:41`），上游实例 `ctx.reflect.provide("sidebarRightTabs", tabs)` + `ctx.reflect.provide("sidebarRight", controller)`，两条 disposer 一起塞进同一个 `ctx.effect`（`dsh-client-ui-sidebar-right/lib/client.js:4965-4971`）。
- 浏览器半边怎么被加载（决定你"改壳"插件的包结构）：`package.json` 里声明 `dsh.client = { platform: 'web', inject: [...], external: [...] }`、导出 `./client`（`dsh-client-modules/README.md:34`；真实清单 `dsh-client-ui-sidebar-files/package.json`）。宿主扫描已启用 Loader 条目，把每个声明变成 `/plugins` 下的 bundle，**按"动态提供者先于消费者"排序**（同处）。bundle 执行只注册 factory，模块体副作用（含 CSS 注入）推迟到首次 materialize（`dsh-client-modules/README.md:72`）。

### 2. 状态与持久化

> **来源边界**：本节先摘录目标项目 README 对其状态的描述；第 60–70 行随后摘录的是 DSH 上游 `dsh-client-ui-sidebar-right` 的 surface layout 实现，不是 better-sidebar v0.28.2 bottom workbench 的实现。目标插件状态模型已按固定 tag 复核，见 [`06_厚工作台-better-sidebar-源码复核.md`](./06_厚工作台-better-sidebar-源码复核.md)。

- **每会话 localStorage**，不是全局：client 半边"state persisted per session in localStorage"（bs_readme.md §Architecture/Development & Build, L236："a single npm package with host/client halves — host (`src/index.ts`): `/sidebar/api/*` JSON API, media / HTML preview / upload routes and two WebSockets; client (`src/client/index.tsx`): native right-sidebar tabs + bottom workbench; state persisted per session in localStorage"）。
- 宿主 profile 侧另有一层：自 DSH 0.1.7 起偏好项存在该插件在 profile 里的 **mount row** 上，默认 entry id `better-sidebar`；插件首次启动时**一次性**迁移旧的 `settings.yaml` 值，且"never overwrites newer values"（bs_readme.md §FAQ, L93："Since DSH 0.1.7, preferences live on this plugin's mount row in the profile (default entry id `better-sidebar`). The plugin migrates your old `settings.yaml` values once on first start and never overwrites newer values."）。即"迁移一次 + 版本比较后再写"的双写共存策略。
- 布局粒度：底部工作台支持"drag-to-split panes / multiple terminal tabs / **per-session** persisted layout"（bs_readme.md §Features, L27）。README 未给字段名。
- 上游同位置的真字段（可直接借用的结构，`dsh-client-ui-sidebar-right/lib/types/client/persistence.d.ts:3,9,15,20`）：
  - key 前缀 `dsh.sidebar-right.v1`（**带版本号后缀**），实际 key 是 `${sidebarPersistence}.${sessionId}`（`dsh-client-ui-sidebar-right/lib/client.js:850,882,894`）。
  - 结构 `SurfaceState = { layout: LayoutState, history, minted }`（`stores.d.ts:33-38`），外层再包一层信封 `{ bySession: Record<sessionId, unknown> }`（`client.js:820`），落盘只写 `{ layout, minted }`、**不写** `history`（`client.js:876-882`）。
  - `layout` 的 zod 结构：`nodes`（pane/split 判别联合，pane 带 `host: 'dock'|'float'`、`tabs`、`activeTabId`、`rect`）、`tabs`（`id/kind/contentId/title`）、`rootId`、`floats`、`activePaneId`、`expanded`、`mode: 'push'|'fullscreen'`（`client.js:781-800`）。
- **损坏/配额满的回落**（这段是整个上游最值得照抄的一段，`dsh-client-ui-sidebar-right/lib/client.js:846-896`）：
  - `typeof localStorage === "undefined"` → 直接 `return`（无痕降级，SSR/受限环境）。
  - `getItem` 抛（存储不可用）→ `catch (_storageUnavailable) { return }`。
  - JSON 或 schema 校验失败 → `catch (_invalidLayout) { clearSidebarLayout(sessionId); return }`，**主动删掉坏 key**，下次从默认布局起。
  - `setItem` 抛（配额满）→ `catch (error) { console.error("Sidebar layout persistence failed:", error) }`，只在控制台报，不抛给 UI。
  - 除 schema 外还有一层**引用完整性校验** `validateReferences()`（`client.js:821-844`）：id 必须与 key 一致、序号不得大于 `minted`、split 必须恰好 2 个子节点、`sizes` 之和与 1 的差 ≤ 1e-9、pane 的 `host` 必须与遍历来源一致（dock 的 root、float 必须带 `rect` 且只有一个 tab）、所有 node/tab 必须被访问到。**schema 过了不代表引用自洽**，这一层是"恢复半个布局"和"恢复崩溃"的分界。

### 3. 性能预算

- **首屏 ~325KB core at startup，重 chunk 按需加载**（bs_readme.md §Features 尾行, L29）。这是全文唯一给出的首屏体积数字，作者把它当卖点写在 feature 行里。
- 会话日志冷读修复的实测对比（bs_readme.md §v0.28.2 "Measured (40.2 MB session, local)", L106，这是全材料里最硬的一组数字）：
  - 场景：**40.2 MB 会话**，本地；并发 **12 条路由 + 36 次 bypass-entry 调用**。
  - 修复后：**1 次 header read、0 次 full read、3 ms、+0.3 MB RSS**。
  - 修复前：**6 次 bypass 调用 = 6 次 full read，峰值 +1.0 GB RSS**（按 36 次外推 **≈6 GB**）。
  - 手法：只读 header 里存的 workspace 地址（"first zstd frame only, header-only"），**per session memoized，且 in-flight 请求共享**（single-flight）；`activeWorktreeRootOf` 不再为 detached session 折叠整份日志。
  - 归因（v0.28.1 为什么没修好）：single-flight 只覆盖了 `/sidebar/api`，而真实启动扇出是"**每个被 watch 的目录一帧 fs-watch + 每个 `/sidebar/file|html` 资源一次 cwd 解析**"，所以 39 MB 的会话仍被并行全量解码几十次（bs_readme.md §v0.28.2 "Why 0.28.1 missed it", L104）。
- v0.28.1 的 OOM 修复口径：十二个 `/sidebar/*` 路由的冷 cwd 读取**按 session + client hint 合并**（bs_readme.md §v0.28.1, L110）。
- 读取上限（明确的预算常数，bs_readme.md §Git Graph, L33）：每页 **200 commits**、offset 上限 **10,000**、**1,000 branches**；tag 装饰保留按 ref name 前 **5,000** 个 tag，再被 **8 MiB** 的"完整行输出前缀"二次截断，超出部分**省略但不让图失败**。
- 另一处数值化防护：病态 `git status` 输出加 **latch + 进程树 kill**，把"宿主死于 `RangeError`"变成"一次失败的 SCM refresh"（bs_readme.md §v0.28.1, L112）。
- 交互预算：attach 前 sidebar 以原项目为根，**下一次 5 s 轮询**再切回（bs_readme.md §v0.28.2, L105）。dsh-context 跳转"idle 时完全不轮询"（bs_readme.md §dsh-context diagnostics, L37）。

### 4. 兼容与版本策略

- peer 声明口径：**13 个 DSH peer floor 全部抬到 `^0.2.1-rc.1`**（bs_readme.md §v0.28.0, L120）。"13 个"这个数字本身说明其依赖面：一个壳插件同时 peer 了宿主侧与 client 侧十几个 `@deepseek-ai/*`。
- README 顶部徽章写 **Supported DSH versions: 0.2.1-rc.1+**（bs_readme.md, L10），安装节又要求 **0.2.1-rc.1+** 并"装完必须硬刷新"（L45）。
- **版本对照表**（bs_readme.md §Pick the plugin version for your DSH version, L52-61）完整可抄：DSH `0.2.1-rc.1+` → 插件 `0.28.2`；`0.2.1-alpha.5` → `0.28.0-alpha.0`；`0.2.0-rc.2` → `0.26.1`；`0.2.0-rc.1` → `0.24.1`；`0.1.7-rc.1 ~ 0.1.7 stable` → `0.22.1`；`0.1.7-alpha.x` → **无兼容版本，先升宿主**；`0.1.6 及更早` → `0.19.1`。配套规则："older releases 一律 pin exact version，因为 `latest` 会往前走"（L62）。
- 不匹配时的**实际行为**：marketplace 安装器**不看宿主版本**、直接装插件 `latest`，于是老宿主得到一条 **version-rejection error**（bs_readme.md §Compatibility warning, L47）。即"拒绝安装"，不是运行时警告。
- 上游这套拒绝的判定规则（值得直接照抄进你的 plugin README）：宿主在 import 插件前，用 `getDshRuntimeVersion()` 的单一版本比对声明——有 `engines.dsh` 就**只**看它、忽略 `peerDependencies`；否则 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*` 的每条 peer range 都必须匹配；prerelease 参与匹配；两者都没有则无约束；空或非法 range（含把 `workspace:` 写进 `engines.dsh`）算不兼容；`engines` 非对象、`engines.dsh` 非字符串算 malformed manifest（`dsh-app-boot/README.md:52`）。拒绝记录带 `incompatible-version` code 与 `name/version/runtimeVersion/requirements`（按 `engines.dsh` 或 peer 包名分组），并可通过 `dsh plugin ... allow-version <pkg@ver> --dsh-version <runtime> --accept-risk` 开豁免（`dsh-plugin-manager/README.md:75`）。
- 安装前 vs 安装后的检查时机：命名了包的 `add` 在 pnpm 跑之前就解析 registry 版本并检查 `engines`/`peerDependencies`，"不满足则**什么都不下载、不跑任何 build script**"；git/tarball 规格拿不到元数据，只能**装完再判**，失败则回滚 profile manifest + lockfile 并重装（`dsh-plugin-manager/README.md:69`）。
- 已知的安装器坑（可直接抄成 FAQ 表）：pnpm 11 拦传递依赖 build script → `pnpm approve-builds`；`minimum release age` 24 小时内新版本 → 等 24h 或让 pnpm 自动加 `minimumReleaseAgeExclude`；"Profile directory not found" → 先跑一次 `dsh web` 初始化 `~/.dsh/profiles/web`（bs_readme.md §FAQ, L89-91）。
- 双挂载自愈：页面出现**两个 sidebar** 时，删掉 `~/.dsh/profiles/web/cordis.patch.yml` 里的老式手动挂载行；"把本包以不同 id 聚合挂载的聚合包会被 auto-yield，无需动作"（bs_readme.md §FAQ, L92）。
- 版本差异的实证口径很硬：`0.2.1-alpha.5 → rc.1` 的全树 diff **355 个文件，全是 `package.json`，零源码改动**（bs_readme.md §v0.28.0, L121）。这句话是"peer floor 抬版本 = 无风险"的证据，也是劝用户升级的话术模板。

### 5. 对宿主布局的侵入点

- 定位方式是**原生 React 树内挂载**而非 DOM 选择器：右栏 tab 走 `ctx.betterSidebar.registerTab`，底部面板是"self-drawn bottom panel that coexists with the native right sidebar"（bs_readme.md §Features, L27）。也就是说它没有对宿主 DOM 做 querySelector 级的侵入——侵入点在槽位层。
- 唯一的 DOM 级侵入在 **iframe**：HTML 预览渲染在 **opaque-origin sandboxed iframe** 里，sandbox 可按 feature 关掉（默认关，带警告）（bs_readme.md §Security, L218）。
- 兼容性后果分级：因为走槽位，宿主改布局时最坏是"tab 注册不上/不显示"，而不是整页崩——但**两处例外**会硬崩：`ctx.layout.selectPanel` 传未注册 key 会 throw（上游 `service.d.ts:26-31` 注释），`root` 槽重复注册会遮蔽整个 AppFrame（上游 `registry.d.ts:20-33`）。
- 硬刷新是硬性要求："Then **hard-refresh the browser** (Cmd/Ctrl+Shift+R)"（L45），升级后同样"re-run the install command, then hard-refresh"（L80）。根因在上游：页面保留自己的 modules bootstrap 与静态 platform 身份，**要移除/替换 bootstrap 必须整页重载**；live replacement 请求在页面本地报错但保留 fiber 与 exports（`dsh-client-modules/README.md:138`）。
- 窄屏降级是布局侵入的另一半：`<768px` 时**没有底部面板**，其 tab 合并进右栏的全宽 drawer（bs_readme.md §Known Limitations, L222）。

### 6. 降级与失败路径清单（原文 + 中文）

### 8. 可直接复用的规则

1. **如果你要给别人留扩展点：只留 `registerX(descriptor) => disposer` 一种形状，并让内置功能走同一条路。** 证据：`registerTab` 返回反注册函数 + `ctx.effect` 包裹 + 内置 6 tab/4 viewer 用同一 API（bs_readme.md L127-137）；上游 `register` 返回 idempotent disposer 且靠调用方 fiber 回收（`registry.d.ts:70-85`）。
2. **如果注册表是 Cordis 服务，`register` 必须写成原型方法。** 证据：`registry.d.ts:70-84` 明写箭头属性会把 `this.ctx` 冻结到服务自己的 root，per-plugin disposal 静默失效。
3. **如果你的持久化要活过版本升级：key 带版本前缀 + 三道回落 + 一层引用完整性校验。** 证据：`dsh.sidebar-right.v1`（`persistence.d.ts:3`）、`typeof localStorage === 'undefined'` / 读抛 / 校验失败即 `clear` / 写抛只 console（`client.js:846-896`）、`validateReferences` 的 7 条不变式（`client.js:821-844`）。
4. **如果你要按会话记状态：用 `${ns}.${sessionId}` 而不是一个全局 JSON blob。** 证据：per-session localStorage（bs_readme L236）+ 上游逐会话 key（`client.js:850`）。
5. **如果你的插件会并发读大对象：memoize per identity + 共享 in-flight Promise，并且盯住"扇出点"而不只是主路由。** 证据：1 次 header read / 3 ms / +0.3 MB vs 6 次 full read / +1.0 GB（bs_readme L106），以及 v0.28.1 只覆盖 `/sidebar/api` 而漏掉 fs-watch 帧与资源路由的复盘（L104）。
6. **如果你要发布给多版本宿主：README 里放一张"宿主版本 → 插件精确版本"的表，并说明"没有兼容版本时该怎么办"。** 证据：bs 的 7 行对照表含一条 "No compatible release — upgrade DSH"（L52-60），以及"old host 得到 version-rejection error"的机制说明（L47 + `dsh-app-boot/README.md:52`）。
7. **如果你的资源有界读：把上限写成常数并公开，超限报显式错误而不是静默截断；但对"装饰性"数据（tag）选择省略不失败。** 证据：200/10,000/1,000 与 5,000 tags/8 MiB（bs_readme L33）。
8. **如果你的插件改了浏览器侧代码：README 第一屏就写"装完/升级后必须硬刷新"，别等用户报 bug。** 证据：L45 + L80，根因是页面保留 module bootstrap（`dsh-client-modules/README.md:138`）。

## 二、dock（AKS1st/dock）

### 1. 注册/接缝的确切形状

**自建服务 `ctx.workbench`，六个注册方法，全部返回反注册函数，全部配 `ctx.effect`**：`registerActivityBarItem` / `registerPanel` / `registerEditorView` / `registerStatusBarItem` / `registerCommand` / `registerSetting`（dock_readme.md §功能, L19）。另加 `registerPlugin({ id, title, description, icon, hasEntry })` 用于让设置窗口能列出插件（§设置 API, L58）。

唯一给了完整调用形状的是 `registerSetting`（dock_readme.md §设置 API, L46-56）：

```ts
ctx.effect(() => ctx.workbench.registerSetting({
  id: 'my-plugin:compact',
  pluginId: 'my-plugin',
  // 文案可以是字符串，也可以是按语言求值的工厂函数
  title: (locale) => locale === 'zh' ? '紧凑模式' : 'Compact mode',
  defaultValue: false,
  component: CompactToggle,
  validate: (value): value is boolean => typeof value === 'boolean',
}))
```

可照抄的四个设计决定：
- `id` 复用 `<pluginId>:<name>` 命名空间，同时**另有** `pluginId` 字段决定设置项归到哪个插件的设置页——即"身份"与"归属"分离（L58）。
- `title` **同时接受 string 与 `(locale) => string`**，多语言不需要重注册（与上游 tab 注册的 thunk 化 title 同一思路，见 `tab-registry.d.ts` 模块注释"Thunked copy … read again on every use"）。
- `validate: (value): value is boolean` —— 用 **TS 类型谓词**做运行时校验，校验发生在**写入前**（L44）。
- 编辑器只接收"当前值 + `onChange` + 当前语言"三样（L44），组件不持有状态。
- 排序规则明确：按 `order`，再按 `id`（L44）。
- 读侧另有三个方法：`getSetting` / `setSetting` / `onDidChangeSetting`（L60）。

**插件侧契约文件的位置本身是接缝设计**：`src/client/contract.ts` 是工作台对外契约（`WorkbenchService`、`ViewProps`、`EditorOpenSeed` 等）；功能插件**只做类型导入**（编译期擦除），运行时全部走 `ctx.workbench`；且"各功能插件内有一份该契约的 **vendored 副本**，改动本文件时需同步更新"（dock_readme.md §插件契约, L120）。这是"没有 workspace 依赖时怎么共享类型"的土办法，代价写得很清楚：改契约要手动同步 5 份副本。

**上游对应物**：dock 的整个工作台外壳与上游 `AppFrame` + 槽位体系同构（活动栏≈`sidebar`、编辑器区≈`main` keyed、状态栏/面板≈`shell.bottom`/`shell.overlay`、命令≈`ctx.shortcuts`），但 dock 选择**自建 `ctx.workbench` 而不是复用 `ctx.slots`**——上游 `sidebar`/`rightbar` 都是 single 槽"OCCUPIED"状态，注册即替换而非叠加（`dsh-client-ui-layout/lib/types/client/index.d.ts:44,70` 的注释），这解释了为什么一个"要同时挂文件树+Git+编辑器"的工作台必须自建一层注册表：single 槽装不下多个功能插件，list/keyed 槽又不足以表达"面板/编辑器视图"这种复合结构。

### 2. 状态与持久化

- 布局（面板/浮窗）存 **localStorage**，"刷新后恢复"（dock_readme.md §功能, L17）。
- 设置值存 **localStorage 的 `dock:settings`** 这一个 key（§设置 API, L60）。
- **损坏/不可用的回落原文**："存储不可用或数据损坏时，工作台使用内存值和默认值继续运行"（L60）——注意它比 better-sidebar 更"软"：**不删 key、不报错，直接以内存值 + default 继续**，即会话内可用、下次刷新回到默认。
- 作用域是**全局**（不是每会话）：`dock:settings` 无 sessionId 后缀，与 better-sidebar 的 per-session 策略正好相反（对比 bs_readme L236）。
- 未持久化的易失状态有明确清单：**入口 pin 只在内存里，插件重载即复位**（这是上游的做法，`dsh-client-ui-sidebar-right/README.md:117` 写"Plugin reload resets pin choices; legacy localStorage values are ignored"）；dock 自己的"入口隐藏后仍可从设置里打开"也属于内存/入口层状态（dock_readme.md L58, L70）。

### 3. 性能预算

README **没有给任何体积/耗时/RSS 数字**——一条都没有。唯一带数字的是**几何量**，属于"每帧要重算的东西"：
- 为 dock 预留空间 = **实测 dock 宽度 + 24px**，只移动右停靠时的会话进度导航栏，"不改变页面宽度或滚动条位置"（dock_readme.md L68）。
- 鱼眼放大：悬停 **1.6×**、相邻 **1.2×**（默认），滑块范围 **1.0–2.5×** / **1.0–2.0×**，步进 **0.05**，"相邻倍数不会超过悬停倍数"（L69）。
- 重算触发点写明三类：dock 栏尺寸变化、窗口缩放、开关切换；关闭开关时偏移归零（L68）。
（结论：这个插件把"性能"表达成"重算边界"而不是"毫秒数"。）

### 4. 兼容与版本策略

- 运行时依赖表（dock_readme.md §依赖, L74-78）：
  | 依赖 | 类型 | 说明 |
  |---|---|---|
  | DSH Web 环境 | 运行时 | 必需，最低 `>=0.1.3-alpha.2` |
  | `cordis` `^4.0.0-rc.7` | peer | 插件框架（DSH 自带） |
  | `react` / `react-dom` `^18.2.0` | **peer（可选）** | "客户端渲染需要；**未提供时工作台 UI 不激活**" |
- 这条"可选 peer + 未提供则 UI 不激活"是最值得抄的一条：**把 UI 依赖降级成可选 peer，缺失时不报错、只是不激活**，这样同一份包能在没有 React 的环境里被加载而不炸。
- 上游的 cordis peer 实际版本是 `~4.0.5`（`dsh-client-ui-layout/package.json`），dock 写 `^4.0.0-rc.7`——两者区间有交集但基线不同；这属于"peer 写宽一点容忍宿主小版本漂移"的实用取舍。
- **无版本对照表**，只有一条最低版本；也没有写不匹配时会怎样（对比 bs 的 7 行表和"拒绝安装"说明）。
- 安装顺序**被显式声明为不敏感**："dock 提供 `ctx.workbench` 服务；功能插件通过该服务协作，**安装顺序不敏感（Cordis 按依赖激活）**"（dock_readme.md L108）。这是 Cordis `inject` 声明式依赖的直接收益，也是"自建服务 + 依赖注入"相对"import 具体实现"的核心优势。

### 5. 对宿主布局的侵入点

这是三份材料里**唯一给出明确 DOM 定位契约**的一份：
- 用 **`data-turn-navigator`** 标记定位宿主的"会话进度导航栏"（dock_readme.md L68）。侵入动作只有一条：右停靠时把它**向左移动 `实测 dock 宽度 + 24px`**，且"不改变页面宽度或滚动条位置"。
- **上游核实结果：`data-turn-navigator` 在 0.2.1-rc.3 的整个安装目录里 0 命中**（对 `<上游根>` 递归 `grep -rn "turn-navigator"` 无输出；`dsh-client-ui-conversation/lib/client.js` 里现有的是 `data-conversation-scroll`、`data-conversation-region`、`data-conversation-header-*`、`data-composer-*` 等）。也就是说这个锚点在当前宿主编译产物里**已经不存在或改名**——它属于"软锚点"：找不到元素时最坏是"偏移不生效"，不会崩（这正是"温和失效"的样板，也是为什么它敢用私有 DOM 标记）。
- 其他侵入是"窗口自身"级别的，不碰宿主 DOM：整个工作台可停靠屏幕四边、支持独立浮窗（可拖动/缩放）（dock_readme.md L14）。
- 上游侧的对应做法是**用 CSS 自定义属性而不是改别人宽度**：`shell.leading` 挂载期间 frame 发布 `--dsh-frame-leading-clearance`，主面板内容贴左上角时按它 padding（`dsh-client-ui-layout/lib/types/client/index.d.ts:112-124`）。这是"侵入方与被侵入方约定一个量"的正规解，dock 的 `+24px` 是它的手工近似版。

### 7. 首次使用路径

没有向导，只有"装 + 加零件"：

### 8. 可直接复用的规则

1. **如果你要做"基座 + 多个功能插件"，就把基座做成零内部依赖 + 一个服务面 + `install order insensitive`。** 证据：六个 register 方法全返 disposer 配 `ctx.effect`（dock_readme.md L19）、"安装顺序不敏感（Cordis 按依赖激活）"（L108）、"dock 自身不依赖任何其他 dock 系列插件"（L80）。
2. **如果你的 UI 依赖可能不存在，就把 React 写成可选 peer，缺失时"UI 不激活"而不是抛错。** 证据：L78 原文。
3. **如果你要长期持有用户偏好：单个命名空间 key（`dock:settings`）+ 写入前 `validate` + 损坏时"内存值 + 默认值继续"。** 证据：L60 + `validate: (value): value is boolean`（L54）。
4. **如果你要碰别人的布局，先定义一个可测量的量再动手，并且只改"位置"不改"尺寸"。** 证据：`实测 dock 宽度 + 24px`、"不改变页面宽度或滚动条位置"、"关闭该开关时偏移归零"（L68）。
5. **如果你的锚点是宿主私有 DOM/私有标记，就必须接受它会消失，并保证消失时只是不生效。** 证据：`data-turn-navigator` 在 0.2.1-rc.3 全树 0 命中（上游 grep）；对比上游正规解 `--dsh-frame-leading-clearance`（`dsh-client-ui-layout/.../index.d.ts:112-124`）。
6. **如果你要防止插件把自己关掉：任何"隐藏/禁用"都要留一条与被隐藏对象无关的逃生入口。** 证据：入口隐藏后仍可从设置打开（L58）、隐藏后仍可右键打开设置（L70）。
7. **如果你要在没有 workspace 的环境里共享类型，就 vendor 一份契约文件并把"要手动同步"写进 README。** 证据：L120。

## 三、dsh-TUI（ccch1mneyyy/dsh-TUI）

> 这份 README 是"改壳"里最极端的一种：它不自绘宿主 DOM，而是**把宿主整个换成一个终端应用**（Ink/Yoga 渲染到 pty）。因此它的"接缝"是 Cordis patch + 导出子组件 + 包根声明；它的"布局侵入点"是终端协议。

### 1. 注册/接缝的确切形状

- **总体装配链（一句话给全）**：`dsh profile → dsh-base → dsh-TUI Cordis patch → agent preset + DSH services → session/event → Channel projection → React components → Ink/Yoga renderer → terminal`（§How It Works, L504-512）。
- **"零核心改动"的自我约束**："Zero core changes: it consumes only DSH's public exports, and is moving from a mounted plugin to an app with its own entry and composition root, where DSH loads in process as the first-party backend. **Install to enable; uninstall leaves no patches behind.**"（L21-25）。这是"改壳"插件最该立的一条自律：装=生效，卸=无残留。
- **插件子组件的准入规则**（很具体、可照抄成校验器）：导出的插件子组件按**其 ESM entry 最近的 package manifest** 做准入，**包括 import-only 与条件导出**；它们**不继承外层包的 identity**（§Plugin Ecosystem, L589-591）。含义：monorepo 里 re-export 别人的组件不会被误判成你的包。
- **后端插件家族 `tui.dsh/v1alpha1` 的 `Backend` contribution**（这是 README 里唯一给了"声明→注册→加载"完整形状的机制，§Plugin Ecosystem, L592-596）：
  - 启动时扫描 profile 声明的 bundle；
  - 准入并注册每个包**根部的 `dsh-plugin.json` 声明**；
  - 实现从包的 **`backend` export** 读取，且"**只在真的选中该 backend 时才 import 那个模块**"；
  - 约束：每个 bundle **最多声明一个** backend，且其 handler id 必须与声明一致；
  - **等待授权的条目不探测也不加载**，即使启动时被显式点名请求。
  这五条合起来＝"声明与实现分离 + 懒 import + 授权前置"，是"可插拔后端"的模板。
- **内置侧面板注册表**：八个内置面板默认全开，**后来注册的插件面板也默认开**，由 `sidePanel.panels: '*'` 表达；在 `/settings` 取消勾选某行即切换成显式列表（§Highlights, L53）。即通配符默认 + 用户显式列表覆盖。
- **设置页分组**：TUI 自己的设置归 **General**，声明了 page 的插件各得一个 tab；`Tab`/`Shift+Tab` 或点 fullscreen 的条带切换；**只有一个 page 时条带隐藏**（§Quick Start, L141-147）。
- **Agent Teams 的工具替换是"声明式抢占"**：只要请求里带 `spawn_teammate`，dsh-TUI **就从请求里丢掉 `subagent`/`subagent_fork`**，团队的 `send_message`/`list_agents`/`interrupt_agent`/`wait_agent` 顶替同名旧控件；团队关闭时旧工具回来；非团队成员的子代理（workflow、ralph）保留 `subagent`（L375-381）。
- **与上游槽位的对照**：TUI 不直接往 `ctx.slots` 注册（它是终端 Renderer，不是 web Renderer），但它**挂在同一个 Cordis 装载器/u 同一套 fiber 生命周期**上；上游那套"声明即独占渲染权"的规则（`dsh-client-ui-layout/lib/types/client/index.d.ts:44` "registering here replaces the navigation column outright"）在 TUI 里对应"整棵树由 Ink 渲染"。
- **首次运行的四步向导与 `/setup` 重跑**（见第 7 节），向导标题是固定的四块：**API key / language+theme / model+workspace / shortcuts**（§Highlights, L45）。

### 2. 状态与持久化

TUI 的持久化位置（README 里能点名的 5 处 + 1 个未给路径的授权存储），全部可枚举（这是三份材料里最完整的持久化清单）：

| 路径 | 内容 | 作用域 |
|---|---|---|
| `~/.dsh-tui/settings.json` | `/settings` 的 `dsh-tui` 段 | **所有 kernel 共享**；首次启动从 profile 的 `cordis.patch.yml`（及更老宿主的 `~/.dsh/settings.yaml`）**导入一次**（§Quick Start, L147-149） |
| `~/.dsh-tui/permission.json` | DSH 后端的 `/permission` 选择 | 全局（§Permissions and Security Boundary, L657） |
| `~/.dsh-tui/backends/<id>/prefs.json` | Claude / Codex 后端的 `/permission` 选择 | 每后端（同处） |
| `~/.dsh-tui/extension-grants.json` | 插件授权的 `grants`/`denies` 条目；**授权在安装开始前先写**，安装失败则回滚该写；registry 包因"落地前读不到声明"改为安装成功后补 `grant` 步（L600）；`enable` 授予、`disable` 回收、`remove` 删除 | 全局，**按 component id 记**；"grants are keyed by component id, so leaving them behind lets any later package reusing that id inherit them silently"（§Plugin Ecosystem, L618） |
| `last-run.json`（README 只给文件名，未给目录） | 上次 boot 的 kernel + session，供 safe mode "retry normal startup" 用 | 全局（L241） |
| `~/.dsh-tui/restart.log` | 更新器的 category / PID / 终止原因 / 最后输出时间戳 | 全局（§Bounded update installation, L752-753） |

- **"一次性导入、不覆盖新值"**：首次启动从旧位置导入一次（L147-150），与 better-sidebar 的 `settings.yaml` 迁移同一策略（bs_readme L93）。
- **内存态与落盘态的分界写得很细**：`/thinking` **不持久化**（§Known Limitations, L528）；"With DSH's current JSONL backend, startup and `/new` keep initial permission events **in memory** until further session activity saves the complete log. Flushing a session that holds only initialization leaves it unstored. Restarting an unstored empty session starts fresh."（§Built-in Commands, L482-484）——即"只有初始化的会话不落盘，重启即全新"。
- **未验证身份的设置项是"临时"的**（罕见的诚实设计）："Panels without a verified Component identity are temporary: settings show their title and **a distinct number for this run**. Their toggles **take effect immediately without being saved**, and unrelated settings changes preserve that choice. Old `actN:panel` entries cannot be mapped safely: remove the placeholder and select the current panel again."（L37）。已验证的组件保留 `actN` 公共运行时地址；显式选择用 `component:actN:panel` 存盘，以免占用旧的匿名条目（L39）。
- **会话外观快照**：session manager 的 first-paint snapshot **跨重启存活**，并且**按 backend 与 storage directory 隔离**（§Built-in Commands, L483-484）。
- **卸载/迁移**：SQLite 迁移脚本用官方 `node:sqlite.backup()`（Node 22.19+/24+），**先探测能力再只读打开源库**，包含已提交的 WAL 得到一致快照，"never copies a live database/WAL pair by hand"（§Storage migration and read budgets, L715-721）。

### 3. 性能预算

这是三份材料里数字最密集的一份。按上下文原样列出：

- **首屏**："After startup the TUI checks for newer versions in the background. **It never blocks the first frame.**"（§Quick Start, L177-179）。没给首屏毫秒数，给的是"首帧不被任何网络阻塞"的约束。
- **启动顺序预算**："**Startup: the screen appears before the session opens**, with only a light profile composed (this package plus the profile's third-party plugins)"（§Experimental: Claude backend, L247-249）。即"先出界面、后开会话"。
- **渲染复杂度**："Long sessions render in **O(visible window)**"（§How It Works, L510-513）；tagline 是 "event-driven projection, virtualization, bounded caches"（L64）。
- **冷读/大对象**：40.2 MB 会话的对比见上一节 bs（同一生态口径）；TUI 侧对应的是"Session-tree reads validate packed rows and check their entire member count against **the remaining scan budget** before expanding events. Oversized rows report truncation; malformed rows report failure. The logical budget **does not eliminate physical JSON/frame parsing or validation**."（§Storage migration and read budgets, L721-723）。
- **后台列表预热**："DST preloads the session list in the background after startup and updates the cache on success. The manager **paints the last successful list immediately**. Opening `/resume` while that read is pending **shares the request** and receives results that have already arrived."（§Built-in Commands, L483-484）；Claude/Codex 首屏各取 **32** 条（`32 recent sessions`，L484）；Codex 复用运行中的连接，"read the first 32 regular results alongside the state DB shortcut"（L485-487）。
- **TPS 口径（含两个数字）**："TPS includes hidden reasoning time and **excludes tool execution time**. … **Decode spans of 500ms or less are excluded from TPS samples**; token and cost totals still include all reported usage."（§Experimental: native Codex backend, L328-329）。
- **光标动画预算**：`/model` 选择器的原生光标在"**0.5 秒静止后**"隐藏；被裁剪区域回落到模型行（§Highlights, L48）。
- **通知预算**：正文单行纯文本、**最多 200 字符**（Markdown 格式剥除）；OSC 777/9 额外 **2048 字节**序列预算（含标题与协议字节），保留完整 grapheme；无回复时只显示标题；BEL 只响（L47）。Windows：首个 toast 向 HKCU 注册 AppUserModelID，**约 3 秒**后出现（= PowerShell 冷启动的代价），换取"零额外安装"（L47）。
- **插件斜杠命令结果块的硬上限**："Each report retains at most **200 lines, 65,536 UTF-16 code units and 4,000 terminal cells per line**, plus a visible truncation marker."；旧块在**共享的 600 行预算**内被驱逐（L440-442）。
- **终端输入的恢复窗口（三处，参数一致）**：不完整 Win32 输入记录最多保留 **1 秒**（自首捕获起、**不被后续输入延长**）、**64 字节**上限；终端响应（DA1/DA2/DSR/DECRPM/XTVERSION）同样约 1 秒 / 64 字节；SGR 鼠标报告同样"at most 1 second; 64 bytes max"（L424, L432, L436-438）。
- **剪贴板**：本地 Windows 复制走 PowerShell + UTF-8 stdin，**每次尝试 2 秒超时**（先 Windows PowerShell，再 PowerShell 7），两者都失败才回落到 OSC 52（§Known Limitations, L523-524）。
- **退出**："Shutdown drains only the actual renderer-owned input after terminal cleanup and **a 150-ms settle window**."（L520-521）。
- **sixel 自愈**：探针允许 **1 个挂起回复（500 ms）**，跳过 resize/handoff，在**未应答查询后或 10 秒内 3 次修复后暂停 60 秒**（L520-521）。
- **堆取证预算**：`DSH_TUI_HEAP_WATCH=1` 才开；**每 15 秒**采样一次；阈值 **1024 / 1536 / 2048 / 2560 / 3072 MiB** 各取一张快照；自管文件保留**最多 4 个 64-KiB 日志 + 2 张快照、合计最多 1024 MiB**；`DSH_TUI_HEAP_MAX_MB` 取 **1–16384**，非法值用 **1024**（§Development, L551-555）。
- **更新安装**：每个 profile 安装器调用 **30 分钟**墙钟上限；`DSH_TUI_UPDATE_TIMEOUT_MS` 改；"**Output activity does not reset this deadline**"；POSIX 取消先杀自己的进程组、**2 秒**后强杀剩余后代；Windows 用 Job Object，且"installer joins that job atomically **while suspended**"（§Bounded update installation, L732-753）。
- **构建/运行环境**：CI 用 **Node 24 + pnpm 11**；包支持 Node **`^22.19 || >=24`**（§Development, L565-567）。

### 4. 兼容与版本策略

- **主兼容目标写在最显眼处**："The primary compatibility target is DSH **0.2.1-rc.5**. This adapter supports its Shell API, V4 session messages, declarative presets, and profile-backed settings; older supported hosts retain their compatibility paths."（§Quick Start, L132-135）。
- **"支持的宿主线"是显式白名单**：`0.2.1-rc.5`、`0.2.1-rc.4`、`0.2.1-rc.3`、`0.2.1-rc.2`、`0.2.1-alpha.5`、`0.2.0-rc.1`、`0.2.0-rc.2`（L368-372）。CLI 自动化引擎另有一份实测清单："validated on 0.2.0-rc.2, 0.2.1-rc.2, 0.2.1-rc.3, 0.2.1-rc.4 and 0.2.1-rc.5"（§CLI, L188）。
- **不匹配时的行为分三档**（这是全文最可抄的一段兼容策略）：
  1. **硬停 + 修复指引**：DSH 0.1.7 上 `/settings` 需要 `@deepseek-ai/schemastery` **3.18.3+**，"an incompatible schema **stops TUI startup with repair guidance** instead of showing an uneditable settings page"（L145-147）。即宁可起不来，也不给一个不能编辑的设置页。
  2. **拒绝并给升级指令**：DSH < `0.1.2-alpha.3` **拒绝** `/model` 热切换并提示升级，因为这些版本的子代理会继承原路由（§Known Limitations, L518）。
  3. **降级 + 一次性说明**：safe mode 的 "retry normal startup" 若记录里的 backend 已不存在，"degrades to a warning plus a cold start"（L235-243）。
- **launcher 自己做 Node 版本闸门**："The launcher checks the manifest's Node range before loading the application. **Known unsupported versions (including Node 23 and prereleases) stop with Node upgrade instructions.** Missing or unrecognized ranges allow startup for compatibility with migrated launchers; `doctor` reports that compatibility cannot be determined. `help` and `version` remain available."（§Development, L567-569）。注意"缺失/无法识别 range 则放行 + 由 doctor 报告无法判定"——**fail-open 但留诊断**，比 fail-closed 更适合 launcher。
- **协议基线（对外部工具的版本契约）**：Codex 协议 **baseline 0.160.1 / minimum 0.144.0**，"other versions may show drift"（§Experimental: native Codex backend, L295-296）；`codex app-server 0.160.1+` 才有 "fork/conversation rewind（first message）"（L332）。
- **peer 锁定关系**：Agent Teams 包"ship in lockstep with DSH and **pin their DSH peers exactly**, so the version must match"（L372-374）——与 better-sidebar 的 `^` floor 是两种相反策略，各自理由都写清了。
- **两条"不要用 git 装"的实测结论**："**Git URL installs are not supported.**"（§Development, L585-587）；原因是源码 manifest 把 `@dsh-std/*` 留作 workspace 依赖、`vendor/dsh-std` 是 submodule，且 pnpm ≥11 默认拒绝 git-hosted `prepare` 脚本（L583-587）。
- **更新器的成功判据**："**Only the final process exit code establishes success: a printed `Done` does not.**"（L736）。以及"Timeout, cancellation, or unconfirmed cleanup returns nonzero and **prevents retries, stale-file removal, repair, and TUI replacement**"（L748-750）。
- **update 的两条自动策略**：pnpm ≥11 会报 `ERR_PNPM_IGNORED_BUILDS`；更新时"**skip foreign-platform natives**——`@img/sharp-*` 与 Claude SDK 的 per-platform bundles——所以只拉本机二进制"，且 `/update` 与 `dsh-tui update` 自动写好这两个设置（§Quick Start, L167-178）。
- **不装作成功**：Codex 后端"Only Codex identification/title changes automatically, not palette or companion."（L338）；"The real 0.160.1 app-server passed nine credential-free offline checks and eight daemon-resume checks, with no model turn or charge; **real subscription login, credentialed model calls and real-TTY interaction were not run**."（L336-339）。把"没测什么"写进 README，是三份材料里唯一一份这么做的。

### 5. 对宿主布局的侵入点

TUI 的侵入不在 DOM，在**终端协议面 + 宿主配置面**，并且每一条都写了"上游/终端不支持时怎么办"：

**终端侧（OSC / CSI / 私有模式）：**
- `OSC 7501`（Program Status Protocol）上报 `idle/working/blocked/done/error`；"terminals that do not implement it **ignore the sequence**"；`DSH_TUI_PROGRAM_STATUS=0` 关闭（§CLI, L230-232）。
- `OSC 777`（Ghostty/WezTerm 分 title/body 字段）、`OSC 99`（Kitty）、`OSC 9`（iTerm2/Warp 用标题前缀）、BEL 铃（L47）。
- `OSC 8` 超链接：Windows 桌面拖放文件到达时是一个 OSC 8 hyperlink，parser 先把 `file://` URI 还原成解码后的本地路径，**再**跑 paste hygiene，避免 `]8;id=…;` 参数字节进入草稿（§Keybindings & Mouse, L454）。
- `OSC 52`：本地剪贴板两条 PowerShell 路径都失败后的最后回落，"requires terminal support"（L523）。
- `DEC 2026`（synchronized output）：可捕获退出时**显式结束**，即使没有最后一帧；SIGKILL / native abort / 事件循环完全阻塞则无法保证进程内清理（L524）。
- **ConPTY 私有模式 `9001`（win32-input-mode）**：识别到 `NVIM`/`VIM_TERMINAL` 的 Windows Neovim/Vim 终端**保留 VT 输入而不启用**；其他不兼容嵌入宿主设 `DSH_TUI_DISABLE_WIN32_INPUT_MODE=1`；"The same gate applies at startup and after resume."（L419-421）。
- **tmux**：OSC 通知需要 `set -g allow-passthrough on`，focus 上报需要 `set -g focus-events on`（L47 同段）。
- 终端无关的兜底：颜色深度 monochrome/16/256/truecolor 四档，"Apple Terminal and tmux use the shared fallback; `NO_COLOR` and `FORCE_COLOR` retain the existing shared color policy"（§Built-in Commands, L460）。
- 路由/键位的**保守闸门**：只有终端真的进入了私有模式才启用重组逻辑——"The platform check only reports that this machine **might** run the private mode; a bare `ESC[` fragment is held **only after one record has actually been decoded**"（L422-424）。

**宿主配置侧（对 DSH profile 的写入）：**
- 读 profile 的 `cordis.patch.yml` 做一次性设置导入（L147-150）。
- 在 `llm-pi-ai` 设置段**种 retry 策略**：5 次尝试、识别 `STREAM_CLOSED` 等传输中断码；"Only routes without an explicit `retryPolicy` are seeded — **dormant channels are never written**"；`upstreamRetry: false` 在 `cordis.yml` 里可退出（§Permissions and Security Boundary, L665-667）。
- 从 kernel Minimal preset 与内置 liangshen preset 里**隐藏 `create_worktree`**（因为它们的常驻 shell 会留在原目录），并隐藏 session-search 的五个工具（§Permissions and Security Boundary, L669-681）。
- 权限默认值要挟：**Windows profile 默认 `danger-full-access` + approval `never`**，README 顶部给了安全警告（§Permissions and Security Boundary, L651-655）：原文 "the Windows profile defaults to `danger-full-access` with approval set to `never`"；另同节 "No sandbox of its own: dsh-TUI uses the active DSH profile's filesystem, shell, sandbox and approval policies."。

**宿主布局改动的后果分级（可反推的失败模式）**：因为全部走公开 export + Cordis patch，宿主升级的表现是"某个能力消失/降级"（例如 `/team` 只在团队服务挂载后才出现在 Help 与 `/` 补全，L368-372；`/plugin list` 对宿主没带的实验特性**整段不显示**，L620-627），而不是整页崩。

### 7. 首次使用路径（逐屏）

1. **安装**（两条路）：Windows 一键安装器 `dsh-tui-setup-win-x64.exe`——"Per-user, no administrator, fully offline, and no preinstalled Node or DSH"（L119-121）；或 `npm install -g @deepseek-ai/dsh @deepseek-harness-tui/dsh-tui` 然后 `dsh-tui`（首次运行**自动初始化 profile**，需要 pnpm）（L155-162）。手动等价：`dsh plugin --profile dsh-tui add @deepseek-harness-tui/dsh-tui`，或仓库的 `sh install.sh`（它跑同一命令并检查所需命令）（L164）。
2. **启动落地页（launchpad）**："every ordinary launch lands on a landing page with a **real input box**（big text + whale + quick actions）"；短/窄终端会"dropping whole blocks"；`/settings` 的 `launchpad` 关掉后直接进 chat（L45）。
3. **四步向导**（首跑自动走，"re-runnable with `/setup`"）（L45）：
   - 第 1 步 **API key**——要求用户提供密钥；DeepSeek 官方路线需要 `DEEPSEEK_API_KEY`，0.2.0-rc.1+ 也可之后用它 `/auth login deepseek-account`（L123-131）。
   - 第 2 步 **language + theme**——中/英文界面与主题。
   - 第 3 步 **model + workspace**——选模型与工作目录。
   - 第 4 步 **shortcuts**——快捷键速览（`?` 随时重看）。
4. **首屏之后看到的东西**：pixel whale 头图（三种开场 intro，点击唤醒，"freezes after the first task"）、实时工作状态、流式 thinking、context 进度条、TPS 表（L21-22, L45）。
5. **第一次干活的输入面**：`/` 与 `@` 补全、`#L12-14` 行区间、历史搜索（`Ctrl+R`，作用域为当前项目）、`Ctrl+O` 详情、`Ctrl+B` 侧面板、`Ctrl+Shift+E` 全屏草稿编辑器、`?` 快捷键（§Keybindings & Mouse, L402-410）。
6. **随时可跑的自检**：`dsh-tui doctor`（pre-flight 环境检查）、`dsh-tui safe`（只读诊断 + 插件清单 + 修复指引）、`dsh-tui safe --rescue`（构建干净救援 profile）、`dsh-tui version` / `help`（"both work even without a `dsh` install"）（§CLI, L193-201）。

### 8. 可直接复用的规则

1. **如果你要"改壳"又不 fork 宿主：只消费公开 export，把"卸载无残留"写成可验收的承诺。** 证据："Zero core changes … Install to enable; uninstall leaves no patches behind."（L21-25）；对照 bs 的"两处 sidebar"自愈（bs_readme L92）。
2. **如果你要做可插拔后端：包根 `dsh-plugin.json` 声明 + `backend` export + 选中才 import + 每 bundle 一个后端 + 未授权不探测。** 证据：`tui.dsh/v1alpha1` Backend 的五条约束（L592-596）。
3. **如果你的启动会碰网络（查更新）：让首帧先出，检查放后台。** 证据："It never blocks the first frame."（L178-180）；"the screen appears before the session opens"；`/resume` 共享同一笔在飞的列表读请求（§Built-in Commands, L483-484）。
4. **如果你要在别人的会话恢复路径上做决定：宁可报错退出，也不要"猜一个"冷启动。** 证据：unknown backend / remembered kernel 不匹配 → "refuses with a clear error and exit code 1 — never a silent cold start, never another backend's session, never a new session"（L235-241）；唯一例外是 safe mode 的 retry（L235-243）。
5. **如果你的输入解析要等后续字节才能判定：给 hold 一个"从首捕获起算、不被后续输入延长"的硬窗口 + 字节上限，超界就**原样重放**。** 证据：1 秒 / 64 字节三处一致，且"literal input can be delayed, but is never dropped"（L424-438）。
6. **如果你的功能依赖某个外部能力（终端协议、剪贴板、通知、sixel）：为每一档能力写一条"退化为 Y"，最少也要留"响铃/文本/不激活"这种不静默的兜底，并允许用环境变量关掉。** 证据：通知四档 + "falls back to the bell instead of going silent"（L47）、图片 text fallback（L49）、OSC 52 兜底（L523）、`DSH_TUI_SIXEL_CURSOR_HEAL=0` / `DSH_TUI_PROGRAM_STATUS=0` / `DSH_TUI_DISABLE_WIN32_INPUT_MODE=1`。
7. **如果你的设置会迁移：一次性导入 + 不覆盖更新值 + 来源路径写进 README。** 证据：`~/.dsh-tui/settings.json` 首次从 `cordis.patch.yml`（及旧 `~/.dsh/settings.yaml`）导入一次（L147-150），与 bs 的 settings.yaml 迁移同构（bs_readme L93）。
8. **如果你的列表/日志可能很大：给"分页 + 扫描预算 + 超限显式报错/截断标记"三件套，并把共享预算写出来。** 证据：每条报告 200 行 / 65,536 UTF-16 单元 / 每行 4,000 cell，超出加可见截断标记，旧块在共享 600 行预算内驱逐（L440-442）；session-tree 读取按剩余扫描预算检查成员数，"oversized rows report truncation; malformed rows report failure"（§Storage migration and read budgets, L721-723）。
9. **如果你的权限/授予只能算"行为约束"：就直说它不是安全边界，并保证授予写失败不阻塞主流程。** 证据：§Plugin Ecosystem L618 两句："grants are keyed by component id, so leaving them behind lets any later package reusing that id inherit them silently" 与 "A failed grant write never blocks an install or enable — it is reported instead."
