## 它想干什么 · 为什么值得借鉴

**意图。** 它想把“多代理”从运行时能力变成一张**可批准的计划**：先给花名册（未 spawn）和任务 DAG（未调度），你点头才开始跑。交付单位是一次经批准的编队，加上它自己那份落在 `.agent-teams/` 的磁盘真相。它明确不在计划阶段创建代理、不新增入口、不靠提示词约束授权，也不做写入时拦截。

**意义。** 多代理样本大多在讲工具数量和并发，它补的是**授权与撤销**这一格：入口有 Web `/plan`、模型工具 approve、以及 create 的默认 automatic 三条；真正被强制的只有“staged 时不得派发”，staging 本身靠提示词约定。它改的惯例是把“用户否掉”从一次点击升级成三层否定——终止当前规划轮次、归档草稿（唯一 durable）、注入“不要再创建”的上下文并依赖系统提示。第三层不持久，重启或 inject 失败后可能被重新创建。

**用户价值。** 装前，多代理一按就跑，花掉的 token 和时间只能事后看账单；否掉一个方案，下一轮它又自己长回来。装后，昂贵操作前先看到“将要发生什么”，在聊天里说一句“把审查那个人去掉”就修订**同一份草稿**，批准后按成员分段的进度条逐一亮起。觉得值的是要跑批量或长链路任务又不敢放手的人；质量门默认关、显式开，是完成时审计而不是写入拦截，审查失败只让下游保持阻塞并另建修复任务。代价是大多数人从没开过那五道门，`memberMaxDepth` 默认 0 意味着成员不再生成员，磁盘真相也只在一个进程内串行。

**表达（界面与交互）。** 第一屏就是**花名册 + DAG**，没有任何代理在跑，入口复用聊天命令，不新增侧栏按钮。交互被压到三件：聊就是编辑、Approve & Run 是唯一开跑按钮、Discard 归档并注入“不要再创建”的上下文（不持久）。默认值保守得具体：质量门 OFF、成员懒创建（第一个任务就绪才建）、`maxMembers 8` 钉住宿主的 `maxActiveSubagents 8`。进度条按成员分段而不是一条总进度，因为并行不均匀时单一进度条会撒谎。

## 2. 机制(可照抄的部分)

### 2.1 计划先行:一个状态机,一个授权点

```
/agent-teams
   ↓
计划模式:花名册(未 spawn)+ 任务 DAG(未调度)
   ├── 聊天里说"改一下" → 终止本轮规划 → 问你想改什么 → 修订【同一份草稿】
   ├── Discard        → 归档草稿 + 注入禁止上下文（非 durable）
   └── Approve & Run  → 成员 spawn、任务进入调度
```

| 细节 | 为什么必须这样 |
|---|---|
| 计划阶段**不 spawn** | 用户看到的是"将要发生什么",不是"已经花了多少" |
| 回到聊天**终止规划轮次** | 不会出现"我在跟你讨论时它偷偷开跑" |
| 修订**同一份草稿** | 聊五轮不会冒出五份计划 |
| 只有 **Approve & Run** 进入调度 | 唯一的、不可误触的授权点 |

> 与 [`生成式界面`](./21_生成式界面-dsh-genui.md) 的"没有 `action` 的按钮渲染为禁用"是同一条原则的两半:`genui` 保证**按钮不骗人**,`agent-teams` 保证**授权不会自己发生**。

### 2.2 三层否定:这一条是本卡最值钱的机制

多代理系统最常见的失败不是"跑错",而是**你否掉它,它下一轮又自己长出来**。它在三个互不相同的层面同时挡住:

| 层 | 动作 | 挡住的是什么 |
|---|---|---|
| **对话层** | "stops the planning turn" | 讨论中途被自动带跑 |
| **草稿层** | "archives the draft, aborts the turn, and **explicitly prevents automatic recreation**" | 下一轮重新生成同一份计划 |
| **上下文层** | "**parks model-facing context that forbids silently creating a replacement team**" | 模型"忘了"被否过,凭对话历史重建 |

> **抄这条**:任何"用户已经否决的决定",只做一次就够了吗?不够。你必须同时挡住:**当前轮次、重试/重建路径、以及模型的记忆**。只挡一层,系统会在另一层复活它。
> 反过来也成立:**"禁止"要写在模型看得见的地方**,否则等于只写了注释。

### 2.3 授权与工具面:少即是多

| 事实 | 含义 |
|---|---|
| 公开 **14 个**协调工具 | 能力齐 |
| 但**只发布 7 个名字**给模型 | 上下文预算 |
| **成员只拿 4 个** | 角色裁剪的实证(不是"每人都拿全套") |
| 只有 Approve & Run 开调度 | 授权点在状态机里,不在提示词里 |

> 对照本线的一个老问题:"14 个工具全部暴露给每个成员"。**它其实做了裁剪**(7 个给队长、4 个给成员),这一条比"14 个工具"更能说明工程成熟度。抄的时候别只抄数量。

### 2.4 质量门:完成时审计,不是写入时拦截

| 项 | 事实 |
|---|---|
| 阶段 | 需求 → 实现 → 验证 → 审查 → 集成,**五道** |
| 默认 | **OFF**,显式开启 |
| 性质 | "**a completion-time audit, not host write interception**"——不会在你编辑文件时打断你 |
| 审查失败 | **不解除下游阻塞** |
| 修复任务 | 另建,**故意不依赖失败的那次审查**(否则死锁) |

> 两个设计决定值得单抄:① **门放在完成时**——写入时拦截会让代理寸步难行,完成时审计只让不合格的交付退回;② **修复任务不依赖失败的审查**——这是避免"等自己"的必要条件。很多工作流引擎在这里死锁。

### 2.5 磁盘真相:进程内串行，跨进程会互相覆盖

| 项 | 事实 |
|---|---|
| 位置 | `<workspace>/.agent-teams/` |
| 一致性 | **单进程内串行**写 |
| 边界 | 无 pid/lease；两个 DSH 进程会互相覆盖；Windows EPERM 退化为直接覆盖 |
| 接管 | `attempt_id` 接管 = **撤销 → quiesce → 新尝试**(不会两方同时写同一个任务) |
| 冷恢复 | 成员失联 → **重试搁浅的尝试**,而不是丢弃 |

> 抄这条:**"磁盘是真相" + "我知道我的锁只在这个进程里有效"**。写成"支持并发"是最容易撒的谎;写成"单进程串行、不跨进程"是用户可以据此安排工作的真话。

### 2.6 上限对齐:别自己发明数字

| 参数 | 它的值 | 宿主对应 |
|---|---|---|
| `maxMembers` | **8** | `maxActiveSubagents` **8** |
| `memberMaxDepth` | 默认 **0** | 宿主 `maxDepth` 默认 1 |

> 抄这条:**把"我的上限"钉在"宿主的上限"上,并在 README 里写出对应关系**。差一档就会出现"我配了 10 个子代理但只有 8 个在跑"。

### 2.7 版本:从枚举改成下界

| 决定 | 后果 |
|---|---|
| `engines.dsh: ">=0.1.2-alpha.2"` —— **只下界,不枚举** | 新宿主发布**不再阻塞安装** |
| 但仍给**推荐配对** `0.2.1-rc.2` + `0.1.28` | 想稳的人有明确答案 |
| CI 矩阵写在 `compatibility.json` | 哪些宿主真跑过,**可查**;legacy 行还带 `legacyDirectInstallReason` |
| `previewTag: next` | 预览版有独立通道 |

**机制依据(可直接引用)**:`[DSH]` `dsh-app-boot/lib/index.js:279-331`——若包声明了自有 `engines.dsh`,**该范围单独决定,所有 peer 被忽略**;否则**每一个** `@deepseek-ai/dsh*` peer 都必须满足;通配键 `@deepseek-ai/*` 会被静默 `continue`(等于没写);比较用 `semver.satisfies(..., { includePrerelease: true })`;不满足即 `ManagementFailure('incompatible-version')`。

> 这是本线对"版本税"最成熟的一次回应:**把"支持"从枚举改成下界,把"验证"从声明改成 CI 矩阵**。对照 [`厚工作台`](./12_厚工作台-better-sidebar.md) 的 7 行对照表,和 [`冻结 fork`](../shell/91_冻结分叉-better-sidebar-N23.md) 的 0.1.x 死锁。

## 3. 体验

### 3.1 首次使用

| 步 | 看到 | 设计 |
|---|---|---|
| 装 | Plugins → Add plugin 填 `github:NanmiCoder/dsh-agent-teams`;npm 装要写**精确版本**(pnpm 11 的 24 小时最小发布年龄会拦住裸 `@latest`) | 两条路都给了 |
| 起 | 聊天里 `/agent-teams` | **不新增入口** |

| 跑起来 | 分段进度条 + 可折叠花名册 + DAG 节点变色 | 看得见每个成员在干嘛 |

### 3.2 三条界面判断

1. **面板是"活动"不是"日志"**:分段进度条**按成员分段**,不是一条总进度。多代理的进度天然并行且不均匀,单一进度条会撒谎。
2. **语言切换不刷新**:用官方 locale 服务,中英**实时切换**。
3. **桌面端装法不同**:官方 Desktop 的 profile 由应用管理,`--profile web` 那条命令**不适用**。

### 3.3 模型看到的

| 变化 | 内容 |
|---|---|
| 新身份 | **队长**(调度)/ **队员**(执行),工具面**不同**(7 vs 4) |
| 新约束 | 计划阶段**不能 spawn**;只有批准后调度才开放 |
| 新通信 | 持久邮箱**异步**投递 → 模型必须处理"对方暂时不在" |
| 新记忆 | 被否掉的计划**在上下文里也有说法**,不是只写进日志 |

> 本线**唯一一个把"模型的身份"编成组织结构**的样本:不是"模型有个工具",而是"**模型在职场上有个岗位**"。

| 多代理要先计划再执行 | 把计划存为团队状态的 staged phase，只有批准后才允许调度。 | `[SRC-TARGET]` team.json phase staged→running + approvedAt；staged 时派发被拒。 | 防止未审计划执行；代价是 staging 靠提示词约定。 | 把 staged 作为服务端不变量，并提供显式批准 UI。 | 批准有三入口，create 的 approval 默认 automatic。 | 以为“唯一授权点” → create 直接开跑。 |

| 任务 DAG 依赖 | 只把 completed 视为满足；failed 上游显式转 blocked，避免永久悬挂。 | `[SRC-TARGET]` 依赖判定与状态机白名单；failed 不满足。 | 语义严格；代价是失败上游会永久阻塞下游。 | 增加失败传播/跳过策略。 | 冷恢复只给一次新 attempt，需队长触发。 | 失败后下游永远 blocked 且无提示。 |
| 多成员并发改文件 | 任务互斥不等于文件互斥：要么加文件锁/merge，要么把冲突检测做成事后审计并阻断交付。 | `[SRC-TARGET]` 无工作区文件锁；review 记录 sha256/drift，交付时判 blocker。 | 不阻塞并行；代价是冲突只能事后发现。 | 定义冲突策略（锁/分区/合并）与审计上限。 | 审计有 200 文件/范围上限并产出 gap。 | 以为任务独占=文件独占 → 覆盖他人改动。 |
| 跨进程/多窗口 | 进程内 Promise 链锁不足；写用 temp+rename，Windows EPERM 会退化为直接覆盖。 | `[SRC-TARGET]` 锁键 team:<root>:<id>；无 pid/lease；appendMailbox 整文件重写。 | 单进程简单；代价是跨进程会互相覆盖。 | 引入文件锁/租约或单写者代理。 | 不是“不协调”，是会覆盖。 | 多开/守护进程并发写坏 team.json。 |
| 队长失联 | 调度每步解析活 captain；无选举；冷恢复需队长活着触发。 | `[SRC-TARGET]` 取不到 captain 即停派发；fork 可 re-attach；无定时器。 | 避免误派发；代价是队长死后团队停摆。 | 增加队长转移/超时接管。 | 队长被删=孤儿目录。 | 队长崩溃后任务永久 claimed。 |
| 活动面板 | 面板读磁盘真值 + 活 agent 状态，轮询而非推送。 | `[SRC-TARGET]` GET state 枚举所有 workspace；1s/5s 轮询；按轮审计。 | 简单可靠；代价是开销与延迟。 | 需要实时性时改事件流并限流。 | 请求不带 sessionId，跨 workspace 可见。 | 面板显示过期状态或泄露其他 workspace。 |
## 6. 失效条件与降级

| 触发 | 行为 |
|---|---|
| 用户 Discard | 归档（durable）+ 注入禁止上下文（重启后失效） |
| 用户中途回聊天 | **终止规划轮次**,不会偷偷开跑 |
| 成员失联 | **重试搁浅的尝试**;冷恢复不丢任务 |
| 归属重新分配 | **撤销旧尝试 → 静置 → 新尝试**;不会两方同写 |
| 审查未通过 | 下游**保持阻塞**;新建修复任务(不依赖失败审查) |
| 质量门未开 | 完全不拦,跑完即交付 |
| 两个 DSH 进程同一 workspace | **没有跨进程协调**(已知边界,需用户自行避免) |
| 新宿主发布 | 因**只声明下界**,不阻塞安装;但未验证 → 看 `compatibility.json` |
| 宿主要求不满足 | `incompatible-version` 拒绝安装;可用精确 `name@version` + `--accept-risk` 豁免 |
| 裸 `@latest` | pnpm 11 的 24 小时最小发布年龄可能拦住 → 写精确版本 |
| 桌面端用 `--profile web` | 装到了别处 → 用应用自带的 profile |
