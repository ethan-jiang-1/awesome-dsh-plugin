## 它想干什么 · 为什么值得借鉴

**意图。** 它盯的是 DSH 只管“装的时候检查”、不管“装完升级之后”的那一格：声明旧范围的插件继续留在 `bundles` 里加载，界面一句提示都没有。交付单位不是一份诊断报告，而是**一次隔离预演加一条可撤销的官方豁免**，或者一句“救不了”。所以它明确不在你的 profile 上试、不预演就放行、也不对起不来的插件强行修复。

**意义。** 它补的是包管理器只做“安装时门禁”、缺“装后复查”这条门；宿主按 `rc` 快速迭代时，这一格每天都在漏。它改的惯例是：静态诊断器只报“可能不兼容”，它把结论推到“能不能救”，并把**顺序**写成安全属性——先在一次性的 `DSH_HOME` 里真启动，再往 `compatibility.json` 写豁免；反过来就是放行一个还没证明能跑的东西。

**用户价值。** 装前，升级后发现某个插件悄悄坏掉，只能逐个试或直接卸；装后，扫一遍就能分清“声明旧了”和“真的不兼容”，点一次 `Check whether it can be saved`、等 30–60 秒，能救的拿一条带撤销的豁免。最觉得值的是装十几个插件又跟着 `rc` 升级的人；维护者那侧也有回音——扫 top 120 把坏插件从 5 个压到 1 个，906★ 的项目在 issue #178 里引用了这次扫描。代价是预演要一次完整启动、必须用户手动触发，而且豁免只证明能启动，不证明每个功能都好用。

**表达（界面与交互）。** 平时它**零存在**：无徽章、无横幅、无侧栏入口，只有出问题时账号菜单上方冒一条“插件有 N 个问题”。每个问题首行先给结论，修复前的确认页把“要写什么、可撤销、不等于官方支持”重述一遍；预演失败时**没有**豁免按钮，只给关掉与生成 brief 两个选项。救生命令默认 dry-run、`boot safe` 只追加 `disabled: true` overlay 且从不禁掉自己——这些“不显示、不打扰、可回退”就是体验本身。

| 它补的是什么缺口 | **DSH 拦新装，不复查已装**：宿主升级后，声明旧范围的插件继续加载、界面无任何提示 | ✅ 这是所有"装完就坏"问题的根 |

## 1. 它在产品里的位置

| 七层 | 动作 | 说明 |
|---|---|---|
| **7 分发** | 安装/升级之后的兼容与修复 | 它不装插件，管"装完了之后还活着吗" |
| 3 槽位 | 设置里的 `Plugin health` 段 + 条件出现的告警条 | 平时不可见 |
| 6 首启 | 升级宿主前的自检（"先跑一次检查再升级"） | 把"首启"前移到"升级前" |

### 1.1 它回答的是「升级之后」这一格

`51_分发与救生页` 处理的是"**起不来**"；这一张处理的是"**起得来，但某个插件已经不该被加载**"——更隐蔽的一格：

```text
装新插件 ──→ 宿主做兼容检查 ──→ 拒绝 / 放行
             （这一格上游做了）
已装插件 ──→ 宿主升级 ──→ ？？？ ← 这一格上游没做，本卡补
```

README 的原话：一个声明 `engines.dsh: 0.2.1-rc.2` 的插件，在 `0.2.1-rc.3` 上"stays in `bundles` and keeps loading … with no warning anywhere in the UI"。

> **抄这条判断**：**"装的时候检查"与"装之后复查"是两条不同的门**。绝大多数包管理器只做前者——所以"装完就坏"永远有市场。

### 1.2 它为什么不是"又一个 doctor"

同赛道有一整排 `dsh-doctor` / `dsh-plugin-doctor` / `dsh-plugin-clinic` / `dsh-sentinel-scanner`（见 [`BACKLOG`](../BACKLOG.md) §2）。分界线只有一条：

| 只读诊断 | 本卡 |
|---|---|
| 读声明，报"可能不兼容" | **在一次性 home 里真启动一次**，再决定 |
| 告诉你哪里可能坏 | 告诉你**能不能救**；能救就写一条可撤销的豁免 |

README 举了三个实测例子（`0.2.1-rc.4` 上）来说明"静态检查会误报"：

| 插件 | 声明 | 隔离里真启动 |
|---|---|---|
| `@nanmicoder/dsh-agent-teams@0.1.27` | ❌ 被拒 | ✅ 94 个入口全部激活 |
| `dsh-find-plugin@0.4.0` | ❌ 被拒 | ✅ 正常运行 |
| `@feng0531/dsh-vcs@0.4.10` | ❌ 被拒 | ❌ 等一个宿主不再提供的服务 |

前两个是静态检查会误杀的；第三个是"豁免了会真出事"的——**所以预演必须存在**。

## 2. 机制（可照抄的部分）

### 2.1 四层，不是一个检查器

| # | 层 | 做什么 | 在哪跑 |
|---|---|---|---|
| 1 | **Detect** | 扫全部已装插件，逐条比对"声明" vs "实跑版本" | 你的机器 |
| 2 | **Verify** | 在被拒插件的一次性 home 里：开豁免 → 安装 → 启动 → 检查每个入口都激活 | **隔离、可丢弃** |
| 3 | **Repair** | 预演启动成功 → 往你的 profile 写**一条**官方豁免，记录、一键撤销 | 你的 profile |
| 4 | **Escalate** | 预演失败 → 什么都不改；两个选项：关掉，或生成 brief（先查上游是否已有报告） | 你决定 |

> **第 2 层是它存在的理由**（README 原话："Without it, layer 3 is a guess."）。

### 2.2 顺序即安全

```text
发现被拒插件
  ↓
一次性 home 里预演：开豁免 → 真启动        ← 你的 profile 完全没动
  ├─ 能启动 → 代码没问题，只是声明旧了
  │    → 确认（明确写出要写什么、可撤销、且不等于官方支持）
  │    → 写一条豁免；记录；盯上游发版
  └─ 起不来 → 真的不兼容，豁免也没用
       → 什么都不改，如实说
       → 两个选项：关掉 / 生成 brief
```

> **反过来做会怎样**：先写豁免再测试——门禁从此不再对这条插件报警，而它可能启动到一半就崩。**"放行"和"证明能跑"必须是同一个动作的两面。**

### 2.3 预演的隔离语义

- **一次性 `DSH_HOME`**：豁免只开在这份临时 home 里；
- 安装、启动、检查入口激活都在里面完成；
- 30–60 秒，期间**不改你的配置**；
- 结论只有两种：全部入口激活 / 没起来。

> 抄的时候注意：预演的成本是"一次完整启动"，所以它必须是**用户点一下才跑**的动作（按钮："Check whether it can be saved"），不能每次扫描都自动跑。

### 2.4 豁免：一条数据 + 三个约束

| 约束 | 做法 |
|---|---|
| 用官方机制 | 宿主自己的 `allow-version` 豁免，落在 `compatibility.json` |
| 可撤销 | 撤销恢复**原来的值**（不是删掉整条） |
| 不等于支持 | 临时豁免只证明 base-only loader 能激活；不代表真实 web/desktop profile 能启动或功能可用 |
| 会过期 | 上游发版后，记录提醒你**撤销并升级** |

> **这条最值得抄**：修复动作要写成**结构化的、可枚举的、可撤销的记录**，而不是一次性的"我已经帮你改好了"。

### 2.5 宿主起不来时：把救生路径放在宿主体外

设置页救不了"DSH 起不来"——它自己就跑在 DSH 里。所以有三个**完全在宿主体外**的命令：

```sh
dsh-plugin-health boot diagnose --profile desktop   # 先读宿主自己的崩溃报告，再做静态检查
dsh-plugin-health boot safe     --profile desktop --apply   # 把所有第三方入口禁用，让 DSH 先起来
dsh-plugin-health boot restore  --profile desktop --apply   # 罪魁修好后，只撤销自己加的那批
```

四条设计纪律：

1. `boot diagnose` **优先读宿主崩溃日志**（`%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-*.log`）——它会直接点名出问题的包；CLI 自己只往 stderr 打，磁盘上什么都没留。
2. `boot safe` **只追加 `disabled: true` overlay**：不删文件、不改插件、不碰宿主条目、**也从不把自己禁掉**（否则解释问题的面板也没了）。
3. `boot restore` **只移除自己加的条目**，用户自己写的 patch 原样保留。
4. 两个命令**默认 dry-run**，要加 `--apply` 才写。

> **抄这条**：救生工具的第一职责是"可解释"，第二才是"能修"。**能把自己关掉的救生工具不是救生工具。**

### 2.6 它真的抓到过东西

README 给了一条可回读的影响力证据（不是形容词）：

- 扫 top 120 插件跨宿主升级：**5 个**在 `rc.2` 能加载、在 `rc.3` 被拒；
- 逐个提了报告，维护者动手；**5 → 1**（4 个已发修复，核验于 2026-10-26）；
- 其中 `Anionex/dsh-vision-toolkit`（906★）的 issue #178 直接引用了这次扫描，修复以 `0.1.48` 发布。

> 这条是本卡最重要的 `[OBS]`：**"兼容检查"本身可以是一个有影响力的产品**——因为它替下游省下了"升级后逐个试"的成本。

## 3. 体验

### 3.1 首次使用逐屏

| 时刻 | 看到 | 设计 |
|---|---|---|
| 装 | 两种：全局 CLI（Node 20+）或装进 profile（只加一个只读工具） | 同一份代码两种交付，不强迫二选一 |
| 打开设置 | 多一个 `Plugin health` 段（中文 `插件健康`，跟宿主语言走） | 命名用用户词，不用内部术语 |
| 一切正常 | **什么都不显示** | 默认值：不打扰 |
| 有问题 | 账号菜单上方一条 `插件有 N 个问题` → 跳转 | 只有一个入口，不做红点雨 |
| 每个问题 | 大白话 + 一个具体下一步；首行给结论（`可以放心用` / `有问题建议处理`） | 新手不读 CLI 文档也能动 |
| 点修复 | 「Check whether it can be saved」→ 30–60 s 预演 → 确认页**重述要写什么**、可撤销、非官方支持 | 写前把话说全 |
| 预演失败 | **没有豁免按钮**，只有两个诚实选项 | 不做"强行修复" |
| 之后 | 每条豁免单列、带撤销；上游发版后被标记 | 修复有生命周期 |

### 3.2 三处值得抄的措辞

- "**A temporary exemption means the gate lets it through — not that it is supported.**"
- "**If nothing is wrong, nothing is shown.**"
- "**We only prove it boots in isolation; whether every feature works is still on you to observe.**"

> 三句都在做同一件事：**把能力的边界说在用户点按钮之前**。

### 3.3 模型看到的

- 装进 profile 时，它只增加一个**只读** `plugin_health` 工具（报告缺 bundle、坏包目录、patch 残留、代理/registry 配置、profile 漂移、不兼容插件）。
- `plugin_health` 这个工具名与输入 schema 在 1.x 内冻结（只增字段）——**给 agent 用的接口也当契约维护**。

## 4. 证据与边界

| 口径 | 值（2026-10-31） |
|---|---|
| ★ / forks / issues | 4 / 0 / 0（GitHub API） |
| npm 近 30 天 | 4,377（含 CI 与镜像） |
| npm 版本 | `1.1.0` |
| 目录条目 | `data/plugins/EasonMWS__dsh-plugin-health.yml`（`dev`） |
| 兼容声明 | `engines.dsh: >=0.1.0-rc.6 <0.3.0-0`（范围，不是枚举） |

**为什么它过门槛**：npm 4,377 ≥ 2,000（★ 只有 4，按插件侧门槛的 npm 一条成立）。这是本线**第一张只靠 npm 过门槛**的卡——理由写在 §4 的偏差里。

**已知偏差**：

- ★ 4 说明它**还没有社区声量**；下载高更可能是"被装进别的发行版/被 CI 拉起"。**不要把 4,377 当成 4,377 个用户。**
- 目录条目的描述是旧的（"只读诊断工具"），与 README v1.1 的修复能力不符——**引用目录描述会低估它**。
- 源码已核：预演是临时 home + base-only profile，不复制/软链真实 profile；但它会执行被测插件安装/启动、继承环境、runs 默认保留，且可能在真实 home 写宿主缓存。
- 判据细节：`runs` 只看 `runtime.details.ok`（不看 `runtime.ok`）；`broken` 还覆盖 worker 超时/崩溃、缺 profile-boot、宿主侧故障；激活审计跳过 `disabled` 行，而宿主 preflight 判别不兼容时正是把行置 disabled，故可能误判。
- `rehearse` 的 `runtimeVersion` 未传入 smoke，也无“预演宿主==写入版本”校验；缓存旧宿主 + 新请求会产生“证明旧、写入新”。
- 豁免 writer 不是 DSH 官方 writer：compatibility.json 写入无锁/原子 rename/备份；undo 在 previous 为 null 时删整键；grant 与账本之间崩溃会留下不可撤销的孤儿豁免。
- `boot safe` 只枚举 profile 自己的 `cordis.patch.yml`；默认 profile 该文件为 `[]`（bundle 行来自 bundle 层），在 bundle-only profile 上可能什么都不禁用，且无匹配时写无 id 的 overlay 会被 DSH 跳过。
- 1.0.x 有安全通告（GHSA-vj8q-543v-9hw5）；引用旧版本行为时先看版本。

## 5. 可迁移洞察

| 触发问题 | 可迁移洞察 | 机制依据 | 为什么有效 / 代价 | 移植时改什么 | 成立边界 | 抄错后果 |
|---|---|---|---|---|---|---|
| 升级后插件被静默拒载 | 把“装后复查”做成独立门：扫 bundles/dependencies/patch insert，声明范围 vs 实跑版本。 | `[DOC][SRC-TARGET]` detect 层；`[SRC-DSH]` allow-version 豁免机制。 | 把安装期检查补到运行期；代价是要枚举所有装载来源。 | 定义声明来源、实跑版本来源与去重规则。 | 扫描“装着什么”不等于验证运行。 | 只看安装时检查 → 升级即坏且无提示。 |
| 静态判定误杀/漏判 | 在一次性 home 里真启动再下结论，而不是只读 manifest。 | `[SRC-TARGET]` `runRuntimeSmoke`：mkdtemp home、`health-smoke` profile、`runProfile` boot、遍历 loader entries。 | 用真实 loader 判激活；代价是分钟级耗时与宿主依赖。 | 写清预演 profile 的 bundle 组成、超时和激活判据。 | **base-only**（`dsh-base`）而非用户 web/desktop bundle；base 无 `webServer`，需 webServer 的插件会误判 broken；反之冲突也看不到。 | 把“预演通过”当“你的 profile 能用” → 放行后仍崩或误杀。 |
| 修复写入不可逆 | 只写一条宿主支持的豁免，记录原值，提供 undo；上游修好提醒撤销。 | `[SRC-TARGET]` allow-version 写 compatibility.json 单条；undo 恢复原值。 | 可撤销、可审计；代价是要跟随上游版本提醒撤销。 | 定义写入键、并发写、原值不存在时的恢复语义。 | 豁免只证明能启动，不证明功能；临时豁免只在临时 home。 | 直接改 bundle/patch → 用户无法复原或放行会崩的插件。 |
| 预演失败仍想“修” | 失败就什么都不改，只给“关掉/生成 brief”两个出口。 | `[DOC]` UI 无豁免按钮；`[SRC-TARGET]` 判 ok=false 时不给 repair。 | 守住“未证明不放行”；代价是用户要自己处理。 | brief 要可直接交给 agent，包含路径/版本/失败原因。 | 若预演环境本身不代表真实 profile，失败也可能是假阴性。 | 强行豁免 → 下一次启动仍失败，救生路径失效。 |
| 顺序错把门禁废掉 | 把“先预演后写入”写成强制顺序，而不是 UI 建议。 | `[SRC-TARGET]` 先 allow-version/add 到临时 home、boot 校验，再写真实 profile。 | 顺序即安全属性；代价是失败路径也要清理临时状态。 | 用状态机/事务记录保证写入在验证之后。 | 本次未运行验证真实顺序；runs 默认保留、无自动清理。 | 先写豁免后测试 → 门禁形同虚设。 |
| 宿主起不来时无处救 | 在宿主体外提供 CLI：diagnose/safe/restore；safe 只追加 `disabled: true` overlay，不删文件、不碰用户 patch、不禁自己。 | `[SRC-TARGET]` bin 命令与 overlay；`[DOC]` 崩溃日志路径。 | 救生工具不依赖坏宿主；代价是 OS 路径/权限差异。 | 定义 overlay 形状、dry-run 默认、日志解析与回退。 | 只对能定位到宿主安装的场景；Windows 祖先孤儿检测缺失。 | 救生工具自己装在宿主里 → 一起死；或删文件式修复不可回退。 |
| 预演“隔离”被误当沙箱 | 明确预演会执行被测插件安装/启动、以用户权限运行、继承环境、runs 保留；不是安全沙箱。 | `[DOC]` SECURITY 明说；`[SRC-TARGET]` 无复制/软链真实 profile，但可能把宿主 npm-install 到真实 home 的 `.plugin-health/host`。 | 用户知道风险边界；代价是恶意插件仍可访问用户环境。 | 在 UI 首次运行前展示“这不是沙箱”，提供 opt-in 与清理命令。 | 无自动清理；真实 home 的 host 缓存写入发生在 verdict 前。 | 把“隔离”当安全边界 → 用户在不信任插件上运行预演。 |
| 给 agent 的接口频繁变 | 工具名/schema 在 1.x 冻结，版本策略写进 README。 | `[DOC]` 版本策略。 | 下游编排稳定；代价是升级要兼容旧字段。 | 定义 schema 版本与弃用窗口。 | 本卡未运行工具接口。 | 改名/加必填 → 下游编排崩。 |
## 6. 已知失效边界与降级

| 触发 | 行为 |
|---|---|
| 预演起不来 | 不给豁免按钮，只给"关掉 / 生成 brief" |
| 宿主完全起不来 | 用 `boot diagnose/safe/restore`（宿主体外）；默认 dry-run |
| 上游已有 issue | `boot`/上报流程先查重，避免重复刷 issue |
| `engines.dsh` 是范围 | 宿主大版本升级（如 0.3.0）需发新版本扩范围——已知的过期点 |
| 全都没问题 | 不添加任何徽章/横幅/侧栏入口 |
| 写路由被本机其他进程访问 | 回环即边界；control key 由 status 端点下发的旧问题已在 1.1.0 修 |
