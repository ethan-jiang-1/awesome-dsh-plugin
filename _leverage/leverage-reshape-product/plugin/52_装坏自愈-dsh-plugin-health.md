## 0. 一页速览(想抄的人只看这 20 行)

| 问题 | 它的答案 | 可抄性 |
|---|---|---|
| 它补的是什么缺口 | **DSH 拦新装，不复查已装**：宿主升级后，声明旧范围的插件继续加载、界面无任何提示 | ✅ 这是所有"装完就坏"问题的根 |
| 第一层 | **Detect**：扫全部已装插件——bundles、`dependencies`、`cordis.patch.yml` 的 insert（含嵌套）、`node_modules`；逐条比对声明范围与实跑版本 | ✅ 扫"实际装着什么"，不是扫样本 |
| 第二层 | **Verify**：在一次性的 `DSH_HOME` 里给它开豁免、装上、**真启动**、检查入口是否全部激活 | ✅✅ 全卡核心 |
| 第三层 | **Repair**：预演能启动 → 往**你的** profile 写一条官方 `allow-version` 豁免；有记录、一键撤销 | ✅ 写最小、可逆 |
| 第四层 | **Escalate**：预演起不来 → 什么都不改，给两个真选项：关掉它，或生成一份交给 agent 的 brief（先查上游有没有报告） | ✅ 不假装能修 |
| 顺序为什么重要 | **先测试再豁免**；反过来 = 你放行了一个还没证明能跑的东西，而门禁从此不再提醒 | ✅✅ 这是安全属性 |
| 宿主起不来怎么办 | CLI **在宿主体外**跑：`boot diagnose` 读崩溃日志、`boot safe --apply` 追加禁用 overlay、`boot restore --apply` 只撤自己加的 | ✅ 救生路径必须离开宿主 |
| 会不会打扰 | **没问题就什么都不显示**：无徽章、无横幅、无侧栏入口；有问题才在账号菜单上方冒一条 | ✅ 自愈类产品的默认值 |
| 豁免长什么样 | 宿主自己 `compatibility.json` 里的一条；撤销时**恢复原来的值** | ✅ 用官方机制，不自造 |
| 已知安全事 | 1.1.0 修了 1.0.2 的 7 个问题（含一个 high）：写路由的 control key 曾由未认证的 status 端点下发；**回环即边界** | ⚠️ 抄之前先读它的信任边界 |

## 1. 它在产品里的位置

| 七层 | 动作 | 说明 |
|---|---|---|
| **7 分发** | 安装/升级之后的兼容与修复 | 它不装插件，管"装完了之后还活着吗" |
| 3 槽位 | 设置里的 `Plugin health` 段 + 条件出现的告警条 | 平时不可见 |
| 6 首启 | 升级宿主前的自检（"先跑一次检查再升级"） | 把"首启"前移到"升级前" |

### 1.1 它回答的是「升级之后」这一格

`51_分发与救生页` 处理的是"**起不来**"；这一张处理的是"**起得来，但某个插件已经不该被加载**"——更隐蔽的一格：

```text
装新插件 ──→ 宿主做兼容检查 ──→ 拒绝 / 放行
             （这一格上游做了）
已装插件 ──→ 宿主升级 ──→ ？？？ ← 这一格上游没做，本卡补
```

README 的原话：一个声明 `engines.dsh: 0.2.1-rc.2` 的插件，在 `0.2.1-rc.3` 上"stays in `bundles` and keeps loading … with no warning anywhere in the UI"。

> **抄这条判断**：**"装的时候检查"与"装之后复查"是两条不同的门**。绝大多数包管理器只做前者——所以"装完就坏"永远有市场。

### 1.2 它为什么不是"又一个 doctor"

同赛道有一整排 `dsh-doctor` / `dsh-plugin-doctor` / `dsh-plugin-clinic` / `dsh-sentinel-scanner`（见 [`BACKLOG`](../BACKLOG.md) §2）。分界线只有一条：

| 只读诊断 | 本卡 |
|---|---|
| 读声明，报"可能不兼容" | **在一次性 home 里真启动一次**，再决定 |
| 告诉你哪里可能坏 | 告诉你**能不能救**；能救就写一条可撤销的豁免 |

README 举了三个实测例子（`0.2.1-rc.4` 上）来说明"静态检查会误报"：

| 插件 | 声明 | 隔离里真启动 |
|---|---|---|
| `@nanmicoder/dsh-agent-teams@0.1.27` | ❌ 被拒 | ✅ 94 个入口全部激活 |
| `dsh-find-plugin@0.4.0` | ❌ 被拒 | ✅ 正常运行 |
| `@feng0531/dsh-vcs@0.4.10` | ❌ 被拒 | ❌ 等一个宿主不再提供的服务 |

前两个是静态检查会误杀的；第三个是"豁免了会真出事"的——**所以预演必须存在**。

## 2. 机制（可照抄的部分）

### 2.1 四层，不是一个检查器

| # | 层 | 做什么 | 在哪跑 |
|---|---|---|---|
| 1 | **Detect** | 扫全部已装插件，逐条比对"声明" vs "实跑版本" | 你的机器 |
| 2 | **Verify** | 在被拒插件的一次性 home 里：开豁免 → 安装 → 启动 → 检查每个入口都激活 | **隔离、可丢弃** |
| 3 | **Repair** | 预演启动成功 → 往你的 profile 写**一条**官方豁免，记录、一键撤销 | 你的 profile |
| 4 | **Escalate** | 预演失败 → 什么都不改；两个选项：关掉，或生成 brief（先查上游是否已有报告） | 你决定 |

> **第 2 层是它存在的理由**（README 原话："Without it, layer 3 is a guess."）。

### 2.2 顺序即安全

```text
发现被拒插件
  ↓
一次性 home 里预演：开豁免 → 真启动        ← 你的 profile 完全没动
  ├─ 能启动 → 代码没问题，只是声明旧了
  │    → 确认（明确写出要写什么、可撤销、且不等于官方支持）
  │    → 写一条豁免；记录；盯上游发版
  └─ 起不来 → 真的不兼容，豁免也没用
       → 什么都不改，如实说
       → 两个选项：关掉 / 生成 brief
```

> **反过来做会怎样**：先写豁免再测试——门禁从此不再对这条插件报警，而它可能启动到一半就崩。**"放行"和"证明能跑"必须是同一个动作的两面。**

### 2.3 预演的隔离语义

- **一次性 `DSH_HOME`**：豁免只开在这份临时 home 里；
- 安装、启动、检查入口激活都在里面完成；
- 30–60 秒，期间**不改你的配置**；
- 结论只有两种：全部入口激活 / 没起来。

> 抄的时候注意：预演的成本是"一次完整启动"，所以它必须是**用户点一下才跑**的动作（按钮："Check whether it can be saved"），不能每次扫描都自动跑。

### 2.4 豁免：一条数据 + 三个约束

| 约束 | 做法 |
|---|---|
| 用官方机制 | 宿主自己的 `allow-version` 豁免，落在 `compatibility.json` |
| 可撤销 | 撤销恢复**原来的值**（不是删掉整条） |
| 不等于支持 | 确认页明写：临时豁免只证明"能启动"，不证明"每个功能都好用" |
| 会过期 | 上游发版后，记录提醒你**撤销并升级** |

> **这条最值得抄**：修复动作要写成**结构化的、可枚举的、可撤销的记录**，而不是一次性的"我已经帮你改好了"。

### 2.5 宿主起不来时：把救生路径放在宿主体外

设置页救不了"DSH 起不来"——它自己就跑在 DSH 里。所以有三个**完全在宿主体外**的命令：

```sh
dsh-plugin-health boot diagnose --profile desktop   # 先读宿主自己的崩溃报告，再做静态检查
dsh-plugin-health boot safe     --profile desktop --apply   # 把所有第三方入口禁用，让 DSH 先起来
dsh-plugin-health boot restore  --profile desktop --apply   # 罪魁修好后，只撤销自己加的那批
```

四条设计纪律：

1. `boot diagnose` **优先读宿主崩溃日志**（`%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-*.log`）——它会直接点名出问题的包；CLI 自己只往 stderr 打，磁盘上什么都没留。
2. `boot safe` **只追加 `disabled: true` overlay**：不删文件、不改插件、不碰宿主条目、**也从不把自己禁掉**（否则解释问题的面板也没了）。
3. `boot restore` **只移除自己加的条目**，用户自己写的 patch 原样保留。
4. 两个命令**默认 dry-run**，要加 `--apply` 才写。

> **抄这条**：救生工具的第一职责是"可解释"，第二才是"能修"。**能把自己关掉的救生工具不是救生工具。**

### 2.6 它真的抓到过东西

README 给了一条可回读的影响力证据（不是形容词）：

- 扫 top 120 插件跨宿主升级：**5 个**在 `rc.2` 能加载、在 `rc.3` 被拒；
- 逐个提了报告，维护者动手；**5 → 1**（4 个已发修复，核验于 2026-10-26）；
- 其中 `Anionex/dsh-vision-toolkit`（906★）的 issue #178 直接引用了这次扫描，修复以 `0.1.48` 发布。

> 这条是本卡最重要的 `[OBS]`：**"兼容检查"本身可以是一个有影响力的产品**——因为它替下游省下了"升级后逐个试"的成本。

## 3. 体验

### 3.1 首次使用逐屏

| 时刻 | 看到 | 设计 |
|---|---|---|
| 装 | 两种：全局 CLI（Node 20+）或装进 profile（只加一个只读工具） | 同一份代码两种交付，不强迫二选一 |
| 打开设置 | 多一个 `Plugin health` 段（中文 `插件健康`，跟宿主语言走） | 命名用用户词，不用内部术语 |
| 一切正常 | **什么都不显示** | 默认值：不打扰 |
| 有问题 | 账号菜单上方一条 `插件有 N 个问题` → 跳转 | 只有一个入口，不做红点雨 |
| 每个问题 | 大白话 + 一个具体下一步；首行给结论（`可以放心用` / `有问题建议处理`） | 新手不读 CLI 文档也能动 |
| 点修复 | 「Check whether it can be saved」→ 30–60 s 预演 → 确认页**重述要写什么**、可撤销、非官方支持 | 写前把话说全 |
| 预演失败 | **没有豁免按钮**，只有两个诚实选项 | 不做"强行修复" |
| 之后 | 每条豁免单列、带撤销；上游发版后被标记 | 修复有生命周期 |

### 3.2 三处值得抄的措辞

- "**A temporary exemption means the gate lets it through — not that it is supported.**"
- "**If nothing is wrong, nothing is shown.**"
- "**We only prove it boots in isolation; whether every feature works is still on you to observe.**"

> 三句都在做同一件事：**把能力的边界说在用户点按钮之前**。

### 3.3 模型看到的

- 装进 profile 时，它只增加一个**只读** `plugin_health` 工具（报告缺 bundle、坏包目录、patch 残留、代理/registry 配置、profile 漂移、不兼容插件）。
- `plugin_health` 这个工具名与输入 schema 在 1.x 内冻结（只增字段）——**给 agent 用的接口也当契约维护**。

## 5. 借鉴食谱表（本卡的产出物）

| 要解决的问题 | 照它的做法 | 你要改的地方 | 抄错的后果 |
|---|---|---|---|
| 升级后插件悄悄坏掉 | 先补"装之后复查"这条门：扫全部已装，比对声明 vs 实跑 | 声明从哪读、实跑版本从哪拿 | 只做安装时检查 → 升级即坏且无提示 |
| 静态检查误报 | **隔离里真启动一次**再下结论 | 隔离要一次性、可丢弃 | 直接报"不兼容" → 误杀好插件 |
| 修复写入不可逆 | **只写一条官方豁免；记录；一键撤销恢复原值** | 用宿主的机制，不自造配置 | 直接改 bundle 列表 → 用户无法复原 |
| 预演失败还想修 | **什么都不改**，给两个真选项（关掉 / 生成 brief） | brief 要能直接交给 agent | 强行豁免 → 放行一个会崩的插件 |
| 顺序错了 | **先测试，后写入** | 把"顺序"写进 UI 文案 | 先豁免后测试 → 门禁失效 |
| 宿主起不来 | **宿主体外的 CLI**：diagnose / safe / restore | 崩溃日志路径按宿主换 | 救生工具自己也在宿主里 → 一起死 |
| 救生要能解释 | `boot safe` 只追加 overlay、不删、不碰用户 patch、**不禁自己** | overlay 形状按宿主 | 删文件式修复 → 无法解释、无法回退 |
| 平时不打扰 | **没问题就什么都不显示** | 有问题的入口要唯一 | 常驻红点 → 用户学会无视 |
| 给 agent 的接口 | 工具名与 schema 在 1.x 内冻结 | 版本策略写进 README | 今天加字段明天改名 → 下游编排崩 |
| 上游修好后 | 记录提醒**撤销豁免并升级** | 需要盯上游发版 | 豁免永久留着 → 下次真的不兼容也放行 |

## 6. 失效条件与降级

| 触发 | 行为 |
|---|---|
| 预演起不来 | 不给豁免按钮，只给"关掉 / 生成 brief" |
| 宿主完全起不来 | 用 `boot diagnose/safe/restore`（宿主体外）；默认 dry-run |
| 上游已有 issue | `boot`/上报流程先查重，避免重复刷 issue |
| `engines.dsh` 是范围 | 宿主大版本升级（如 0.3.0）需发新版本扩范围——已知的过期点 |
| 全都没问题 | 不添加任何徽章/横幅/侧栏入口 |
| 写路由被本机其他进程访问 | 回环即边界；control key 由 status 端点下发的旧问题已在 1.1.0 修 |
