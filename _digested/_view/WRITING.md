# 领域册写作规范(view_xx 通用)

> 目的只有一个:**让第一次打开这本册的人,在 30 秒内判断"这事跟我有关吗、我该不该用、值不值",然后再决定要不要读技术细节。**
>
> 本文件管三件事:卡片顺序、领域册/子分类的结构、质量门。通用底线(数字可复现、时效标注、证据等级、八段契约)仍在 [`../AGENTS.md`](../AGENTS.md);校验器 `verify.mjs` 只保证形式,**内容质量靠本文件 + 人工复核**。

## 一、卡片:先场景,后机制

### 标准顺序(新卡强制)

| # | 小节 | 回答什么 | 建议长度 |
|---|------|----------|---------:|
| 1 | `## 它替谁解决什么问题` | 具体角色、在什么场景、现在的笨办法/痛点、为什么现在需要 | 12–18 行 |
| 2 | `## 适用面:谁该用、谁别用` | 适合 / 不适合 / 前置条件,三块写齐 | 10–16 行 |
| 3 | `## 业务价值` | 能算清的 / 只是预期,两档分开 | 10–16 行 |
| 4 | `## 一屏事实` | 可核对的表:条目/类目/自述/★/包形态/规模/commit/证据级 | 8–12 行 |
| 5 | `## 它到底是什么` | 机制拆解,不是自述转述 | 按复杂度 |
| 6 | `## 怎么接进 DSH` | profile/patch/依赖/注册点/权限边界 | 按复杂度 |
| 7 | `## 关键实现` | 文件结构 + 核心模块 + 数据流 | 按复杂度 |
| 8 | `## 为什么它突出` | **只用本插件自身证据**(扩散/声量/机制独特性) | 6–12 行 |
| 9 | `## 代价与边界` | 权限、外部依赖、失败模式、维护成本 | 10–20 行 |
| 10 | `## 可信度与复现` | 读了什么、没读什么、复现命令 | 6–15 行 |
| 11 | `## 待验证` | 还缺什么才能下判断 | 5–12 行 |

> 1–3 节是**给评估者的**,4–7 节是**给实现者的**,8–11 节是**给复核者的**。不要把 4–7 节搬到前面,也不要用 4 节的表格代替 1–3 节的叙述。

### 第 1 节怎么写

- 开头一句就是"谁 + 在什么情况下 + 疼在哪",不写"随着……的发展"。
- 角色要具体:Windows 团队、单仓库维护者、值班者、个人开发者、插件作者;不要写"用户"。
- 写清**现在的笨办法**(手动转述、翻日志、开第二个 profile、复制粘贴),以及它为什么不够。
- 不写"提升效率/赋能/一站式"这类词;写可观察的动作和次数。

### 第 2 节怎么写

三块缺一不可:

- **适合**:规模(单仓/单团队/个人)、OS、渠道、维护能力、已有 DSH 版本;
- **不适合**:明确写"多仓/强合规/不能接受 worker 以 OS 用户执行/没有维护者"等;
- **前置条件**:profile、`stateDir`、git/gh、npm/手工安装、宿主 rc 范围。

### 第 3 节怎么写

分成两档,不许混:

- **能算清的**:少一次人工转述、从 N 步安装降到 1 步、单条工单可见、npm 月下载/真实 issue/被复用次数;
- **只是预期**:更快、更少打扰、更容易审计——标"推断",不给数字。

不写 ROI、不写"节省 X 人天"除非有实测;星标、下载、依赖三种量纲分开(见 [`../AGENTS.md`](../AGENTS.md) §一)。

### 反模式(出现即打回)

- 第一屏是"一屏事实"表格,读者不知道这东西跟自己有什么关系;
- "适用面"写成功能列表,没有"不适合";
- "业务价值"全是形容词,没有一个可核对的动作或数字;
- 用 README 自述当机制证据;用星标当采用证据;用"应该/大概"代替未验证;
- 同一张卡里混用不同采样日期的数字而不标日期。

## 二、领域册 README:先读者,后目录

每本 `view_<领域>/README.md` 的前 3 屏固定:

1. **状态行**:已立/前沿、卡数、数据截止、上游基线;
2. **读者与价值**(10–15 行):谁该读、解决什么问题、适用面、业务价值;**再往下**才是"为什么单独一册 / 定义 / 快照";
3. **卡表**:按子分类列卡,带层/一句话/星标/链接;未立卡成员单独列。

图谱 `plugin-map.svg` 是导航,不是内容;图上的证据级必须与卡 frontmatter 一致。

## 三、子分类 README:定义、边界、成员、立卡条件

- 定义三条以内,必须能与相邻子分类划界;
- 成员表:条目、星标、一句话、卡链接(有卡);
- 立卡条件:默认门槛 + 本轮例外,写清为什么破例;
- 不复制卡内事实,只给"读哪张卡"。

## 四、质量门(人工复核 8 条)

1. 新读者只读 1–3 节 + 一屏事实,能否回答:为谁?何时用?何时别用?值多少?
2. "不适合"是否具体到场景,而不是"视情况而定"?
3. 业务价值是否分了"能算清/预期",且没有 ROI 神话?
4. 每个机制断言是否指向文件/行,而不是 README?
5. 影响力是否标明量纲(星标/下载/依赖)与日期?
6. 代价是否写了权限、升级、维护、失败模式?
7. "待验证"是否真的列出了缺的证据,而不是空话?
8. 卡与领域册/图谱/`_data` 是否一致(`node _digested/verify.mjs` + `view_data.py`)?

## 五、存量卡的回填策略

现有 `view_*` 的 40 张旧卡多数以"一屏事实"开头,不满足 1–3 节。**不要求一次性重写**,按以下顺序回填:

1. **锚卡优先**:better-sidebar、hindsight、openviking、ouroboros、treg、agent-teams、dsh-TUI、genui——这些是读者第一站;
2. **本轮被分析插件有新提交/扩散变化的卡**,改卡时顺手补 1–3 节;
3. **新卡强制**:自 0007 起新增卡必须含 1–3 节,否则不合并。

回填时保留原技术段,只在前面插入三节;不改变已有结论与证据。
