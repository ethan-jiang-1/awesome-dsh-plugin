# toolchain-meta — 工具链元层

> 本身不完成业务,但被其他工具依赖:门控、注册、编排工具。

## 成员(人工确认)

| 条目 | 星标 ⚠ | 说明 |
|------|--------|------|
| Noob-stupid/dsh-plugin-gating-hub | 54 | 文件层升级门控:契约预检/备份回滚/启动失败隔离;无 `ctx.provide`,不是调用链锚([01](01-gating-hub.md) ★★★) |

## 立卡条件

被 ≥3 个第三方条目依赖,或成为某类工具的前置。

> 本轮破例:第三方依赖为 0;按"唯一一个把升级/回滚/隔离做成可执行门控的样本"立卡。门槛未变。

## 生长

**元层比单点工具更可能是潜在锚**:它不抢业务,但占据调用链的关键位置。星标低不代表影响小,判断看依赖数。

**但源码判读修正了"元层"的含义**:gating-hub 的元层是**权威意义上的,不是接口意义上的**——全插件没有 `ctx.provide`,第三方无法 `inject` 一个服务;它只挂在一条 `/plugin-console` HTTP 前缀下,靠改 profile 补丁、备份框架树、隔离启动失败行来"守门"。因此它不占据调用链的关键位置,也不被任何条目依赖;按两轴口径是**单点工具,不是锚**。这恰好说明子分类的定义("被其他工具依赖")必须用依赖证据验证,不能凭"它管插件"就默认。

**判断**:toolchain-meta 要出现真锚,得等到某个元层暴露稳定的服务键或协议,让第三方**接它**而不是**绕它**。现在还没有。
