# 组合包 · dsh-suite：策展、钉版本、注入默认值

> **状态**:`observed`(README 级核过) · **基线**:DSH `0.2.1-rc.3`(README 未给兼容矩阵,只写"安装后重启") · **读于**:2026-10-31
> **类**:`1` 壳与工作台 · **层**:3(槽位)+ 5(默认值)+ 7(分发) · **npm 近 30 天 8,230 次下载**(2026-09-30 ~ 10-29) · **★ 3**(GitHub API,2026-10-31)
> **一句话**:它不是"一个新产品",而是**把 18 个独立插件变成一件可交付物**:固定版本、统一默认配置、一条命令、整包更新——**组合包卖的是策展,不是界面**。
> **借鉴价值**:**① 组合包是"策展 + 钉死版本"的产品,不是把包堆在一起;② 共享默认配置用一条补丁注入,组件仍可单装;③ 扁平化(无 git 子依赖)让安装可复现;④ 更新走整包,何时重启由用户决定;⑤ 多 profile 支持:desktop 与 web 同一条命令换 profile 名。**

## 1. 它在产品里的位置

**七层坐标**:**3**(槽位:18 个组件各自的面板)+ **5**(默认值:共享配置补丁)+ **7**(分发:一条命令、整包更新)。

**它和 `dsh-web` / `codex-ui` 的区别**:

| | `dsh-web` | `codex-ui` | **本卡** |
|---|---|---|---|
| 卖什么 | 功能广度 + 自家商店 | 界面深度 + 伴侣管理 | **策展 + 默认值 + 版本钉死** |
| 界面是否统一 | 是(自有导航/主题) | 是(整屏重做) | **否**(18 个组件各长各的) |
| 组合方式 | 自研 20+ 包 | 单包六微内核 | **别人的 18 个包 + 一条组合补丁** |

**一句话**:它证明 profile 级产品还有第三种形态——**不重做界面,只做"装什么、默认怎么配、版本怎么锁"**。

## 2. 机制(可照抄)

### 2.1 组合补丁:一条命令注入共享默认

- 组合包本身是一个补丁层,把 18 个组件的**默认配置**一次写进去;
- 组件仍是独立包,可单独安装、单独配置;
- 目录条目明确:一条命令统一注入默认配置(办公流/媒体工坊/DevOps/通知/预设)。

> **照抄点**:组合包的价值在**默认值**,不在"多装几个包"。用户买的是"装完就能用",不是"装完还要配 18 次"。

### 2.2 版本钉死:可复现的共同加载

- "**固定组件版本**,便于复现安装与共同加载检查";
- 18 个组件之间有共同加载/冲突关系,版本漂移会让"上次能跑"变成"这次不行"。

> **照抄点**:聚合包的版本策略必须是**锁定**,不是 `^`。要升级就整包升,别让 18 个组件各自漂。

### 2.3 扁平化:无 git 子依赖

- 目录条目写明"扁平化设计,无 git 子依赖";
- 安装只走 npm,不 clone 子仓库。

> **照抄点**:聚合包每多一层 git 子依赖,安装失败率就多一档。**扁平是可用性,不是洁癖。**

### 2.4 多 profile:同一条命令,换名字

- 桌面版:`dsh plugin --profile desktop add …`(或插件面板);
- 网页版:把 `desktop` 换成 `web`;
- 装完**重启该 profile**。

> **照抄点**:profile 级产品的文档要写**两行命令**,而不是一句"装上即可"——`desktop` 与 `web` 的安装入口不同。

### 2.5 更新与重启:把决定权交回用户

- Suite 安装的组件**通过整包更新**;
- "是否安装及何时重启由你决定"。

> **照抄点**:组合包不要替用户自动更新 18 个组件。**整包更新 + 用户决定重启**是唯一可控的节奏。

## 3. 体验

- **第一次**:装包 → 重启 → 插件列表里出现 Suite 与 18 个组件(带鲸鱼娘图标)→ 只配要用的那几个。
- **日常**:邮件/日历/媒体各自工作;组件页底部能看更新。
- **升级**:整包更新,重启时机自己定。

## 5. 借鉴食谱

| 要解决的问题 | 照它的做法 | 要改的地方 | 抄错的后果 |
|---|---|---|---|
| 自己有一堆插件,想一次交付 | 组合包 + 一条命令 + 共享默认配置 | 默认值要**可覆盖**,不能写死 | 用户改一次就被还原 → 组合包变成骚扰 |
| 18 个包版本漂移 | **固定版本** + 整包更新 | 升级要能回滚 | 用 `^` 放任漂移 → "上次能跑"变"这次不行" |
| 安装太脆 | 扁平化,无 git 子依赖 | 组件之间不要互相 clone | 层层 git 子依赖 → 装失败率飙升 |
| 用户不知道装没装好 | 装完"检查 Suite 与组件加载情况" | 给出**一条可复制的自检命令** | 只说"装好了" → 实际半挂载 |
| 多 profile 装错地方 | 文档写 desktop / web 两行 | 写清"换 profile 名 + 重启该 profile" | 一句"装上即可" → 桌面用户照 CLI 装失败 |
| 自动更新打断用户 | 整包更新,重启由用户决定 | 提供更新日志 | 静默更新 18 个组件 → 用户不知道哪坏了 |

## 6. 失效条件与降级

- **组件依赖外部环境**:邮件/日历要账号,媒体要本机工具——组合包装完也可能"一个都用不了"。
- **版本锁定**:钉死版本意味着**上游安全修复不会自动进来**,要等整包升级。
- **界面不统一**:18 个组件各自的面板与风格,不构成"一个产品"的观感。
- **星标低**:社区可见度弱,issue 响应与长期维护是风险。
