## 1. 它在产品里的位置

| 层 | 与上游的关系 |
|---|---|
| 3 槽位 | **同层**:同样自建 `ctx.betterSidebar`,不换接缝 |
| 2 表层 | **取代**上游外壳(48px 顶栏 + 活动栏) |
| 4 身份(边际) | 多出 `terminal_*` 工具注入(可选项) |

**位置判断**:它做的是"**同一层、更深一个版本**"。这恰恰是最危险的位置——**它没有换接缝,所以没有独立的技术护城河;它只是把上游的代码改得更复杂,然后把版本钉死。**

---

## 2. 机制(反面:它到底做了什么导致失联)

### 2.1 三件独立的事,被绑成了一个死结

| # | 它做了什么 | 单独看是否合理 | 合起来的结果 |
|---|---|---|---|
| 1 | 深度重写外壳(顶栏 + 活动栏) | 合理:这是它的差异点 | 深度 ↑ → 上游一旦改布局就必然冲突 |
| 2 | 保留上游的 `ctx.betterSidebar` 接口 | 合理:生态兼容 | 接口不变 → **没有理由让第三方为它写适配** |
| 3 | peer 写 `>= 0.1.0-rc.6 < 0.2.0` | 合理:它只验证过 0.1.x | **① + ② 让第 3 条成为唯一结局**:深度改造无法快速跟进,而接口又不足以独立成生态 |

> **抄错的形状**:深度改造 + 兼容原有接口 + 钉死版本 = **一个必须被上游反复重建的镜像**。你不换接缝,就没人为你适配;你钉死版本,就没人能装你。

### 2.2 版本闸门到底怎么判的(可复现)

`[DSH]` `dsh-app-boot/lib/index.js:279-331`:

| 条件 | 判定 |
|---|---|
| 包声明了**自有** `engines.dsh` | **该范围单独决定,所有 peer 被忽略**(`:281-287`,注释 `:299-303`) |
| 未声明 `engines.dsh` | **每一个** `@deepseek-ai/dsh*` peer **都必须满足**(`:291`) |
| 通配键 `@deepseek-ai/*` | **被静默 `continue`**——等于没写 |
| 比较方式 | `semver.satisfies(..., { includePrerelease: true })`(`:276-278`) |
| 失败结果 | `ManagementFailure('incompatible-version', ...)`,**拒绝安装,什么都没装** |

它的 peer 是 `>= 0.1.0-rc.6 < 0.2.0`、没有 `engines.dsh` → 在 `0.2.1-rc.3` 上**上界不满足 → 安装期直接拒绝**。

> **注意上界这件事**:写 `>= X < Y` 与写 `>= X` 的差别不是"谨慎 vs 激进",而是"**在 Y 发布那天,我会不会被静默淘汰**"。`< Y` 是**主动设了一个死亡日期**,而且死因是"宿主升级",用户完全看不见。

### 2.3 为什么"功能更多"救不了它

| 它的优势 | 为什么无效 |
|---|---|
| 真 diff / 暂存提交 / 内嵌浏览器 / 真 shell | 都在**它自己的代码里**;`0.2.x` 用户根本装不上,看不到 |
| 保留了上游接口 | 生态插件的选择是"上游包名",不是"接口形状" |
| 同作者还发了第二个包 | 两份都要各自跟进上游,成本翻倍 |

> **判断规则**:fork 的生死不看"我比上游多什么",看"**上游升级时,我的追更成本是否低于用户重装我的成本**"。它显然不是——用户重装上游只需一条命令,而它要重写整个外壳。

## 3. 体验(站在用户的角度看这次失联)

| 时刻 | 用户遇到的事 | 用户的理解 |
|---|---|---|
| `0.1.x` 时代 | 装得上,功能齐全,体验甚至更好 | "这是更好的那个版本" |
| DSH 升到 `0.2.0` | `dsh plugin add` **报 peer 冲突**,什么都没装 | "是不是我命令写错了?" |
| 找到 README | 看到"针对 `0.1.1-rc.2` 验证" | "所以我得降级 DSH?" |
| 降级 DSH | 那 `0.2.x` 的其他插件又不能用了 | 死循环 |
| 最终 | **装上游**,失去那些额外功能 | "那个 fork 消失了" |

> 这张表是本卡真正的产品结论:**版本钉死的代价,不是"暂时没更新",而是"用户被推进一个不可能满足的两难"。**

## 5. 借鉴食谱表(本卡是"反食谱":六条禁令 + 三条正确替代)

| 禁止的形状 | 为什么错 | **正确替代** |
|---|---|---|
| peer 写上界 `< Y` | 主动设死亡日期;死因是"宿主升级",用户看不见 | 写 `engines.dsh: ">= X"` 只给下界 + **把验证挪到 CI 矩阵**(对照 [`协作`](../plugin/81_协作-dsh-agent-teams.md)) |
| 深度重写但保留上游接口 | 没有独立生态,又必须跟上游改 | 要么**换接缝**(自建服务 + 自己的 contract,对照 [`薄基座`](../plugin/11_薄基座-dock.md)),要么**别 fork**,把改造做成上游能接受的插件 |
| 用"功能更多"作为 fork 的理由 | 功能在**你的代码里**,上游一升级用户就看不到 | fork 的理由只能是"**上游拒绝这个方向**",且要有持续跟进上游的人力 |
| 把一次验证过的版本写成范围 | `0.1.1-rc.2` 验证过 ≠ `>= 0.1.0-rc.6 < 0.2.0` 都验证过 | 声明**已验证的那个点** + 推荐配对;范围要明确标注"未验证" |
| 以为"接口一样"就有生态 | 生态按**包名**选择,不按接口形状 | 想有生态就得拥有那个包名,或者拥有那个**服务名**且上游不提供 |
| 指望用户降级宿主 | 降级会砸掉别的插件 | 提供**迁移说明**:哪些功能在 0.2.x 有替代(对照上游 `0.28.x` 已补齐的 diff/暂存等) |

**判断清单(给任何准备 fork 的人)**:

1. 上游升级时,我**改一行还是重写一半**?后者别 fork。
2. 我的接口是否**独占一个服务名**?没有 → 我不会有生态。
3. 我有没有**持续跟进上游的人力**?没有 → 只能做一次性补丁。
4. 用户弃用我的成本,是否**低于我追更的成本**?不是 → 我注定被弃用。
5. 我能否把改造做成**上游可接受的插件**?能 → 就别 fork。
6. 我是否已经**写死了上界**?是 → 我知道自己哪天死吗?

## 6. 失效条件与降级

| 触发 | 行为 |
|---|---|
| DSH 升到 `0.2.0+` | peer 上界不满足 → **安装期拒绝**,什么都没装 |
| 用户强行 `allow-version` 豁免 | `[OPEN]` 未验证;外壳重构大概率对 `0.2.x` 的槽位/布局假设失效 |
| 用户降级 DSH 到 `0.1.x` | 能装,但**`0.2.x` 的其他插件全部不可用** |
| 上游继续演进 | 它**不会**自动获得 bug 修复与安全修补(它是独立代码库) |
| 生态插件想同时支持两者 | 需要**两套适配**(接口一样但包名/版本不同),实际无人做 → 被引仅 1 条 |
