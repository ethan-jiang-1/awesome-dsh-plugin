# local-store — 本地存储与检索

> 记忆自己落盘:SQLite、markdown、分层目录,不依赖外部服务。

## 定义

插件自带存储与检索,数据留在本地。判定标准:断网可用,数据路径可由用户检查。**注意"默认"二字**:有的插件默认本地、可选远端 provider;有的插件默认远端、clone 才本地,后者归 [host-backed](../host-backed/README.md)。

## 立卡条件

≥300 星,或被 ≥5 个条目引用存储格式。

> 本轮三张卡都未达 300 星(109/58/160),破例理由:一张是 41 340 行的框架 + 4 条硬依赖,一张把"服务 seam + 审批 + 审计 + 协议套件"做成了可执行契约,一张把"索引上限"做成了宿主级硬拒绝。门槛未变。

## 生长

本地存储的竞争力在**结构设计**(分层、审计、审批),不在星标。写卡时重点看:数据模型几层、写入是否可撤销、审计留痕在哪。这是最容易被"看起来都能做"掩盖差异的分支。

**读源码后的三条修正**:

- **"本地"不等于"纯自研存储"**。dsh-mnemon 的存储根与元数据归插件,但 SQLite schema、SQL 与向量检索都在外部 Go 程序 `mnemon` 里;默认 embedding 关闭,项目档案是词法检索。它的 4 条硬衍生接的正是"存储布局/provider SDK"这一层。
- **"审批门"不等于安全边界**。dsh-memento 的写路径确实过审批与审计,但 `service.store` 是公开属性,同进程内可绕过;它的价值是把写语义、审计格式和 22 例一致性套件一起定义,供第三方 Provider 实现——目前第三方采纳为 0。
- **"纯 markdown"是另一种极端**。engramory 没有工具、没有 MCP、没有依赖,整个适配层只做两件事:注入索引、拦截超限写入;索引由模型手写,唯一硬拒绝是 `ctx.tools.guard` 里的"既超限又变大"。它唯一的衍生者没有依赖它,而是照文档重写了另一套格式——**存储约定是可读的范本,不是可链接的接口**。

**判断**:本分支三张卡都是"机制上值得读、生态上未收敛";真正的收敛信号应看第三方是否开始接它们的存储布局或协议,而不是星标。
