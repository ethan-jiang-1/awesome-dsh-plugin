# 09 · 控制预算:七个样本为什么都收敛到三个动词

> **状态**:`observed` · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b` · **样本**:本域 02–08 七张卡的横向比较(每个样本的机制已在各自卡片给出来源)
> **坐标**:本域 02–08 七张卡的横向比较(每个样本的仓库与版本见各卡页头与域 README「样本坐标」表)
> **一句话**:防灾难不需要复杂策略,**需要的是把「判断」与「不可逆性」分开**。七个互不引用的实现最后都收敛到同一套词汇——`allow / ask / deny`、默认拒绝、单点不可推翻、判不了就拒绝——这不是抄袭,是**独立收敛**,因此比任何互引都更能说明这套词汇是对的。

## 1. 命题

> 控制复杂度不是靠「少写规则」压下来的,而是靠**把复杂度分配到四个互不干扰的预算**里:判断预算(每次决策能花多少算力)、打断预算(能问人几次)、状态预算(要记住多少东西)、解释预算(能对模型/人说清多少)。**任何一处超支,都会以「审批疲劳」「规则膨胀」「覆盖幻觉」中的一种形式暴露出来。** 而防灾难的最小充分集只有三件事:一个不可绕过的沙箱、一个针对不可逆动作的确定性否决、一个失败即拒绝的默认方向。

可证伪点:若能找到一个**没有**沙箱、**没有**确定性否决、仅靠模型判定与规则表就长期不出事故的实现,命题不成立。本域七个样本里没有这样的实现;唯一接近的(纯判定器)都自带硬拒层(02 卡)。

## 2. 杠杆点:七个样本各自只做一件事

| 卡 | 样本 | 它唯一做的事 | 主要花掉的预算 |
|---|---|---|---|
| 02 | `dsh-approval-gate` | 把人工确认折算成额度与规则 | **打断** |
| 03 | `dsh-auto-review` | 把「要不要问人」交给第二个模型 | **判断** |
| 04 | `dsh-danger-guard` | 在同步守卫里否决最便宜的那几类 | **判断**(近零) |
| 05 | `dsh-permission-rules` | 用有序 YAML 表达 allow/deny/ask + 进程出口代理 | **解释** |
| 06 | `dsh-defend` | 把检测挂到文本进模型之前 | **覆盖** |
| 07 | `dsh-workspace-only` / `workspace-folders` | 在沙箱之外补/放工作区边界 | **状态** |
| 08 | `dsh-plugin-sentinel` / `gating-hub` | 装前看形状、装后可回滚 | **可逆性** |

**七个样本没有一个是「全能」的,每一个都在某个预算上超支、在另一个上节省。** 这是本域最重要的结构事实:**安全能力不是叠加的,是置换的。**

## 3. 机制:八条从样本里长出来的设计律

### L1 先选缝,再写规则 —— 缝决定表达力(06)

`agent/pre-step` 能看见入站文本但**没有理由字段**;`tools/pre-execute` 能带原因、能 `ask`;`ctx.tools.guard` 不可推翻但**同步**;`approval/request` 能协商但**看不见动作细节**(只能看 reason 与 callId)。

> 想防「模型被说服」,只能挂 `pre-step`;想「解释为什么不行」,必须挂能带理由的缝;想「不可推翻」,只能用 guard。**三者不在同一条缝上,所以「全面防护」这句话在 DSH 里没有落点。**

### L2 至少有一处不可推翻(02、04)

`approval-gate` 的硬拒层写明「判定模型无权推翻」;`danger-guard` 的 `ctx.tools.guard` 是**单调**的,后续监听器无法把拒绝改回允许。

> 一个全部可协商的策略系统,等于没有策略系统——因为任何一层都能被下一层说情。**「不可推翻」不需要很多,一处就够,但必须有。**

### L3 判不了就拒绝,或者换档——不许借档(04、06、08)

`danger-guard` 的三处「判不了」全部指向拒绝或保守档,并且**明确不复用 workspace-write 档**(那档假设沙箱在场);`defend` 在版本不可解析时同样 fail closed;`sentinel` 把「不可审查」的文件计入 review 而不是 pass。

> 「没法判断」最常见的有害处理方式是**当成安全的**。三个样本各自独立地选择了「当成不安全」,这是收敛证据。

### L4 默认值必须点名失效方向(05、07、02)

`permission-rules` 的 `auto` 档在没有沙箱策略服务时回落 `allow-all`——这是**唯一的默认 fail-open 样本**,而它把这件事写在了 README 里。`workspace-only` 在无应答者时拒绝;`workspace-folders` 在原因前缀不匹配时退回询问。

> 默认值不是配置项,**是策略**。凡是默认「跟随另一个组件」的,必须点名那个组件缺席时会发生什么。

### L5 可逆性优于预测(08)

`gating-hub` 不去预测「哪个插件会坏」,而是**先建回滚点**;自动禁用只禁**有确证证据**的行,且框架行永不禁用。

> 安装面无法判定行为,但永远可以判定「能不能退回去」。**把预算从「预测」挪到「回滚」,是安装面唯一稳赚的交易。**

### L6 复杂度放进数据,不放进分支(02、05、08)

`approval-gate` 是一条**直线**管道,每层只有一个动作,没有组合条件;`permission-rules` 是**有序规则表**,首个命中胜出;`sentinel` 是**规则 + 权重 + 绝对阈值**。

> 三者都把「策略」外置成数据,把「引擎」压成几十行。**引擎里的 `if` 越多,新增策略时越可能改变旧策略的语义;数据里的行越多,只影响它自己。** 这是「控复杂度」最具体的一条工程结论。

### L7 区分「检查完」与「没检查完」(04、08)

`danger-guard` 的「零命中」结论要求子树被完整读完,截断就不给结论;`sentinel` 的超限文件标记为「不可审查」;`gating-hub` 用**闭包判据**替代「目录空不空」(误报 237 → 0)。

> 「我检查过了,没发现问题」这句话,只有在能同时回答「检查范围有多大」时才有意义。**没有覆盖率陈述的检测结果,是一种修辞。**

### L8 成本不对称决定默认值(03、04、07)

`auto-review` 的本地小模型基准:阈值 0.45 时 0/58 条破坏性命令被放行、3/33 条常规命令被放行;阈值降到 0.4 时 **`cat /etc/shadow` 通过**。`danger-guard` 的凭据拒绝**不做任何让位**,理由是「误拦一次让人去终端,漏一次泄露且很难发现」。`workspace-folders` 不自动批准 `bash`,因为「无法可靠判断命令会写哪里」。

> 默认值应当由**错误的相对代价**决定,而不是由「多数情况」决定。**在不可逆动作上,假阴性比假阳性贵一个数量级**——这句话应当写在每个安全插件的配置注释里。

## 4. 样本账本:控制预算的横向对照

| 样本 | 判断成本 | 打断次数 | 记住什么状态 | 可解释性 | 失效方向 | 覆盖边界 |
|---|---|---|---|---|---|---|
| 02 approval-gate | 中(每次越界一次判定) | **高→中**(额度折算) | 规则表 + 指纹 + diff 快照 | 高(字段化卡片) | 首挂转人工 / 阈值满 fail-open | 只覆盖沙箱越界请求 |
| 03 auto-review | **高**(每调用一次模型) | 低 | 熔断计数 + 60 s 判定缓存 | 中(拒绝理由注入) | 默认 rejected | 只认 `ai` 策略;`run_code` 外层不审 |
| 04 danger-guard | **近零**(同步谓词) | 低(多数是 deny) | 读取账本 + 基线水位 | 高(替代写法) | 判不了→拒绝/保守档 | 只覆盖工具调用 |
| 05 permission-rules | 低(规则匹配) | 由规则决定 | 规则链 + 代理状态 | **最高**(规则可读) | 建连失败 502 | 只覆盖子进程出口 |
| 06 defend | 低(自动机) | 中 | 环形缓冲(有界) | 低(pre-step 无理由) | 无应答者即最严 | 规则词汇可绕 |
| 07 workspace-only / folders | 低 | 中 / **零**(自动批准) | 会话白名单 / 工作区目录表 | 中 | 拒绝 / 退回询问 | 只覆盖工具层 |
| 08 sentinel / gating-hub | 低(静态) / 中(预检) | 一次性(报告) | 阈值 / 回滚点 / 快照 | 高(报告 + 恢复命令) | review / 不动 | 装前与装后,不覆盖运行期 |

**读法**:没有一行全优。`danger-guard` 判断成本最低但覆盖最窄;`permission-rules` 可解释性最高但**只管子进程**;`workspace-folders` 打断为零但**把边界写进了 JSON**。**选型问题不是「哪个最安全」,而是「你愿意让哪一项预算超支」。**

## 5. 最小充分集:如果只能装三样

```
1. 沙箱(官方)                 —— 提供不可绕过的底座,代价:只管文件
2. 一处确定性否决(不可推翻)   —— 挡住不可逆的那几类,代价:覆盖窄、会误报
3. 失败即拒绝的默认方向       —— 让缺席、超时、解析失败都落到「不行」
```

三样之外的一切——规则语言、第二模型、额度、审计、网关、回滚——都是**在某一项预算上做优化**。它们不是错的,但它们**不能替代**上面三样。反过来,本域没有一个样本是靠「第 4 样」防住灾难的。

**新增一个控制点之前,先回答七问**:

1. 它拦的是**不可逆动作**吗?如果不是,它大概不该用 deny。
2. 它的缝**能看见**需要的全部信息吗?看不见就别在那条缝上做这个判断。
3. 判不了时它落到哪?这个落点是**换档**还是**借档**?
4. 它要记住什么?这些状态**存在哪、谁清理、损坏时怎样**?
5. 它的默认值在**依赖缺席**时会怎样?
6. 拒绝时模型能看到**怎么改**吗?看不到就会重试。
7. 它的**覆盖率陈述**是什么?「检查完」与「没检查完」如何区分?

## 6. 体验

**人看到的**:七个样本给出七种打断形态——审批卡(02)、AI 审查折行(03)、拒绝文本(04)、被拦连接的诊断(05)、静默拒绝(06)、三键裁决卡 / 沉默自动批准(07)、分级报告 + 回滚按钮(08)。

**模型看到的**:几乎全部是**该次工具调用的错误结果**,而不是新的系统提示。DSH 的接缝设计把「拒绝」放在结果里,而不是放在上下文里——这带来一个副作用:**模型只能从失败中学习,不能从规则中学习**。官方的历史测量(见 01 卡)说,直接把限制写进提示会让模型干脆不尝试调用工具,所以这是**刻意的取舍**。

**这条取舍的代价应当被承认**:安全插件写得再好,模型也只能通过「撞墙」知道墙在哪。**墙越多,撞墙次数越多,长任务的成功率越低。** 控制预算最终是在「拦住多少」与「任务还能不能做完」之间分配。

## 7. 失败模式:复杂度失控的四种形态

| 形态 | 表现 | 本域样本里的对应 |
|---|---|---|
| **审批疲劳** | 用户开始无脑点同意,打断失去信息量 | 02 用额度折算缓解,代价是一处刻意的 fail-open |
| **规则膨胀** | 规则表长到没人敢删,旧规则与新规则互相覆盖 | 02 的 39 条规则 / 05 的 `maxRules` 上限 / 08 的绝对阈值 |
| **覆盖幻觉** | 把「我覆盖的那一块」说成整体 | 05 的代理不管宿主 fetch;06 的词汇可绕;07 只看工具层 |
| **自指风险** | 防线自身持有关键能力(读凭据 / 联网 / 起子进程) | 01 卡 §5:认证网关 46 条里 18 条读凭据、40 条联网 |

**四种形态有一条共同解法**:**把覆盖边界写成一句话,放在 README 的第一屏。** 本域做得最好的三个样本(04、05、08)都有一节标题叫「Known boundaries / 已知限制 / 安全边界」,而且内容具体到「哪一类输入抽不到」「哪个进程不走代理」「哪个判据对哪种失效形态免疫」。**这不是谦逊,是工程要求**:没有边界陈述的安全声称,无法被任何人复核。

## 8. 评估清单(给一个「控制预算」做审计用)

1. 它把复杂度放在**数据**还是**分支**里?新增一条策略会不会改变旧策略的语义?
2. 每层的动作是否**唯一**?有没有「A 且非 B 则 C」这类组合条件?
3. 有没有**一处**不可推翻?在哪?
4. 判不了的三种情形(超限、解析失败、身份未知)各自落到哪?
5. 依赖缺席(沙箱服务 / 审批应答者 / 网络 / 版本不可解析)时,默认值是什么?
6. 状态存在哪?会话级还是全局?损坏时是拒绝加载还是清空?
7. 拒绝文本里有没有「怎么改」?
8. 覆盖率陈述是否具体到「哪一类不算」?
9. 假阴性与假阳性的相对代价,写在配置注释里了吗?
10. 它自己用了它要防的能力吗?若用了,披露了吗?

## 9. 移植清单:从零做一个安全控制点时的八个决定

> 这一节是全域的**收口**。它不复述前面八条设计律,而是把它们变成**做决定时的顺序**——按 1→8 走完,你的控制点就既防得住灾难,又不会长成一个没人敢碰的策略引擎。

### 决定一:这个控制点必须存在的理由是什么?

先填这一行,填不出来就别做:

```
我防的是:<一个具体的、不可逆的后果>
它在什么条件下发生:<可复现)
如果没有我,系统现在会怎样:<官方沙箱/审批挡不住的那一段>
```

本域的正确答案长这样:*「防 `rm -rf ~` 先清空工作区再撞墙:因为沙箱是路径白名单,不提供原子性」*——**具体、可复现、且指出了官方机制为什么不够。**

反面:*「防各种危险操作」*——无法验收,也无法证明它值得存在。

### 决定二:强制点在哪条缝上?(查表)

| 你防的东西 | 缝 | 代价 |
|---|---|---|
| 恶意文本进模型 | `agent/pre-step` | 拒绝**无理由**,模型只会重试 |
| 具体工具调用 | `tools/pre-execute` | 可解释、可 `ask`,但可被后续监听器重排 |
| 绝不能放过的动作 | `ctx.tools.guard` | 同步,只能做便宜判断 |
| 要不要打扰人 | `approval/request` | 只看得到 reason 与 callId |
| 环境里没有这个维度 | 自建(代理 / 网关 / 包装层) | **覆盖率必然只是子集** |

**填这一行的产出是「我不覆盖什么」**:选了 `guard` 就是不覆盖「需要读盘才能判断」的;选了代理就是不覆盖「宿主自身的 fetch」。

### 决定三:撤掉它会发生什么?(默认值设计)

这一条决定成败。逐格填:

| 依赖缺席的情形 | 你的默认 |
|---|---|
| 审批应答者不存在 | ? |
| 判定模型超时 / 返回畸形 | ? |
| 配置解析失败 | ? |
| 版本无法判定 | ? |
| 沙箱状态读不到 | ? |
| 网络/上游不可达 | ? |

**合格的答案只有三种**:拒绝(fail-closed)、转向人(fail-through-human)、保留旧配置继续生效(fail-safe)。

**唯一需要额外论证的是 fail-open**,而且必须满足两个条件:① 放行范围被缩到「已经批准过的那个具体动作」;② 写明触发条件(`02` 卡是这个形态的唯一样本)。

> **反面教材清单(可直接当审查项)**:`Number(x)` 把解析失败变成第 0 项 / `fetch` 跟随重定向 / 超时被归类为业务错误 / 缓存键不含上下文 / 熔断后直接放行 / `auto` 档回落到 `allow-all`。

### 决定四:怎么被说服?(枚举表示)

**这一条只有一句话,但它值一个 CVE**:

> **裁决协议不要用整数索引。** 用字符串,或显式校验 `typeof`。并且让「解析不了」落到**拒绝**,而不是落到**第 0 项**。

配套三条(都来自 03 卡的真实修复):

- 辅助字段(置信度、理由)解析失败,**不得改变主裁决方向**;
- 只有 `risk + decision` 的合法组合被接受,其余一律 schema 失败 → 失败关闭;
- 审查者的推理**不进主对话**(否则模型会学着取悦它)。

### 决定五:动作表怎么组织?(数据而不是分支)

按 `02` 卡的八层模板落,每层一个动作、一个可否决属性。落地时守三条:

1. **顺序即策略**——不可推翻的层必须排第一,「危险词/围栏」必须早于白名单与学习;
2. **一层一个动作**——出现「A 且非 B 则 C」就拆层;
3. **可解释性用数据换**——新增策略 = 新增一行;改引擎最容易伤到旧策略。

### 决定六:它记住什么?(状态与边界)

三问:存在哪(会话日志 / 会话级文件 / 全局文件)?谁清理?**损坏时是拒绝加载还是清空**?

答案模板:**能进会话日志就不进文件;会话级状态用主会话 id 隔离;全局文件原子写 + 损坏时拒绝加载。**

再加一条硬边界:**任何「我检查过了」都必须能回答「检查了多大范围」**——超限、截断、不可读,一律不给「通过」结论。

### 决定七:拒绝时说什么?(模型与人的两份文本)

**给模型的**(这是它唯一的学习信号):

```
[原因]  哪条规则、哪个事实命中
[范围]  这次会动到什么
[怎么改] 替代写法,或「别重试,把原文贴给用户」
```

**给人的**:字段化,不是散文——操作 / 路径 / 影响 / 命令 / 原因,外加一句「本次授权覆盖什么」。

> 这两份文本合起来是**最便宜的一次复杂度腾挪**:说明写清楚了,你就不必为每个场景写一条规则。

### 决定八:怎么证明它有效?(基准与边界表)

| 必须产出 | 形式 | 反例 |
|---|---|---|
| 基准集 | N 条命令/输入,含最危险的那几类,进测试 | 「覆盖 OWASP 前 10」 |
| 覆盖率陈述 | 「这批 N 条里拦了 M 条,已知绕过 K 条」 | 「能有效防护」 |
| 边界表 | 每条:不判什么 + 为什么 + 当前裁决被哪个测试钉住 | 「本插件不适用所有场景」 |
| 自攻击面 | 用了它要防的能力吗?披露 | 不披露 |

**最后一条判据**:如果你的 README 里没有一个叫「已知边界 / Known boundaries」的章节,那本卡的结论是——**你还没有完成设计,只是完成了实现。**

### 附:一次自检(30 秒)

拿你自己的控制点,回答这三个问题:

1. **不带任何配置装上去,它挡得住什么?**(零配置防护水平——见 06 卡 §9.4,这是采用率的实际决定因素)
2. **把它的一个依赖拔掉,它会怎么失败?**(默认值)
3. **它的 README 第 5 屏之后,有没有人能照着复核它的覆盖范围?**(可验证性)

三个都答得出来,它就是一个能长期活着的控制点;答不出来,它大概率会在三个月后变成「没人敢删也不敢信」的那一层。

## 10. 开放问题

- [ ] 七个样本按名互引为 **0**(`census.py --probe` 对每个包名逐一检索,命中均为 0 或仅命中自身)。这支持「独立收敛」的解释,但也意味着**生态没有交叉验证**:没有人写「我用 A 补 B 的洞」。
- [ ] 三动词词汇(`allow / ask / deny`)是否足够表达「有条件放行」(例如「允许写,但必须先读」)?04 的事实闸门用 `deny` + 证据变相实现了它——这是否说明三动词不够,还是说明**条件应当被编码成证据而不是动词**?
- [ ] 控制预算有没有**可测量的总量**?比如「每 100 次工具调用最多 5 次打断」——若有,它可以成为产品默认值的依据(归 `lever-reshape-product`),但测量方法归本域。
- [ ] 本域七个样本中,只有 08 的样本量级(15,638/月)与「安全」的普遍需求匹配;其余在 2k–7k。**是安全插件整体小众,还是最有效的做法恰好不被需要?**
- [ ] 决定八的「基准集」在生态里几乎没有公开版本。若本域要更进一步,下一步应当**自己构造一个小基准集**并拿八个样本跑一遍——那会把「独立收敛」从观察变成测量。
