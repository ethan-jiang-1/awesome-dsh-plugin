# 07 · 沙箱之外:同一个缺口的两种利用——收紧与放松

> **状态**:`observed` · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b` · **样本**:`DevilSpiderX/dsh-workspace-only-plugin`(回读 README/配置)+ `Fleey/dsh-workspace-folders`(回读 README + `src/approval.ts` 源码)
> **坐标**:`DevilSpiderX/dsh-workspace-only-plugin`(仓库 **0.2.6**,npm 未发布)+ `Fleey/dsh-workspace-folders`(仓库 **0.1.0**,npm 未发布)
> **一句话**:官方沙箱每会话只有一个工作区根,而「额外可写根」不在策略词汇里。同一个缺口,一个插件往里收(任何模式下越界都要裁决),一个往外放(读写目录的 `write`/`edit` **自动批准沙箱提权**)。两者都不是错的——**它们共同证明:缺一块策略词汇,既让收紧变贵,也让放松变得极其便宜。**

## 1. 命题

> 当环境缺少某个策略维度时,生态会围绕这个缺口长出两种插件:补丁型(自己实现缺失的策略)与豁免型(替用户跳过缺失策略带来的确认)。**两者的实现成本不对称**——补丁要造拒绝路径,豁免只要答一个 `allowed-once`。因此缺口的自然演化方向是**变松**,不是变紧。

可证伪点:若某生态里补丁型插件数量与豁免型相当、且被同等采用,命题需限定「在缺少强制点的维度上」。

## 2. 杠杆点

| 样本 | 位置 | 阶梯级 | 它在这一层做什么 |
|---|---|---|---|
| workspace-only | 工具前置 + 审批应答(对所有文件类工具,含 `bash`/`pwsh`) | 4(policy) | 在**任何沙箱模式**下把访问限制在会话工作区内;越界弹三键卡 |
| workspace-folders | `tools/execute` 记录 + `approval/request` 应答 | 4(policy) | 对「读写目录」内的 `write`/`edit` **预先批准**沙箱提权 |
| 两者共同依赖 | 沙箱提权的请求形状:`sandbox_permissions` + 固定 reason 前缀 | 4(policy) | 提权不是「授予权限」,而是**一次可被审批的请求** |

**强制点可命名**:workspace-only 在审批应答上拒绝(默认 120 s 超时即拒绝);workspace-folders 在审批应答上 `allowed-once`,且**只对匹配的那一次调用**。

## 3. 机制

### 3.1 提权的真实形状 `[CAT]`

`workspace-folders` 的 `src/approval.ts` 把机制写得比任何文档都清楚:

> 在 `workspace-write` 下,文件沙箱只允许 `write`/`edit` 修改会话工作区。越界调用会带 `sandbox_permissions: "danger-full-access"` 重试,工具在运行前询问 `ctx.approval`。本模块在调用的派发生命周期内记住目标(经 `tools/execute`),当规范化后的目标位于一个读写目录下时,用 `allowed-once` 回答匹配的 `approval/request`。**其余全部委托给下一个应答者**,用户仍然决定。无论哪种情况,审批服务都会把问题与决定记进会话日志。

它的匹配条件有五条,少一条就不答:

| 条件 | 写法 | 防的是什么 |
|---|---|---|
| 调用身份 | `request.callId` 命中被跟踪的那次调用 | 别处的提权请求被顺手批准 |
| 同一 agent | `call.agent !== request.agent` → 委托 | 子代理冒用父级批准 |
| 同一工具 | `call.toolName !== request.toolName` → 委托 | 用 `write` 的批准去跑 `bash` |
| 原因前缀 | `request.reason` 必须以 `escalate sandbox to danger-full-access:` 开头 | 把**别的**审批请求误判成提权 |
| 目标与模式 | 规范化目标落在某读写目录内,**且**当前沙箱模式允许该目录 | 只读目录 / 只读会话 / 完全访问下都不该走这条路 |

结果就是一张很干净的语义表:

| 当前模式 | 目录权限 | 行为 |
|---|---|---|
| `workspace-write` | 读-写 | 自动 `allowed-once` |
| `workspace-write` | 只读 | 仍询问 |
| 会话「只读」模式 | 任意 | 不自动批准 |
| 完全访问 | 任意 | 本就不受限(仍记录) |
| 任意 | 终端命令 `bash` 写这些目录 | **仍询问**——「插件无法可靠判断命令会写哪里」 |

**最后一行是最重要的边界声明**:它没有把「目录在白名单里」推广成「任何能写该目录的动作都放行」。**只放行它能看清的那一种调用。** 这正是本域反复出现的正确姿势:宁可不覆盖,也不假装覆盖。

### 3.2 反向:任何模式下都重新围栏 `[CAT]`

`workspace-only` 的规则更硬:

- 拦截**任何沙箱模式**下越界的 `read` / `write` / `edit` / `read_image` / `glob` / `grep` / `bash` / `pwsh`,**包括 Full access**;
- 越界弹**三键卡**:仅此一次 / 总是允许该目录 / 拒绝;
- **默认拒绝**:120 s 超时按拒绝处理;没有应答者时**失败关闭**;
- 每会话有一个档位选择器(仅工作区内 / 工作区外只读 / 完全放开),**写进会话日志**,并作为可继承快照传给子代理;
- 即使 Full access 下,**敏感路径模式仍然询问**;
- `deny` 规则优先级最高;
- **重复/畸形的升权请求故意不跳过**——防「重复升权绕过」;
- 白名单按会话隔离:`<DSH_HOME>/dsh-workspace-only-plugin/sessions/<主会话id>/whitelist.json`;
- 子代理并发请求**排队**处理,不并发弹卡。

**第 7 条值得单独记**:绝大多数审批实现在收到「同一次调用的重复请求」时会去重。它反过来——**去重就是绕过通道**:先发一个能过的,再发一个不同目标的,去重逻辑把第二个当成重复跳过,就等于批准。这条经验在本域具有普遍性。

### 3.3 两者的结构性对照 `[CAT]`

| | workspace-only | workspace-folders |
|---|---|---|
| 对缺口的姿态 | 补丁:自己造「工作区边界」 | 豁免:替用户跳过提权确认 |
| 覆盖工具 | 文件类 + `bash`/`pwsh` | 仅 `write`/`edit` |
| 多目录支持 | 白名单(按目录、按会话) | 工作区级目录列表,读写/只读两档 |
| 配置存储 | 会话日志 + 会话级白名单文件 | `$DSH_HOME/workspace-folders.json`(原子写、串行) |
| 损坏处理 | — | **拒绝加载并指出文件路径,绝不用空列表覆盖** |
| 默认方向 | 越界 → 拒绝 | 越界写 → 自动批准(仅限读写目录) |

**两者共享同一个前提**:沙箱是「工作区根 + 提权」的二值结构,没有「多个根、各自权限」的表达。这个前提一天不改,这两种插件就一天不会消失。

## 4. 样本(对照)

| 样本 | 覆盖方式 | 代价 |
|---|---|---|
| workspace-only | 在**工具层**重新围栏,任何模式都生效 | 多一次裁决;`bash` 的目标靠路径判定,可能误判;每会话白名单文件是新的状态面 |

| `dsh-permission-rules` `[CAT]` | 路径 glob + 规则 | 规则要人写,不自动跟随目录 |

## 6. 体验

**人看到的**:workspace-only 是一个**稳定出现**的模态卡(三键,120 秒倒计时按拒绝);workspace-folders 是「添加目录」对话框与 `/add-dir` 命令,以及**沉默**——因为它在批准,不弹卡。

**模型看到的**:workspace-folders 在每次请求的运行时上下文里(紧跟沙箱策略之后)列出额外目录及其读写权限,并写入会话日志可回放;workspace-only 则通过拒绝理由告诉模型「越界了,可以申请一次」。

**这里有一个值得警惕的体验不对称**:「自动批准」的插件让流程更顺,用户**感知不到边界在被移动**;「每次裁决」的插件让流程更卡,但边界是可见的。**审批疲劳与边界可见性,在同一处接缝上直接冲突。**

## 7. 失败模式(具名)

| 失效条件 | 后果 | 方向 |
|---|---|---|
| workspace-folders:目录列表被手改成 `/` | 全盘写自动批准 | fail-open(配置面) |
| workspace-folders:reason 前缀变化(宿主改文案) | 预批准静默失效,退回询问 | fail-safe |
| workspace-folders:`bash` 写额外目录 | 仍询问(不覆盖) | 未覆盖 |
| workspace-only:应答者缺失 | 拒绝 | fail-closed |
| workspace-only:重复升权请求被去重 | 绕过 | **它刻意不跳过** |
| 两者:直连 Node 的写入 | 不经过工具层 | 结构性缺口 |

## 8. 评估清单

1. 它覆盖的是**工具调用**还是**真实副作用**?后者需要沙箱/OS 支持。
2. 自动批准的是**一次调用**还是**一类调用**?前者是 `allowed-once` 还是永久 grant?
3. 预批准前核对了几个字段?少核对一个就是越权通道。
4. 终端命令被覆盖了吗?没有的话,它自己说了吗?
5. 重复/畸形的升权请求会被去重跳过吗?
6. 白名单存在哪?会话级还是全局?损坏时是拒绝加载还是清空?
7. 符号链接、`..`、大小写、`/tmp` vs `/private/tmp` 这些等价路径处理了吗?
8. Full access 下还拦不拦?如果不拦,是设计还是遗漏?

## 9. 能搬走的东西:补边界与放绿灯的通用做法

> 这一节是**设计借法**。左半是「怎么在别人的沙箱外面再围一道」,右半是「怎么安全地开一个口子」。

### 9.1 重新围栏的四条规则(照抄)

**规则一:围栏必须覆盖「所有模式」,而不是「较弱模式」。**

样本的取值是「任何沙箱模式,包括 Full access」。理由很实际:**用户切到 Full access 是为了别的理由(A 项目要写 /tmp),不是为了「取消工作区约束」。** 如果不覆盖 Full access,那最高危的模式恰好是唯一没人管的模式。

**规则二:默认拒绝,而且把超时也算成拒绝。**

| 情形 | 裁决 |
|---|---|
| 用户点「拒绝」 | 拒绝 |
| 用户 120 秒没点 | **拒绝** |
| 根本没有应答者 | **拒绝**(fail-closed) |
| 卡片渲染不出来(无 Web 端) | 回退到通用问答卡 → 官方审批弹窗 → **再没有就拒绝** |

**规则三:敏感路径在任何档位都问。**  这不是「多加一条规则」,而是承认**档位是粗粒度的**,总有一些目标不该由档位决定。

**规则四:重复/畸形请求**不要**去重跳过。**

> 样本原话:带 `sandbox_permissions` 的升权调用**仅当目标模式严格宽于会话当前模式**时才跳过插件门禁(避免双弹窗);**重复(等于当前模式)或畸形的升权请求**在官方侧零弹窗直接放行/报错,**一律照走三键门禁**,堵死「重复升权绕过」。

**这是全卡最反直觉、也最该抄的一条**。大多数审批实现的默认反射是「同一次调用的重复请求去重」——而这里,去重恰好是绕过通道:先发一个能过的,再发一个不同目标的,去重逻辑把第二个当成重复跳过,等于批准。

**可搬的判据**:审批去重的键必须是「**调用身份 + 目标**」,不是「调用身份」。**目标不同就是新请求。**

### 9.2 放绿灯的五条匹配(少一条就是越权通道)

如果你想实现「某个目录里的写入自动批准」,照抄这五条,一条都不能省:

```
① request.callId  命中被跟踪的那一次调用      ← 别处的请求不能被顺手批准
② call.agent      === request.agent          ← 子代理不能冒用父级批准
③ call.toolName   === request.toolName       ← write 的批准不能给 bash
④ request.reason  以固定前缀开头              ← 别的审批请求不能被误判成提权
⑤ 规范化目标落在白名单目录内 且 当前模式允许该目录
```

**以及最重要的一句**:

> 终端命令 `bash` 写这些目录**仍询问**——「插件无法可靠判断命令会写哪里」。

**这就是「只放行你能看清的那一种调用」**:目录在白名单里 ≠ 任何能写该目录的动作都放行。**宁可不覆盖,也不假装覆盖。**

### 9.3 「自动批准」的可搬清单

| 要回答的问题 | ✅ 好答案 | ❌ 坏答案 |
|---|---|---|
| 批准的是**一次**还是**一类**? | `allowed-once`,生命周期 = 一次调用的派发 | 永久 grant / 「本目录始终允许」 |
| 核对几个字段? | 调用 + agent + 工具 + 原因 + 目标 + 模式 | 只看目标路径 |
| 看不清的动作怎么办? | 不覆盖,仍然询问 | 一律放行 |
| 只读目录怎么办? | 仍然询问 | 和读写目录一起放行 |
| 会话是只读模式? | 什么都不批准 | 照常批准 |
| 存储损坏? | **拒绝加载并指出文件路径** | 用空列表覆盖 |

**最后一行是「配置面 fail-closed」的样本**:`$DSH_HOME/workspace-folders.json` 损坏时,它「拒绝加载并指出文件路径,**绝不用空列表覆盖**」。空列表看起来无害,实际上是**悄悄把全部授权撤销**,用户下次打开发现自己配的东西没了——比报错更糟。

### 9.4 状态放在哪:一张决策表

| 状态 | 放会话日志 | 放会话级文件 | 放全局文件 |
|---|---|---|---|
| 本会话的档位选择 | ✅ 可回放 | — | ❌ |
| 本会话的白名单目录 | — | ✅ `<DSH_HOME>/<plugin>/sessions/<主会话id>/` | ❌ |
| 工作区级额外目录 | — | — | ✅ 但要**原子写 + 串行** |
| 用户的全局偏好 | — | — | ✅ |

**三条可搬的规则**:

1. **能放进会话日志的就不放进文件**——日志可回放、可恢复、自动按会话隔离。
2. **会话级状态用主会话 id 做目录名**——子代理继承快照,但写各自不串。
3. **全局文件必须原子写 + 串行**,损坏时**拒绝加载而不是清空**。

### 9.5 符号链接:默认不解析,但要能开

样本给了一个很诚实的做法:**词法围栏默认不解析符号链接**(工作区内指向区外的链接,词法上仍是「工作区内」→ 不拦),并提供 `realpathCheck` 开关做 opt-in 复核,解析失败时 **fail-closed 按越界询问**。

**可搬的判据**:

- 打开复核后,`root` 与目标**双方**都要 canonicalize(否则 macOS `/tmp` → `/private/tmp` 会误拒);
- 对**尚不存在**的目标,取「最深存在的祖先」canonicalize 后重拼余段(覆盖「写新文件、父目录是链接」);
- **残余面要写明**:白名单与 deny 规则**仍按词法路径匹配**,链接路径与其真身不互通。

**最后一句是教科书式的边界登记**:它没有说「我们处理了符号链接」,而是说「我们收窄了残余面,但白名单仍按词法匹配」。**能被逐条挑战的陈述,才是可信的陈述。**

## 10. 开放问题

- [ ] 官方会不会给 `SandboxExecutionPolicy` 加「多可写根 + 各自权限」?若加,这两个插件同时失去存在理由——这是本域最清晰的**复核触发条件**之一。
- [ ] 「自动批准提权」是否应当被视为一种**策略变更**(而非体验优化)?若是,它就该像模式切换一样留下可回放事件——目前它只留下 `approval/asked` + `approval/decided`。
- [ ] workspace-only 的白名单按主会话隔离,子代理继承快照——**继承的是权限还是目录**?两者的安全含义不同。
- [ ] 「词法匹配 + 可选 realpath」这种双层结构,能否推广成通用做法?它把「默认便宜、需要时精确」做成了配置项。
