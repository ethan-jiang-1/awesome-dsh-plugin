# 08 · 安装面:事前审计「组合特征」,事后只做「可回滚的隔离」

> **状态**:`observed` · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b` · **样本**:`BotonJ/dsh-plugin-sentinel`(回读 README + `src/rules.js` / `src/audit.js`)+ `Noob-stupid/dsh-plugin-gating-hub`(回读 README 升级/门控/自救章节)
> **坐标**:`BotonJ/dsh-plugin-sentinel`(GitHub:`BotonJ/dsh-plugin-sentinel` · 仓库 **0.1.0** · ⚠️ npm 同名包属于 `dushaobindoudou`,勿混)+ `Noob-stupid/dsh-plugin-gating-hub`(GitHub 同名 · npm `@noob-stupid/dsh-plugin-console` **0.5.98**)
> **一句话**:安装面没有「运行期强制点」可用,只有两个动作:**装之前看一眼**,和**装坏之后退回去**。前者正确的判据不是「有没有危险 API」,而是**「危险 API 的组合形状」**;后者正确的判据不是「预测哪个插件会坏」,而是**「坏了能不能一条命令回到上一版」**。

## 1. 命题

> 在安装面,「防灾难」等价于**降低不可逆性**,而不是**提高预测准确率**。因为插件的真实行为在安装前不可判定(生命周期脚本、原生模块、patch 层改写),所以任何「我会判断它安不安全」的声称都必然有假阴性;而「我能退回上一版」在失败时仍然成立。**生态里做得最好的那个,把这两件事分开做了。**

可证伪点:若存在一个安装前扫描器,能在不执行代码的前提下判定任意插件的安全性(而非风险特征),命题不成立。

## 2. 杠杆点

| 样本 | 位置 | 阶梯级 | 它在这一层做什么 |
|---|---|---|---|
| sentinel | 安装**前**:读 tarball | 7(市场/协议) | 静态审计源码与 manifest,给 `pass / review / block` |
| gating-hub | 安装**后**:版本门 + 回滚点 + 自动隔离 | 7(市场/协议) | 升级前契约预检、失败自动回滚、有确证证据才禁用 |
| 两者共同依赖 | `plugin_manager` 的安装流程 | 7 | 官方只强制**版本兼容**与**构建脚本批准**(且批准不核实对话) |

**强制点可命名**:sentinel 是**装前拒绝**(人可以不看,它不拦);gating-hub 是**装后隔离 + 回滚**(它真的改 profile 配置)。

## 3. 机制

### 3.1 组合特征:单看每一项都合理,合起来才是形状 `[CAT]`

sentinel 的规则分四组,其中第三组是全部价值所在:

```js
COMBO_RULES = [
  { id: 'COMBO-EXFIL-SECRETS',  requires: ['JS-READ-ENV|STR-SENSITIVE-PATH', 'JS-IMPORT-NET|JS-NET-CALL'] },
  { id: 'COMBO-DECODE-EXEC',    requires: ['STR-LONG-OPAQUE', 'JS-EXEC-EVAL|JS-IMPORT-VM'] },
  { id: 'COMBO-SHELL-EXFIL',    requires: ['JS-EXEC-CHILD-PROCESS|JS-IMPORT-CHILD-PROCESS', 'JS-IMPORT-NET|JS-NET-CALL'] },
]
```

它自己的解释写得比规则更值钱:

> 单独可解释的能力,**组合起来才是形状**。读凭据 + 能外发 = 凭据窃取的标准形状,**与意图无关**。

**这条是安装面唯一可用的判据**:意图不可判定,形状可以。「Web 搜索插件需要联网」是合理的;「Web 搜索插件需要读 `process.env` 并联网」就是另一种东西。

配套的还有两类「配置层」规则:

| 规则 | 严重度 | 为什么 |
|---|---|---|
| `PKG-LIFECYCLE-SCRIPTS`(`preinstall` / `install` / `postinstall` / `prepare` / `prepack` / `prepublish`) | critical | 安装即执行,扫描器读的是**装前**的包,脚本还没跑 |
| `PKG-NO-DSH-BUNDLE`(声明是插件却没有 `dsh.bundle`) | medium | 「装上了但不会作为插件加载」是常见误解,也是伪装空间 |
| patch 行关键字受保护(`sandbox` / `approval` / `permission` / `guard` / `policy` / …) | — | `!!js`、`disabled: true` 能让一整行沙箱/审批**静默失效** |

### 3.2 评分与阈值:把「严重度」折成一个可解释的数 `[CAT]`

| 级别 | 权重 | 判定 |
|---|---|---|
| critical | 10 | 任一 critical,或总分 ≥ 10 → **block** |
| high | 5 | 任一 high,或总分 ≥ 5 → **review** |
| medium | 2 | — |
| low | 1 | — |

阈值是**绝对值**(10 / 5),不是百分比。好处是**可预测**:加一条 critical 规则,所有命中它的包立即 block,不需要重算基线。代价是规则权重需要人工维护——但这是**安装面唯一能保持可解释的算法**。

### 3.3 零自攻击面:它自己不能成为新的风险 `[CAT]`

README 自述的四条,逐条都是「用它要防的那类能力」的反面:

- 无依赖、无构建脚本;
- **纯 JS 在内存里解 tar,不落盘**(恶意 tarball 的路径穿越没有落点);
- 不起子进程(`child_process` 一次都没用);
- 词法处理会剥离注释与字符串,**但保留 `${}` 插值**——因为插值里的代码是真会跑的。

**最后一行的取舍值得单独记**:剥离字符串会漏掉模板插值里的动态执行;保留插值会引入误报。它选了**保留**,即「宁可误报」。这与 04 卡(危险守卫)的「判不了就拒绝」是同一条原则的不同表达:**在安装面,假阴性比假阳性贵得多。**

它自己声明的边界也诚实:**不是完整 AST,不具对抗完备性**——退化的写法(动态 `import(变量)`、拼接的 `require`)能绕过。

### 3.4 可逆性:升级前的四个「先」 `[CAT]`

gating-hub 的升级链是一条**先建立退路、再动手**的顺序:

| 顺序 | 动作 | 失败时的意义 |
|---|---|---|
| 1 | 契约预检(消息契约 / 依赖 API / 配置 schema / 被移除的 API / loader 契约) | 装之前就知道会不会不兼容 |
| 2 | 备份配置 + **全树回滚点**(校验回滚点有效) | 有退路 |
| 3 | 在线安装(服务保持运行) | 不停机 |
| 4 | **版本校验** | 防「假成功」 |
| 5 | 失败 → **自动全树回滚**;卡死 → 15 分钟硬超时 + 诊断日志无更新即切源 | 不留在半坏状态 |

配套的三条「绝不」,比功能列表更重要:

- **安装脚本绝不自动放行**,pnpm 的供应链闸**绝不绕过**;
- **绝不 kill / spawn 进程或抢端口**(「那正是『应用无法启动或已意外停止』的来源」);
- 自动禁用**只禁有确证证据的行**,`@deepseek-ai/*` 与受保护/核心行**永不禁用**,禁前先写「安全启动快照」,每次禁用留一条**可读的恢复命令**。

「有确证证据」被定义成三种可核事实:行引用的包**在所有解析基准上都解析不到**、`file://` 目标确实不存在、启动失败日志**点名**该行。**没有证据就不动**——这条把「自动修复」从猜测变成了执行。

### 3.5 判据要选对:「目录空不空」vs「依赖闭包能不能解析」 `[CAT]`

真机事故(2026-10-14):框架包被掏空 + 三个包成了空目录 ⇒ 54 个插件 import 失败 ⇒ 进程退出 1。它的诊断工具用的是**闭包判据**:

- 按「目录空不空」粗扫:误报 **237** 个;
- 按「依赖闭包能不能解析」:精准通过 **287** 个包。

`--repair` 从**本地 npm 缓存**按 lock 的 integrity 装回,**不联网、不猜版本**,lock 里没有的包如实报 `no-lock-entry`。修完**不重启服务**——让人自己重启。

**这一节是本卡最好的方法论样本**:同一个故障,换一个判据,误报从 237 降到 0。「安全工具的质量,一半在判据选择上」,而判据选择不是靠更努力,是靠**先问「这个判据对哪种失效形态免疫」**。

## 4. 样本(对照)

| 样本 | 时点 | 能防 | 不能防 |
|---|---|---|---|
| sentinel | 装前 | 生命周期脚本、动态执行、凭据外传组合、patch 越权 | 退化写法、运行时下载的二次载荷 |
| gating-hub | 装后 | 不兼容升级、半坏状态、框架被掏空 | 恶意的「正常工作」插件 |
| 官方 `plugin_manager` `[DSH]` | 装时 | 版本兼容;**构建脚本批准**(自述「不核实对话」) | 内容审计 |
| `dsh-permission-rules` `[CAT]` | 运行期 | 运行期动作 | 安装面 |

**四者拼起来才是一条链**:官方管「版本对不对」,sentinel 管「像不像坏东西」,gating-hub 管「坏了退得回去」,运行期插件管「跑起来之后碰什么」。**没有任何一环能单独称为「安装面安全」。**

## 6. 体验

**人看到的**:sentinel 给一份分级报告(`建议拒绝安装` / `安装前需人工审查` / `存在低风险特征`),每条带文件与行号;gating-hub 给一张卡片(检测更新 / 升级 / 回滚)、一个实时进度窗、以及每次自动禁用后的一条**可读恢复命令**。

**模型看到的**:基本什么都看不到——这两者都**不向模型上下文注入内容**。它们的消费者是**人**,不是 agent。

**这条不对称值得注意**:运行期的插件(02–07)都在给模型写拒绝理由,安装面的插件在给人写报告。**同一句「安全」,对模型是「别重试」,对人是「你可以决定」。**

## 7. 失败模式(具名)

| 失效条件 | 后果 | 方向 |
|---|---|---|
| sentinel 遇到退化写法(动态 import、拼接 require) | 漏报 | fail-open(自陈) |
| 扫描超限文件(`maxFileKb`) | 标记为「不可审查」并计入 review | fail-safe |
| tarball 里没有可审文本 | `review`(而不是 pass) | **fail-safe** |
| gating-hub:控制台未加载(dsh 起不来) | 所有门控失效,只能靠进程外脚本 | 结构性缺口 |
| 框架行被误判 | **永不禁用**已排除 | fail-safe |
| 无确证证据 | 不动任何行 | 不改 |
| 自动禁用后无人回滚 | 插件长期停用 | 可恢复 |

## 8. 评估清单

1. 它的判据是「有没有危险 API」还是「**危险 API 的组合形状**」?
2. 它自己用了它要防的那些能力吗(子进程、网络、落盘、构建脚本)?
3. 阈值是绝对分还是百分比?加规则时会发生什么?
4. 「不可审查」的输入(超限、加密、无可读文本)会得到什么裁决?
5. 失败时它**动了什么**?动之前有没有回滚点?
6. 自动修复有没有「证据门槛」?没有证据时是修还是不动?
7. 判断「包坏了」用的是哪个判据?这个判据对哪种失效形态免疫?
8. 它自己坏了的时候,还有哪条路能救?

## 9. 能搬走的东西:装前审计与装后可逆的模板

> 这一节是**设计借法**。左边是一份可以照抄的规则清单,右边是一套可以照抄的自救流程。

### 9.1 组合特征:直接可用的四条形状

不必从零设计规则,**先抄这四条**(它们覆盖了绝大多数真实恶意插件的行为形状):

| 形状 | 组成 | 为什么它是形状而不是意图 |
|---|---|---|
| **凭据外传** | (读环境变量 **或** 触碰敏感路径) **且** (能联网) | 读凭据合法,联网合法,**两个一起**就只能是为了外传 |
| **解码执行** | (长的不可读字面量) **且** (`eval` / `vm`) | 混淆文本合法,`eval` 合法,一起出现就是载荷 |
| **Shell 外传** | (起子进程) **且** (能联网) | 同上 |
| **安装即执行** | manifest 里有 `preinstall` / `install` / `postinstall` / `prepare` | **扫描器读的是装前的包,脚本还没跑** |

**设计规则**:每条组合规则的 `requires` 里用 `|` 表达**或**,用数组表达**且**。这样一条组合规则就能覆盖若干种单规则的排列,不需要把每种组合都写一遍——**这就是「用少量组合规则替代规则爆炸」的具体做法。**

再加三条 manifest / 配置层规则,成本极低但命中率很高:

| 规则 | 严重度 | 检查什么 |
|---|---|---|
| `PKG-NO-DSH-BUNDLE` | medium | 声明是插件却没有 `dsh.bundle`——「装上了但不会加载」,也是伪装空间 |
| patch 行受保护关键字 | 高 | `cordis.patch.yml` 里出现 `sandbox` / `approval` / `permission` / `guard` / `policy` 行时,标为受保护 |
| `!!js` / `disabled: true` | 高 | 这两者能让**一整行沙箱或审批静默失效** |

**最后一行是两个具体的越权语法**:`!!js` 让你在配置里执行代码;`disabled: true` 让一行安全策略直接不生效。**审配置比审源码便宜得多,而收益往往更大**——因为配置能直接关掉防线。

### 9.2 绝对阈值 > 百分比(可解释性优先)

```
critical=10  high=5  medium=2  low=1
任一 critical  → block
总分 ≥ 10      → block
任一 high      → review
总分 ≥ 5       → review
```

**为什么用绝对值**:加一条 critical 规则后,所有命中它的包**立即 block**,不需要重算全生态的分布。百分比阈值在插件生态里几乎不可维护——**「分布」本身每时每刻在变。**

**可搬的口径**:安全评分用**绝对阈值 + 人工维护权重**,不要用「相对排名」。排名会随别人变好而变坏,而你的安全性不该取决于邻居。

### 9.3 「不可审查」必须落到 review,而不是 pass

| 输入 | 裁决 |
|---|---|
| 超出 `maxFileKb` 的文件 | `AUDIT-FILE-SKIPPED`(**info**,但计入 review) |
| tarball 里没有可审文本(纯二进制/加密) | **review** |
| 词法剥离后仍是动态拼接的 `import(变量)` | 已知不可判(自陈边界) |

> **原则**:「我没看到问题」和「问题不存在」是两件事。前者只能给 `review`,给 `pass` 就是把「没看」伪装成「安全」。

### 9.4 装后自救:五步顺序(照抄)

```
1. 契约预检    ← 消息契约 / 依赖 API / 配置 schema / 被移除的 API / loader 契约
2. 建退路      ← 备份配置 + 全树回滚点,并**校验回滚点有效**
3. 在线安装    ← 服务不停机
4. 版本校验    ← 防「假成功」
5. 失败 → 自动全树回滚;卡死 → 硬超时(15 分钟)+ 诊断日志无更新即切源
```

**顺序本身就是设计**:先建退路再动手。绝大多数「升级把环境搞坏了」的事故,不是因为没有回滚代码,而是因为**回滚点在建完之后才想起来建**。

### 9.5 自动修复的三条铁律

| 铁律 | 样本做法 | 可搬的判断 |
|---|---|---|
| **只做有确证证据的事** | 三种可核事实:行引用的包在所有解析基准上都解析不到 / `file://` 目标确实不存在 / 启动失败日志**点名**该行 | **没有证据就不动**——把「自动修复」从猜测变成执行 |
| **永不碰基础设施** | `@deepseek-ai/*` 与受保护/核心行**永不禁用**(70+ 行在 UI 标「受保护」) | 你的自动修复有没有「绝不碰」清单?没有的话它迟早会关掉一件必要的东西 |
| **每次动作留可读的恢复命令** | 每次自动禁用都记:时间 / 行 / 证据 / **恢复命令** | 不是「已记录」,是「用户能一键撤回」 |

**第三条最容易漏**:「我们有审计日志」不等于「用户能恢复」。样本写到 `dshHome()/plugin-console/auto-disable.log`,而且格式是**可直接复制执行的命令**。

### 9.6 判据选择的通用方法:问「它对哪种失效形态免疫」

样本的真机数据(2026-10-14 框架被掏空):

| 判据 | 结果 |
|---|---|
| 目录空不空 | 误报 **237** 个 |
| **依赖闭包能不能解析** | 精准通过 **287** 个包,**0 误报** |

**可搬的方法**:设计任何「检测坏了/没坏」的工具之前,先填这张表:

| 你担心它出问题的方式 | 哪个判据能看出来 | 这个判据会不会误报 |
|---|---|---|
| 文件缺失 | 存在性 | 会(可选依赖、平台差异) |
| 文件被清空但保留目录 | 目录为空 | 会(合法空目录) |
| **依赖链断裂** | **闭包可解析性** | 低 |
| 版本漂移 | lock 与 package.json 对照 | 会(可接受的漂移) |

**结论**:选判据不是选「最严格的」,是选「对你想防的那种失效形态免疫的」。**严格但误报高的判据会被用户学会忽略**,那比没有判据更糟。

### 9.7 零自攻击面:清单式自检

样本自述的四条,可以直接当你的上线检查表:

- [ ] 无依赖(或者依赖数量被刻意压到最低);
- [ ] 无构建脚本(别人装你时不执行任何东西);
- [ ] **在内存里解析归档,不落盘**(恶意归档的路径穿越没有落点);
- [ ] 不 import `child_process`;
- [ ] 词法处理**保留 `${}` 插值**(插值里的代码是真会跑的)。

**最后一条是一个真实的取舍**:剥离字符串会漏掉模板插值里的动态执行,保留插值会引入误报。它**选了保留**——即「宁可误报」。这与 04 卡「判不了就拒绝」是同一条原则。

> **一条可搬的判据**:在安装面,**假阴性比假阳性贵得多**。误报让人多看一眼,漏报让人装进木马。

## 10. 开放问题

- [ ] 组合特征的**假阴性**没有被公开测量。要评估它,需要一批恶意包做基准——生态里目前没有。
- [ ] gating-hub 的自动禁用是「修复」还是「治疗症状」?它禁掉的是不兼容的插件,不是坏插件。
- [ ] 安装面的两道门都依赖「人看报告」或「有确证证据」;有没有可能做成**默认拒绝 + 白名单**?那样会不会把生态变成封闭市场?这条与 `lever-reshape-product` 相邻,但失效数据归本域。
- [ ] 组合特征的四条形状已经足够稳定,能否做成**跨插件共享的规则集**?目前每家都各自维护一份。
