# 01 · 信任三层：只有文件那一环是硬的

> **状态**:`observed` · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b` · **样本**:8 组,回读 catalog 原文
> **一句话**:DSH 的安全边界是**一条链，不是一道墙**。链上最硬的一环是文件沙箱，最软的两环是安装面（靠自觉）与网络/进程面（根本没有策略词汇）。

## 1. 命题

> 生态里绝大多数“安全插件”做的是**披露与网关**，而不是**强制**；因为官方只在文件操作上给了强制点，其余边界（安装、网络、进程）必须靠生态自己在 DSH 之外搭。

可证伪点：如果能找到一批插件**不改执行环境、不替换启动器**，却真的阻止了网络外传，命题不成立。

## 2. 杠杆点

| 层 | 强制点 | 阶梯级 | 供给(证据) |
|---|---|---|---|
| 安装面 | `plugin_manager` 安装流程 | 7(市场/协议) | 安装前扫描 44 条 `[CAT]` |
| 运行面·文件 | 沙箱模式（唯一有策略词汇的维度） | 4(policy)+5(backend) | sandbox 子主题 235 条 `[CAT]` |

## 3. 机制：官方到底强制了什么

### 3.1 文件沙箱：唯一有策略词汇的维度 `[DSH]`

`dsh-sandbox-policy` 的解析优先级写得很清楚:

> 已批准的显式模式 **>** 会话最后一条 `sandbox/mode` 事件 **>** 部署默认值

切换本身是**写进会话日志的一条事件**（`sandbox/mode`），因此覆盖通过回放跨重启保留，两个会话也永不共享状态。工作区根来自会话创建时记录的不可变 `SessionHeader.cwd`——**工作区标识不需要事件，因为它不会变**。

这是本域最值得学的设计:**权限状态是日志事实，不是实时开关**。任何“改权限”的动作都留下可回放的记录。

**但它的两条限制是这个域的“地基裂缝”**:

1. **每会话只有一个主要工作区根**——额外可写根不属于 `SandboxExecutionPolicy`
2. **仅限文件操作模式**——官方原话:

> `SandboxMode` 管控文件操作；**网络和进程策略不在其词汇中**，因此这里没有限制它们的旋钮。

**这一句是整个杠杆层安全主张的支点。** agent 可以在 `read-only` 模式下照样 `curl` 出去、照样起子进程——沙箱只拦文件写。

### 3.2 权限预设：两个旋钮，不是一套策略 `[DSH]`

`dsh-permission-presets` 把**沙箱模式**与**审批策略**捆成预设。它的限制很关键:

- **只组合两个机制级旋钮**；固定 Auto 可以额外增加准入行为，但 **agent/profile 选择不属于 `PresetSpec`**
- `custom` 只能推导得出:**无法通过此服务选中或持久化一个具名的 custom 预设**
- 配置预设表在插件生命周期内固定
- **Auto 不能成为默认值**（只在 integration 存活期间存在，且有意不进 `permission` 设置 schema）

也就是说:**权限预设不是策略引擎，是两颗开关的命名组合。** 想表达“哪些工具在哪些目录下可写”这类细粒度策略，官方结构中无处安放。

### 3.3 自动审查：官方唯一的“模型判模型” `[DSH]`

`dsh-experimental-auto-review` 在每次原生或 PTC inner 工具调用前，用**当前 agent 自己的模型**评估待执行动作，按效果分三档:

| 档 | 判定 | 处置 |
|---|---|---|
| low | 项目内操作、精确清理本 Session 创建的对象 | 直接允许（Full access 执行） |
| medium | 不可逆删除既有对象、生产操作、外部写入、安全控制变更 | 需要 human 或**直接父级**明确授权：动作、目标、范围 |
| high | 跨信任边界泄露敏感信息 | **始终拒绝** |

它选择 Auto 时设 `ask` 审批策略，被拒调用转人工；**进程内委派 child 固定 `never` 策略，其拒绝是最终结果**；reviewer 响应不合法或技术失败时**调用失败且从不执行**（fail-closed）。

**但它自己的限制把代价写全了**:

- **不提供文件沙箱**
- **外层 `run_code` transport 及 PTC 程序内直接 Node 效果不经过 inner-tool review** ← 逃生通道
- **模型分类可能出错**，不提供确定性工具豁免、持久 grant、可配置策略或重试层
- 进程外 child 在父委派调用获准后**保留原生权限系统**（即不受 Auto 约束）

**洞察**:官方把“模型判模型”做成了**默认关闭的实验层**，并且明说它可能误放行。这是诚实的做法——但它同时说明：**在 DSH 里，“智能审批”不是被当作安全边界，而是被当作体验优化。**

### 3.4 安装面：最软的强制 `[DSH]`

`dsh-plugin-manager` 的几处原文值得逐条摆:

1. **profile 变更跨会话持久化，已安装的 Host 代码在宿主进程内运行，不受工作区沙箱限制。** ← 插件运行时**完全在工作区沙箱之外**
2. **依赖构建脚本仍需单独批准。**
3. 构建批准机制:Web 插件页可“允许这些脚本并重试”;工具可在用户于对话中批准后通过 `approvedBuilds` 代为授权,**服务只校验待决定的名字,不核实对话中的批准**;授权按包名保存在当前 profile,**允许以宿主用户的权限执行命令**,再次安装失败后仍保留。
4. 版本检查:本地路径直接读 `package.json`;registry spec 用 `pnpm view` 拿 `engines`/`peerDependencies`,**未满足 DSH 版本要求会在 pnpm 运行前失败**;但 **git/tarball spec 必须先抓取,因此只能安装后判定**——此时已恢复清单与锁文件并重装,而**已获准构建脚本的副作用可能保留**。
5. **版本豁免不授权依赖脚本**;豁免存 `compatibility.json`,升级不继承授权,必须 `acceptRisk: true`。

**结论**:安装面的强制只有“版本兼容”这一项是自动的;**“代码做了什么”没有任何自动检查**——这正是 44 条安装前扫描器存在的理由。

### 3.5 数据面：身份与凭据是分开的两件事 `[DSH]`

- `dsh-credentials`:**让配置引用密钥名称**（如 `DEEPSEEK_API_KEY`）而把值留在配置之外;存按插件组织的凭据记录;界面可报“是否设置/来自哪里/能否写入”而**不暴露值**;空值视为不存在。
- `dsh-authorization`:**通过人引导的登录、输入码或问答获取凭据**;每次尝试只把 notice 与 prompt 发到发起它的界面;**只有新凭据已存储时才报 `authorized`**。它自己**不提供任何提供方的授权方法**。
- 浏览器边界:`dsh-client-connection` 每个进程生成一个**随机启动令牌**，只在 `GET /` 接受 `?token=`，写入绑定 authority 的**签名 cookie** 后重定向清掉令牌;**缺失、过期、畸形或 authority 不匹配的 cookie 会在 RPC 分发前得到 401**;静态资源保持公开;cookie 签名密钥本身是 `ctx.credentials` 里的一条 grant 记录。
- 远端边界:`dsh-api-gateway` 每次调用**必填 Peer**，从不提供默认 Peer;`dsh-api-remote-access` 在**参数解码与 lookup 解析之前**就询问策略;列表方法经 `allows()` **逐项过滤**。

数据面是三层里设计最完整的:**凭据不外泄、授权要人参与、远端每次调用都带身份**。

## 4. 生态在做什么

### 4.1 补文件面的洞 `[CAT]`

`DevilSpiderX/dsh-workspace-only-plugin`:**把任何沙箱模式下的文件访问限制在会话工作区内**,越界访问一律请用户裁决;每会话还能用 composer 旁档位把门禁放宽为“工作区外只读”或“完全放开”。

它存在的理由正是限制 3.1-①:**额外可写根不在官方策略词汇里**。这类插件是“在策略之上再套一层自己的策略”。

### 4.2 反向的样本:`dsh-workspace-folders` `[CAT]`

`Fleey/dsh-workspace-folders` 也加额外工作目录，但它的默认行为是:**对读写目录的 `write`/`edit` 默认免去沙箱提权确认**，终端命令仍会询问。

同一处接缝，一个往里收（更多裁决），一个往外放（跳过提权）。**这不是对错问题，而是同一个缺口的两种利用方式**——它说明“策略词汇缺失”既让收紧变难，也让放松变得极其容易。

### 4.3 审批从“问人”变成“问模型” `[CAT]`

`IamNewHands/dsh-approval-gate` 的限制最值得读:

> **判定器不可用时，确认次数已达阈值的中立操作直接自动放行**，不再重复弹人工审批。

这是 **fail-open** 的显式设计，理由可以理解（避免审批疲劳），但它把“判定器挂了”翻译成了“放行”。同一插件还提供了**确定性硬拒**（凭据外泄、系统路径销毁）、判定输入脱敏、判定模型候选链、带操作指纹的放行规则——也就是说，**它自己也知道纯模型判定不可靠，所以在外面又套了一层确定性规则。**

`AntaresCorn/dsh-auto-reviewer` 走另一条路:新增 auto-review 权限档，安全提权自动放行、危险或模糊转人工、未确认的致命操作直接拒绝。

### 4.4 工具级守卫:挂在 pipeline 上 `[CAT]`

`JayYuen666/dsh-danger-guard` 用 **`tools.guard` 谓词**按当前权限档位，对危险 shell 命令（跳过 git 钩子、灾难性 `rm`、下载即执行、重写 git 历史）与“写凭据路径”“没写过目标文件的首次编辑”逐条给放行/询问/拒绝，并把**成因与可行替代写法**交回模型。

`PerryLink/dsh-defend` 更宽:在 `agent/pre-step`、`tools/pre-execute`、`tools/post-execute` **三个接缝**检测提示词注入、越狱与密钥泄露，按 **allow/ask/block** 分层，附脱敏审计事件。

**这两种做法的差别值得记住**:guard 挂在 `tools.*`，只能管工具调用;defend 挂到 `agent/pre-step`，连**进模型的文本**都能看。想防注入，必须挂 pre-step;**挂 tools 层永远防不了“模型已经被说服”**。

### 4.5 安装前扫描:和官方 mandate 赛跑 `[CAT]`

`BotonJ/dsh-plugin-sentinel`:生命周期脚本、动态执行、凭据外传组合特征、patch 层风险;零依赖、**tar 包全程内存解析不落盘**。

它覆盖的四类，正好对应 3.4 里官方**没有自动检查**的那些:安装脚本、动态执行、凭据+网络组合、patch 越权。**安装前扫描器本质是在替官方补第 3.4 节那张表。**

### 4.6 网络面:只能造网关 `[CAT]`

`0QwQ0/dsh-ui-auth` 的做法很典型:**登录门覆盖 pages、`/api`、`/plugins` 与 WebSocket upgrade**，PBKDF2 + 每用户盐、HttpOnly SameSite cookie、按 `DSH_HOME` 命名的会话cookie、基于 IP 的登录锁定、邀请码注册、TOTP/WebAuthn 双因子。

`GDWhisper/dsh-web-startup-auth` 更彻底:**替换 `dsh web` 启动器**以允许绑定 `0.0.0.0`。

它们的共同点:**都需要在 DSH 的 HTTP/启动层之外动刀**。原因就是 3.1 的限制 ②——网络不在沙箱词汇里，所以网络防护只能做成“整个 HTTP 面的网关”，粒度必然粗。

## 5. 自指问题：安全插件自身的能力披露

`data/capabilities.json`(2026-09-24 静态扫描,至今仍是唯一来源)按插件名聚类后:

| 类别 | 样本 | 读凭据 | 联网 | 动态执行 |
|---|---|---|---|---|
| 安装前扫描/审计 | 21 | 4 | 8 | 3 |
| 注入/守卫 | 59 | 5 | 27 | 4 |
| 审批/判定 | 72 | 3 | **33** | 6 |
| 认证网关 | 46 | **18** | **40** | 2 |
| 远端接入 | 62 | **21** | 49 | 5 |

**两处必须点名**:

- **认证网关 46 条里 18 条自己读凭据、40 条联网**。这未必是错——网关本来就要验令牌——但它意味着:**你认为用来加强边界的那件东西，本身就在边界内部持有着你最敏感的能力。**
- **审批/判定类 72 条里 33 条联网**。一个判定器需要联网，说明它在把**待审内容**发到外部模型。这正是 `dsh-approval-gate` 要做“判定输入脱敏”的原因。

**这条不能用“所以它们不安全”来结论**——那是把披露当判决。正确的读法是:**边界内每多一个持有关键能力的组件，信任链就多一环，而这一环的可验证性目前等于它的自述。**

## 6. 标杆

**配额**:本卡只深读 **1 个主标杆 + 2 个对照**。其余 S/A 级样本见本域 [`README.md`](./README.md#本域研究对象主读单一归属)。

### 主标杆 · 官方 `dsh-sandbox-policy`(S 级)

| 必答项 | 内容 |
|---|---|
| **代表什么典型** | DSH 里**唯一有策略词汇**的强制维度;它的边界就是整个生态安全投入的边界 |
| **为什么选它** | 过 **G 已核**:优先级链(显式授权 > 会话 `sandbox/mode` 事件 > 部署默认)、单一工作区根、只覆盖文件操作,三条都写自官方 README |
| **影响力多大** | 不靠被引,靠**覆盖**:所有文件工具、所有插件、所有子代理都在这条策略下 |
| **主要特点** | 权限状态是**日志事实**——切换是一条 append-only 事件,回放跨重启保留,两个会话永不共享 |
| **代价 / 失效** | **网络与进程不在其词汇中**;每会话只有一个主要工作区根,额外可写根无策略表达 |
| **证据级别** | `[DSH]` · 状态 `observed` |

### 对照 · `PerryLink/dsh-defend`(A 级,运行·注入)

- **过门**:**C 接缝 + D 零披露**;自述点名 `agent/pre-step`、`tools/pre-execute`、`tools/post-execute` 三条缝
- **影响力**:无可复核外部量(披露为空且能力边车无此条);**靠 C 进入**,是「挂哪条缝」这一课的最好样本
- **特点**:allow/ask/block 分层 + 脱敏审计事件 + `defend_report` 工具 + 危险删除命令门禁
- **代价**:只能按模式匹配;挂三条缝意味着它本身要读进模型的文本

### 对照 · `IamNewHands/dsh-approval-gate`(A 级,同时是 E 级反例)

- **过门**:**D 能力**(network/llm 等)+ **E 反面**:判定器不可用时**自动放行**
- **影响力**:D 可复核(能力披露);E 是本域**唯一一条明确 fail-open 的样本**
- **特点**:阈值后自动放行、确定性硬拒(凭据外泄/系统路径销毁)、判定输入脱敏、指纹级放行规则
- **代价**:fail-open;依赖指纹规则维护;自己也要联网问判定器

> 旁支留档(B 级,不立卡):`DevilSpiderX/dsh-workspace-only-plugin`(把文件访问收进工作区)、`JayYuen666/dsh-danger-guard`(`tools.guard` 谓词)、`BotonJ/dsh-plugin-sentinel`(安装前 tarball 扫描)、`0QwQ0/dsh-ui-auth` / `GDWhisper/dsh-web-startup-auth`(HTTP 层网关)、`lifeopsgo/dsh-capability-toggle-plugin`(三级开关,作用域仅当前 agent)。

**`defend` 与 `danger-guard` 的对照是全卡最实用的一课** `[CAT]`:guard 挂在 `tools.*`,只能管工具调用;defend 挂到 `agent/pre-step`,连**进模型的文本**都能看。**想防注入必须挂 pre-step,挂 tools 层永远防不了「模型已经被说服」。**

## 7. 体验

**人看到的**:这一域的体验几乎全是**打断**——审批卡片、登录页、配对码、扫描报告、越界裁决弹窗。而打断的**质量**决定了边界是否被绕过:

- 审批疲劳 → 用户开始无脑点同意 → `dsh-approval-gate` 用“阈值后自动放行”来缓解，代价是 fail-open
- 说明不清 → 用户不知道自己批准了什么 → 该插件特意“由真实的沙箱模式、命令与路径生成中文说明”

**模型看到的**:

- 每个 agent 的运行时上下文里有 `sandbox:policy` 一段，官方特意写明它**不枚举已挂载的能力**,并要求模型“不要仅凭这条策略就拒绝修改,先尝试调用并遵循返回的拒绝与升权引导” `[DSH]`
- 子代理额外有一条:权限范围启动时固定、需要审批的操作自动拒绝、**不要重试被拒操作** `[DSH]`

**这构成一个微妙的设计权衡**:官方刻意让模型**先撞墙再学规矩**,理由是历史测量发现“直接告知限制”会导致模型干脆不尝试工具调用。**质量门禁与模型主动性在这里是对立的**——这条张力值得整个生态认真对待。

## 8. 评估清单

1. 它落在哪一层?安装面 / 运行面 / 数据面?
2. 强制点在哪?没有强制点的，是不是只是披露?
3. 出错时 fail-closed、fail-open,还是转人工?写清楚了吗?
4. 它保护的是**文件、网络、进程、凭据**中的哪一项?该维度在 DSH 里有原生策略词汇吗?
5. 它自己用不用它要防的能力?（读凭据 / 联网 / 动态执行）
6. 它挂在哪条缝上?`tools.*` 只能管工具调用,`agent/pre-step` 才能看到进模型的文本。
7. 拒绝时给出的说明,能否让用户真正判断“我在批准什么”?
8. 它绕开了官方哪条限制?这个绕法是补强还是放松(toggle 默认值就是答案)?

## 9. 开放问题

- [ ] `[OPEN]` 沙箱只覆盖文件，是分阶段实现还是设计立场?若长期如此,网络与进程的安全**只能**由生态在 HTTP/进程层实现,粒度必然粗。
- [ ] `[OPEN]` 每会话单工作区根是简化还是原则?若支持多根，需要一整套新的策略词汇(可写根 + 分级)吗?
