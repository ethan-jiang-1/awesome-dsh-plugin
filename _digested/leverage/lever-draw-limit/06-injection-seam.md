# 06 · 缝的位置:挂 `pre-step` 才能看见「模型已经被说服」

> **状态**:`observed` · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b` · **样本**:`PerryLink/dsh-defend`(回读 README 全文,含「已知限制」)+ 其自我替代记录
> **坐标**:`PerryLink/dsh-defend`(GitHub:`PerryLink/dsh-defend` · npm `dsh-defend` **0.3.25**)
> **一句话**:同样的规则库,挂在 `tools/pre-execute` 只能看见「调用」,挂在 `agent/pre-step` 才能看见「进入模型的文本」。但**看见之后能不能拦**,取决于那条缝给不给理由字段——`pre-step` 的 reject **没有理由字段**,于是它只能静默拒绝。**这是接缝形状决定策略表达力的典型:不是作者不想解释,是缝没有那个口。**

## 1. 命题

> 提示注入的防线必须放在**文本进入模型之前**,而不是工具调用产生之后。因此「挂在哪条缝」比「规则写得多好」更决定成败。而每条缝的表达力不同:**能拦 ≠ 能解释 ≠ 能协商**——三者在 DSH 里分属不同接缝。

可证伪点:若能找到只在 `tools/*` 层拦截、却能在模型被注入后阻止其后果的实现(例如通过结果纠偏完全挽回),命题需要限定为「不能阻止**意图**的形成」。

## 2. 杠杆点

| 位置 | 具体接缝 | 阶梯级 | 它在这一层做什么 | 表达力 |
|---|---|---|---|---|
| 入站文本 | `agent/pre-step` | 4(policy) | 扫描进入模型的消息;clean → `next()`,ask → 审批,block → 拒绝本步 | **无理由字段**(自述) |
| 工具参数 | `tools/pre-execute` | 4(policy) | 扫描参数;allow → `next()`,ask → 审批,block → deny | 可带模型可见原因 |
| 工具结果 | `tools/post-execute` | 4(policy) | 扫描结果;block → **纠正性反馈** | 可纠正 |
| 审计 | `defend/*` 会话事件 | 3(slot) | 规则 id / family / 类别 / 严重度 / 决策——**从不含匹配文本** | 受 `ignorable` 门限制 |

**强制点可命名**:三条接缝上的三条分支;它自己不做执行,只产出 deny/ask/block 决策。README 明确写:**「沙箱与审批系统仍是执行权威」**。

## 3. 机制

### 3.1 两层相互独立的防线 `[CAT]`

| 层 | 内容 | 设计来源 |
|---|---|---|
| 第一层:危险删除门禁 | 递归删除类命令**除非每个目标都是会话工作区内的显式绝对路径且不触碰受保护前缀**(家目录配置、`.dsh`/`.claude`、系统目录)才放行 | 「8·14 / 8·16 事故教训的可执行形态」 |
| 第二层:检测 | 25 条注入规则 + 25 条越狱模式(纯 TS **Aho-Corasick** 自动机)+ 12 条密钥语法 + 保留为回归基准的攻击数据集 | 四个上游资产(Apache-2.0) |

**第一层的一个细节值得单独记**:dry-run 标记(`-WhatIf`、`--dry-run`、`git clean -n`)**放行**——理由是「它们正是教训要求的删除前核对」。这是把**事故教训**编码成规则,而不是把「所有删除」一刀切;放行的是**更安全的那个动作**,不是更宽松的档。

### 3.2 有界性:三条上限写在配置里 `[CAT]`

| 上限 | 默认 | 防的是什么 |
|---|---|---|
| `detection.maxScanChars` | 10000(只扫头部) | 恶意输入消耗无界资源 |
| 每条规则至多一条匹配 | — | 匹配风暴 |
| `maxReportEntries` | 200(内存环形缓冲) | 报告撑爆内存 |
| `secretMinEntropy` | 3.0 bits/char | 低熵误报(密钥规则命中的字符串熵太低就丢弃) |

**这组参数回答了本域的一个常见问题**:「检测类插件会不会自己被喂爆?」——会,除非它把上限写成**配置**,而不是写在代码注释里。

### 3.3 一次因为「会话可能恢复不了」而主动关掉审计 `[CAT]`

这是全卡最值得读的一节。它要给会话追加 `defend/detection` 审计事件,但:

- 所有已发布线(含 `0.2` 走廊)对 envelope 的 `ignorable: true` 标记**静默丢弃**;
- 宿主 `0.1.2-rc.1` 保留信封字段但只用于**存量日志读取兼容**,写入同样会让会话无法加载;
- 读取路径对**未注册的未知事件类型 fail-closed**。

于是它的选择是:

> 在**第一次追加之前**就判定(peer 版本预判;版本不可解析时同样 **fail closed**),并以一次性告警**停用会话日志审计**。设 `detection.allowUnmarkedAudit: true` 可重新开启,接受会话无法恢复的风险。

**这条决策把「可观测性」与「可恢复性」的优先级排清楚了**:当两者冲突时,保恢复。对照 05 卡(permission-rules 选择加标记 + 提供修复脚本),同一问题有两种解法——**关掉写入** 与 **写下去再修**。本域应当记录这个分叉,而不是宣布唯一正解。

### 3.4 冻结:被「更窄但采用度高一个数量级」的替代品超过 `[CAT]`

2026-10-05,维护者冻结本包(「不再新增功能,仍可正常使用」),理由写在 README 里:

| | 包 | 周下载 |
|---|---|---|
| 本包 | `dsh-defend` | 937 |
| 更值得推荐 | `cc-safety-net` | **13,087** |

自述的独有能力:从三类上游资产移植的 **Aho-Corasick 模式引擎**、对**用户消息 / 工具参数 / 工具结果**三处的 allow/ask/block、以及脱敏的 `defend/*` 审计。替代品**范围更窄**(只管破坏性命令与密钥文件),但采用度高一个数量级。

**这组事实构成本域一个重要判断**:安全插件的「能力面更宽」不构成竞争优势,**范围窄 + 默认值对 + 装得上**才是。原因不难推:用户装安全插件是为了「挡住那几件我怕的事」,不是为了「获得一套可编程的检测框架」。

## 4. 样本(对照)

| 样本 | 缝 | 能看见 | 能解释吗 |
|---|---|---|---|
| `dsh-defend` | `agent/pre-step` / `pre-execute` / `post-execute` | 入站文本、工具参数、工具结果 | 前两者:pre-step **不能**(无理由字段);后两者:能 |
| `dsh-danger-guard` `[CAT]` | `ctx.tools.guard` | 工具调用 | 能(理由成为工具错误) |
| `dsh-permission-rules` `[CAT]` | `tools/pre-execute` | 工具调用 | 能(规则的 `reason`) |
| `dsh-approval-gate` `[CAT]` | 审批应答 | 沙箱越界请求 | 能(字段化说明) |
| `cc-safety-net` `[CAT]` | 编程 Agent 的 CLI hook | 命令 | 能 |

**对照结论**:越靠近「文本进入模型」这一端,接缝的表达力越弱(不能解释、不能协商);越靠近「执行」这一端,表达力越强(可 ask、可给理由)。**安全性与可解释性在这里是一个 traded-off 的连续谱,不是可以同时最大化的两个指标。**

## 6. 体验

**人看到的**:`/defend` 命令与 `defend_report` 工具给出汇总(记录/拦截/询问数)、按 family 计数、最近 20 条——**从不含匹配文本**。密钥命中在构造上只留类型。

**模型看到的**:入站消息被拒时**没有理由**;工具参数被拒时有 deny 原因;工具结果被拦时收到**纠正性反馈**。三种体验不对等,而原因不是设计失误,是接缝字段的差异。

**这条差异值得所有做安全插件的人记住**:如果你的防线挂在 `pre-step`,你**无法**告诉模型「你刚才那条消息里有个注入模式」。你只能关掉这一步。想要解释,就得把防线搬到能解释的缝上——代价是那时模型可能已经被说服了。

## 7. 失败模式(具名)

| 失效条件 | 后果 | 方向 |
|---|---|---|
| 新措辞 / 形近 Unicode / 多步攻击 | 漏检 | fail-open |
| 无审批应答者 | 最严格决策 | **fail-closed** |
| 会话日志不支持 `ignorable` | 主动停用审计(一次性告警) | 保恢复 |
| `maxScanChars` 之外的尾部 | 不扫 | fail-open(有界) |
| 规则库停更(已冻结) | 覆盖面随新攻击衰减 | 时间性失效 |
| 只在 `tools/*` 层拦 | 无法阻止模型被说服 | 结构性缺口 |

## 8. 评估清单

1. 它挂在哪条缝?这条缝**能看见什么**、**不能看见什么**?
2. 这条缝给不给理由字段?不给的话,拒绝是静默的——能接受吗?
3. 决策是 allow/ask/block 三档,还是两档?`ask` 交给谁?
4. 失败方向:无应答者、服务缺失、版本不可解析时各是什么?
5. 有界性:扫描上限、单规则匹配数、缓冲上限写在哪?
6. 审计写入会不会影响会话恢复?有没有「宁可不写」的开关?
7. 它自己读了什么、连了什么、起了什么进程?
8. 上游是否已合并/替代?维护状态如何?

## 9. 能搬走的东西:怎么选缝,以及怎么不做被替代的那个

> 这一节是**设计借法**。前半段教你**把防线放在哪**,后半段教你**别让防线变成没人用的那个**。

### 9.1 接缝选型表(先查表,再写代码)

| 你要防的事 | 唯一可用的缝 | 该缝给你的 | 该缝不给你 |
|---|---|---|---|
| 恶意文本进模型 | `agent/pre-step` | 在模型看到之前拦下 | **理由字段**、`ask` 的细粒度协商 |
| 危险的具体工具调用 | `tools/pre-execute` | 可 `deny` 带原因、可 `ask` | 看不见「模型为什么这么想」 |
| 需要零误判的高危动作 | `ctx.tools.guard` | **不可推翻** | 同步、不能 `ask`、不能读盘 |
| 结果被污染(注入藏在工具输出里) | `tools/post-execute` | 可替换/可加纠正反馈 | 副作用可能已发生 |
| 是否需要打扰人 | `approval/request` | 可协商、可缺席 | 只看得到 reason 与 callId |

**选型口诀**:「**文本进模型 → `pre-step`;动作要拦 → `pre-execute`;绝不能被推翻 → `guard`;问人要不要 → `approval`**」。四条缝的功能不可互换,混用会得到一个「看起来全覆盖、实际每处都差一点」的实现。

### 9.2 如果你必须挂 `pre-step`,接受这三件事

1. **拒绝是静默的**——没有理由字段。所以不要把复杂的判断放在这一层:模型拿不到反馈,只会重试。
2. **你的判断必须极便宜**——它在每一轮对话前跑。样本的三条上限(`maxScanChars` 10000、每条规则至多一条匹配、`maxReportEntries` 200)不是优化,是**可用性前提**。
3. **它只能「拦截」,不能「说服」**——想改变模型的方向,必须回到工具层用拒绝理由。

**推论**:正确的组合是**两层**——`pre-step` 做便宜的模式检测(挡最明显的注入),`pre-execute` 做带解释的拒绝(告诉模型怎么改)。样本 `dsh-defend` 正是这么做的,只是它的 `pre-step` 那一层受限于接缝,无法解释。

### 9.3 检测层的价值怎么证明(而不是自我宣称)

样本的做法值得抄:**它不声称「能防住」,而是给一个可复现的命中率**。

- 25 条注入规则 + 25 条越狱模式(纯 TS 自动机);
- 12 条密钥语法;
- **保留为回归基准的攻击数据集**,实测下限 27/28 钉进测试。

**可搬的三条**:

| 做法 | 具体 |
|---|---|
| **有基准集,且基准集进测试** | 不是「我们覆盖了 OWASP 前 10」,是「这 28 条里有 27 条被拦,剩下 1 条是已知绕过」 |
| **报告不含匹配文本** | 审计里只有规则 id、family、类别、严重度、决策——**从不含匹配的原文**。理由是「报告本身不能变成泄漏源」 |
| **自陈边界** | 「不是完整 AST,不具对抗完备性」——写进 README,而不是等人发现 |

**第三条最能区分成熟与不成熟**:一个检测工具说「能检测注入」,和说「能检测这批模式,不具对抗完备性,退化写法可绕」,是两种完全不同的工程态度。**后者才可能被正确使用。**

### 9.4 不要做「被替代的那个」:范围 × 默认值 × 装得上

这是本卡最反直觉、也最该被借鉴的一节。样本**能力更宽**(三条缝、自动机、脱敏审计),却在 2026-10-05 **主动冻结**,推荐一个**范围更窄**的竞品,理由只有一行数字:周下载 937 vs **13,087**。

**为什么窄的赢了**:

| 维度 | 宽的那个 | 窄的那个 |
|---|---|---|
| 用户目标 | 「获得一套可编程检测框架」 | 「挡住我害怕的那几件事」 |
| 装的时候 | 要理解规则、要配 | 装完就生效 |
| 误报成本 | 由用户承担 | 由默认值承担 |
| 心智负担 | 高 | 近零 |

**可搬的判断**:安全插件的竞争力不在**能力面**,在**默认值**。

> **给做安全插件的人的一句话**:用户装你不是为了获得能力,是为了**不必再想这件事**。每多一个必填配置项,你就多一个装到一半被卸载的理由。

**推论(可当设计目标用)**:把「零配置下的防护水平」当成你的核心指标,把「可配置性」当成次要指标。样本 `cc-safety-net` 赢的正是这一格。

| 名字 | 坐标(2026-10-31) | 本卡用它做什么 |
|---|---|---|

| `drscrewdriver/dsh-perm-gate` | GitHub `drscrewdriver/dsh-perm-gate` | **目录内唯一引用 `cc-safety-net` 的条目**(`census.py --probe "cc-safety-net"` → 1/7924)——「竞品被引、本域样本未被引」的证据 |

## 10. 开放问题

- [ ] `pre-step` 的 reject 没有理由字段,是**故意的设计**(不给注入者反馈信号)还是待补的能力?两种解释都成立,需要官方文档确认(`[OPEN]`)。
- [ ] 「检测而非执法」意味着它永远不能单独构成边界。那么**检测层的价值如何计量**?现有的 27/28 基准只测规则命中率,不测「拦下之后模型是否绕路」。
- [ ] 一个被冻结但「范围更宽」的实现,与一个活跃但「范围更窄」的实现,哪一个在 6 个月后覆盖率更高?这是本域可证伪的经验问题。
- [ ] 「零配置下的防护水平」能否成为本域的评分维度?若能,它比规则条数、缝数量都更能预测采用率。
