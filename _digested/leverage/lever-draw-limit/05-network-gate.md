# 05 · 网络门:进程级出口闸门,以及一次「工程师的欲望」被明确拒绝

> **状态**:`observed` · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b` · **样本**:`PerryLink/dsh-permission-rules`(回读 443 行 README · 网络策略 / 安全边界 / 已知限制 / 会话日志修复)
> **坐标**:`PerryLink/dsh-permission-rules`(GitHub:`PerryLink/dsh-permission-rules` · npm `dsh-permission-rules` **0.7.20**)
> **一句话**:官方沙箱的词汇里**没有网络**。这个插件做的不是「沙箱扩展」,而是**在沙箱外面再架一道自己的门**:给 shell 子进程装本地 HTTP/CONNECT 代理,按有序规则裁决每个连接。它最值得学的不是代理怎么造,而是它**明确写下代理管不到谁**——以及一次为了「更安全」而链式上游的改动,如何被自己的规则否决。

## 1. 命题

> 环境没有提供强制点时,生态只有两条路:改环境(替换启动器/网关),或者在**自己能控制的边界**上再套一层。套层是可行的——但套得再细,也只是「覆盖某个子集」;把已覆盖的子集说成整体,是这一类实现最常见的失真。

可证伪点:如果 DSH 出现网络策略词汇(沙箱模式扩展到网络),这道门会从「必需」降级为「重复」。

## 2. 杠杆点

| 位置 | 具体接缝 | 阶梯级 | 它在这一层做什么 |
|---|---|---|---|
| 工具前置(URL 抽取) | `tools/pre-execute` 热路径 | 4(policy) | 从 web 工具参数与嵌入 bash/pwsh 命令文本里抽 URL 候选 |
| **进程出口** | 内置本地 **HTTP / CONNECT 代理** | 5(seam backend) | shell 子进程的流量逐连接裁决 |
| 审批 | `ask` 动作交回官方审批接缝 | 4(policy) | 无应答者时 harness 失败关闭 |
| 审计 | `permissionRules/decision` / `permissionRules/network` | 3(slot) | 命中**和透传**都落盘;仅日志,不注入模型上下文 |

**强制点可命名**:代理在**建连时**裁决——「代理按裁决到的地址建连,不做二次 DNS 解析;裁决未解析出任何地址的连接以 502 关闭失败,**绝不按名字拨号**」。

## 3. 机制

### 3.1 三档模式映射到官方预设 `[CAT]`

| `network` 模式 | 映射到的官方预设语义 | 未列目标 |
|---|---|---|
| `deny-all` | 只读沙箱 | 全断 |
| `whitelist` | workspace-write | `unlisted: ask`(或 `deny`) |
| `allow-all` | danger-full-access | 全放 |
| `auto`(默认) | 跟随沙箱预设 | 无沙箱策略服务的宿主上解析为 `autoFallback`(**`allow-all`**) |

**最后一行是本域必须点名的一处默认值**:默认档是 `auto`,而 `auto` 在没有沙箱策略服务时**回落到全放**。这不是 bug——它是「跟随宿主」的忠实实现;但它把「有没有沙箱策略服务」变成了安全前提。**任何一道门,只要它的默认档是「跟随另一个组件」,就必须点名那个组件缺席时会发生什么。**

### 3.2 三处「宁可失败也不靠近路」 `[CAT]`

| 做法 | 拒的是什么 |
|---|---|
| 代理按**裁决到的地址**建连,不二次 DNS | DNS 重绑定(裁决看一个地址、连接去另一个) |
| 上游不可达/超时(10 s)/非 2xx → **502**,刻意**没有静默回退直连** | 配置错误被静默吞掉 |
| 链式上游**永不**用于:回环目标、由 `ips` 作用域规则产生的裁决 | 「连接落在规则看过的地址上」在链式后不再成立(issue #21) |

第三条是本域**最好的一个设计样本**:作者原本想让白名单流量走上游代理(便于集中管控),后来发现——**一旦把主机名交给上游,`ips` 规则就不再掌握连接落在哪个地址**,于是把这一整类裁决排除在链式之外,宁可失去集中管控也不让规则失真。这是「控制边界优先于功能完整」的正面例子。

### 3.3 放行按钮:写在索引 0,且验证后再报告 `[CAT]`

设置页每条近期拦截提供「放行」:在**真正裁决该连接的那个规则文件的最前面**(索引 0)写入一条最小规则:

- 为什么索引 0:规则**首个命中生效**,追加在既有 `deny` 之后只会成为死文本。
- 只写 `domains`:该维度包含子域、与端口/scheme 无关,所以同一主机在下一个端口上不会被重新拦截。
- 写完**即刻重读缓存链并重算裁决**,因此提示报告的是**真实**结果——「绝不在连接仍被拦截时声称成功」。
- 拒绝写入而不动磁盘一枚字节的情形逐条列出:未知工作区、不在已知规则源内、只读的内置基线、文件不可读/不可解析、连接已被放行。

**这条设计的可移植性很强**:「一键放行」几乎是所有安全插件最危险的按钮,因为它把「人的意图」变成了「持久的配置」。它用三条约束控制了风险——写在生效位置、维度最小、写完复验。

### 3.4 会话日志修复:披露型是非的诚实记录 `[CAT]`

它给审计事件加了 `ignorable` 标记,并提供**修复脚本**。原因写在 `dsh-defend` 的 issue #2 里(同一家族):宿主对未识别的会话事件类型**历史上有过 fail-closed**,一旦事件未被打标,更严格的构建上**会话将无法恢复**。

**这是本域一个反复出现的结构性代价**:「多写一点审计」在 DSH 里不是免费的——**会话日志是恢复的唯一依据**,往里面加东西等于改恢复格式。任何以「增加可观测性」为名的写入,都必须先回答「旧版本读到它会怎样」。

## 4. 样本(对照)

| 样本 | 层 | 覆盖范围 | 失效方向 |
|---|---|---|---|
| `dsh-permission-rules` | 工具前置 + 进程出口代理 | shell 子进程;web 工具的 URL 候选 | 代理建连失败 → 502(失败关闭) |
| `PerryLink/dsh-defend` `[CAT]` | `tools/pre-execute` + `post-execute` | 命令文本与工具结果 | 检测而非执法;无应答者即失败关闭 |
| `GDWhisper/dsh-web-startup-auth` `[CAT]` | 启动器(替换 `dsh web`) | 整个 HTTP 面 | 改环境 |
| `0QwQ0/dsh-ui-auth` `[CAT]` | HTTP/WS 网关 | `/api/*`、`/plugins/*`、HMR、WS upgrade | 缺现代传输能力时挂「明确拒绝」监听(503 / WS 销毁) |
| 官方 `dsh-sandbox-policy` `[DSH]` | 文件 | 文件操作 | 词汇里没有网络 |

**对照结论**:四道门覆盖了四个不同的子集(子进程出口 / 命令文本 / 启动器 / HTTP 面),**没有一道覆盖「宿主自己发起的网络请求」**——README 明确指出:`undici` 全局 dispatcher 在启动器启动时就已设定,**宿主自身的 fetch 流量不经过该代理**。这正是「套层」的天花板。

## 6. 体验

**人看到的**:一条被拦截的连接会带 `[network: …]` 消息,**点名被拦目标、做出裁决的模式或规则、以及处置办法**;设置页有块计数器、近期拦截与「放行」按钮;带凭据的 URL 在告警与快照里一律打码成 `http://user:***@host:port`。

**模型看到的**:被拒连接是该次工具调用的错误结果,里面带**是哪条规则拦的**。没有额外的上下文注入——README 特意写明审计事件「仅日志,不会向模型上下文额外注入任何内容」。

**对照 02 卡**:审批插件的拒绝理由里带「怎么改」;这一张的拒绝消息里带「哪条规则 + 处置办法」。两处的共同点是——**拒绝必须可归因**,否则模型无法收敛,只能重试。

## 7. 失败模式(具名)

| 失效条件 | 后果 | 方向 |
|---|---|---|
| 宿主自身发出的请求 | 不经代理 | 未覆盖 |
| 命令里拼接构造的 URL | 抽取不到,不裁决 | fail-open |
| 无沙箱策略服务的宿主 + 默认 `auto` | 回落 `allow-all` | **fail-open(默认值)** |
| 上游代理不可达 | 502,不静默直连 | fail-closed |
| 规则文件损坏 | 保留旧规则,绝不崩溃 | fail-safe(旧配置继续生效) |
| 审计事件未被打标 + 严格宿主 | 会话可能无法恢复(已提供修复脚本) | 恢复面 |

## 8. 评估清单

1. 这道门覆盖**谁**的流量?进程内?子进程?宿主自身?
2. 默认档是「跟随别人」吗?别人缺席时会怎样?
3. 裁决看的是**规则里的名字**还是**要连的地址**?两者不同就是重绑定入口。
4. 上游/外部依赖失败时,是失败关闭还是**静默回退**到更宽松的路径?
5. 「一键放行」写在哪里?维度是否最小?写完是否复验?
6. 配置错误是**加载期大声失败**还是运行期静默降级?
7. 审计写入会不会改变会话恢复格式?
8. 规则的匹配子集有多大?glob/正则的病态输入怎么处理?

## 9. 能搬走的东西:给一个没有强制点的环境加一道门

> 这一节是**设计借法**。如果 DSH 明天给沙箱加了网络词汇,这张卡的**结论**会过期,但这套**做法**不会——它适用于任何「你想管、但平台没给你管」的维度。

### 9.1 四步定位法:先问「谁在发起」

任何一个出口门,先画这张表,把每一格填上「经过 / 不经过」:

| 发起方 | 是否经过你的门 | 怎么补 |
|---|---|---|
| 你的插件自己 | 你说了算 | 直接不发起 |
| 衍生的 shell 子进程 | **能管**(设环境变量/`HTTP(S)_PROXY` 到本地代理) | 这是主战场 |
| 宿主进程自身的 `fetch` | **管不到**(dispatcher 在启动时已设定) | 只能改启动器/网关,或承认不覆盖 |
| 其他插件的进程内请求 | **管不到** | 同上 |
| 外部客户端访问你这台机器 | **完全不同的问题**(入站,不是出站) | 交给 HTTP 网关(见 §9.4) |

**样本实测的答案就落在第 3 行**:`undici` 的全局 dispatcher 在启动器启动时就设好了,**宿主自身的 fetch 流量不走代理**。这一行的存在,决定了这张卡的天花板——**任何「进程内代理」方案都必须先回答第 3、4 行**。

### 9.2 出口门的三条硬规则(照抄)

**规则一:裁决看地址,不看名字。**

```
✅ 解析域名 → 按解析出的 IP 建连 → 不做二次 DNS
❌ 判定 "example.com 在名单里" → 然后按名字拨号
```

**理由**:DNS 重绑定。跳过 `二次 DNS` 是唯一能保证「规则看过的地址 = 实际连接的地址」的写法。样本的措辞:「代理按裁决到的地址建连,不做二次 DNS 解析;裁决未解析出任何地址的连接以 502 关闭失败,绝不按名字拨号。」

**规则二:外部依赖失败时,绝不静默回退到更宽松的路径。**

| 情形 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 上游代理不可达 / 超时 / 非 2xx | **502**(样本刻意没有静默回退直连) | 直连放行 |
| 解析不出地址 | **502** | 按名字拨号 |
| 规则文件损坏 | 保留旧规则继续生效 | 清空规则 = 全放行 |

**「配置错误因此始终可见」是这条规则的目的**——不是为了让用户烦,而是为了让错误不被吞掉。**一次静默回退,会让后面所有的审计都失去意义。**

**规则三:链式上游时,必须放弃「规则在意的东西」。**

样本放弃集中管控的那一类裁决,是最值得抄的设计判断:

> `ips` 作用域规则产生的裁决**绝不链式**——因为链式会把主机名交给上游,「连接落在规则看过的地址上」恰恰会在规则真正在意地址的地方不再成立。

**可搬的判据**:当你的门把请求转交给另一个组件时,问一句「**我刚做的那个判定,在转交后还成立吗**?」不成立就别转交。

### 9.3 「一键放行」的三条约束(最能直接抄的一节)

几乎所有安全插件都有这个按钮,而它把「人的一次意图」变成「持久的配置」。样本用三条约束控制风险:

| 约束 | 具体做法 | 为什么 |
|---|---|---|
| **写在生效位置** | 规则列表**索引 0** | 规则是**首个命中生效**;追加在既有 `deny` 之后只会成为死文本 |
| **维度最小** | 只写 `domains`(含子域、与端口/scheme 无关) | 同一主机换个端口不该被重新拦截 |
| **写完复验** | 立即重读缓存链并重算裁决 | 「绝不在连接仍被拦截时声称成功」 |

配套的拒绝写入清单(逐条都是可借鉴的边界):未知工作区、不在已知规则源内、只读的内置基线、文件不可读/不可解析、连接已被放行——**任一成立就一个字节都不动**。

> **模式化**:「自动写配置」这类功能,统一用 `写入位置 + 最小维度 + 写后复验 + 拒绝清单` 四件套。样本的教训直接适用于任何「自动修复」「自动忽略」按钮。

### 9.4 两个必须分开的门:出站 vs 入站

| | 出站(本卡) | 入站(HTTP 网关) |
|---|---|---|
| 强制点 | 本地代理 | 在 dispatch 之前包住整个 HTTP 服务 |
| 覆盖 | shell 子进程 | `/api/*`、`/plugins/*`、HMR、SPA fallback、WS upgrade |
| 失败方向 | 502 | 401 / 302 / **WS destroy** |
| 默认档 | 跟随沙箱预设 | 未认证即拒 |

**不要把它们做成一个插件**。样本 `0QwQ0/dsh-ui-auth` 的入站门有一个极具借鉴价值的细节:**缺现代传输能力时,挂「明确拒绝」监听(HTTP 503 + WS 销毁),而不是降级成不设门**。这就是 §9.2 规则二在入站侧的同一句话——**能力缺失 ≠ 安全默认**。
