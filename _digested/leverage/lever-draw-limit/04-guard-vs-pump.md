# 04 · 守卫与泵:同步谓词只能回答一次,复杂策略必须搬去别处

> **状态**:`observed` · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b` · **样本**:`JayYuen666/dsh-danger-guard`(回读 254 行 README)+ 官方 `dsh-tools` 流水线语义
> **坐标**:`JayYuen666/dsh-danger-guard`(GitHub:`JayYuen666/dsh-danger-guard` · npm `@jayyuen66/dsh-danger-guard` **0.1.10**)+ 官方 `@deepseek-ai/dsh-tools` 流水线语义
> **一句话**:`ctx.tools.guard` 是**同步、单调、不可推翻**的一票否决——正因为不可推翻,它只能装价值高却极便宜的那种、立刻答得上来的判断;需要看文件内容、需要询问、需要跨调用记忆的守卫,必须换成 `tools/pre-execute` 的 deny/ask 分支。**这一条把「防灾难」与「控复杂度」的边界画得很清楚:复杂度不在策略里,而在接缝选择上。**

## 1. 命题

> 一个安全插件能管多少事,不取决于它的规则写得多聪明,而取决于它站在**同步断言**还是**异步流水线**上。同步断言的位置换来了不可绕过,代价是「判定成本必须接近零」。**凡是想在同步提升里做重活的实现,最终都会退化成超时/异常/无判定,而那时它必须选一个失效方向——多数实现选了放行。**

可证伪点:如果能找到在 `tools.guard` 内做文件遍历 + 模型调用、且仍保持可预测行为的实现,命题不成立(未发现)。

## 2. 杠杆点

| 位置 | 具体接缝 | 阶梯级 | 它在这一层做什么 |
|---|---|---|---|
| 工具守卫 | `ctx.tools.guard(...)`:`tools/pre-execute` **之后**的单调同步谓词 | 4(policy) | 返回字符串即拒绝;后续监听器**无法把拒绝改回允许** |
| 证据收集 A | `tools/post-execute`:`accept{additionalContexts}` | 3(slot) | 只读检查(如 `read`)把「谁引用了它」随该结果一起交给模型 |
| 证据收集 B | `tools/pre-execute`:`deny{reason}` | 4(policy) | 没读过目标的写操作,把目标内容与引用面**写进拒绝理由**;同形重试凭「交付水位」通过 |
| 判定顺序 | guard 在审批**之后仍会再跑一次** | — | 用户点了 Allow 仍可能被拒 |

**强制点可命名**:`ctx.tools.guard` 本身;拒绝理由变成该调用的错误结果,模型看到的是「为什么被拒、该怎么改」而不是静默失败。

## 3. 机制

### 3.1 为什么是同步谓词:官方语义 `[DSH]`

`@deepseek-ai/dsh-tools@0.2.1-rc.3` 把每次调用固定成一条流水线:

> `tools/pre-execute`(可扩展的允许／拒绝／询问)→ 已注册**单调守卫** → `tools/execute`(环绕分发包装层)→ `tools/post-execute`(检查／替换、附加上下文)→ `finalizeContent` → 仅观测的 `tools/result`

原文对守卫的定性是「**单调同步守卫**:返回的理由会拒绝调用,后续监听器无法把该拒绝重新变为允许」。

这条性质带来了本域最重要的一个**结构性事实**:

| | `tools/pre-execute` | `ctx.tools.guard` |
|---|---|---|
| 能否被后续监听器推翻 | 能(可重排、可覆盖) | **不能** |
| 能否 `await` | 能(可以问人、可以问模型、可以读文件) | **不能** |
| 能否返回 `ask` | 能 | 只能「拒绝」或「放行」 |
| 合适的判断 | 需要证据、需要询问、需要记忆 | 纯函数式字符串/结构判断 |

**推论**:想要「防灾难」,应当把最便宜的那部分判断放进 guard;想要「可协商」,必须放进 pre-execute。把两者混淆的实现,会在人类点了 Allow 之后仍然被拒——而 README 明确指出,**这正是 `tools.guard` 同步而审批异步带来的结构性陷阱**:同一个键不能同时属于「写入档」与「询问档」。

### 3.2 实测出的三个「不判断」比「判断」更重要 `[CAT]`

`dsh-danger-guard` 的规则价值不在它拦了什么,而在它承认了三处**无法判断**并各自指了方向:

| 场景 | 做法 | 理由(自述) |
|---|---|---|
| 目标路径太长,读不完 | `opaqueTarget` → **拒绝**,提示「把路径原样贴给用户,不要照抄重试」 | **判不了 ≠ 安全** |
| shell 嵌套太深,解析不出真实命令 | `nestedShellUnconfirmed` → 按档位 `ask` / `allow`;超长命令直接落到这一档 | 同上 |
| 认不出沙箱后端是否在限制 | 不变量:取**保守档**——写侧全部拒绝,「判不了」仍然 `ask`,**不复用 workspace-write 档**(那档依赖沙箱兜住部分伤害) | 复用等于假设沙箱在场 |

第三行是最容易做错的一处。多数插件把「读不到沙箱模式」当成 workspace-write 处理,而它明确写了:**不读就换一档,而不是借一档**。

### 3.3 沙箱让位:只在「双向都不包含」时才让 `[CAT]`

`rmrf` 家族只有在**执行器自报在限制** + **它自报的默认模式本身是阻塞的** + **解析出的模式不是完全访问** + **目标既不包含可写根、也不位于任何可写根之内**时,才让位给沙箱。这张判定表读四条来源:工作区根、执行器给出的 `additionalWritableRoots`、`/tmp`、平台临时目录。**任一条读不出来,整张表视为不可信,一律不让位。**

理由写得比结论更重要:

> `workspace-write` 意味着工作区**内部**可写,所以 `rm -rf ~`(工作区在 `~` 下)**会先清空工作区**,然后才撞到边界——**沙箱是路径白名单,不提供原子性**。因此 `~`、`/`、`.`、`..` 永不假手沙箱。

这句话值得进本域的核心洞察:**沙箱能阻止越界,但不能阻止越界之前已经发生的破坏**。任何「交给沙箱」的判断,都必须先确认「目标是否包含可写根」。

### 3.4 事实闸门:证据的记账规则 `[CAT]`

它还有第三层:「首次编辑事实闸门」。要点不在规则本身,而在**证据怎么算**:

- **只有成功的调用才算「读过」**——证据账本按 `callId` 把 `tool/call` 与 `tool/result` 配对;没有配对的调用状态未知,**不计数**。
- 「读的是哪个版本」与「何时变旧」是**同一条记录**,只在该次读取**成功后**提交;失败或被拦的读取**不能推进基线**,否则一次没成功的读会把外部改动吞掉。
- 「零命中」的结论要求该子树**被完整读完**;扫描带走过的文件(超限、凭据隔离、不可读)任一存在,这一层就不给「0 命中」结论。**「没找到」与「没找完」必须回答不同。**
- 引用搜索的判据是「**遍历未被截断** 或 **找到引用**」;「零命中 **且** 被截断」= 什么也不给。

**这条规则可以一般化**:任何「我检查过了」的自动判定,都必须能区分「检查完没发现问题」与「没检查完」。本域目前只有少数实现做到了这一点。

## 6. 体验

**人看到的**:几乎没有新增界面——它把判定塞进已有的工具结果与审批事件。误报时用户看到的是拒绝文本里的**替代写法**,而不是一个「去设置里关掉我」的按钮。

**模型看到的**:拒绝理由里带**缺失的证据**(目标内容、引用面、为什么判不了),重试时凭「交付水位」通过。README 明确解释了为什么不用 `agent.inject()`:

> 那个 API 把上下文排给**下一次** pre-step,而决策是**逐 step** 做的——证据会在编辑落地**之后**才到。

**这是一条容易忽略的正确性条件**:安全插件的反馈必须在**本次调用**的结果里,不能排进下一轮。排进下一轮的反馈等于没有反馈,只会让模型重试。

## 7. 失败模式(具名)

| 失效条件 | 后果 | 方向 |
|---|---|---|
| 规则表没覆盖的新写法 | 漏过 | fail-open |
| 在 guard 里做重活(文件遍历/网络) | 阻塞主线程或超时 | 未定义(实现事故) |
| 沙箱模式读不到却复用 workspace-write 档 | 假设沙箱在场,真让位 | fail-open |
| 「零命中且被截断」被当成零命中 | 假阴性 | fail-open |
| 事实闸门 + `maxDenies` 额度耗尽 | 重复拒绝直到额度释放并给警告 | 转人工/放行 |
| 审批通过后 guard 再跑一次拒绝 | 用户点了 Allow 仍被拒 | **设计陷阱**(类型已排除) |

## 8. 评估清单

1. 守卫是**同步**还是**异步**?同步的能不能 `ask`?
2. 它的拒绝**能被后续监听器推翻**吗?如果能,顺序由谁保证?
3. 「判不了」时走哪一档?是**换档**还是**借档**?
4. 沙箱让位前,是否确认了「目标不包含任何可写根」?
5. 「我检查过了」的结论,能不能区分「没发现问题」与「没检查完」?
6. 有没有允许清单?如果只有收紧项,误报的出路在哪?
7. 证据(读过什么、读过哪个版本)只记成功调用吗?
8. 反馈落在本次调用结果里,还是排进下一轮?

## 9. 能搬走的东西:同步守卫的四条铁律

> 这一节是**设计借法**。同步守卫的价值全在「便宜且不可推翻」,一旦你往里面塞了贵的东西,它就从保险丝变成了炸弹。

### 9.1 铁律一:守卫里只允许「纯函数级」判断

| 允许 | 禁止 | 原因 |
|---|---|---|
| 字符串匹配、正则、词法拆分 | 读文件、遍历目录 | 阻塞工具调用路径 |
| 查内存里的配置/账本 | 发起网络请求 | 同上,且结果不可预测 |
| 纯算术、表查找 | `await` 任何东西 | `guard` 是同步的 |
| 已有的事实(如「本次调用读过没有」) | 现算的事实(如「现在磁盘上是什么」) | 现算 = 读盘 |

**判据**:如果你需要「等一下」才能回答,那这个判断就不属于守卫,属于 `tools/pre-execute` 的 `deny` 分支。

### 9.2 铁律二:三个「判不了」各自要有归宿

照抄这张表,把你的「判不了」逐条填进去:

| 判不了的情形 | 应当的归宿 | 绝不能 |
|---|---|---|
| 输入太长/太深,读不完 | **拒绝**,并提示「把原文贴给用户,不要照抄重试」 | 当成「没问题」 |
| 解析不出真实目标(嵌套 shell、变量、编码) | **转人工**或按最保守档拒绝 | 拿字面量当目标去比对 |
| 读不到环境状态(沙箱模式、平台、账户表) | **换到保守档**,不复用「假设环境在场」的那一档 | 借用别的档位的结论 |

**第三行是唯一需要「有环境知识」的判断**,也是最容易写错的:样本明确写了「不读就换一档,而不是借一档」。借档的后果是——沙箱其实不在,而你以为它在。

### 9.3 铁律三:沙箱让位必须过五道闸

如果你打算把某个判断交给沙箱(而不是自己拒绝),先满足全部五条:

```
① 目标不包含任何可写根(工作区根 / additionalWritableRoots / /tmp / 平台临时目录)
② 执行器自报在限制中,且它自报的默认模式本身是阻塞的
③ 解析出的模式不是完全访问
④ 上述四类可写根全部**读得到**(任一读不到 → 整张表作废,不让位)
⑤ 目标不是 `~` / `/` / `.` / `..`
```

**第 5 条的理由是全卡最重要的一句话**:

> `workspace-write` 意味着工作区**内部**可写,所以 `rm -rf ~` 会**先清空工作区**,然后才撞到边界——**沙箱是路径白名单,不提供原子性**。

**推论**:凡是「目标包含可写根」的动作,沙箱帮不了你,因为它会先执行完再报错。**这类动作只能由守卫自己拒绝。**

### 9.4 铁律四:反馈必须落在本次调用,不能排进下一轮

样本明确解释了为什么不用 `agent.inject()`:

> 那个 API 把上下文排给**下一次** pre-step,而决策是**逐 step** 做的——证据会在编辑落地**之后**才到。

**可搬到你的项目**:任何「先提示、再执行」的设计都是错的;正确的顺序是「**拒绝本次 + 把证据放进拒绝理由**」,让模型带证据重试。样本的做法是把「目标内容 + 引用面」写进 deny 的 `reason`,并用**交付水位**让同形重试通过。

### 9.5 边界登记表模板(把「已知限制」写成可验收的条目)

样本的 `Known boundaries` 一节有 9 条,每条都是「**这一类不判** + **为什么** + **当前裁决被测试钉住**」。照这个格式写你自己的:

```markdown
- **<不判的类别>** —— 具体例子:`<可复现的输入>` 仍然逃逸:`<原因>`。
  当前裁决:`<放行/询问/拒绝>`,由 `<测试名>` 钉住。
```

**为什么这个格式值得抄**:它把「我们没做」变成了「**我们知道没做,而且测出来了**」。对照写法「本插件能有效防护危险命令」——后者无法被复核,前者可以被逐条挑战。

样本里几条可以直接借用的判断:

| 它不判的东西 | 理由 | 你的项目里对应什么 |
|---|---|---|
| `cmd.exe /c` 的命令体 | `%VAR%`、`^` 续行、`&` 不切分段的引用规则离 POSIX 太远,用 POSIX 词法器去读会引入一批误拦 | 多平台命令解析:只覆盖你能正确解析的那个 shell |
| `-WhatIf` / `--dry-run` 修饰符 | dry-run 是否豁免是**没人做过的策略决定**,所以当前裁决原样钉住 | 任何「看起来无害的修饰符」都不要顺手豁免 |
| 裸 `~user`(无路径分隔符) | 是否展开取决于机器的账户表,而守卫**既不查文件系统也不查用户** | 需要「查机器状态」的判断,不该进同步守卫 |
| shell 重定向写入(`> f`、`tee`、`sed -i`) | 事实闸门挂在 `edit`/`write` 上,覆盖它们要解析重定向 | 你的「必须先读再写」检查覆盖了哪些写路径?列出来 |
| 超过 1 MiB 的内容自证 | 读回整个文件会占住同步路径,所以返回「unknown」并要求先读一次 | 任何「读回来比对」的自证都有大小上限 |

**最后一条尤其值得抄**:它没有为了完整而阻塞,而是**在超限时退化成一个更保守的结论**(「这次改动算外部改动,下次编辑前必须先读一次」)。**降级路径写清楚了,才叫有界。**
