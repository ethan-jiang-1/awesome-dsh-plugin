# lever-reshape-product · 不改上游，DSH 能被组装成什么产品

> **标语**:*What product can DSH become without forking it?* —— 产品的单位不是插件，是 profile。
> **状态**:`observed`(机制已核) · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b`

## 这个域问什么

一个 DSH profile 能把同一个运行时组装成完全不同产品：终端、Web、桌面、无头 CI、SDK 内嵌、IDE 面板、别人的产品内核。这里不研究“哪个插件好看”，只研究**产品栈的哪一层被谁改、改到哪一层就必须 fork**。

判断标准只有一条：**能不能只靠 profile / bundle / patch / preset / slot 完成，而不动上游代码。**

## 收录 / 不收录

收录：

- 定义或替换**产品外壳**的（工作台、侧栏、桌面壳、启动器、整站布局）
- 定义**身份与默认值**的（preset、persona、品牌、首启、系统提示装配）
- 定义**分发通道**的（bundle 组合、插件市场、profile 打包与安装）

不收录：

- 只增加一个工具或一个 skill 的 → 影响面在杠杆阶梯 1–2 级，归 `ecosystem/`
- 只为某个具体能力换后端（搜索源、模型源）→ 归 `ecosystem/`，除非它同时改了产品默认值
- 主题、配色、动效 → 属 3 级 slot，除非主题系统本身被替换（那时才入本域）

## 准入:什么能进这个域的研究

**不是抓到一个就琢磨。** 通用准入门(A/B/C/D/E/F/G)与 S/A/B/C 分级见 [`../horizon.md`](../horizon.md),这里是本域的专项条件。

**本域强制的加分项(二选一)**
- **指到层**:能点明它改的是 **2 表层 / 4 身份 / 6 首启 / 7 分发** 中的哪一层;只动 3 槽位的,必须额外证明它把槽位变成了**开放注册表**(`ctx.workbench` 那一路)。
- **替代官方对象**:自述替换了 profile、启动器、官方页面或官方默认行为——这是 B 级证据,本域最看重。

**本域明确不收**
- 换皮主题、配色、动效、单页面板、只加设置项 → 3 级 slot,归 `ecosystem/`
- 只加工具或 skill 的 → 1–2 级
- “装了以后挺好用”的体验陈述 → 无论多流行,没有层与代价,一律不进

**本域现役 S/A 级**(逐条含过门证据):见 [`../horizon.md`](../horizon.md) §6。

## 选择要求

样本必须同时满足三条，否则不立卡：

1. **占位可指认**：能说清它占的是 profile / bundle / preset / slot 的哪一类，而不是“加了些界面”。
2. **无 fork**：能在不改上游仓库的前提下装上去；若它 fork 了，必须写明 fork 的是哪一层、为什么非 fork 不可（这本身是最有价值的证据）。
3. **代价可说出**：至少一条失效条件或成本——升级断裂、patch 覆盖、与其他 bundle 的优先级冲突、上游改 token 就坏。

## 领域骨架：产品栈七层

一个问题一层，卡里逐层给证据。**层序就是“越往上越必须 fork”的顺序。**

| 层 | 问题 | 谁在改 | 代表卡 |
|---|---|---|---|
| 7 分发 | 装什么、谁决定装什么、怎么升级 | bundle 列表、市场索引、profile 打包 | [01-product-stack](./01-product-stack.md) |
| 6 首启 | 第一次打开看到什么、默认权限是什么 | onboarding、setup 向导、首启 patch | 同上 |
| 5 默认值 | 模型、权限档、网页检索源、默认工作目录 | 配置项 + `cordis.patch.yml` | 同上 |
| 4 身份 | 这个 agent 是谁、遵循什么规矩 | `agent-preset`、`persona`、系统提示装配 | 同上 |
| 3 槽位 | 界面上有什么、放在哪 | `ctx.theme`、UI slot、right rail、settings 页 | 同上 |
| 2 表层 | 这一轮的交互模型是什么（对话/终端/无头/内嵌） | profile 选层：`dsh-web-app`、`dsh-headless`、`dsh-acp-app`、`dsh-sdk-app` | 同上 |
| 1 运行时 | 一切皆插件的装配器本身 | 上游 | 不改即为本域前提 |

**核心洞察(待验证)**:1–3 级插件叠加不产生产品；**产品 = 2 层 + 4 层 + 6 层的组合**。只改槽位的插件永远只是“装了插件的 DSH”。

## 与其他域的分界

| 重叠情形 | 判给谁 | 理由 |
|---|---|---|
| 改了默认权限档 / 默认沙箱模式 | **本域** | 它改的是产品默认值（5 层） |
| 权限档本身的强制与审批逻辑 | `lever-draw-limit` | 那里问“边界由谁强制” |
| 桌面壳里内置了多 agent 协同面板 | **本域** | 主证据是产品形态；协作机制归 `lever-cross-boundary` |
| 市场索引与 bundle 分发 | **本域** | 分发通道是产品栈 7 层 |
| 安装前扫描、供应链校验 | `lever-draw-limit` | 那里问“谁能被装进来” |
| 把 profile 打包成可交付镜像 | **本域** | 但“产物是否可复现”归 `lever-prove-output` |

## 复核触发条件

- 上游新增或删除 profile（现为 `dsh-web-app` / `dsh-headless` / `dsh-acp-app` / `dsh-sdk-app` / `dsh-sdk-minimal`）
- bundle / patch 的叠加语义变化：**patch 是整行替换 `config`**，这条一变，5 层全部结论作废
- `ctx.theme` 或 UI slot 契约变化
- 市场索引格式版本变化（当前格式 1）
