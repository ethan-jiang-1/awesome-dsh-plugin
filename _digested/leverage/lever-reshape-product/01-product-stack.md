# 01 · 产品栈：七层里只有三层是产品

> **状态**:`observed` · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b` · **样本**:5 组,回读 catalog 原文
> **一句话**:同一个运行时能被组装成差别极大的产品,但**能改变产品的只有表层、身份、首启三层**;其余四层要么是手感,要么在本仓库里根本没人动。

## 1. 命题

> 产品 = 表层选择 + 身份装配 + 首启设定。槽位换得再多也不换产品,而**本仓库 7924 条里,首启层样本只有 1 条,且与首启无关**。

命题拆成两个可证伪的部分:

- **P1**:只改 3 层(slot)及以上的插件,不产生产品差异——可被“某个纯 slot 插件装完就像另一个产品”推翻。
- **P2**:6 层(首启)存在真实接缝但无人使用——可被“确实有一批 onboarding 插件,只是我的检索词不对”推翻。

## 2. 杠杆点

| 层 | 位置 | 阶梯级 | 本仓库供给(证据) |
|---|---|---|---|
| 7 分发 | bundle 列表 / 市场索引 / profile 打包 | 7 | 市场类 322 条 `[CAT]` |
| 6 首启 | ？ | 6? | **1 条,且是无关词命中** `[CAT]` |
| 5 默认值 | 配置 + `cordis.patch.yml` | 4 | 散布在各类,无独立类目 |
| 4 身份 | `agent-preset` / `persona` / 系统提示装配 | 6 | preset 类 417 条 `[CAT]` |
| 3 槽位 | `ctx.theme` / UI slot / right rail / settings 页 | 3 | 工作台/换壳 1068 条 `[CAT]` |
| 2 表层 | profile 选层 | 6 | 上游 5 个 profile `[DSH]` |
| 1 运行时 | 上游 | — | 不改即前提 |

**关键结论**:供给量的排序是 **3 层 >> 4 层 > 7 层 >> 2 层 > 6 层**,而影响面排序几乎是反过来的。生态集中在最不改变产品的那一层。

## 3. 机制：为什么「加插件」不等于「做产品」

### 3.1 profile 是组合,不是代码 `[DSH]`

`@deepseek-ai/dsh` 随包提供 5 个 profile:`dsh-web-app` / `dsh-headless` / `dsh-acp-app` / `dsh-sdk-app` / `dsh-sdk-minimal`。每个 profile = 一串 bundle patch,`dsh-base` 只是往空根上插一行。

所以**2 层(表层)是免费的**:换 profile 就从“对话产品”变成“CI 里的一个命令”(`dsh-headless`:不开端口、跑完退出,退出码 0/1)或“编辑器背后的 JSON-RPC 服务”(`dsh-acp-app`)。这件事不需要任何插件。

### 3.2 patch 是整行替换 `[DSH]`

`dsh-plugin-manager` 写明:插件开关只改 `cordis.patch.yml` 中**最后一条匹配覆盖项**的 `disabled`,匹配依据是条目 id 加模块名;没有匹配就追加到末尾。而 patch 层替换的是那一行的整个 `config`。

这条机制直接决定 5 层(默认值)的天花板:

- 想改一个 bundle 里某个条目的一个配置键,**必须重述该条目的全部 config**,否则重述不全的部分会丢。
- 多个插件都想改同一个默认值 → **最后写赢**,没有合并,没有冲突提示。

### 3.3 三个桌面壳的真实做法 `[CAT]`

| 样本 | 它怎么做的 | 据此可判 |
|---|---|---|
| `hyperion2144/dsh-desktop-tauriapp` | 桌面 chrome + 通知桥**只在 DSH 运行于桌面应用内时才生效**;装进普通 DSH 只是附带一个“把 Web GUI 打包成 Tauri 应用”的 skill | 真正的 2 层改造发生在**DSH 之外**,插件里那一半是壳内的适配器 |
| `cilis/dsh-tauri-launcher` | 检测/安装全局 `@deepseek-ai/dsh` → 起 Web server → 嵌进自己窗口 | 同上:**profile 一个没改**,产品却变了 |
| `xswt442-cmd/dsh-xswt-tauriapp#dsh-desktop-app` | 插件只做安装引导:下载安装包、比对 `SHA256SUMS`、交给系统安装器 | 插件在这里是**分发通道**(7 层),不是产品层 |

**洞察**:所谓“桌面版 DSH”几乎全是**宿主级产品**(2 层以外),不是 profile 级产品。它们绕开 DSH 插件系统去改产品,代价是拿不到插件生态的组合能力。

### 3.4 有人直接替换启动器 `[CAT]`

`GDWhisper/dsh-web-startup-auth` 自述“Replaces the dsh web startup to allow binding 0.0.0.0”。这是 2 层唯一一种**在 DSH 内部**改产品的办法:替换启动器而不是组合 profile。代价立刻可见——它同时承诺了签名 cookie、`/api` 路由保护、设置页鉴权标签和重置 CLI,等于自己承担了半个安全边界(`[CAT]` 自述)。

### 3.5 把槽位做成注册表,是 3 层升到 6 层的手法 `[CAT]`

`AKS1st/dock` 提供的不是界面,而是 `ctx.workbench` **开放注册表** + VSCode 风格外壳(活动栏/侧边栏/编辑器区/面板/状态栏)。随后 `dock-editor`、`dock-files`、`dock-git`、`dock-images`、`dock-markdown`、`dock-spreadsheet` 逐个挂进来。

**这一个动作把“装插件”变成了“装生态”**:3 层的槽位一旦变成注册表,后来者就在别人的产品里开发,而不是在 DSH 里开发。这是本域最强的一个杠杆,也是唯一一个**在 DSH 内部、不 fork、真的改变了产品**的样本。

### 3.6 官方页面可以被替换 `[CAT]`

`HiSeax/dsh-better-model-setting` 自述“Replaces the official Models settings page”。这说明官方设置页在实现上是可整体替换的(而非只能往里加 section)。这类替换的风险固定在**上游改页面结构**——它替换的对象越具体,升级断得越彻底。

## 4. 标杆

**配额**:本卡只深读 **1 个主标杆 + 2 个对照**。其余 S/A 级样本见本域 [`README.md`](./README.md#本域研究对象主读单一归属),不在卡片里堆。

### 主标杆 · `AKS1st/dock`(S 级)

| 必答项 | 内容 |
|---|---|
| **代表什么典型** | 「把槽位变成平台」的唯一已走通样本:不提供界面,提供 `ctx.workbench` 注册表 + VSCode 式外壳 |
| **为什么选它** | 过 **C 接缝 + D 零披露** 两道门;C 的证据是自述里的具名服务 `ctx.workbench`;D 走的是「空披露」一档——纯前端插件,不是低能力 |
| **影响力多大** | 目录内被引 **0** 次(in-degree 只算按名提及,`dock` 是短词不进 A 口径),因此**不靠 A**;真正的量在**谱系**:`dock-editor` / `dock-files` / `dock-git` / `dock-images` / `dock-markdown` / `dock-spreadsheet` 六个兄弟包跟着它长出来 `[CAT]` |
| **主要特点** | 3 层(槽位)通过**开放注册表**升到 6 层(平台)。后来者在**它的产品里**开发,而不是在 DSH 里开发 |
| **代价 / 失效** | 面板锁进 dock 的布局模型,离开 dock 无处可挂;注册表是私有服务还是挂在公开 seam 上,未核 |
| **证据级别** | `[CAT]` catalog 自述 + 兄弟包命名 · 状态 `observed`(机制)/ `inferred`(注册表是否公开) |

### 对照 · `All3nCN/dsh-better-sidebar-N23`(A 级,同时是 E 级反例)

同样做工作台,选择了 **fork**:自述为 `dsh-better-sidebar` 的完整 fork,并明写与同类插件共享 `/git` 路由前缀而**互斥** `[CAT]`。
- **过门**:B 替代(完整 fork 上游)+ D 能力(shell/fs/network/host-runtime 4 项)+ **E 反面**(明指不可共存)
- **影响力**:上游 `omdsh-dev/DSH-better-sidebar` 被引 **31** 次,是本目录里**谱系最清晰**的一个——一批插件自述「基于 dsh-better-sidebar」
- **代价**:上游改进不再流入;与同类抢同一个路由前缀

### 对照 · `hyperion2144/dsh-desktop-tauriapp`(A 级,**过不了机器门**)

- **代表什么典型** | 「真正的产品改造发生在插件系统之外」:桌面 chrome 与通知桥只在 DSH 运行于桌面应用内时生效;装进普通 DSH 只提供一个「把 Web GUI 打包成 Tauri 应用」的 skill
- **为什么选它** | **机器门失败**:无 in-degree、不自述接缝、能力边车无此条。现靠 **F 稀缺 + G 已核** 人工进入
- **影响力多大** | 无可复核量。这是本卡最弱的一格
- **代价** | 产品在 DSH 之外,插件生态对它无感;仅 macOS/Windows

> **注**:上述第三格是本域最弱的一格,已登记为已知缺口——若下一轮仍拿不到可复核证据,应降级为 B 或删除。

**`dock` 与 `better-sidebar` 是这组对照的全部意义**:同一件事(做工作台),一个选**开放注册表**(可被生态扩展),一个选**fork 加功能**(自足但与上游脱钩)。这组对照比任何单一样本都说明问题。

## 5. 体验

**人看到的**(按层):

- 2 层:`dsh --profile headless "run the tests"` → 没有窗口,只有一行最终答案和一个 exit code。同一产品,入口完全不同。
- 3 层:dock 之后是活动栏 + 侧栏 + 编辑器区;powerdesk 之后是 GPU 终端 + CodeMirror;原生 Web 是单栏对话。
- 6 层:**看不到**——没有首启向导,新用户第一次打开就是完整界面 + 默认权限档。

**模型看到的**(关键不对称):

模型**几乎感知不到产品形态**。无论在 Web、headless 还是 ACP 里,它拿到的是同一套工具、同一段 `sandbox:policy` 上下文、同一条 `subagent:delegation` 声明 `[DSH]`。产品差异对模型不可见,只对人和运维可见。

**这是本域最值得记住的一条**:所谓“把 DSH 变成另一种产品”,改的是**人和运维面对的壳**,模型的处境几乎不变。反过来说,任何声称“改变 agent 行为”的产品化,如果没动 4 层(预设/人格)或 5 层(默认值),就只是换了张皮。

## 6. 洞察

1. **产品是组合出来的,不是写出来的。** 2 层已经给了你五种产品形态,零代码。
2. **供给与影响面倒挂。** 1068 条在改槽位,1 条(还是误命中)在改首启。生态在做手感,不是在造产品。
3. **真正的壳在 DSH 之外。** 三个桌面壳全部是宿主级产物,插件只是它们伸进来的手。
4. **注册表 > 功能。** `ctx.workbench` 一个注册表带来的生态,多于任何一个具体面板;这是 3 层通向 6 层的唯一已走通的路。
5. **fork 是一个诚实的成本项。** `better-sidebar-N23` 说明 fork 能让产品立刻完整,代价是与上游永久分叉;`dock` 说明不开 fork 也能做壳,代价是要先设计注册表。

## 7. 失败模式

| 失败 | 表现 | 根因 |
|---|---|---|
| patch 打飞 | 改一个默认值,同条目其他配置变回默认 | patch 整行替换 `config` |
| 优先级暗战 | 装两个插件后行为随机变 | bundle 开关追加到列表末尾 + 最后写赢 |
| 升级断裂 | 上游发版后某个页面消失或白屏 | 直接替换官方页面/启动器 |
| 生态孤岛 | dock-* 面板在别的壳里无处安放 | 面板挂在特定注册表上 |
| 桌面版装不上 | catalog 直接写“仅支持 Web/CLI,桌面版无法安装” `[CAT]` | 桌面壳不是 profile,插件与宿主版本不对齐 |
| 伪产品化 | 装了一堆 UI 插件,产品和昨天一样 | 只在 3 层做功,没碰 2/4/6 层 |

## 8. 评估清单

给任何声称“把 DSH 变成 X”的插件打分,六问:

1. 它改的是哪一层?能指到 `profile` / bundle / preset / slot 中的哪一个具体吗?
2. 换层了吗——是 3 层换皮,还是 2/4/6 层换了产品?
3. 在 DSH 内部还是外部?壳在 DSH 之外,插件对生态意味着什么?
4. 有没有给后来者留位置(注册表),还是把所有功能都焊进自己?
5. 它替换了哪些官方对象?上游升级时断点在哪?
6. 模型侧有无变化?没有就说明它只改了人的界面。
