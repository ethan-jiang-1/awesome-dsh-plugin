[`03`](./03-turn-end-reconciliation.md) 讲「拿本轮证据对账」,[`04`](./04-evidence-index.md) 讲「只判出处」。本卡讲最主流、也最容易被误认为验收的那一类:**请另一个模型打分**。生态把这条路走了至少四遍,四遍的差别**不在提示词,在判官装在哪、什么时候出结论、出结论之后能不能改文本**。

---

## 1. 命题

> 「独立评审」里,「独立」有三种含义,而绝大多数插件只做到第一种:**换一个模型**(判官与被判者不同)、**换一个上下文**(只看用户原话,不看被污染的历史)、**换一个运行时**(在不同进程/机器上判)。三种独立的成本相差一个数量级,而只有第三种能挡住「被评审者影响评审者」。

可证伪:

- **P1**:若「换模型」就足以消除自评偏差,则不需要过滤上下文,也不需要分叉子代理。
- **P2**:若分数阈值是主要质量来源,则 `maxChallenges` 上限（steer 次数）不该被称为「防漏护栏」。

P1 不成立:四个样本里,**每一个**都另外花力气处理了上下文或运行时(过滤 `source.kind === 'plugin'`、fork 子代理、`llm/stream` 扣留)。
P2 不成立:answer-reviewer 自己说「**cap is a leak guard, not the real gate; the score threshold is**」——两句都在,说明两者都不能省。

## 3. 机制

### 3.1 主标杆 answer-reviewer 的三个设计抉择

**① 判官看到的是「用户真说过什么」,不是「harness 恰好带着什么」。**

它取会话里**每一个**真实用户提示(过滤掉 `source.kind === 'plugin'` 的消息),用 `<all_user_prompts>` 包起来,加上 `<reply>`,交给评审模型。**插件注入的上下文(文件变更通知、AGENTS.md、技能内容、系统提醒)被滤掉。**

这一条是「上下文独立」的具体实现,也是对本地的一个提醒:**上下文工程越好,判官越容易被上下文骗。** 一份塞满「你已完成验收」的注入,足以让任何评审模型给出高分。

**② 分数不是内部指标,它挂在答案上。**

```
● 评分 92            ← 绿灯：score >= threshold，第一次就过
● 评分 61 · 第2次     ← 琥珀：被 steer 回重做，数字是最终生效的那一次
● 评分 55 · 第4次     ← 琥珀：仍低于阈值且 maxChallenges 用尽，没有推进
```

四个细节值得抄:

- **绑在答案上,不绑在轮次上**——分数记在 `assistant/message → data.message.id` 这个**持久消息 id** 下,与宿主给操作行的 id 相同。`chip 与门禁永远不会对「这个分数属于哪条答案」产生分歧`。
- **没有分数就什么都不渲染**——插件停用、无评审路由、回复无法解析、重试上限耗尽,操作行与原生 dsh **逐字节一致**(没有占位、没有转圈、没有预留空间)。
- **重试可见**——被 steer 过的轮次,最终通过的答案上写着 `第2次`,一次第三次才通过的评分不会被读成一次通过。
- **重试上限只关「推进」,不关「评审」**——上限耗尽的那轮**仍然发布**最终分数,并标 `capped`。否则用户真正读到的那条答案,恰好会成为唯一没有分数的那条(0.7.1 修的就是这个)。

**③ 走后门的数据面是「不允许跨源读」。**

分数走 `ctx.webServer.register(...)` 挂的同源 JSON:`GET /api/dsh-answer-reviewer/reviews`,每条 `{ messageId, score, threshold, decision, attempt, turn, reason, at }`,最新在前,最多 200 条。它由宿主的连接栅栏保护(Host/Origin 检查 + 登录 token cookie),所以页面无需放宽 CORS 就能读。
自建的 `127.0.0.1:3987` sidecar **刻意不授予跨源读**——「否则用户访问的任何网站都能读取并篡改他们的评审配置」。

### 3.2 失败方向的四个选择(作者逐条写明)

| 边界 | 方向 | 原文要点 |
|---|---|---|
| 回复无法解析成 `{score, reason}` | **fail-closed** | 返回 `"1.5"`、`"99.9%"`、`"I score this..."` 一律按解析失败——「**failing open would let a misbehaving reviewer buy a pass by returning garbage**」 |
| 会话重启 / 轮次取消 | 评审中途取消,轮次不动 | 不留下半个判定 |
| 子代理轮次 | 跳过 | 子代理的答案不经评审 |
| 超过 `maxChallenges` | 放行并标 `capped` | 「硬预算,不是软提示」 |

**注意它在这一点上和 [`03`](./03-turn-end-reconciliation.md) 的 second-angle 相反**:second-angle 对账 fail-open(异常就放行),answer-reviewer 对**解析**fail-closed。区别在于可判定性:分数是一个整数,解析失败是**确定**的坏;而语义对账失败,**可能**只是判官想多了。

### 3.3 阈值 80 与上限 5,各管什么

- `threshold` 默认 **80**(闭区间 1–100):**低于它就 steer**。
- `maxChallenges` 默认 **5**,硬上限 **8**:**超过就允许按原样关轮**。

两者分工明确:**阈值决定「多好算好」,上限决定「最多重做几次」**。把上限当质量标准的用法是错的——上限放开到无穷的后果不是质量更高,而是**永远关不上轮**。

### 3.4 官方那一格:判官在**动作前** `[DSH]`

`dsh-experimental-auto-review` 用当前 agent 的 provider/model 在**每次原生或 PTC 内层工具调用之前**评估待执行动作:普通工作区操作与「本会话所建对象的精确清理」为低风险放行;对既有对象的不可逆删除、生产操作、外部写入、安全变更为中风险(需当前人类或直接父级明确授权);跨信任边界的敏感外泄为高风险**永远拒绝**;**含糊的副作用与未决的授权冲突一律拒绝**。

它的读者价值在于**它也是「模型判模型」,而且官方明说会错**:「它可以放行不安全动作、拒绝有用工作、并花费额外 token」;`run_code` 外层传输与 PTC 程序内的直接 Node 副作用**不经过内层评审**。

**把它与生态的评审插件摆在一起,得到一个清晰的分界:**

| | 官方 auto-review | 生态 answer-reviewer 等 |
|---|---|---|
| 判什么 | **动作**(副作用) | **文本**(答案质量) |
| 拒绝后的效果 | 转人工审批,动作**不执行** | 转回 agent 重答,文本**已发出** |
| 官方对它的定位 | 实验性**体验优化**,不是安全边界 | 质量门禁 |

**判动作可以真的拦住;判文本永远只能追赶。** 这是本卡最重要的一句话。

### 5.1 一个值得单独讨论的设计:让 agent **不要提**评审

原文:「The steer message explicitly instructs the agent to address the finding silently.」

利:**不污染对话**,用户不会读到自己不关心的内部审计话术。
弊:**用户不知道这条答案被拦过几次**,除非去看 chip。而 chip 上的「第4次」恰好是唯一的线索——**这正是「重试可见」这条设计存在的理由**:既然过程不可见,就把**次数**做成可见的。

**这是质量工具的一条通用技巧:当过程必须隐藏时,把过程的**计数**暴露在产物上。**

## 7. 可借鉴:九条可以直接搬走的做法

### B1 · 判官只读「用户真说过什么」

**做法**:评审输入取会话里**每一个**真实用户提示,过滤掉 `source.kind === 'plugin'` 的消息,用 `<all_user_prompts>` 包起来,再加 `<reply>`,交给评审模型。

**为什么有效**:这是本卡最重要的一条,因为它反直觉——**上下文工程越好,判官越容易被骗**。一份塞满「你已完成验收」「所有测试通过」的插件注入,足以让任何评审模型给高分。判官应该只看**用户的需求**与**答案**,不看中间过程。

**怎么搬**:给评审器构造输入时,先做一个**来源过滤**:只留「用户亲口说的」与「待评的产物」。文件变更通知、AGENTS.md、技能内容、系统提醒一律剔除。**然后把这个过滤写成一行日志**,这样将来发现判错时可以立刻检查是不是上下文污染。

**反面**:过滤掉上下文后,判官会误判「答案省略了显而易见的内容」——因为它不知道有那些内容。解决办法是**在评审提示里明说「你只看用户需求与答案」**,而不是把上下文补回去。

---

### B2 · 判决绑在「产物 id」上,不绑在「轮次 id」上

**做法**:分数记在 `assistant/message → data.message.id` 这个**持久消息 id** 下——与宿主给操作行的 id 相同。

**为什么有效**:「这一轮的分数」是个含糊概念:一轮里可能有多次 steer、多条消息、甚至多个子代理。绑到消息 id 上,**chip 与门禁永远不会对「这个分数属于哪条答案」产生分歧**。这是「同一份数据两个消费者」的经典一致性要求。

**怎么搬**:任何判决/评分都要有一个**指向产物的稳定键**。检查方法:把 UI 上显示分数的位置和做判定决策的位置放在一起看,问「它们用的是同一个 key 吗」。**不是就一定会漂。**

**反面**:产物 id 在 fork/重启后是否稳定?若会变,判决要跟着迁移;这比绑轮次贵,但比值错便宜。

---

### B3 · 没有分数就什么都不渲染

**做法**:插件停用、无评审路由、回复无法解析、重试上限耗尽 → 操作行与原生 dsh **逐字节一致**(没有占位、没有转圈、没有预留空间)。

**为什么有效**:质量插件的默认体验应该是**不存在**。「正在评审...」的转圈会让用户等待一个他们没要求的东西;而占位符一旦出现,卸载插件就会让界面塌一块。**零状态 = 零成本,这是可插拔性的硬要求。**

**怎么搬**:列出你的插件的每一种「无数据」状态,逐个验证渲染结果与「插件不存在」完全一致。**包括布局空间**——预留的空间也是成本。

**反面**:完全静默会让用户不知道功能在运行。取舍点:**「运行中」可以不可见,但「有结果」必须可见**。answer-reviewer 选了静默运行 + chip 显示结果,这个分工是对的。

---

### B4 · 让「重试次数」在产物上可见

**做法**:被 steer 过的轮次,最终通过的答案上写 `第2次`。

**为什么有效**:这一条和上一条是配套的,而且它解决了一个真实矛盾——steer 消息明确要求 agent **不要向用户提及评审**,所以过程不可见。**既然过程必须隐藏,就把过程的**计数**暴露在产物上。**

**这是质量工具的一条通用技巧**:

> **当过程必须隐藏时,把过程的计数暴露在产物上。**

用户不需要读审计记录,但需要知道「这条答案是第一次就过,还是第五次才过」。

**怎么搬**:找出你的产物上能挂一个数字的位置(角标、行尾、文件名后缀),挂上**尝试次数 / 复查次数 / 变更版本号**。一次就过的和反复修改的,在用户眼里必须不同。

**反面**:计数暴露了「质量波动」,可能损伤信任。但这比隐藏它好——隐藏的代价是用户在不知情的情况下依赖一个反复失败的产出。

---

### B5 · 判决不可解析时 fail-closed(这是确定性的坏)

**做法**:回复无法解析成 `{score, reason}` 时——返回 `"1.5"`、`"99.9%"`、`"I score this..."` 一律按解析失败,不放行。原文:「**failing open would let a misbehaving reviewer buy a pass by returning garbage**」。

**为什么有效**:这和 [`03`](./03-turn-end-reconciliation.md) 的 second-angle(对账 fail-open)相反,而两者都对。区别在**可判定性**:

- 分数是一个整数,**解析失败是确定的坏** → fail-closed;
- 语义对账失败,**可能只是判官想多了** → fail-open。

**怎么搬**:给每个检查标一个「失败是否可判定」:

| 失败形态 | 方向 |
|---|---|
| 格式/结构不符(确定的坏) | **fail-closed** |
| 语义判断拿不准(概率的坏) | fail-open + 记录 |
| 依赖不可用(环境问题) | **既不是通过也不是失败**——单独报错 |

**第三种最常被漏掉:判官超时不是「答案不合格」,是「没判」。**

---

### B6 · 阈值与次数上限分工清楚

**做法**:`threshold` 默认 **80**(闭区间 1–100)——低于它就 steer;`maxChallenges` 默认 **5**,硬上限 **8**——超过就允许按原样关轮。原文:「cap 是防漏护栏,阈值才是真门禁」。

**为什么有效**:两者回答不同问题:**阈值决定「多好算好」,上限决定「最多重做几次」**。把上限当质量标准是错的——上限放开到无穷的后果不是质量更高,而是**永远关不上轮**。

**怎么搬**:任何「反复重试直到满意」的机制,都必须同时有**质量线**和**工作量线**,并明确写出「工作量线触发时会发生什么」。**没有工作量线的质量循环,在生产环境里就是一个不会结束的会话。**

**反面**:上限触发时若**静默放行**低分答案,等于质量线被工作量线打败。answer-reviewer 的做法是**仍然发布最终分数并标 `capped`** ——让失败可见,而不是隐藏。

---

### B7 · 判官可换,且默认要警告你它在自查

**做法**:`reviewProvider` / `reviewModel` 可选;**为空时回落到 agent 自己的路由**。

**为什么有效**:换模型是最容易实现的一种独立性(只改一个配置),但**默认值决定了大多数人拿到的是不独立的版本**。这个设计诚实的地方在于:**它是可配置的,而不是声称自己独立**。

**怎么搬**:任何评审组件都要暴露「判官是谁」的配置,并在**使用默认(同模型)**时给出明确提示。若你能负担,更好的做法是**默认拒绝自查**、要求显式选择同模型——但这会显著降低采纳率,是一个产品判断。

**反面**:换了 provider 不等于换了能力。若判官模型弱于被判者,误判率会上升。**换模型是「换一个盲区」,不是「消除盲区」。**

---

### B8 · 数据面用同源注册,不开放跨源读

**做法**:分数走 `ctx.webServer.register(...)` 挂**同源 JSON**(`GET /api/.../reviews`),由宿主的连接栅栏保护(Host/Origin 检查 + 登录 token cookie);自建的 `127.0.0.1:3987` sidecar **刻意不授予跨源读**——「否则用户访问的任何网站都能读取并篡改他们的评审配置」。

**为什么有效**:这是**默认安全**的具体形态。一个 UI 插件需要把数据送到浏览器,最省事的做法是开 CORS,最正确的做法是用宿主的同源通道。**「省事」和「安全」在这里的差别只是一行注册方式。**

**怎么搬**:优先用宿主提供的同源注册/持久化通道;必须自建 HTTP 服务时,**默认拒绝跨源**,并把「为什么需要跨源」写进注释。同时限制:请求体大小、只读端点严格只读、会话键先校验。

**反面**:同源通道受宿主版本影响(接口可能变)。要声明 `engines` 范围,并在升级后回归测试数据面——**数据面坏了,质量插件会静默消失([B3] 的零渲染会让故障完全不可见)。**

---

### B9 · 多维评审 + 把「团队标准」外置

**做法**(来自对照 `CAI-MH/dsh-quality-review`):四维(事实准确 / 完整 / 逻辑一致 / 指令遵循)可开关;另有 **SOP 目录**——文件名当匹配关键词,用户提示命中即加载**整个目录**的文件内容作为评审标准,并追加「是否符合 SOP 规范」维度;目录**每轮重扫**,加文件不用重启。

**为什么有效**:通用维度解决「普遍好不好」,但真实团队缺的不是评审,是**同一份评审口径**。把标准做成**可放入的文件**而不是插件里的字符串,意味着:① 团队可以维护自己的标准;② 改标准不用改代码、不用重启;③ 标准本身可被评审(**这是最重要的一点——标准成了可审查的产物**)。

**怎么搬**:凡是「按标准判定」的工具,都把标准做成**外置目录 + 可读格式**。同时明确两件事:① 命中规则(子串?正则?文件名?)二是**误命中怎么办**——quality-review 用独立的 `exemptPatterns` 跳过表来处理。

**反面**:加载整个目录会显著增加评审 prompt 的长度,并在多标准冲突时让判官无所适从。**SOP 目录适合「一任务一标准」,不适合「一个目录装所有标准」。**
## 8. 体验

**人看到的**:一个分数 chip(`● 评分 92`)、一次「重答」(内容不同但你没被问)、一份 `Verdict: rework required` 报告。**三者体验差别极大**:chip 是**信息**,重答是**打扰**,rework 是**返工**。

**模型看到的**:一条 steer 消息,里面写着评审发现和「不要提及本次评审」。这带来一个微妙的行为引导:**被要求沉默的批评,比公开的批评更容易被忽略**——但公开它会破坏对话。answer-reviewer 选了沉默 + chip,doublecheck 选了报告 + 判决。**同一信息,两种交付面。**

**一个反直觉判断**:轮末评审的**主要收益可能不是拦住坏答案,而是让好答案被标记为好答案**。chip 的存在使「92 分」成为一个可比较的产物属性——这比拦截更常被使用。质量工具的价值,经常在**记账**而不是**拦截**。

## 9. 失败模式

| 失败 | 表现 | 根因 |
|---|---|---|
| 自查冒充验收 | 不配 `reviewProvider`,判官就是被判者 | 默认回落到 agent 路由 |
| 上下文污染 | 判官看到塞满「已完成验收」的注入 | 未过滤 `source.kind === 'plugin'` |
| 迟到修正 | 分数低但用户已读完 | `turn-stopping` 在流之后 |
| 上限当标准 | 次数用尽就放行低分答案 | 上限是防漏护栏,不是质量门 |
| 分数不可审计 | 只知道 61 分,不知道哪句错了 | 标量判决 |
| 过程不可见 | 用户不知道答案被拦过 | 「不要提及评审」的静默要求 |
| 默认不阻断 | `intensity: remind` 时门只是提醒 | 默认值决定门是否存在 |
| 版本耦合 | 依赖的 rc 不在目标环境 | `engines.dsh` 已声明范围,但生态普遍不声明 |

## 10. 评估清单

1. 判官与被判者是**同一个模型**吗?配了 `reviewProvider` 吗?
2. 判官看到的是**用户原话**还是**整个上下文**?插件注入被过滤了吗?
3. 判官站在哪个接缝?**能不能改用户已经读到的文本**?
4. 判决不可解析时 fail-open 还是 fail-closed?哪种是**确定的坏**?
5. 分数/判决**绑在什么 id 上**?会不会张冠李戴?
6. 低于阈值的答案最终交付了吗?**用户知道吗**(chip / 报告 / 什么都不说)?
7. 上限(`maxChallenges`/`maxRounds`)与阈值(80)分工清楚吗?
8. 默认 `intensity` 是什么?默认档是提醒还是阻断?
9. 它有没有把「标准」外置(团队 SOP),还是内置一套通用维度?
