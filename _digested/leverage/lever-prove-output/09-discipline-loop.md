# 09 · 纪律环：把质量写成流程，然后让默认值决定它是否真实存在

> **状态**:`observed`(机制逐条有源码行号佐证) · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b`
> **样本**:2 组(`PerryLink/dsh-doublecheck` 主标杆 · `1052326311/dsh-plan-lattice` 对照)

前面七张卡都在**某一个接缝**上做判定。本卡讲另一种野心:**把六环串成一条流程**,让每一步都有门。它有本域最高的星标,也踩到一个本域反复看到的坑——**默认档位决定了门是不是真实存在**。

---

## 1. 命题

> 「流程即质量」这条路能走通,前提是三件事同时成立:①每一步的门有**可判定的证据形态**(跑过的测试、提交的规格);②门之间**顺序不可交换**(red 必须在实现之前);③默认强度是**阻断**而不是提醒。少任何一条,流程就退化成一份清单。

可证伪:

- **P1**:若流程图(grill → design → red → green → review → verify)本身就有约束力,则强度配置是多余的。
- **P2**:若「回到计划模式重开会话」不是必需的,门失败后可以直接继续。

P1 不成立:`intensity` 默认 `remind`,而 `remind` **不阻断**。P2 不成立:交付门的报告原文要求「re-open the work in plan mode」。

## 3. 机制

### 3.1 六个阶段,每阶段的证据形态不同

| 阶段 | 判据 | 证据形态 |
|---|---|---|
| **grill** | 审问六个需求维度;**未达成共识前拒绝实现** | 一次对话结论 + `doublecheck_spec` 提交的结构化规格 |
| **design** | 规格落盘(会话 + 工作区) | `doublecheck-spec.md` |
| **red** | **实现编辑之前**有一次失败的测试跑,证明缺口 | 一次 `bash`/`pwsh` 测试命令的**失败**结果 |
| **green** | 编辑之后测试通过,闭环 | 同一条命令的**通过**结果 |
| **review** | **分叉子代理**做对抗批评,对着规格审 | 子代理判决 |
| **verify** | `doublecheck_report` + 每维度的验证流程 | `doublecheck-report.md` + 交付门判决 |

**red 这一格是整个环的支点**:它要求「先有一个失败的测试」,而不是「最后有一个通过的测试」。前者证明缺口存在,后者只证明「有一条命令能过」。

### 3.2 `red` 的可判定性来自一张正则表

「是不是一次测试跑」不能靠模型说,所以它被写成配置:

| 配置 | 默认 | 作用 |
|---|---|---|
| `testToolNames` | `['bash','pwsh']` | 哪些 shell 算「能跑测试」 |
| `testCommandPatterns` | `pnpm/npm/yarn/bun test`、`pytest`、`go/cargo/make test`、`node --test`、`deno test`、`uv run pytest` | 命令**必须匹配**才计入一次测试跑 |
| `testFilePatterns` | 测试目录、`*.test.*`、`*.spec.*` | 测试文件**永远可编辑**,不受 red 门限制 |
| `guardTools` | `['edit','write']` | 两道门盯着哪些改动工具 |
| `vagueTaskMaxChars` | `200` | 超过 200 字符的任务**永不被当作「含糊」** |
| `remindOnce` | `true` | 每条提醒每会话最多注入一次(**跨重启持久**) |

**这张配置表是「流程硬化」的真实样貌**:每一个判断都要落到一个能被机器匹配的形态;匹配不到的部分,门就管不了(`testFilePatterns` 的豁免就是为「先写测试」留的口子)。

### 3.3 「对抗评审」用的是分叉子代理,而且不止一个

- `verifyProvider: 'fork'` —— 维度检查器跑在**分叉子代理**里,不是主会话里再问一遍;
- `verifyMode: 'all'` —— **每个维度一个并行检查器**(`single` 是合并成一个);
- `verifyMode` 与 `intensity` 正交:前者决定**判官数量**,后者决定**判决强度**。

这是 [`06`](./06-judge-placement.md) 那张「判官位置」表之外的一个新格子:**判官在子会话里**。它解决了「上下文污染」的一半(子代理看到的是快照而不是滚动上下文),但**没有解决「同一模型」**——fork 用的是同一个模型。

### 3.4 默认值:整卡的结论在这里

```
intensity: 'remind'    ← 提醒
          'warn'       ← 警告
          'block'      ← 阻断
```

默认 `remind`,`enableByDefault: true`(未被 `/doublecheck on|off` 记录的会话默认开启)。

也就是说:**默认配置下,这条纪律环在提醒,不在阻断。** 想要严格的,要自己套一层 overlay:

```sh
dsh --profile web --patch ./node_modules/dsh-doublecheck/strict.patch.yml
```

README 自己写明:`strict.patch.yml` 是「每个门都 `block` 强度、且要求门覆盖率」的**零配置严格模式**。

**这不是缺陷,是权衡**——一个默认阻断的质量插件会劝退所有第一次用它的人。但它带来一个必须写清楚的事实:**装上 ≠ 生效**。本域 [`02`](./02-goal-gate-hard-floor.md) 的 goalloop 也做了同样的取舍(`requireStamp` 默认关闭),区别是 goalloop 的**核心判定永远在**,开关只额外加严。

### 3.5 交付门:判决是「返工」,不是「失败」

```
# Delivery gate report

> **Verdict: rework required** — 2 red item(s)
> The gate is red. Re-open the work in plan mode to re-check the open items before delivering.
```

**「rework required」的措辞值得学**:它不说「你错了」,它说「把这些打开的项目在计划模式里重新过一遍再交付」。这是一条**可执行**的失败信息——回到 [`01`](./01-quality-chain.md) §6 那条规律:**错误消息是质量链的一部分**。

### 3.6 对本域自审的一条纪律:`Observed from <file:line>`

这份 README 的每条示例都标注了出处,形如 `Observed from plugins/dsh-doublecheck/src/guard/prose.ts:191-192; .../tests/command.spec.ts:201-208`。**注意:这个 `plugins/` 前缀是作者内部 monorepo 的布局,公开仓库里代码在根 `src/` 下——照抄 README 的路径会 404**(已在 [`00`](./00-sample-lineage.md) §1.12 核实)。

**这是本域见过的最强的一种文档诚实度**:它把「我读过的代码」与「我推测的行为」用行号切开。本卡把这条当成方法论借用——[`02`](./02-goal-gate-hard-floor.md) 与 [`05`](./05-custody-chain.md) 之所以能标 `observed`,用的是同一种做法(读源码),只是没有逐条注行号。

## 7. 可借鉴:八条可以直接搬走的做法

### B1 · 把「是不是一次测试跑」写成正则表,而不是靠模型判断

**做法**:`testToolNames` 限定哪些 shell 能跑测试;`testCommandPatterns` 列出 `pnpm/npm/yarn/bun test`、`pytest`、`go/cargo/make test`、`node --test`、`deno test`、`uv run pytest`——命令**必须匹配**才计入;`testFilePatterns` 让测试文件**永远可编辑**(不受 red 门限制)。

**为什么有效**:流程要硬,判据就必须能被机器匹配。让模型判断「这是不是一次测试跑」,等于用一个概率判断去支撑一个硬门禁——[`03`](./03-turn-end-reconciliation.md) 的结论在这里同样适用。

**怎么搬**:把你的流程判据都写成**可匹配的形式**(正则、路径模式、退出码、文件存在性)。写不出来的部分,承认它是软的。**然后给「写不出来」的那部分留一条显式豁免**(如 `testFilePatterns`),否则流程会被自己的硬判据卡死。

**反面**:白名单必然会漏掉合法的自定义 runner,导致合法流程被误挡。**缓解方式有二**:① 提供配置项让用户扩展;② 保证失败信息说清「这条命令不在白名单里,可加到 `testCommandPatterns`」——而不是只说「没有测试」。

---

### B2 · red 必须先于 green:先证明缺口存在

**做法**:`red` 阶段要求**实现编辑之前**有一次**失败**的测试跑;`green` 阶段是编辑之后的通过。

**为什么有效**:这是本卡最重要的可借鉴点。它区分了两个完全不同的命题:

- **「最后有一条命令能通过」** —— 可能这条命令从来没测过缺口;
- **「先有一个失败的测试,改完它通过」** —— 缺口被证明确实存在,且改动确实闭合了它。

**只要求后者,是把测试驱动从一种习惯变成一个可被正则匹配的门。**

**怎么搬**:任何「修复 / 补全 / 实现」类任务,都要求一个**前置失败证据**:

| 任务类型 | 前置失败证据 |
|---|---|
| 修 bug | 一个能复现 bug 的失败测试 |
| 加功能 | 一个断言新行为不存在的失败测试 |
| 改配置 | 一条当前配置下失败的健康检查 |
| 修文档 | (无——**这类任务不该套这个门**) |

**反面**:探索性任务、一次性脚本、文档修改不需要这个门。**先分类,再套门**——doublecheck 用 `vagueTaskMaxChars: 200` 把「含糊的短任务」排除在外,是一个具体做法。

---

### B3 · 对抗评审放进**分叉子代理**,而不是主会话

**做法**:`verifyProvider: 'fork'` —— 维度检查器跑在分叉子代理里;`verifyMode: 'all'` —— **每个维度一个并行检查器**(`single` 是合并成一个)。

**为什么有效**:子代理看到的是**快照而非滚动上下文**,所以它不会被主会话里逐渐形成的结论带走。这解决了「上下文污染」的一半——[`06`](./06-judge-placement.md) 的 B1(answer-reviewer 过滤插件消息)解决的是输入侧,分叉解决的是**累积侧**。

**怎么搬**:任何评审都应该在**一个不共享对话历史的上下文**里跑。最简方式:把「规格 + 产物」序列化成一段文本,交给一个全新的会话/子代理,**不传任何中间过程**。

**反面**:fork **没有解决「同一模型」**——它用的是同一个模型,共享同一批盲区。要真正换盲区,必须换 provider(见 [`06`](./06-judge-placement.md) B7)。

---

### B4 · 默认软、可选硬,并把严格模式做成一行命令

**做法**:`intensity` 默认 `'remind'`(`remind` / `warn` / `block`);严格模式是 `strict.patch.yml` 一个 overlay:

```sh
dsh --profile web --patch ./node_modules/dsh-doublecheck/strict.patch.yml
```

**为什么有效**:这是一个**诚实的取舍**。默认阻断会劝退所有第一次用它的人;但把严格模式做成一行命令,就把决定权交给了使用者,而不是替他们选。

**怎么搬**:如果你的门禁默认是软的,**必须在三处说明**:① README 第一屏;② 插件启用时的提示;③ 门被触发时的日志(「已提醒,未阻断(当前 intensity: remind)」)。加上 **一行严格模式命令**。

**反面**:默认软 + 完全不提示,等于用户以为有门而实际没有。**这是本域最常见的失败模式之一。**

---

### B5 · 失败判决要可执行,不要只说「不通过」

**做法**:交付门输出

```
Verdict: rework required — 2 red item(s)
The gate is red. Re-open the work in plan mode to re-check the open items before delivering.
```

**为什么有效**:错误消息是质量链的一部分([`01`](./01-quality-chain.md) §6)。「rework required」不说「你错了」,它说「把这些打开的项目在计划模式里重新过一遍再交付」——**这是一条可执行的下一步**,而且它把「回计划模式」这个动作写明了。

**怎么搬**:任何判决都要包含三样:① **结论**(一句话);② **数量**(几项);③ **下一步动作 + 在哪里做**。缺少第③项,模型会开始猜,用户会开始烦。

**反面**:下一步动作若依赖某个只有人类能做的操作(如「回计划模式」),要给模型一条**可调用的替代路径**,否则它只能转述给用户,而用户不一定看得懂。

---

### B6 · 每条论断标注「我读过的代码」

**做法**:README 的每条示例都标 `Observed from plugins/dsh-doublecheck/src/guard/prose.ts:191-192; .../tests/command.spec.ts:201-208`(**它自己的路径写错了层级,见本节反面**)。

**为什么有效**:这是本域见过的最强的一种文档诚实度——**它把「我读过的代码」与「我推测的行为」用行号切开**。读者可以直接跳过去核对,也可以一眼看出哪些断言没有出处。

**怎么搬**:在你的文档/研究里,给每个**机制性断言**注明来源行号。做不到全部时,至少给**最反直觉的那几条**注明。这个习惯的副产品是:**写的时候你会发现自己有几条其实没验证过。**

**反面**:两个都真实存在。

1. **行号会漂移**,维护成本高。缓解办法是注明**版本**(如 `@ v0.2.1-rc.2` + commit)。本域的做法见 [`00`](./00-sample-lineage.md):把 `repo@commit:path:line` 一起记下来。
2. **路径可能写错层级而自己不知道**。doublecheck 的 README 写 `plugins/dsh-doublecheck/src/guard/prose.ts`,公开仓库里实际是 `src/guard/prose.ts` —— **按它抄会 404**。这是「注来源行号」这条纪律自己的一种失效方式:**注了出处但出处打不开,比不注更糟,因为它看起来可验证。**

**所以这条纪律要加一句:注了出处,就必须验证出处能打开。**

### B7 · 用「配置表」暴露每一个判断点

**做法**:一张表列出所有可配置键与默认值:`specFile`、`reportFile`、`reportVerify`、`verifyProvider`、`verifyMode`、`intensity`、`enableByDefault`、`language`、`guardTools`、`vagueTaskMaxChars`、`remindOnce`、`testToolNames`、`testCommandPatterns`、`testFilePatterns`、`modules.grill`……

**为什么有效**:这张表本身就是**设计文档**。它告诉读者:这个系统在哪些地方做了判断,每个判断的默认值是什么。**评估一个质量插件最快的方式,就是看它的配置表**——默认值决定它默认是提醒还是阻断,配置项暴露了它实际考虑过的情形。

**怎么搬**:写出你的配置表,然后逐行问两个问题:① 这个默认值是什么?② 改它会怎样?**答不上第②个的配置项,通常是不该存在的配置项。**

**反面**:配置项越多,组合越多,测试覆盖越难。要区分「值得暴露的决策」与「实现细节」——`specFile` 值得,「内部缓存大小」不值得。

### B8 · `remindOnce` 这类「跨重启持久」的小开关

**做法**:`remindOnce: true` —— 每条提醒**每会话最多注入一次**,且**跨重启持久**。

**为什么有效**:提醒类门禁的边际效用急速递减——第一次提醒有效,第五次就被忽略,第十次开始污染上下文。而「跨重启持久」是关键:不持久的话,重启后又从头提醒一遍。

**怎么搬**:所有「注入提示」的机制都要有**去重 + 持久化**。用会话/工作区的稳定键记录「已提醒过哪些」,并设一个上限(例如每种提醒每会话一次)。

**反面**:去重会让「用户忘了这条规则」时得不到再次提醒。取舍点:**提醒应该记住的是「已经说过」,而不是「对方已经懂了」**——所以周期性重置(比如每天一次)可能比永久去重更合适。
## 8. 体验

**人看到的**:一次需求审问(grill)、一份落盘规格、一次「先写失败测试」的拒绝、一份 `Verdict: rework required` 报告、一个 `/gate run` 命令。

**模型看到的**:阶段化的提醒/拒绝/评审语(injected prose,`language: en|zh` 可切),`remindOnce` 保证**跨重启只注入一次**——这是对上下文成本的自觉。

**一个反直觉判断**:这条环最有价值的部分不是六个阶段,而是 **`red` 必须先于实现**。它把「测试驱动」从一种习惯变成**一个可被正则匹配的门**。六个阶段里,只有这一条是可机械判定的硬约束;其余五条都还需要模型配合。**流程的硬度不是平均的,它由其中最硬的那一步决定。**

## 9. 失败模式

| 失败 | 表现 | 根因 |
|---|---|---|
| 装上但不生效 | 用户以为有门,实际只是提醒 | 默认 `intensity: remind` |
| 流程走形 | 形式上有 red/green,测的是无关行为 | 门判「跑没跑」,不判「测得对不对」 |
| 合法 runner 被挡 | 自定义测试命令不计入,流程卡住 | `testCommandPatterns` 白名单 |
| 六环只硬一半 | ①意图环仍靠对话,规格写错就对得错 | 无强制接缝 |
| 同模型批评 | 分叉子代理与被评审者同模型,共享盲区 | fork 不等于换模型 |
| 版本耦合 | 升级 Harness 后门禁路径失效 | 依赖 rc 级 API |
| 提醒疲劳 | `remindOnce` 关掉后反复注入,模型忽略 | 提醒的边际效用递减 |
| 默认开+提醒 | 用户不知道插件在运行,却付 token | `enableByDefault: true` + 静默提醒 |
