# 01 · 质量链：六环里只有两环是硬的

> **状态**:`observed` · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b` · **样本**:6 组,回读 catalog 原文
> **修订(本轮)**:`263311487-ux/dsh-verify` 的定位从「另一种运行时」收窄为「独立进程」;2×2 表补了适用边界;撤下 1 行无样本支撑的失败模式;补 3 行有样本支撑的失败模式;新增 2 条开放问题;交叉引用 [02](./02-goal-gate-hard-floor.md)–[10](./10-quality-control-playbook.md)。
> **一句话**:DSH 原生的质量保证只有两处是**机制**——动作前的持久化检查点、以及文件版本新鲜度。其余四环要么是提示词，要么根本不存在；生态把绝大部分力气花在最后那环（验收）上。

> **本卡是本域的底盘,不是结论。** 六环骨架在这里;[02](./02-goal-gate-hard-floor.md)–[09](./09-discipline-loop.md) 是九个样本的逐卡深挖,[10](./10-quality-control-playbook.md) 是横向结论。**只读这张卡会得到两个错误印象**:以为「验收整环缺席」等于「没人做」;以为四个做法穷尽了生态——⑥ 环至少有五种判官位置,其中最硬的一种(`llm/stream`)全库只有 **7/7924** 条。

## 1. 命题

> 质量提升 = **把检查从 prompt 层搬到 policy / 持久化层**。凡是只改文字不改门禁位置的，无论措辞多强,都只是建议。

可证伪点：如果存在一个纯提示词插件，能稳定阻止它声称要阻止的失败（有拦截率数据、且不依赖模型自律），命题不成立。

## 3. 机制：原生到底保证了什么

### 3.1 唯一真正的“硬门禁”：检查点 `[DSH]`

`dsh-session-checkpoint-policy` 的设计非常克制——**没有配置、不加提示词、不加工具 schema**，只包装三处：

| 屏障 | 时机 | 保证 |
|---|---|---|
| 模型请求 | 适配器流构造**之前** | 响应前的崩溃不会重放未持久化的请求 |
| 顶层工具调用 | 工具正文运行**之前** | 已记录调用在任何外部副作用前已持久 |
| `agent/pre-step` | 派生下一个请求**之前** | 前一步骤的响应与有序工具结果已刷新 |

失败语义是 **fail-closed**:持久写入成功前，适配器或工具正文不会运行；取消在 flush 等待期到达时返回规范的 `ABORTED_BEFORE_DISPATCH`，**绝不进入工具正文**。

**但它的三条限制决定了它的上限**（官方原文意译）：

1. **记录执行意图，而非恰好一次副作用**——它记录“调用已分派”，不记录“副作用已完成”。有副作用的工具应自己转发 `exec.callId` 作幂等键。
2. **活跃模型 attempt 内没有检查点**——硬崩溃可能丢失尚未进入持久 `assistant/message` 的瞬态帧。
3. **记录未知结果，而非自动重试**——恢复时给模型一条 `TOOL_OUTCOME_UNKNOWN`，要求它验证状态或请求确认。

这三条合起来是一句话：**DSH 保证“你至少知道发生了什么”，不保证“事情只发生一次”。** 幂等是工具作者的责任，不是运行时给的。

### 3.2 第二硬：文件版本新鲜度 `[DSH]`

`dsh-fs-observation-policy` 要求编辑前先读，且读后文件变了就拒绝：

- 未读就 `edit` → `FS_NOT_OBSERVED`（模型侧统一成 `cannot modify "<path>": file has not been read — read the file, then retry`）
- 读后文件变了 → `FS_STALE_VERSION`，提示重读重试
- 读的是缺失文件 → 授权 `createIfAbsent` 创建，**仍防覆盖并发创建者**

**它的实现方式是本域最有教学价值的一点**:插件**不做任何文件 I/O**，只把“观察记录”转换成提供方的可选防护，由提供方执行原子新鲜度检查。这是“策略只做决策，不做事”的范式。

**四条限制里最要命的是第一条**:

> **已观察状态无法在会话恢复后保留**——恢复的会话必须重新读取文件，才能执行防护写入与编辑。

也就是说:**跨 resume 的“我读过这个文件”是假的**。任何依赖长期观察状态的质量设计，在恢复后都从零开始。第二条同样锋利:“没有 agent 会话的参与者绝无法满足策略”——非 agent 调用方写入永远走 `createIfAbsent`。

### 3.3 计划环：官方明说是软的 `[DSH]`

`dsh-plan-mode` 的自我描述第一句就是:

> **引导而非强制**——计划模式只通过文本约束；需要强制限制的部署要分别配置沙箱模式与审批策略。

还有两条与质量直接相关:存活子级**无法**打开计划评审(会失败,并被要求把未决决策写进最终结果);只有 Web UI 有专门的 `plan-review` 渲染器。

**这解释了生态为什么有 235 条“计划/门禁”样本**:官方的计划环是软的，所以想做硬门禁的人只能自己造。

### 3.4 产物环：原子但不持久 `[DSH]`

`dsh-atomic-write`:替换文件时不暴露部分内容、不跟随临时路径符号链接、跨进程串行化读-改-写、每次替换在新 inode 上用调用方指定的权限位。**但它明确不保证崩溃持久性,因为不调用 `fsync`。**

`present` 呢?它记录路径与说明、**不复制文件内容**,而且官方限制写得很直白:

- 元数据与路径检查**无法原子性地**阻止桌面应用打开文件前发生的路径替换
- 编辑会改变打开的内容;源文件删除/移动后无法通过原声明打开
- **Session ZIP 导出包含声明，不包含文件内容**——“交付版本持久化和写时复制存储延期实现”

**结论**:DSH 的“交付”是**指针**，不是**快照**。产物在磁盘上被改、被删、被移动，交付声明不会知道。

### 3.5 验收环：完全没有原生机制

这是本域最大的空白。原生没有任何“独立于 agent 的判定器”。生态因此长出了一整层:**验收器**。

**本轮补:**「独立」不是一种,是三种——换模型、换上下文、**换运行时**。全库真正做到换运行时的只有少数几条(`--probe "真(实)?浏览器|chromium"` 34 条里多数做不到);而**能改变已发送文本的**,只有站在 `llm/stream` 上的那一种(`--probe "llm/stream"` **7/7924**)。这张位置表在本域 [`06`](./06-judge-placement.md) §2。

## 4. 生态在做什么：四种可复用的硬做法

### 做法 A · 哈希链回执 `[CAT]`

`030611/qiushi-dsh-evidence-audit`:把工具结果与会话事件的 receipt 写入本地**哈希链 JSONL**,并且**不保存**提示词、工具参数、结果正文或原始会话 ID。

这个取舍极精准:它要证的是“**发生过什么、顺序如何、是否被篡改**”，而不是“内容是什么”。**最小化留存本身就是一种安全设计**——回执可用于追责,却不构成新的泄密面。

### 做法 B · 可重放的证据定位符 `[CAT]`

`1687210989/agent-clinic`:22 项具名诊断,每条附**可复核的证据定位符**(形如 `session.v4.jsonl.zstd#L101-L110`),每个问题给一条**可执行处方**(profile patch 片段或命令,含当前值→建议值、风险、验证方式),并支持“标记已拒绝”让处方消失。零依赖、默认零外发、会话文件只读。

**这是“诊断”与“判决”的正确分离**:它给定位符和处方,不给分数。可复核性来自**定位符**,不来自它的结论。

### 做法 C · 阈值门禁 + 可复验回执 `[CAT]`

`4444wjt/dsh-plugin-veriscope`:两条通道(重放既有归档 / 仅用 Node 对 Ragas 导出做阈值判定),返回 PASS/FAIL/**REVIEW**,附出处与可复验回执;支持逐条阈值与**精确十进制比较**;并明确三条:**不重新评测、不调用模型、REVIEW 永不转 PASS**。

「REVIEW 永不转 PASS」是这一环最重要的一条设计纪律——**不确定性不允许被自动消解**。

### 做法 D · 独立验收：换执行环境 `[CAT]`

`263311487-ux/dsh-verify`:JSON 规格进,真实 Chromium 结论出。它的价值不在断言写得漂亮,而在于**判定由一个独立进程、一种独立运行时执行**——agent 无法通过"我说通过了"影响结论。

**修正(本轮)**:上一版写的是"另一种运行时",这个说法过强。`dsh-verify` 是一个**独立进程**,但它跑在**同一台机器、同一个 OS** 上,只把被判对象换成了**浏览器渲染后的页面**。真正的"另一种运行时"是 `veriscope` 式的**纯 Node 阈值判定**(不启浏览器、不调模型),或 CI 上的一次干净重跑。判定的独立性来自**三个可分别成立的维度**——换进程、换引擎、换机器——而不是笼统的"换环境"。

四种做法合起来覆盖证据环的两个正交维度:

| | 证明"发生过" | 证明"结果对" |
|---|---|---|
| **同环境** | A 哈希链回执 | C 阈值门禁 |
| **异环境** | B 定位符(可回看) | D 独立浏览器 |

**这张 2×2 的适用边界(本轮补)**:它只在**④ 证据环**内成立,不进 ⑥ 验收环。⑥ 环的判官有**五种位置**(文本流前 / 轮末 / 交付门 / 动作前 / 会话外),每一种能改变的东西都不同——那张表在 [`06`](./06-judge-placement.md) §2。把这张 2×2 当成"验收的所有做法"会漏掉最关键的一条:**能改已发送文本的,只有站在 `llm/stream` 上的那一种。**

## 6. 可借鉴:六条设计律(全篇的纲)

这一节是本域所有卡片的**共同结论**,也是 [`02`](./02-goal-gate-hard-floor.md)–[`09`](./09-discipline-loop.md) 每一节「可借鉴」的共同来源。**如果只读一处,读这里。**

### L1 · 把检查从 prompt 层搬到 policy / 持久化层

**做法**:同一个规则,写在 SKILL.md 里是建议;写在 `tools/pre-execute` 的 deny 分支里、或写在 `fs-observation-policy` 的版本检查里,才是机制。

**为什么有效**:这不是「更严」的问题,是**谁来执行**的问题。提示词由模型执行——而模型正是可能犯那个错的东西;policy 由运行时执行,运行时**不参与那个错**。**任何要模型自己执行的规则,都有和它要防的错误同源的失效风险。**

**怎么搬**:对你的每条质量规则问一句:「执行这条规则的是模型,还是框架?」是模型的,降级为「建议」并如实标注;是框架的,才叫门禁。

---

### L2 · 门禁的位置决定它能改变什么,能力是次要的

**做法**:`tools/pre-execute` 能阻止动作;`agent/turn-stopping` 只能让模型重说;`llm/stream` 能扣住文本;`conversation.view` 只能让人事后决定。

**为什么有效**:同一份判定逻辑,放在不同接缝上会得到完全不同的产品。把「评审」放在轮末,它只能追加一次修订;放在 `llm/stream`,它能改变用户读到什么。**先选接缝,再写逻辑**——反过来做,通常会得到一个结论正确但毫无作用的东西。

**怎么搬**:画一张自己的接缝表,列出每个接缝「能看到什么 / 能改变什么 / 用户何时感知到」。然后决定你的检查该落在哪一行。

---

### L3 · 否决权按结论的确定性分配

**做法**:命令退出码、路径存在性 → 可 deny;语义对账、质量打分 → 只能 steer / 报告。同一插件里可以有两种相反的失败方向(second-angle 的对账 fail-open + 动作 fail-closed)。

**为什么有效**:给概率判断否决权,等于用一次误判阻断一个可能正确答案;不给确定性判断否决权,等于明知危险还放行。**这里的错误都是对称的:两个方向都会让工具失去信任。**

**怎么搬**:给每条规则标 `确定性 / 概率性`,再决定它能不能拦。**一旦你在给概率性规则加 `block` 开关,先停下来问:误杀时用户会怎么想。**

---

### L4 · 判决必须绑定一次具体输入,且输入变了就作废

**做法**:`goalloop` 绑 `treeDigest`;`veriscope` 绑 GatePolicy + 输入 + 环境;`workproof` 绑单文件 SHA-256 + 大小。三者粒度不同,规则相同。

**为什么有效**:不绑定输入的判决,会在输入变化后**静默地继续有效**——这是本域最危险的失败形态,因为它不报错。绑定的副作用是「每次变化都要重判」,那是必须付的代价。

**怎么搬**:每一个「通过 / 已接受 / 已验证」都必须能回答「对哪一份输入成立」。做不到的,改成「本次有效」并缩短其寿命。

---

### L5 · 必须有一种状态专门用来「等人」

**做法**:`goalloop` 的 `BLOCKED`(假完成 2 次后冻结,等人 `/goal-reset`)、`veriscope` 的 `REVIEW`(永不转 PASS)、`doublecheck` 的 `rework required`、`dsh-plan-mode` 的评审式退出。

**为什么有效**:二值判决会把「不确定」挤进一个箱子——算不出、拿不准、数据缺一角,都只能落到通过(静默放行)或失败(误报,久了没人看)。**第三态的存在,是自动化诚实的标志**:它承认有些事机器不该判。

**怎么搬**:任何自动判定都加第三个出口 `UNKNOWN / REVIEW / BLOCKED`,并遵守两条:① 它**不会因为重跑而变成通过**;② 清除它需要**人的动作**。同时要给这个状态配一个**接手工位**(谁看、多久看),否则它只是「另一种卡住」。

---

### L6 · 默认值决定门是否存在

**做法**:`doublecheck` 默认 `intensity: 'remind'`;`goalloop` 的 `requireStamp` 默认关;`answer-reviewer` 的 `maxChallenges` 默认 5。每一个默认值都在回答「这个门默认开不开」。

**为什么有效**:**评估一个质量插件,先读默认值,再读功能。** 一个功能齐全但默认只提醒的插件,装上之后等于没有;一个默认阻断的插件,会在第一次误杀后被卸载。默认值是产品意志的落点。

**怎么搬**:为每个门写一行「默认档 + 如何加严 + 加严后用户会看到什么」。三者缺一,用户就不知道自己在用什么。

---

### 借用示例:把它们用在一个真实需求上

假设你要做一个「交付前自动检查」的插件。六条律依次给出:

| 律 | 决策 |
|---|---|
| L1 | 不用 SKILL.md 描述规则;用 `tools/pre-execute` 拦「交付声明」这个调用 |
| L2 | 明确它只能阻止**声明**,不能撤回已经写在对话里的话——要撤回必须去 `llm/stream`(本域 [`06`](./06-judge-placement.md)) |
| L3 | 命令退出码可以 deny;「文档质量」只能报告 |
| L4 | 判定绑 `git tree` + 产物哈希;文件变了 → 判决作废,不判失败 |
| L5 | 判不了 → `REVIEW`,要人确认;不要默认通过 |
| L6 | 默认 `warn`,严格模式一行命令;`README` 第一屏写清默认档 |

**这六行就是一张设计契约。** 本域 [`10`](./10-quality-control-playbook.md) §7 把它扩展成 64 条编号原则,§8 给八个问题的检查顺序。
## 7. 体验

**人看到的**:门禁的体验几乎全是**打断**——计划评审弹窗、审批询问、`REVIEW` 状态、处方列表。质量工具的体验成本就是“多一次点击”。

**模型看到的**(两个细节值得记):

- 被拒时,错误文本会**教它下一步**:`cannot modify "<path>": file has not been read — read the file, then retry`;`FS_STALE_VERSION` 追加 `— re-read the file, then retry`。**错误消息是质量链的一部分**,写不好就会变成重试循环。
- 崩溃后恢复,模型会收到 `TOOL_OUTCOME_UNKNOWN`,官方要求它“重试只读或幂等工作,对有副作用的调用**验证状态或请求用户确认**” `[DSH]`。这是一条罕见的、把不确定性显式交给模型的运行时设计。

**这带来一个反直觉的判断**:DSH 的质量保证大量依赖**模型正确地响应错误**。门禁越硬,错误消息的质量就越关键——生态里那批“证据门禁”插件若只输出“未通过”,实际是在制造重试循环。

## 8. 失败模式

| 失败 | 表现 | 根因 |
|---|---|---|
| 提示词门禁 | 规则写在 SKILL.md 里,模型偶尔遵守 | ② 环官方明说“引导而非强制” |
| 假观察 | resume 后直接编辑,以为读过 | 观察状态不跨会话保留 |
| 交付物蒸发 | 用户点开交付文件,内容已变/已删 | present 是指针,不复制内容 |
| 重复副作用 | 崩溃恢复后同一命令跑了两次 | 检查点记意图不记副作用;幂等是工具责任 |
| 重试风暴 | 门禁拒绝但错误信息没给下一步 | 错误消息质量不足 |
| 自查冒充验收 | agent 自己写测试自己判过 | 判定与执行在同一环境 |
| 迟到纠正 | steer 的修订在用户读完原文之后 | `agent/turn-stopping` 在文本送达**之后**才触发([`03`](./03-turn-end-reconciliation.md) §8) |
| 默认软门禁 | 插件装了,门只是提醒 | 默认 `intensity: remind` / `requireStamp` 关([`09`](./09-discipline-loop.md) §3.4) |
| 哈希当正确性 | 文件哈希正确,内容算错 | 观测 ≠ 判断([`08`](./08-delivery-receipt.md) §3.4 演练 2) |

> **本轮撤下的一行**:上一版失败模式表有「REVIEW 被吞——验收器允许 REVIEW→PASS」。回读本轮 11 个样本后没有找到任何允许 REVIEW 转 PASS 的实现(`[OPEN]`:这是抽样结论,不是全库结论——`REVIEW|待复核` 全库 756 条,本轮只回读了其中 0 条与三值判决相关的)。因此这一行撤下,不再作为对生态的指控。

## 9. 评估清单

1. 门禁挂在哪一环?是 ③ 动作前、④ 动作后、⑤ 产物、还是 ⑥ 外部判定?
2. 拒绝时是 fail-closed 还是 fail-open?有没有把“不确定”降级成“通过”?
3. 它留下的证据,别人能独立重放吗?是重放**输入**还是重放**定位**?
4. 判定与执行是否在不同环境?同一个 agent 自己判自己的,一律不算验收。
5. 错误消息有没有给出下一步?(没有的话,它就是重试循环的来源)
6. 它依赖“已观察/已读过/已批准”这类状态吗?这些状态跨 resume 还在吗?
7. 它证明的是“发生过”还是“结果对”?(两者不可互相替代)
