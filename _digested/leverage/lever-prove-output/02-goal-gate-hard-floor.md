# 02 · 完成声明门禁：唯一能在副作用后说「不」的位置

> **状态**:`observed`(源码已核,非仅自述) · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b`
> **样本**:4 组(`samirliu/dsh-goalloop-agentteams` 主标杆 · `Jonah-Wu23/dsh-gungnir` 对照 ·
> `JayYuen666/dsh-quality-gate` 对照 + 反例格 · 官方 `dsh-tool-goal` 借用一句)

本卡回答 [`01`](./01-quality-chain.md) 没敢答的问题:⑥ 验收环既然没有原生机制,**生态把门禁装在了哪一格**、那一格的代价是什么。答案比「换一个更严的评审」更结构性:**验收只能装在「完成声明」这个动作上,而那个动作一旦发生,副作用早已结束**。

---

## 1. 命题

> 在一轮对话里,能被**确定性地**否决的东西只有两样:**即将执行的工具调用**(`tools/pre-execute`)和**即将宣布的完成**。前者在副作用之前,后者在副作用之后——所以质量控制的真正分水岭不是「门禁多严」,而是**你接受哪一种不完美**:早拦(可能拦错、可能死锁)、还是晚拦(可能已经写坏了三个文件才被驳回)。

可证伪:

- **P1**:若存在一种机制能在**副作用之前**校验「这轮会做完吗」,则「验收必然晚于副作用」不成立。
- **P2**:若完成声明门禁能**只靠自述**工作(不重跑检查)而仍有效,则「必须自己重跑检查」这个设计代价不成立。

两条都成立——见 §3 与 §6。

## 3. 机制:goalloop 的门到底怎么落的(源码级)

自述「零模型信任」的插件很多,能落到代码的很少。`lib/index.js` 的拦截器结构如下(**已读源码,`observed`**):

```js
// 双枝,绝不 throw —— 注释原文:一律 {kind:'deny'},绝不 throw(throw 会和 quality-gate 的异常路径混淆)
const claim = isGoalClaim(exec, a) || isTaskClaim(exec, a);
const root = workspaceRoot(exec);
if (root === null) { if (claim) return deny('state-error', ...); return next(); }  // fail-closed
if (!fs.existsSync(contractPath(root))) return next();   // 没契约 = 没启用门控,不堵死
if (!claim) return next();                                // 读写命令不受账本锁影响
const release = acquireLedgerLock(root);
if (!release) return deny('busy', ...);                   // 拿不到锁就明说 busy,不静默继续
```

这段代码里有四个值得抄的设计决定:

### 3.1 门禁只认「声明」,不认「工作」

拦截目标是穷举出来的:`update_goal(action:'complete')`、`agent_teams_update_task(status:'completed')`、`team_task_update(action:'complete')`、`task_board_manage(action:'move-done')`(`update_task` 作旧名兼容)。读、写、跑命令**全部放行**。

这不是省事,而是唯一能让门禁**不倒扣效率**的划法:质量门禁一旦拦在普通写操作上,agent 的每一次试探都要付一次判定成本,失败会退化成「什么都干不了」。**门禁的粒度必须等于它保护的临界区**,这条注释在源码里被明确写成一条 P0 修正记录:

> 锁只在真的需要判定的时候取。原来「有契约就取锁、抢不到就 deny」会让一次卡住的判定把整个工具面(含 read/ls/status)全部拒掉。

### 3.2 判定权在门禁,不在模型

门禁拿到契约后**自己重跑每条 AC 的 check 命令**(`runGate(...)`,零模型参与),再看结果:

- `rc === 0` → 绑定 `treeDigest`,放行,交给后面的层(任务板判官等);
- 否则 → `state.falseCompletes += 1`,deny,`reason` 里带上是哪条 AC 没过。

「假完成」不是形容词,是一个**计数器**。到 2 次:

```js
if ((state.falseCompletes ?? 0) >= 2) {
  return deny('blocked', `false-completes=… ≥ 2; gate blocked. 等人介入。`);
}
```

**冻结比报错更狠**:`BLOCKED` 之后**任何**完成声明都拦,只有人类 `/goal-reset` 能解。这是把「模型反复宣称完成」这个死循环从运行时里切掉——不是让它更努力,而是让它停手。

### 3.3 verdict 绑定内容摘要:改过就不再算数

```js
const currentDigest = treeDigest(root);
const digestMoved = saved !== undefined && saved !== currentDigest;
if (digestMoved) { delete state.digests[key]; /* 用同一 baseline 快照重判 */ }
```

这里有个极易写错的细节,作者显式处理了:**摘要变化 ≠ 假完成**。改过文件只作废旧 verdict、重新判定,真的不过才计假完成次数;而且重判用的是**本轮开始前的基线快照**(`baselineSnapshot`),避免被本轮写入的值污染。**这是「回执绑定产物版本」的最完整实现**,比只写一句「证据需附 digest」强得多。

### 3.4 契约被改 = 批准失效

```js
if (state.approval && state.approval.stamp !== currentStamp) {
  return deny('contract-revised', `契约在上次批准(…)后被修改…确认新契约后 /goal-stamp 重新批准`);
}
```

盖章(`/goal-stamp`)冻结的是**done 的定义**。改了 AC 却不重新批准,等于偷偷换了考卷——门禁拒绝的不是完成,是**换考卷**。这个语义在生态里几乎见不到。

### 3.5 失败语义表(goalloop 的 `deny` 不是一种,是七种)

| reason code | 触发条件 | 语义 | 谁解 |
|---|---|---|---|
| `state-error` | 无工作区 / 契约畸形 / 账本 HMAC 不匹配 | **fail-closed**:判不了就拦 | 人(MCP 不可静默重建) |
| `busy` | 账本锁被另一成员持有 | 明确拒绝,要求重试而**不是**重复声明 | 稍后 |
| `contract-revised` | 盖章后契约被改 | 批准失效,需重新盖章 | `/goal-stamp` |
| `unstamped` | 可选严模式,未盖章就想完成 | 默认**关闭**(装上插件不堵死旧会话) | `/goal-stamp` |
| `blocked` | 假完成 ≥ 2 | 冻结,停手等人 | `/goal-reset` |
| `rounds-exhausted` / `time-budget` | 轮次/墙钟预算耗尽 | 「除非门控 GO,否则停下等人」——**green 交付不被没收** | 人 |
| 门禁自己的 code | AC 未过 / 检查改了工作区 / 证据失联 | 普通 NO-GO,列出不过的 AC | 下一轮 |

**一张表里三种失败策略并存**(fail-closed / 停手 / 重试),且每一种都写清楚了谁来解——这比「fail-closed」四个字诚实得多。本域 §选择要求第 3 条要的正是这个。

### 3.6 它自己承认的三个洞

- **检查会改工作区**:检查把产物写脏了就判无效(`check-mutated-tree`),测量必须写到 `.goal-gate/evidence/`。**「测量污染被测对象」被当成一类缺陷处理**。
- **`calib:` 不采信自述**:门禁自己拿 probe 对已知好/坏夹具各跑一次,好夹具必须过、坏夹具必须不过。这是**判官的对照实验**,判断「这个测量有没有分辨力」,而不是判断「这次过没过」。
- **沙箱策略不可解析 → 门禁不跑**:与 `JayYuen666/dsh-quality-gate` 同一处境(见 §6),两者都选择**不猜**。

### 5.1 它为什么可信:作者写下了「不采信什么」

生态里的质量插件,多数只写「我检查了什么」。这一条额外写清楚了**它拒绝相信谁**:

- 不采信成员自报的 `commandsRun` exit code(README 原文:`verify` 命令**不会**被运行时重跑,`commandsRun` 的退出码由成员提供);
- 不采信评审自述的 `calib-good: PASS`(门禁自己跑夹具);
- 不采信模型的验收结论(judged AC 必须附 `artifact:` + `digest: sha256:`,且证据文件必须落在**被评估的工作区内**);
- 不采信「摘要没变就等于没改」(它自己重算 `treeDigest`)。

**这四点合起来是一个可迁移的设计原则:每一条「我验证过了」都要追问一句「这句话是谁替你担保的」。** 答案若是被验证方自己,那它就不是证据。

### 5.2 它明说的分层:确定性门禁是地板,不是天花板

README 自己给了三层叠放关系(**直接引用,不依赖任何其他文档**):

| 层 | 判什么 | 已知的洞 |
|---|---|---|
| Agent Teams 的 quality kinds | 每一步是否遵守自己的契约 | `verify` 命令不被重跑;`commandsRun` 由成员给 |
| 任务板验收门 | 看起来对不对(LLM A/B 比较,阈值 0.65) | **每张卡都能 `skipVerification` 退出** |
| goalloop 门禁 | 每条 AC 自己重跑 | 不判「语义对不对」,只判「命令过不过」 |

**「每张卡都能 opt out」这一条值得单列**:任何带 opt-out 开关的验收门,在压力下都会被 opt out。确定性门禁的价值不是更聪明,是**没有开关**。

### 对照 B · `JayYuen666/dsh-quality-gate`(B 级,只作一行对照 + 一格反例)

- **过门**:C(`agent/turn-stopping` + 用 `agent.followup` 开修复轮)

- **反例格**:`0.2.1-rc.3` 官方 `dsh-agent/README.md` 明写 handle 有 `followup()` / `steer()` / `inject()`——**同一条 API 在不同 rc 上时有时无,任何依赖它的质量门禁都有版本耦合**。这条记入 §8 失败模式表。

### 官方借一句 · `dsh-tool-goal` 的机械下限 `[DSH]`

原生把「门禁」做进了工具本身:`update_goal(action:'blocked')` **在连续 N 轮(默认 3)之前被机械拒绝**,模型只能在 `blocked_reason` 里描述条件;`complete/blocked` 只在**目标轮**里接受。这是原生里唯一一处「模型不能自宣终止」的硬约束——但注意它拦的是**放弃**,不是**完成**。`complete` 在目标轮里可以立即生效。

**由此得到本域的一条判据:原生的硬约束全部朝向「不许轻易放弃」,没有一条朝向「不许轻易宣布成功」。** ⑥ 环的空白因此不是疏忽,而是**方向性选择**:运行时相信模型能判断「做完了」,只对它「不干了」保持怀疑。

## 7. 可借鉴:七条可以直接搬走的做法

这一节是本卡的产出。每一条都给出 **做法 / 为什么有效 / 怎么搬(含反面)** 三段,可以独立于 goalloop 使用。

### B1 · 只拦「声明」,不拦「行为」

**做法**:不试图阻止模型写文件、跑命令(那些没有对错,只有需求),只在它**说「完成了」的那一刻**介入。工具面上只加一个动作:`update_goal { status: "complete" }`。

**为什么有效**:两个理由,缺一不可——

1. **主权清晰**:结果是否符合目标的判定权必须在门禁手里,不在被判者嘴里。模型不能自评。这和一个验收函数在 PR 中拥有否决权、而不在提交者手中,是同一个道理。
2. **拦截点最少**:一次会话可能有 200 次工具调用,但只有 1 次完成声明。**把门禁放在调用次数为 1 的位置,摩擦与覆盖率同时最优。**

**怎么搬**:在你自己的 agent 里找到那个**每个任务只出现一次**的动作(完成、提交、部署、关闭工单),把门禁放在那里;不要试图在每一次编辑上判「对不对」——判不了,判了也不会有人用。

**反面**:如果把同一个校验挂在每次写文件上,会得到两样东西:误杀率暴涨,以及用户把插件卸载。

---

### B2 · 门禁自己重跑,不采信被拦者提供的执行记录

**做法**:AC 的 `check` 必须写成**命令行**;门禁收到完成声明后,自己按顺序重跑这些命令,以退出码 `0` 为准。成员上报的 `commandsRun` 退出码**被忽略**。

**为什么有效**:模型说「我跑了,通过了」和门禁看着它跑是两件事。前者可能是幻觉、可能是陈旧结果、可能是只跑了第一个断言就断言全过。**采信执行记录,等于把门禁变成一句话的回声。**

**怎么搬**:凡是「代理声称跑过某个检查」,都要问三个问题——① 这个检查能不能表达成一条命令?② 我能不能自己跑?③ 我采信的是退出码还是它的叙述?三个都答得上的,才算门禁。

**反面**:`dsh-verify` 的泄漏点可以当作警示——**规格仍然由被判定者写**。重跑能被采信,前提是 AC 本身写对;而「AC 写对」这件事,门禁自己判不了。

---

### B3 · 一次通过不够,要连续 N 次

**做法**:「假完成」(声明完成但证据不支持)记一次;`false-complete-limit` 默认 **2**,达到就置 `BLOCKED`,**冻结**该 agent 的目标推进,直到人工 `/goal-reset`。

**为什么有效**:单次误判的代价是重跑;一个**反复**误判的 agent,其声明本身就失去了信息量。冻结的不是一次调用,是「这个 agent 还有权继续自称完成」这件事。**把不可信状态持久化,比反复拒绝更有效**——因为冻结改变了激励:模型从「再试一次也许能过」变成「必须停下等人」。

**怎么搬**:给任何门禁加一个**升级阶梯**:第 1 次拒绝 → 指出原因;第 2 次 → 冻结并要求人工介入。没有阶梯的门,等于允许无限重试;而有阶梯的门,让「反复失败」成为一个可观察的信号。

**反面**:不要对**一次**失败就冻结。`gugnir` 的对照表明单次误判很常见;2–3 次是经验值,低于这个数会误伤正常的长任务。

---

### B4 · 契约被改动 = 批准失效

**做法**:AC 的每一条都带 `id`;门禁自己跑的命令绑 `digest: sha256:`;**契约被改过之后,之前的批准自动失效**,必须重新批准。

**为什么有效**:规格是做事的**宪法**,不是可编辑的笔记。一条 AC 被悄悄改松(「检查 `git status` 干净」改成「检查 `git status` 可执行」),就足以让后续所有「通过」变成空话。把批准绑在**契约内容的哈希**上,使修改契约必然产生新的一次批准。

**怎么搬**:凡是「先批准一套规则,再根据规则判定」的系统,批准必须绑规则版本的摘要。这一条对 CI 配置、lint 规则、部署清单、评测基准**同样成立**。

**反面**:`digest` 会与文件路径、工作区布局耦合;契约文件放错位置(不在被评估工作区内)会让每轮都判失败。**要标出一条明确的「契约必须在这里」的规则,并让失败信息说清是位置问题而不是内容问题。**

### B5 · 判定结果绑定树摘要,但不把「移动文件」当成假完成

**做法**:每次判定绑定当时的 `treeDigest`;事后树变了 → **判决作废**,下次带着 `baselineSnapshot` 重判,**棋盘保住**;只有「声明完成而证据不支持」才算假完成。

**为什么有效**:这两件事容易被混为一谈,但代价完全不同——

- 把「树变了」算成假完成 → 任何一次正常的后续编辑都会累加坏记录,两次就冻结一个无辜的 agent;
- 不绑定树摘要 → 判定针对的是一个不存在的现场。

**折中:让判决作废,让人和模型承担重判的成本,而不是让模型承担坏记录。**

**怎么搬**:任何「基于现场快照」的判定,都必须区分三种情况——① **现场变了**(判决作废,重判即可);② **证据不支持结论**(这才是失败);③ **判不了**(检查本身出错,应报错而非判失败)。把三者混成一种「失败」,是门禁误杀的最大来源。

**反面**:如果重判频率过高(每一步都改树),会产生大量无意义的重复判定。需要一条「什么时候值得重判」的策略,goalloop 把它放在完成声明这个点上。

---

### B6(补)· 退出的每一种方式,各自有上限

**做法**:推进轮、时间预算、无进展轮**各自独立计数**。goalloop 源码里 `NO_PROGRESS_TURNS = 4`,`time-budget` 与 `rounds-exhausted` 是两种不同的事故。

**为什么有效**:**没有统一的「轮次预算」可用** `[DSH]`——官方明确说 `dsh-agent-loop`「没有内建轮次预算,要限轮必须从 `agent/turn-stopping` 这类既有生命周期点取消」。既然要自己做,就必须回答「我到底在限什么」:

| 你其实想限的是 | 该用的计数 | 误判后果 |
|---|---|---|
| 花太多时间 | `time-budget` | 慢任务被砍 |
| 转圈没有进展 | `no-progress` | 探索任务被砍 |
| 总轮数太多 | `rounds` | 长任务被砍 |

**三者合并成一个「轮次上限」,是最常见的偷懒,也是误杀最集中处。**

**怎么搬**:任何「停下来」的机制,先写清**停下是因为什么**,再定阈值。**不同原因的停下,应该有不同的错误码和不同的恢复动作。**

### B7 · 错误消息要教下一步,`deny` 永远不要 throw

**做法**:`deny` 的每一种都带**具体原因 + 下一步**;且**一律返回 `{ kind: 'deny' }`,绝不抛异常**。

**为什么有效**:后者在源码注释里写明了理由——**抛出异常会与 quality-gate 的异常路径混淆**,让「门禁拒绝了」和「门禁自己坏了」在日志里不可区分。**这是多门禁共存时的第一条纪律**:拒绝是一个**值**,不是一次**崩溃**。

**怎么搬**:

- 拒绝路径返回**结构化对象**,不 throw;
- 每种拒绝有**稳定的错误码**(goalloop 有 7 种);
- 每条错误消息给出**下一步动作**(改什么、跑什么、找谁);
- **门禁自己的异常**是第三种结果,不是拒绝,必须单独上报。

**反面**:把所有失败都 throw 成同一个 `Error` 的实现,在日志里无法统计,在体验上让模型只会重试。**生态里大量证据门禁只输出「未通过」,实际是在制造重试循环。**
## 8. 体验

**模型侧看到的是教学式拒绝。** 每一条 deny 都带 reason code 和下一步:`contract-revised` 告诉它去 `/goal-stamp`;`false-completes=2 ≥ 2` 告诉它「等人介入」;NO-GO 列出具体哪条 AC 没过。**这决定了门禁是「一次拦截」还是「重试风暴」**——[`01`](./01-quality-chain.md) §6 把这条当成规律提出,这里拿到了一个正面样本。

**人类侧看到的是一次中断,而且是一次有信息的终端中断。** `BLOCKED` 不是错误,是一次**交接**:会话停在那里,等人 `/goal-reset`。这在体验上更难接受(agent 看起来「摆烂了」),但它是唯一能终止「我再检查一下」无限循环的设计。

**一个隐性的体验负债**:门禁生效后,agent 在写代码时**就**知道自己会被检查,于是行为向「让命令通过」倾斜。这是 Goodhart 的经典形态,goalloop 用 `goal_gate_grill`(审不可伪造、Goodhart 代理、未绑定判定的 verdict、缺失噪声带)来挡——但**grill 本身是一次 LLM 调用**,门禁的地板因此仍然是「命令过不过」。

## 9. 失败模式

| 失败 | 表现 | 根因 | 谁中招 |
|---|---|---|---|
| **验收晚于副作用** | 完成被驳回时,磁盘上已有三个文件被写坏 | 完成声明必然发生在动作之后 | 全部同类插件 |
| **声明可绕过** | 不调 `update_goal` / 不 `move-done`,门禁永不触发 | 门禁挂在**可选动作**上 | goalloop、gungnir |
| **opt-out 被滥用** | 每张卡都能 `skipVerification`,验收形同虚设 | 验收门自带开关 | 任务板验收层 `[CAT]` |
| **预算被读成失败** | 轮次耗尽 deny,模型理解为「我做错了」 | 预算拒绝与质量拒绝共用 deny 通道 | goalloop(已用 code 区分,模型仍可能误读) |
| **测量污染被测对象** | 检查脚本把工作区写脏,自己把自己判失败 | 测量与产物同处一个工作区 | goalloop 已命名为 `check-mutated-tree` |
| **判官无分辨力** | 好夹具也过、坏夹具也过,「通过」无信息量 | 只跑「这次」,不做对照 | goalloop 用 `calib:` 夹具挡住 |
| **版本耦合** | 门禁依赖的 API(`agent.followup`)在某 rc 上不存在 | 插件对宿主 API 无锁定 | quality-gate(记 `[OPEN]`) |
| **门禁静默失效** | 沙箱策略不可解析 → 不跑门禁,无提示 | 选择「不猜」但未提示 | quality-gate |

**反例格的使用说明**:第 2、3 行是本域认为**所有**完成声明门禁都逃不掉的结构性缺陷,不是实现缺陷。任何声称「这个门禁能防止假完成」的说法,必须同时回答「怎么防止绕过」,否则只算建议。

## 10. 评估清单

评审一个「完成声明门禁」时按序问:

1. **它拦的是哪个动作?** 拦声明(可绕过,语义准)还是拦轮末(不可绕过,语义弱)?
2. **判定由谁执行?** 门禁自己重跑,还是读被判定方提交的 exit code?
3. **verdict 绑定什么?** 不绑定内容摘要的 verdict,在文件被改后仍然有效吗?
4. **证据的 `digest` 谁算?** 被判定方自算的摘要等于自述。
5. **「假完成」有计数器吗?** 没有计数器的门禁会在同一个循环里永远重试。
6. **冻结怎么解?** 只能人工解 vs 自动解——前者才叫冻结。
7. **预算拒绝与质量拒绝是否用了不同通道?** 混用会让模型把「没钱了」读成「做错了」。
8. **list 出它不采信谁**:成员自报、判官自述、模型结论、旧摘要——四条缺几条?
9. **有没有 opt-out 开关?** 有开关的验收门在压力下一定会被关掉。
