# 07 · 换运行时验收：判官不在会话里

> **状态**:`observed`(机制、退出码、能力边界已核) · **基线**:DSH `0.2.1-rc.3` · 名单 7924 条 @ `efe602e7b`
> **样本**:3 组(`263311487-ux/dsh-verify` 主标杆 · `4444wjt/dsh-plugin-veriscope` 对照 ·
> `Jonah-Wu23/dsh-gungnir#dsh-plugin` 的离线复核器借用一句)

前三张卡里的判官都还在会话里:它们读文本、调模型、发 steer。本卡讲**另一种**:把判定搬到**另一个进程、另一种运行时**里,让被判定者**无法参与判决过程**。这是 ⑥ 环唯一一种真正意义上的「独立验收」。

---

## 1. 命题

> 判定的独立性有三个层次:**换模型**(同一个进程,便宜但可被上下文影响)、**换上下文**(过滤输入)、**换运行时**(另一个进程 → 另一个引擎 → 另一个机器)。只有第三层能保证**被判定者无法在判决时说话**。代价是:规格必须**事先写成可执行的形式**,而写规格的人仍然可能是被判定者自己。

可证伪:

- **P1**:若「规格由谁写」不影响验收价值,则独立性只是运行时问题。
- **P2**:若三值判决(PASS/FAIL/REVIEW)不比二值更好,则 veriscope 的 `REVIEW 永不转 PASS` 属于过度设计。

P1 不成立——`dsh-verify` 自己写:「the app and spec may come from the same agent; review the spec separately when independence matters」。
P2 不成立——见 §6.1:`REVIEW` 是把「机器判不了」这一事实**显式留存**,二值判决做不到。

## 3. 机制

### 3.1 dsh-verify:一台不参与对话的判官

**输入是一份 JSON 规格**:顶层 `title`、`serve`(静态目录)或 `base`(目标 URL)、`browser`、`steps`。步骤是确定性动作——click、fill、text、classes、computed styles、URLs、console/network 错误、像素比对(`expect_screenshot`,带阈值,`--update-baselines` 刷新基线)。

**输出是三层**:

1. **退出码** —— `0` 仅当**全部**通过;`1` 表示失败。
2. **结构化判决** —— `--json` 给 CI;HTML 报告 + 截图 + 差异图给人看。
3. **一条明确的免责**:「`Exit 1 alone does not distinguish assertion failures from runtime errors; inspect the structured verdict and failed actions`」。

**这条免责是本域最值得抄的一句话**:退出码是**门禁信号**,不是**诊断**。把两者混用的 CI 会把「浏览器没启动」当成「功能坏了」。

**它为什么存在——一个真实事故**(作者原话):

> 一个 4 人 agent 团队(规格作者 → 前端 → QA → 评审),他们自己的评审结论是 **「✅ 全部需求已满足,未发现问题」**。在真浏览器里,暗色模式开关**什么也没做**:`.dark` 类被切换了,但 CSS 规则根本没写。每一次 agent 自测都通过,因为页面里**没有任何东西可供 agent 执行**。

| 构建 | agent 自述 | 真浏览器 |
|---|---|---|
| `demo/buggy` | 「未发现问题」 | ❌ **FAIL** —— 背景从不改变 |
| `demo/fixed` | 加了一条 CSS 规则 | ✅ **PASS** —— 主题翻转 |

**「没有东西可供自测」是自测失效的机理**,这比「模型喜欢自我表扬」精确得多:自测不是判错了,是**判了一个不存在的对象**。

**它对自己能力的边界写得很硬**(直接引用):

> 「A PASS applies only to the supplied checks in that run; it does not establish complete coverage, security, accessibility, or independent authorship. The app and spec may come from the same agent; review the spec separately when independence matters. Reports retain assertion details and explicitly requested screenshots, not a complete audit trail.」

**四句话四个「不」**:不证明覆盖率、不证明安全、不证明无障碍、不证明独立作者;外加「报告不是完整审计轨迹」。**一个验收工具的价值,一半在它能判什么,一半在它敢说自己判不了什么。**

**入口的三个位置,三种独立性**:

| 入口 | 谁在用 | 独立性 |
|---|---|---|
| MCP server(`verify_spec` / `verify_url` / `generate_and_verify`) | **agent 自己**中途验 | 低——被判定者发起 |
| CLI | 人或 CI | **中——发起者与被判定者分离** |
| GitHub Action | 每次 push | 高——与 agent 会话完全无关 |

**`generate_and_verify` 的设计值得单独点出**:AI 起草清单,真浏览器**确定性执行**。原文一句话总结得极准——「**The AI drafts; it never judges**」。这是把「模型擅长什么」与「什么可信」分工得最干净的一条。

`init` 的设计同样克制:`init [directory]` 只写本地夹具与两份 JSON 规格,**从不调用 LLM、不启动浏览器、不下载任何东西**;目标目录必须是新的(父目录存在),已存在则拒绝且**不做任何改动**,**没有 force/覆盖选项**。这是一个「首启路径不许有副作用」的工程决定。

### 3.2 veriscope:不重新评测的判定

它的两条通道:**重放既有归档**,或**仅用 Node** 对 Ragas 导出做阈值判定。核心是一组精确的纪律:

- 三条结论 **PASS / FAIL / REVIEW**,并明确 `REVIEW 永不转 PASS`;
- 支持 `row_threshold` 的逐行阈值与**精确十进制比较**(token 计数这类整数不该被浮点吞掉);
- 判定绑定 `GatePolicyV1/V2`,输入、策略或环境一变,**回执失效**;
- `veriscope_gate_complete` **只在当前有效的 PASS 时**返回。

**「回执失效」是它与 dsh-verify 的共同点**:两者的判决都绑定一次具体输入;输入变了,旧判决不继承。

### 3.3 离线复核器(借一句)

`dsh-gungnir` 带一个 `dsh-gungnir-verify`,以退出码 `0/1/2` 报告结果——这是 [`02`](./02-goal-gate-hard-floor.md) 那个完成声明门禁的**外部复核面**:门禁在会话内判,复核器在会话外判,**同一份契约**。

### 5.1 它的真正发明:把「验收契约」写成 JSON

大多数「验收」是**一次判定**;`dsh-verify` 的规格是一个**可被审阅、可被复用、可被 diff 的产物**。这带来三个后果:

1. 规格可以被**另一个人**(或另一个 agent)审查——独立性从「谁判」转移到「谁写规格」;
2. 规格可以被**版本化**,于是「这次 PASS 意味着什么」不再依赖读报告;
3. 规格可以被**替换攻击**——改规格让检查变松,是这条路最大的漏洞。作者的对策是**明确告知**(review the spec separately),而不是假装能防。

### 6.1 `REVIEW 永不转 PASS` 为什么是本环最重要的一条纪律

二值判决的失败方式是**把不确定挤进一个箱子**:算不出、拿不准、数据缺一角,都只能落到 PASS 或 FAIL。落到 PASS 就是**静默放行**;落到 FAIL 就是**误报**,久了就没人看。

三值判决把「不知道」**单独存一格**,并且规定它**不可被自动化消解**。这与 [`02`](./02-goal-gate-hard-floor.md) 里 goalloop 的 `BLOCKED`(等人 `/goal-reset`)、`rounds-exhausted`(停下等人)是同一种思路:

> **自动化的边界必须由人划,而且必须有一种状态专门用来「等人」。**

**反过来,任何没有「等人」状态的验收流水线,在压力下都会把不确定性判成通过。**

### 6.2 两条路的对比

| | dsh-verify | veriscope |
|---|---|---|
| 判什么 | **行为**(浏览器里发生的事) | **数字**(评测导出里的指标) |
| 谁产生被测数据 | 它自己跑 | 别人跑好给它 |
| 成本 | 一次浏览器会话 | O(1) 读文件 |
| 不确定性 | 折进退出码(0/1)+ 结构化判决 | **显式三值**,REVIEW 终态 |
| 失效条件 | 规格覆盖不到的地方 | 导出不可信 |
| 共同点 | **判决绑定一次具体输入**;输入变了旧判决作废 | 同 |

## 7. 可借鉴:九条可以直接搬走的做法

### B1 · 把验收契约写成**可审阅的产物**,不是一次判定

**做法**:一份 JSON 规格——顶层 `title`、`serve`(静态目录)或 `base`(目标 URL)、`browser`、`steps`;步骤是确定性动作(click、fill、text、classes、computed styles、URLs、console/network 错误、像素比对)。

**为什么有效**:大多数「验收」是**一次判定**——跑完给个结论,下次再跑一遍又是新的一次。把契约做成文件带来三个后果:

1. 规格可以被**另一个人**(或另一个 agent)审查——**独立性从「谁判」转移到「谁写规格」**;
2. 规格可以被**版本化**——「这次 PASS 意味着什么」不再依赖读报告,而是读 diff;
3. 规格可以被**替换攻击**——改规格让检查变松。**这是这条路最大的漏洞,而它只能被告知,不能被防住。**

**怎么搬**:把任何验收从「一段脚本」升级为「一份可读的规格 + 一个执行器」。规格要**人类可读、可 diff、可单独评审**。然后**在 README 里明写「本规格由谁写、谁审」**——因为工具防不住这一点。

**反面**:规格越通用,写起来越像编程(JSON 里的 DSL 会失控)。保持步骤集合**小而确定**,超出的用自定义脚本,不要造一门语言。

---

### B2 · 退出码给门禁,结构化判决给诊断,两者分开

**做法**:退出 `0` 仅当**全部**通过;`--json` 给 CI;HTML 报告 + 截图 + 差异图给人看。并明确:「**`Exit 1` 单独看无法区分断言失败与运行时错误;要检查结构化判决和失败动作**」。

**为什么有效**:这句话是整卡最值得抄的一句。CI 里最常见的错误是把「进程挂了」当成「功能坏了」,于是开始排查一个不存在的 bug。**退出码是门禁信号,不是诊断。**

**怎么搬**:三条输出,三个消费者:

| 消费者 | 形态 | 必须能回答 |
|---|---|---|
| 流水线 | 退出码 | 过 / 不过 |
| 诊断者 | 结构化详情 | **哪一条**失败、期望什么、实际什么 |
| 人 | 报告 + 证据(截图/差异图) | 我信不信这个结论 |

**关键:三者不能互相代替。** 只有退出码的,无法调试;只有报告的,无法自动化。

---

### B3 · 失败信息必须带「期望 vs 实际」

**做法**:失败输出形如 `❌ expect_text #total: got "0" want "99"`。

**为什么有效**:换运行时的判官**必须把失败翻译成被判定者能行动的形式**,否则 agent 会开始猜——而猜测会让它去改一个没坏的地方。`got/want` 是这套格式里最小的充分信息。

**怎么搬**:任何断言失败都输出 `定位(选择器/路径) + 期望 + 实际` 三元组。**再加一条:如果能在一条命令里复现,把那条命令也打出来。**

**反面**:`got` 值可能很长或含敏感内容。要截断并标记截断——[`08`](./08-delivery-receipt.md) 的 `64 KiB + 显式截断标记` 是同一个要求。

---

### B4 · `init` 路径零副作用、零网络、零模型调用

**做法**:`init [directory]` **只写本地夹具与两份 JSON 规格**,从不调用 LLM、不启动浏览器、不下载任何东西;目标目录必须是**新的**(父目录存在),已存在则**拒绝且不做任何改动**;**没有 force/覆盖选项**。

**为什么有效**:首次运行是用户信任最脆弱的时刻。任何「init 时顺手干点别的」都会把这一时刻变成风险点。而且「无 force 选项」比「有 force 但要小心」安全一个数量级——**没有开关的破坏性操作,就不需要靠人记住**。

**怎么搬**:给首次运行设计一条**纯写本地**的路径,并遵守三条:① 不联网;② 目标已存在就拒绝且不留痕;③ **不提供 `--force`**。需要重来时让用户自己删——多一步,少一类事故。

**反面**:没有 force 意味着 CI 里重跑会失败。解法是让默认目标目录带时间戳/临时目录,而不是加 force。

---

### B5 · AI 起草,永远不判

**做法**:`generate_and_verify` —— AI 学习真实页面后起草检查清单,**然后交给真浏览器确定性执行**。原文:「**The AI drafts; it never judges**」。

**为什么有效**:这是把「模型擅长什么」与「什么可信」分工得最干净的一条。模型擅长**生成候选项**(该检查什么),不擅长**判定结果**(实际发生了什么)。让它在有创造价值的环节出力,在有对错要求的环节闭嘴。

**怎么搬**:把你的流程切成两段:

- **生成段**:可以让模型参与(起草检查项、生成用例、提出假设);
- **判定段**:必须由确定性执行器完成(退出码、断言、哈希比对)。

**两段之间的接口就是整个设计**:起草出的清单必须是**可执行、可复现**的形式,否则判定段无法接管。

**反面**:AI 起草的清单可能**系统性地漏掉**某些类别(比如无障碍、错误路径)。要显式要求覆盖类别,或者用固定骨架 + AI 填充细节。

---

### B6 · 独立性取决于**谁触发**,不取决于工具

**做法**:三个入口——MCP server(agent 自己中途验)、CLI(人或 CI)、GitHub Action(每次 push)。同一条规格,三种独立性。

**为什么有效**:这是本卡最反直觉、也最实用的一条。人们评估「验收工具」时总在问「它够不够独立」,但**独立性是调用关系的属性,不是工具的属性**。MCP 调用是自查;CI 调用是独立验收——**同一份规格,同一条命令。**

**怎么搬**:给你的验收器至少两个入口,并在文档里明确写出**每个入口提供什么独立性**。然后在内部分级:MCP 触发 = 自查(结论不能作为交付依据),CI/人触发 = 验收。

**反面**:CI 触发也有盲区——**规格还是同一个人写的**(见 B1)。

### B7 · 三值判决,且「待复核」永不自动升级

**做法**(来自对照 `4444wjt/dsh-plugin-veriscope`):`PASS / FAIL / REVIEW`;`REVIEW` 是**终态**,不会因为重跑而被升级为 PASS;输入、策略或环境任一变更 → 回执失效;`gate_complete` 只在**当前有效** PASS 时返回。

**为什么有效**:二值判决的失败方式是**把不确定挤进一个箱子**——算不出、拿不准、数据缺一角,都只能落到 PASS(静默放行)或 FAIL(误报,久了没人看)。三值把「不知道」**单独存一格**,并规定不可被自动化消解。这与 [`02`](./02-goal-gate-hard-floor.md) 的 `BLOCKED`、`doublecheck` 的 `rework required` 是同一种思路:

> **自动化的边界必须由人划,而且必须有一种状态专门用来「等人」。**

**怎么搬**:任何自动判定都加第三个出口 `UNKNOWN/REVIEW`,并遵守两条纪律:① 它**不会因为重跑而变成 PASS**;② 它的清除需要**人**的动作(批准、补数据、改策略)。同时给每个判定绑定输入版本,**输入变了旧判定作废**。

**反面**:`REVIEW` 会卡住流水线。没有明确的**接手工位**(谁看、多久看、看不了怎么办),它和 FAIL 的区别只是「卡住的方式」。**引入第三态的同时必须引入接手人。**

---

### B8 · 给「换运行时」写清它的四个「不」

**做法**:原文四条——「A PASS applies only to the supplied checks in that run; it does not establish **complete coverage, security, accessibility, or independent authorship**. The app and spec may come from the same agent... Reports retain assertion details and explicitly requested screenshots, **not a complete audit trail**。」

**为什么有效**:一个验收工具的价值,一半在它能判什么,一半在它**敢说自己判不了什么**。四条「不」直接决定了这个 PASS 能不能被用作合规证据。**没有这四条的验收器,会被用户过度外推。**

**怎么搬**:给你的验收器写一段固定的免责,覆盖:① 覆盖率(只对提供的检查成立);② 相邻属性(安全/性能/无障碍);③ **作者独立性**;④ 留存完整性(报告 ≠ 审计轨迹)。**放在 README 开头、CLI `--help` 里、报告的页脚。**

**反面**:免责写得太多会削弱信任。分界线是:**免责要精确到「什么样的结论不能推出」,而不是笼统的「结果仅供参考」。**

### B9 · 「检查期间文件在变化」要有独立状态

**做法**(来自 [`08`](./08-delivery-receipt.md) 的同源纪律):检查期间发生变化的文件**不获得 `ok` 观测**,单独显示 `unverifiable`。

**为什么有效**:在一个文件正在被写的同时计算它的哈希,会得到一个**从未存在过的状态**——比缺失更危险,因为它看起来是有效的。**观测必须能区分「没有观测到」「观测到异常」「观测到正常」。**

**怎么搬**:任何基于现场快照的判定,读取时都要**:读前取元数据 → 读内容 → 读后取元数据 → 三者一致才算有效**。不一致就报「变化中」,而不是重试到一致(重试会掩盖一个真实的并发问题)。

**反面**:严格的一致性检查会在高频写入的环境里大量失败。这时应改为**要求一个稳定的输入源**(构建产物、冻结的目录),而不是放宽检查。
## 8. 体验

**人看到的**:一份 HTML 报告 + 截图 + 差异图(`dsh-verify`);一份 PASS/FAIL/REVIEW + 回执(`veriscope`);一个退出码(CI)。**三者是给三种不同读者的**:人要看证据,流水线要看信号,事后审计要看回执。

**模型看到的**:一个 MCP 工具结果或一条 CLI 输出。关键体验在于**它能否读懂失败**:`dsh-verify` 的失败输出带具体断言(`expect_text #total: got "0" want "99"`),这比"FAIL"有用一个数量级。**换运行时的判官必须把失败翻译成被判定者能行动的形式**,否则 agent 会开始猜。

**一个反直觉判断**:这条路最强的用法不是「agent 验自己」,而是「**CI 验 agent**」。同一条规格,由 MCP 调用是自查,由 GitHub Action 调用是独立验收——**独立性不取决于工具,取决于谁触发它**。

## 9. 失败模式

| 失败 | 表现 | 根因 |
|---|---|---|
| 规格由被判者写 | 检查全部通过,漏掉关键行为 | 独立性从「谁写规格」处漏掉 |
| 规格被放宽 | 为了让 PASS 而删检查 | 规格可编辑,无审批 |
| 退出码当诊断 | 「浏览器没启动」被当成「功能坏了」 | 单一退出码不区分原因 |
| 过度外推 | 「PASS」被读成「完成、安全、无障碍」 | 覆盖率不在工具能力内 |
| 数据来源不可信 | 阈值判决基于伪造的导出 | 判官信任输入 |
| 二值挤压不确定 | 算不出来的被记为通过 | 没有 `REVIEW` 这类「等人」态 |
| 离线不可用 | 首次安装需下载浏览器 | 依赖外部资产 |
| 只覆盖可观测面 | 后端逻辑正确性完全没验 | 运行时边界 |

## 10. 评估清单

1. 判官在**会话之外**吗(独立进程 / 独立引擎 / 独立机器)?谁触发它?
2. 验收契约是**可审阅的产物**(JSON/规格文件)还是**一次判定**?
3. 契约能不能被**悄悄放宽**?有没有审批或版本对比?
4. 失败时给出的是**可行动的断言细节**还是只有一个码?
5. 退出码与诊断分开了吗?
6. 它对**覆盖不到的部分**有没有写清(覆盖率、安全、无障碍、作者独立)?
7. 有没有「等人」状态(REVIEW / BLOCKED / 中断),而不是把不确定挤进二值?
8. 判决有没有绑定输入版本?输入变了旧判决还成立吗?
