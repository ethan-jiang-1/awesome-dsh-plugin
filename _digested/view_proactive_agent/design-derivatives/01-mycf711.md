# session-superagent — 留住管线，换掉记账单位：默认 inline 把 super-agent 缩成一次唤醒

> 证据等级 ★★★：`MYCF711/dsh-session-superagent@fe1c356efa66fb52e87403ffeb1660cdf97c876d`(2026-11-25，`Merge pull request #69 … release/session-superagent-2.0.0`)。读了 `README.md`、`package.json`、`cordis.patch.yml`、`lib/index.js` 的关键段、`lib/rooms/` 的 `ticket-state.js`/`executor-host.js`/`admission-eval.js`/`modular-runtime.js`（调用点）、`lib/state-migration.js`、`client.js` 的 slot 注册段，以及 `docs/` 的设计、对比、官方拆解三组文档；**没有**实装运行，也没有逐行 diff 上游(仓库里没有可 diff 的对象)。

## 它替谁解决什么问题

**角色**：一个人同时开着好几个 DSH 会话的个人开发者或独立维护者——一个项目一个长期会话,会话里已经有项目上下文、历史决策、仓库约定。

**场景**：手上几个仓库同时有 issue/PR 动静。他要的不是「再开一个 agent 替我干」,而是「仓库有动静时,把我正在用的那个会话叫醒」,让它在已有上下文里接着判断。

**现有笨办法**：手动切到 GitHub 刷 issue,回来上下文已经断了;或者给每个任务起独立实例、独立 profile、bot 账号和 webhook——凭证、部署、升级都要再维护一套。

**痛点**：多开太重,手动盯又盯不过来;三天后才看到 bug report 是常态,而问题往往在「有没有注意到」,不在「会不会做」。

**为什么现在需要**：DSH 0.2.x 的 `Agent.followup()` 让「叫醒」可以只是一条普通用户消息,不必常驻一个执行体;插件把轮询、过滤、冷却、回写封在一个包里,安装成本降到一条命令。

**边界**：这是注意力问题,不是吞吐问题——它不替你并行干活,只保证你不错过。

## 适用面:谁该用、谁别用

- **适合**：单用户、单机、每仓库一个长期会话的人;愿意把 GitHub/Gitee 凭证交给插件(凭证不进模型)。
- **适合**：只需要「发现 → 叫醒 → 回写」这条闭环,不需要多执行体编排的人。
- **不适合**：团队、多人授权、需要「谁能派活」之外权限模型的场景——`allowAuthors` 只是过滤器,不是权限系统。
- **不适合**：需要多 Ticket 审计、Ticket 可移交、换执行体接着干的人;默认 inline 没有这些,`worker` 也只是半成品。
- **不适合**：需要并行隔离执行或 webhook 级实时性的人;默认执行体就是你的会话,延迟下限是轮询间隔。
- **前置**：DSH `>=0.2.2-rc.1 <0.3.0-0`、Node `>=22.19`;npm 装(2.0.2)或 `file:` 手工装;`gh` 已登录;装完重载宿主。
- **注意**：`worker` 模式才建独立 Session,预设是内置 `standard`;2.0 的房间不改变默认路径的记账单位。
- **一句话**：它替你「注意到」,不替你「扛并发」;能接受这条边界,它就很划算。

## 它到底是什么

**它保留管线的形状，把记账单位从「Ticket」换成「水位 + 唤醒」。** 一条会话守一个或多个仓库，轮询发现有动静 → 过滤 → 冷却/配额 → 把一条**任务书式的用户消息**注入当前会话。没有独立执行体，也没有 Ticket 状态机在管「这条还在进行中」——`seen` / `updated_at` 前进即视为处理过。

**两种执行方式是这个取舍的开关：**

- **`inline`（默认）**：唤醒消息走 `Agent.followup()`，注入你正在打字的会话(`lib/index.js:1659-1661`)；不建 Session、不建目录、不装预设。
- **`worker`（显式）**：每个 Ticket 一个持久 Session，名字 `worker-<ticketId>`(`lib/rooms/executor-host.js:6-11`)，工作区由 `workspaceRegistry.create(workdir)` 建，预设用内置 **`standard`**(`executor-host.js:43`)，不是上游的 `dsh-superagent-worker`。

**2.0 把四样里的两样补成了「房间」，另外两样仍然没有对应物。** `lib/rooms/` 20 个模块里，Ticket 生命周期(`ticket-state.js`)与订阅(`thread-subscription.js`)都在，还多出派工(`execution-assignment.js`)、发件箱(`outbox.js`)、两层准入(`admission-eval.js`)；`modular-runtime.js` 也真的被 `recordRuntimeDelivery` 调用(`lib/index.js:47,649-676`)。因此 Ticket 对象会在「模块化 runtime」里出现。但 **Mandate 与结构化 Report 至今无对应物**，而**执行体只有 `worker` 模式才存在**——inline 的 Ticket 仍不可移交给另一个执行体。

**血缘是文档级的，不是代码级的。** `docs/official-decomp/` 按上游目录树逐文件拆 `src/app`、`src/core`、`src/sources`、`src/client`、`prompts/`，给出吸收表与「不吸收」理由(`01-structure-tree.md:293-307,331-336`)；`BASELINE.txt` 只有一行 `8c32a9d`，没有 vendored 源码目录。

## 怎么接进 DSH

**① patch 只有一行 `insert`。** plugin id `session-superagent`，不接管 profile 的 `bundles` 列表——那一行是运维动作(`cordis.patch.yml:1-10`)。装法是 `dsh plugin --profile <name> add`，开发时用 `file:` 并跑 `pnpm run sync:profile`(`README:66-75`)。

**② 不 inject `orchestrator`。** 全仓 `grep -rn orchestrator lib/ bin/ cordis.patch.yml client.js` = **0 命中**；不读 `orchestrator.sqlite`、不挂 `bridge.js`、不共享 `stateDir`。D2 的三条接法它一条都没用。

**③ 它要的是宿主能力，不是上游服务**：工具注册(`ctx.tools.register`)、四个客户端 slot、`sessionController`、`workspaceRegistry`、`agents`。缺宿主能力时**显式失败**，不回退当前会话(`executor-host.js:1,29-31`)。

**④ 工具面是主入口**：`watch_start` / `watch_ack` / `watch_trace` / `watch_doctor` / `watch_status` / `watch_pr_*`，外加一个 GitHub API 直通工具(`lib/index.js:4482,4697,4742,5299`)。写操作必须显式 `confirm: true`(`:4958-4970`)，`watch_ack` 的 `comment: true` 还要同时给 `note`。

**⑤ 自有状态文件，自有版本号。** `watchers.json` 写 `schemaVersion`，有显式迁移 `v0 → v1`、未知未来版本直接拒绝、失败回退 `.bak`、损坏文件改名 `watchers.json.corrupt-*`(`lib/index.js:404,880`；`lib/state-migration.js:1,28-30`)。这是 D2 那套「吃上游契约」的反面：版本由自己管。

**⑥ 界面四处，全在 DSH 的 slot 里**(`client.js`)：

| 入口 | slot | 位置 |
|---|---|---|
| 输入框左侧「卫星环」 | `conversation.composer.dock`，order **-10** | `client.js:5745-5749` |
| 会话右栏 tab + 标题 | `sidebar.right.pane.tab` / `.tab.title` | `client.js:5636-5653` |
| 会话头部开关 | `conversation.session.header.utilities`，order -6 | `client.js:5658-5660` |
| 左侧全局页 | `main` + `sidebar.panellist`，order 20 | `client.js:5595-5612` |

## 关键实现

**20 个房间按职责分四组**(`lib/rooms/`)：

| 组 | 房间 | 干什么 |
|---|---|---|
| 取数与水位 | `data-provider`、`watermark-state`、`watermark-decision`、`scheduler` | GitHub/Gitee 拉取与 ETag、水位合并、判定、间隔调度 |
| 准入与工单 | `admission-eval`、`ticket-state`、`thread-subscription`、`execution-assignment`、`executor-host` | 两层 gate→assessment；`open → assigned/waiting → ended`；订阅、派工、宿主适配 |
| 交付 | `delivery`、`outbox`、`modular-outbox-host`、`projection`、`ticket-projection` | 回写、FIFO、投影 |
| 其余 | `source-registry`、`draft`、`prompt-config`、`skill-pack`、`i18n`、`modular-runtime` | 来源清单、草稿、提示词分段、技能包、文案、总装 |

**数据流(默认 inline)**：

```
轮询(GitHub 带 ETag / Gitee 每轮真读)
  → filters: allowAuthors / onlyNewComments / 活跃时段 / 批大小(默认 5)
  → decideWatermark:seen 与 updated_at 只前进
  → 闸:冷却 180 s → 单守 6 次/小时 → 会话 12 次/小时 → 3 s 合并窗口
  → 会话空闲?followup 注入任务书 : 记 lastDeferred「会话正忙，下一轮重试」
  → 人办完:watch_ack 打标签 + 推进 seen(+可选 comment)
```

四道闸的常量都能指到行：`DEFAULT_COOLDOWN_MS = 180_000`(`lib/index.js:324`)、`DEFAULT_WAKES_PER_HOUR = 6`(`:149`)、`DEFAULT_SESSION_WAKES = 12`(`:140`)、`WAKE_WINDOW_MS = 3000`(`:1469`)；合并窗口的动机写在注释里——三个守同会话会把三条唤醒挤在 1 秒内，合并既不丢也不饿死(`:1463-1468`)。

**忙就是没有 slot。** inline 没有「worker slot + 给人留一个额外 slot」那种队列对象；`decideWake(agent.status, runningSubagents)` 不过就 `entry.lastDeferred = '会话正忙，下一轮重试'`(`lib/index.js:2581-2583`)。未送达不推进水位，所以重启后按原事件重建队列(`:1474-1477`)。

**隔离是一次性 `git worktree`。** 每次唤醒在目标仓库开 worktree + 分支，`maxIsolated` 默认 5、`isolateKeepDays` 默认 3，回收时 `worktree remove --force` + `branch -D` + `prune`(`lib/index.js:1291-1341`)。

**Ticket 房只做到最小状态机。** `open → assigned / waiting → ended`，人类显式 `resume` 必须是 `actor: 'human'`(`lib/rooms/ticket-state.js:1-9,165`)；不订阅评论、不启执行器——那两件事在别的房间。

**失败收敛的方向是「不确认就不推进」**：未送达不推进水位、失败退避、`readState()` 归一、`.bak` 回退、迁移失败保留现场(`lib/index.js:355-404`)。

**UI 每 5 秒轮询** `/session-superagent/state`(`POLL_MS = 5000`，`client.js:711`)，没有服务端推送——真正的延迟下限是轮询间隔(`README:155`)。

## 代价与边界

**默认 inline 牺牲的是四样上游语义，不是四个功能：**

| 上游概念 | 被换成什么 | 后果 |
|---|---|---|
| Ticket 作为**可移交主体** | 水位 + 唤醒；worker 模式才有一一绑定的 `worker-<ticket>` | 没有「换一个执行体接着干」；ticket 只能跟着原会话走 |
| **Mandate / Policy 版本** | 只有 `filters.allowAuthors`(`lib/index.js:5310`) | 授权不可追溯、不可撤销、不可重验；停下来的方式只有删守/暂停 |
| **Subscription 扇出** | `onlyNewComments` + `seen` 检测 `updated_at`(`README:95-101`) | 后续讨论不会自动到达执行体，必须再唤醒一次 |
| **结构化 Report / Attention 六态** | ack 标签 + 可选 `note` 自由文本(`lib/index.js:4483-4490`) | 没有 `progress/waiting/ready/blocked/failed/dropped`(上游 `001-domain.md:112`)，`watch_trace` 只回答「为什么没叫醒」，不回答「办到哪了」 |

1. **一旦默认 inline，就没有审计面。** 谁让它干的、按哪一版规则、干到哪一步，都散在会话历史里；上游把这些留在域内。
2. **`worker` 是半成品边界。** 有独立 Session 与目录，但没有 worker slot、没有 prepare 命令、没有后台收敛，预设是内置 `standard` 而不是上游的 worker 预设。
3. **宿主耦合在 rc 之间就变过。** 它按 `sessionController.resolveAgent/create` 与 `workspaceRegistry.create` 的**当前形状**调用(`executor-host.js:29-43`)；rc 一改签名，这里就整体不可用。
4. **单人假设是硬边界。** 没有多用户、身份映射、跨 Source 关联；`allowAuthors` 只是「谁能派活」的过滤器，不是权限系统。
5. **发布错位（会误导安装者）。** 0.10.x 与 2.0 是两条线：看到 52★ 去装的人，在 2026-11-25 拿到的是 0.10 线，不是这页分析的代码。**11-26 复查时 2.0.x 已发布**，但 npm 上的 2.0.2 是否等于 `fe1c356` 未验证。
6. **文档边界与代码边界不是同一条。** 0.9 的「不吸收」表与 2.0 的 20 个房间并存，读旧文档会误判能力。
7. **轮询延迟是产品下限。** 延迟等于轮询间隔，不是 webhook；UI 再叠 5 秒轮询(`README:155`；`client.js:711`)。
